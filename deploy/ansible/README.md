# Установка клиентского Brai

`install.yml` разворачивает самостоятельный клиентский экземпляр на чистой Ubuntu 24.04 x86_64. Ему не нужны Admin, DEV и архив сервера. Рецепты скачивают целый репозиторий Brai на закреплённой ревизии, OCI-поставки с проверкой digest, системные пакеты, runtime и модели через lifecycle Local AI. Хранилища создаются пустыми, схемы — штатными миграциями владельцев компонентов. Личные инструкции, память и переписка не переносятся.

Состав определяет `brai_install_manifest`: принятый PROD. Встроенный `product.json` закрепляет прежний состав. Новые принятые компоненты, включая GameCore, Providers, Hermes и Instaloader, устанавливаются по манифесту завершённого выпуска. Наличие исходников в репозитории само по себе не включает компонент в продукт.

## Запуск

На управляющей машине нужны checkout Brai с этим каталогом и Ansible. Цель — чистая Ubuntu с SSH и sudo, интернетом, ресурсами для объявленных моделей и свободными адресами подсетей из манифеста. DNS клиентского домена должен указывать на эту машину; TCP 80/443 должны быть доступны для HTTPS.

```yaml
# /secure/client-hosts.yml — вне Git
all:
  children:
    managed:
      hosts:
        client:
          ansible_host: 192.0.2.10
          ansible_user: ubuntu
```

```sh
ansible-playbook -i /secure/client-hosts.yml deploy/ansible/install.yml \
  --extra-vars @/secure/brai-install-inputs.yml
```

Защищённый YAML содержит `brai_install_manifest` и `fresh_install_inputs`. Первое поле можно опустить только при использовании точного встроенного `product.json`. `fresh_install_inputs.manifest_sha256` — SHA-256 канонического JSON манифеста (UTF-8, sort_keys, indent=2, завершающий LF). Нельзя смешивать описание одной версии с настройками другой.

В `fresh_install_inputs` нужны:

- `files`: ровно `config_paths` манифеста; для каждого — `content` в base64, `mode`, `uid`, `gid`. Это ограниченные настройки компонентов, не архивы и не пользовательские данные.
- `environments`: отдельные значения окружения для каждой пары `project/service`, объявленной через `env_file`; `program_environment` — настройки native-программ; `roles` — начальные SQL-роли и их пароли.
- `provision`: отдельные `user` и `password` установщика для ограниченных операций NATS/Local AI.
- `registry`: GitHub `username` и `token` с доступом к нужным GHCR-поставкам. Для клонирования используется `git` с такими же полями либо `registry`.
- `hf_token`: токен с принятым доступом к gated VAD из профиля GigaAM; права к внешним API и Codex находятся в соответствующих конфигурациях.
- `public_origin`: HTTPS origin клиентского экземпляра; `public_urls`: URL проверки, обычно `<origin>/api/timer`. Origin в web/auth/artifacts и остальных файлах должен соответствовать этому домену.
- `mcp_servers`: только продуктовые `brai_history`, `brai_results`, `brai_supabase` с настройками экземпляра.

Строковые значения установочного комплекта помечаются `!unsafe`, чтобы Ansible сохранил буквальные шаблоны Local AI вроде `{{modelPath}}`. Автоматический экспорт Admin делает это сам; при редактировании и шифровании Vault теги сохраняют. Публичный манифест остаётся JSON.

Храните файл вне Git с правами 0600 либо в Ansible Vault (`--ask-vault-pass`). Для нашей машины Admin умеет выделять согласованный клиентский вход из принятого PROD. Для другого пользователя нужны его собственные доступы, домен и пароли: наш защищённый экспорт содержит наши ключи и не предназначен для передачи клиенту. `partition.product_inputs()` выделяет настройки PROD и меняет известный origin; это не сервис выдачи новых credentials.

## Native Hermes

При наличии `native_runtimes.hermes` установщик запускает native gateway, а не MCP-адаптер `tools.mjs`. Профиль и новая память находятся в `/var/lib/brai/hermes`, конфигурация — в `/etc/brai/hermes`. Клиент получает отдельного пользователя `brai-hermes-production` и единственный canonical HOME `/var/lib/brai/hermes-owner`; состояние Admin и DEV ему не требуется.

К защищённому входу нужно отдельно добавить `native_hermes_auth.content` — base64 собственного canonical Codex OAuth JSON — и `native_hermes_token_environment` — содержимое окружения собственного Telegram-бота с ключом `TELEGRAM_BOT_TOKEN`. Отсутствие этих входов вызывает отказ. Экспорт нашего сервера намеренно их не заполняет: он не является готовым комплектом чужой авторизации. Файлы сохраняются с правами 0600, auth принадлежит единственному пользователю Hermes, окружение бота — root. Чаты и пользователь Telegram задаются в `native_hermes.telegram` клиентского входа.

Движок Hermes закреплён на `517b5e10febd619ce30bb22580e29b160266eb43`, source kit — на `e0b72f2a982b0f87dded09b11533bffada7ed07d`, MemOS — на `a7367d07e55db61099f7b4e2c1108bc5831a24f3`. Обязательные Telegram overlays `9b1bcd4ab4901d263ff6056dd2133f8309bbddc9` и `2f0d6684bd234e7a2a7168bc7d803f2dc9914bea` проверяются по SHA-256 вместе с итоговыми файлами движка. Media-среда устанавливает yt-dlp 2026.8.19 и Instaloader 4.15.3 с закреплёнными зависимостями. Chrome также закреплён по версии и SHA-256. Прикладные адаптеры и инструкции читаются только из принятой immutable OCI-поставки Hermes.

После подготовки зависимостей и моделей Local AI установщик выполняет настоящий native handoff и проверяет запись, чтение, перезапуск MemOS, повторное чтение и точную очистку тестовых записей. Только успешная приёмка разрешает включение памяти и gateway. На общей машине допускается явно описанное совместное использование установленного движка и единственного OAuth owner; клиентский манифест заменяет эту зависимость собственной установкой, сохраняя отдельные профиль, БД, браузер и Telegram-бота.

Явные настройки простоя моделей входят в `local_ai[project/service].settings`: `embeddinggemma2_llama_cpp.idleUnloadSeconds: null` сохраняет embeddings загруженными, `silero_pytorch.idleUnloadSeconds: 600` разрешает выгрузку TTS через десять минут. Отсутствующий ключ сохраняет стандартное поведение сервиса. Эти настройки применяются через lifecycle Local AI и для уже установленных моделей.

## Повтор и административное дополнение

Повтор с теми же описанием и входом продолжает свою установку, сохраняя ключи, Git checkout и данные. Чужой сервер, изменённые inputs или несовместимое состояние вызывают отказ. Установщик не является механизмом обновления работающего продукта. Состояние и квитанции находятся в `/var/lib/brai-install`, доступ только root. Ежедневный `brai-install-verify.timer` проверяет готовность без восстановления и миграций.

Admin может установить весь сервер сразу или дополнить такую клиентскую установку DEV и средствами разработки. Дополнение разрешается только при точном совпадении клиентской части декларации и уже принятых доступов. Разрешено добавление административных проектов в Agent и корней чтения publisher; остальные продуктовые настройки сохраняются. Это не перенос чужого клиентского сервера в нашу среду.

## Сопровождение

Общие рецепты находятся только в `roles/brai_install`. Дополнительные рецепты и параметры нашей машины принадлежат Admin. Изменяя запуск, зависимости, каталоги или конфигурацию, агент Codex обновляет соответствующие установочные задачи в той же работе. Разработка в DEV не меняет состав клиентского продукта.

После успешного проверенного Ansible-выпуска Admin автоматически формирует два согласованных комплекта: клиентский из принятого PROD и административный из DEV+PROD. Каждый защищённый комплект включает свой манифест, поэтому новые принятые ревизии не требуют копирования рецептов между репозиториями. Ошибка установки или отдельной проверки не запускает экспорт. Ошибка самого экспорта видна в результате операции и требует разбора; уже установленный runtime сохраняется. Встроенный `product.json` закрепляет исходный PROD этой версии установщика; для последующего принятого выпуска используется манифест из нового комплекта.

Проверка кода без развёртывания:

```sh
python3 -B -m unittest discover -s deploy/ansible/tests -v
ansible-playbook -i /secure/client-hosts.yml deploy/ansible/install.yml --syntax-check
```

Полная установка и перезагрузка отдельной чистой Ubuntu пока не проверялись: тестовая машина не предоставлена. Проверки исходников и Compose не заменяют этот прогон.
