# Локальный выпуск DEV

`brai-dev` готовит поставки из точного Git commit и передаёт их установленному
операторскому helper. Codeworks, GitHub Actions и внешний registry в этом пути
не участвуют. Программа не устанавливает npm-пакеты и не меняет PROD.
Наличие исходников компонента не включает его в установленный экземпляр.

## Команды

В чистом рабочем дереве запустите:

```sh
brai-dev release --source <полный-40-символьный-SHA-текущего-HEAD>
brai-dev status
brai-dev status <operation-id>
brai-dev reconcile <operation-id>
brai-dev rollback --release <previous-release-id>
```

До установки команды тот же интерфейс доступен через
`node deploy/brai-dev.mjs`. Рабочий каталог должен быть корнем подготовленного
дерева. `--source` принимает полный SHA, совпадающий с чистым `HEAD`;
branch/ref, другой commit, изменённые и новые неигнорируемые файлы отклоняются.
Перед сохранением кандидата точный commit закрепляется через неизменяемую
`refs/brai-dev/releases/<releaseId>` с проверкой отсутствия прежней ссылки.
Эти ссылки сохраняются и попадают в Git backup с `--all`.

Базой сравнения служит принятый DEV-выпуск из root-owned состояния оператора,
а не `origin/dev`. Начинайте задачу от принятого source commit: перед сборкой
программа проверяет, что он является предком переданного `--source`. Отставшая
или разошедшаяся ветка отклоняется; автоматического слияния нет. Если первая
наблюдаемая композиция не имеет единого source commit, сначала требуется её
отдельная однократная сверка оператором. Программа сравнивает fingerprints компонентов и включает
затронутых потребителей. Если в принятом выпуске ещё нет fingerprints, они
вычисляются из его закреплённого исходного commit через временный Git archive.
Остальные компоненты не собираются и не упаковываются. Правила fingerprints,
объявленные команды и состав поставки находятся в
[описании средств компонентов](components/README.md).

Перед сборкой проверяются поддержка обработчиков и актуальность принятой базы.
Перед передачей кандидата повторно проверяются чистота исходников и база.
Root helper проверяет `expectedBase` под собственным lock. Неподдерживаемый
обработчик завершает команду ошибкой до сборки, импорта и изменения runtime.

Для каждого выбранного компонента runner последовательно выполняет `build`,
`check` и `package` в одном вызове. Проверенные receipts позволяют повторно
использовать сборку и результат проверки при совпадении её ключа и явно
объявленном полном наборе инструментов; без него проверка выполняется заново. Поставщик проходит
этот путь перед своим потребителем. Компоненты вне выбранного набора не
передаются runner даже как неявные зависимости.

При отсутствии изменений команда возвращает `state: "unchanged"`, прежний
`releaseId` и отдельный `acceptedSourceSha`. Новый выпуск и пустой кандидат не
создаются; исходный commit принятого DEV не подменяется новым SHA.

## Кандидат и завершение

Кандидат сохраняется в `tmp/dev-release/<releaseId>/candidate.json`. Он содержит
версию `1`, контур `dev`, UUID выпуска, точный source SHA, ожидаемую принятую
базу и выбранные компоненты. Для каждого компонента передаются абсолютный путь
локальной поставки, SHA-256 payload, SHA-256 точных байтов
`artifact-manifest.json`, fingerprints и ссылки схемы. Этот путь не выполняет
миграции: `before` и `after` должны совпадать, откат должен быть совместим.

Root helper импортирует и запечатывает локальные файлы, затем запускает
операцию через systemd. CLI ждёт `accepted` для своего UUID и совпадения
`current.releaseId`. `failed`, `recovery-required`, смена наблюдаемой операции
или неподтверждённый ответ завершают команду ненулевым кодом. Очередь или
успешный импорт сами по себе не означают успешного выпуска.

У ожидания нет скрытого срока. Остановка CLI не отменяет уже принятую
root-операцию. После потери ответа сначала прочитайте `status <operation-id>`;
для незавершённой операции используйте `reconcile <operation-id>`, не
повторяйте изменение вслепую. Reconcile сверяет указанный ID с активной
операцией. Откат разрешён только к `previous.releaseId` и передаёт текущий ID
как условие compare-and-swap.

Результат включает длительности проверки исходников, получения базы,
планирования, каждой сборки, проверки, упаковки и проверки пакета, передачи
кандидата и ожидания. Отдельно возвращаются доступные root timings, включая
runtime smoke. Успешный отчёт сохраняется рядом с кандидатом в `report.json`.
Ошибка содержит завершённые фазы и фазу сбоя с длительностью. Подготовка входит
в общий замер команды.

## Два preview-слота

```sh
brai-dev preview --slot 01 --source <полный-SHA>
brai-dev preview --slot 02 --source <полный-SHA> --expected <current-preview-release-id>
brai-dev preview-stop --slot 02 --expected <current-preview-release-id>
```

Допустимы только слоты `01` и `02`; автоматического выбора или вытеснения нет.
Обычный `brai-dev status` включает статусы обоих слотов и их текущие release ID.
Для пустого слота можно опустить `--expected` или передать `--expected none`.
Для занятого слота точный текущий preview release ID обязателен. Статус слота
проверяется до сборки, а root helper повторяет compare-and-swap перед заменой.

Preview собирает, проверяет и упаковывает только `web`, запечатывает его через
оператор `seal`, затем передаёт payload hash в фиксированную root-операцию
`prepare`. Она создаёт COPY-only образ из запечатанной поставки и локального
закреплённого базового образа без скачивания. После этого `update` запускает
ровно указанный слот. Результат считается успешным только при `status: "ready"`
и совпадении source SHA. Возврат прежнего контейнера после неуспешной замены
не считается успешным preview.

Обычный DEV-выпуск не меняет preview-слоты. Preview не применяет миграции и не
выполняет компонентные операции иных сервисов. Доступ к DEV backend определяется
установленной политикой слота и сам по себе не подтверждает изоляцию
пользовательских действий в браузере.

## Граница привилегий

Непривилегированная программа вызывает только установленные фиксированные
helper: `/usr/local/libexec/brai-dev-release/operator.py` для выпуска и
`/usr/local/sbin/brai-dev-preview` для слотов. Оператор получает строго заданную
команду и локальный кандидат; preview получает JSON через stdin. Правила
установки, доступные обработчики, root-owned policy, systemd и sudoers принадлежат
операторскому установщику. Доступ к произвольной root-команде, Docker socket или
группе `docker` этому CLI не требуется.

Проверки frontend: `node --test deploy/brai-dev.test.mjs`. Они проверяют
сценарии через подставные helper и реальную локальную упаковку; не выпускают
код в действующий DEV и не обращаются к пользовательским данным.
