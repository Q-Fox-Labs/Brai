# Пробная клиентская установка в GitHub Actions

Workflow **Client install smoke** запускает штатный `ansible/client/install.yml` на бесплатном раннере `ubuntu-24.04` публичного Brai. На раннере создаются пустые базы, загружаются объявленные пакеты и модели. После установки workflow проверяет состояния контейнеров и системных служб и выполняет запрос к Web из контейнера. GitHub удаляет раннер после задания.

## Подготовить тестовый комплект

1. Возьмите клиентский манифест `brai-clean-install-v1` с точным SHA проверяемого Brai. Для кандидата до выпуска нужен подготовленный оператором манифест со всеми версиями компонентов и OCI digest. Штатный экспорт Admin формирует комплект из принятого PROD. Замена SHA в этом экспорте не даёт состав RELEASE.
2. Сгенерируйте заготовку и заполните её настройками отдельного тестового экземпляра.

   ```sh
   python3 deploy/ci/client-install-fixture.py template "$BRAI_SHA" product-candidate.json test-settings.json
   ```

   Заполните `files` текстом конфигураций и числовыми `uid`, `gid`, `mode` из рецептов установки. Заполните значения `environments` и `program_environment`, добавьте роли приложений. Используйте один маркер `@CI_SECRET(db-example)@` в пароле роли, URL подключения и связанных файлах. Раннер создаст для каждого имени отдельный случайный секрет. Публичный origin теста — `https://brai-ci.localhost`. Используйте отдельные тестовые токены для внешних сервисов, которые нужны выбранным компонентам.

3. Упакуйте входы и передайте файл в Actions secret `BRAI_CI_INSTALL_BUNDLE`.

   ```sh
   python3 deploy/ci/client-install-fixture.py pack "$BRAI_SHA" product-candidate.json test-settings.json fixture.b64
   gh secret set BRAI_CI_INSTALL_BUNDLE --repo Q-Fox-Labs/Brai < fixture.b64
   ```

Workflow использует клиентскую установку без развёртывания персональных профилей Auth. Поддержка инфраструктуры в составе определяется самим манифестом. Оставьте список `public_urls` пустым для локальной проверки Web. Полные журналы Ansible и тестовые настройки хранятся на одноразовом раннере.

## Настройки Actions

| Переменная репозитория | Значение |
| --- | --- |
| `BRAI_CI_ADMIN_REPOSITORY` | По умолчанию `Q-Fox-Labs/Q-Server`. Для переопределения укажите `владелец/репозиторий`. |
| `BRAI_CI_ADMIN_SHA` | По умолчанию `8ef49bf67e2aa3870a609bcdae487c291ce241eb`, устанавливающий Codex 0.171.0. Для переопределения укажите полный SHA. |

Добавьте `BRAI_CI_ADMIN_TOKEN` с правом чтения репозитория Admin и `BRAI_CI_HF_TOKEN` тестового аккаунта с доступом к закреплённому VAD. Workflow читает OCI через `GITHUB_TOKEN`. Для отдельного допуска к пакетам задайте секрет `BRAI_CI_REGISTRY_TOKEN` и переменную `BRAI_CI_REGISTRY_USER`.

До появления **Client install smoke** в ветке по умолчанию задайте переменную `BRAI_CI_SOURCE_SHA` с полным SHA кандидата. Публикация правок в workflow или `deploy/ci` на ветке `feature/clean-install-actions-da582c9` запустит проверку. Изменение переменной само по себе не запускает workflow.

Когда **Client install smoke** появится в ветке по умолчанию, его можно запускать напрямую с полным `source_sha`. Раннер подтверждает наличие коммита, выводит свободное место и сообщает имена недостающих входов. Для установки комплект должен содержать тот же SHA и совпадающую контрольную сумму манифеста.

## Место на диске

В принятом PROD-коммите `4ff7ff4` Docker показал 4,06 ГБ по уникальным образам, а четыре комплекта весов заняли 1,97 ГБ. Для оценки пика учитывайте инфраструктурные образы, распаковку, `npm ci`, сборку и временные файлы. Workflow печатает свободное место до и после удаления предустановленных Android и GHC. Во время установки он каждые пять секунд замеряет свободное место на файловых системах установки, Docker и временных файлов. Точный расход зависит от проверяемого манифеста.
