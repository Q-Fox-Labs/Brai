# Пробная клиентская установка в GitHub Actions

Workflow **Client install smoke** запускает штатный `ansible/client/install.yml` на бесплатном раннере `ubuntu-24.04` публичного Brai. На раннере создаются пустые базы, загружаются объявленные пакеты и модели. После установки workflow проверяет состояния контейнеров и системных служб и выполняет запрос к Web из контейнера. GitHub удаляет раннер после задания.

## Подготовить тестовый комплект

1. Возьмите клиентский манифест `brai-clean-install-v1` с точным SHA проверяемого Brai. Для кандидата до выпуска нужен подготовленный оператором манифест со всеми версиями компонентов и OCI digest. Штатный экспорт Admin формирует комплект из принятого PROD. Замена SHA в этом экспорте не даёт состав RELEASE.
2. Сгенерируйте заготовку и заполните её настройками отдельного тестового экземпляра.

   ```sh
   python3 deploy/ci/client-install-fixture.py template "$BRAI_SHA" product-candidate.json test-settings.json
   ```

   Заполните `files` текстом конфигураций и числовыми `uid`, `gid`, `mode` из рецептов установки. Заполните значения `environments` и `program_environment`, добавьте роли приложений. Используйте один маркер `@CI_SECRET(db-example)@` в пароле роли, URL подключения и связанных файлах. Раннер создаст для каждого имени отдельный случайный секрет. Публичный origin теста — `https://brai-ci.localhost`. Используйте отдельные тестовые токены для внешних сервисов, которые нужны выбранным компонентам.

3. Упакуйте входы и передайте файл в Actions secret `BRAI_CI_INSTALL_BUNDLE`.

   ```sh
   python3 deploy/ci/client-install-fixture.py pack "$BRAI_SHA" product-candidate.json test-settings.json fixture.b64
   gh secret set BRAI_CI_INSTALL_BUNDLE --repo Q-Fox-Labs/Brai --env brai-clean-install < fixture.b64
   ```

Для манифеста с Telegram заполните `identity_deployment` по [контракту клиентского установщика](https://github.com/Q-Fox-Labs/Q-Server/blob/main/ansible/client/IDENTITY.md). Укажите отдельный тестовый токен бота. Реестр Auth остаётся пустым. Ссылку на переносимый SDK берите из того же манифеста. В защищённом окружении Actions задайте `BRAI_CI_MEMOS_SDK_URL` с временной HTTPS-ссылкой на несжатый `.tar`. Первым в архиве должен идти `distribution.json`, за ним перечисленные в нём файлы. Записи каталогов не нужны. Раннер сверяет SHA-256 манифеста и каждого файла перед передачей штатному Ansible.

Для прогона из собранных пакетов RELEASE добавьте `release_oci_archive_sha256` в тестовые настройки и задайте секрет `BRAI_CI_RELEASE_PACKAGES_URL` с временной HTTPS-ссылкой на OCI tar. Раннер сверяет хеш архива, хеши каждого указанного OCI-пакета и его содержимое штатным валидатором. Установщик затем сверяет эти же payload при этапе `sources`. Внешние CLI устанавливаются штатно по закреплённому OCI digest.

Оставьте список `public_urls` пустым для локальной проверки Web. Полные журналы Ansible и тестовые настройки хранятся на одноразовом раннере.

## Настройки Actions

| Переменная репозитория | Значение |
| --- | --- |
| `BRAI_CI_ADMIN_REPOSITORY` | По умолчанию `Q-Fox-Labs/Q-Server`. Для переопределения укажите `владелец/репозиторий`. |
| `BRAI_CI_ADMIN_SHA` | По умолчанию `8b0e16d38e29541a43caaabca4bf71641abc9317`, устанавливающий Codex 0.171.0. Для переопределения укажите полный SHA. |

Ограничьте окружение Actions `brai-clean-install` веткой проверки. В этом окружении задайте `BRAI_CI_ADMIN_SSH_KEY` с ключом развёртывания только на чтение репозитория Admin или `BRAI_CI_ADMIN_TOKEN` с тем же доступом. Добавьте `BRAI_CI_HF_TOKEN` тестового аккаунта с доступом к закреплённому VAD. Workflow читает OCI через `GITHUB_TOKEN`. Для отдельного допуска к пакетам задайте секрет `BRAI_CI_REGISTRY_TOKEN` и переменную `BRAI_CI_REGISTRY_USER`.

Запустите зарегистрированный workflow **Client install smoke** с ветки, в которой находится его файл. Для опубликованного workflow по умолчанию передайте ветку `main`.

```sh
gh workflow run client-install-smoke.yml --repo Q-Fox-Labs/Brai --ref "$WORKFLOW_BRANCH" -f "source_sha=$BRAI_SHA"
```

Раннер подтверждает наличие коммита, выводит свободное место и сообщает имена недостающих входов. Для установки комплект должен содержать тот же SHA и совпадающую контрольную сумму манифеста.

## Место на диске

Для RELEASE с Hermes `d415983` распакованные слои запущенных образов заняли 7,41 ГБ, веса с VAD — 1,98 ГБ. Поставки компонентов и MemOS SDK заняли ещё 0,59 ГБ. Если Docker одновременно хранит сжатые копии слоёв, оценка этого набора достигает 12,45 ГБ до установки дополнительных образов, `npm ci` и сборки. Для полного сценария лимит 14 ГБ требует замера пика. Workflow печатает свободное место до и после удаления предустановленных Android и GHC, затем каждые пять секунд замеряет использование диска.

## Запустить кандидат из исходников

Выберите `install_path=compose`, чтобы собрать образы Web, Auth, Timer и Artifacts из того же SHA и запустить их с изолированными PostgreSQL и NATS. Web собирается через штатный prepared runtime. Workflow использует тестовые миграции, роли и конфигурацию из `deploy/compose.production-test.yml` кандидата. Он проверяет готовность контейнеров и HTTP endpoint Web, скачивает и сверяет по SHA-256 открытые веса GigaAM, EmbeddingGemma и Silero и замеряет общий расход диска. Этот путь проверяет запуск перечисленных компонентов. Для полной клиентской установки, включая модели и Hermes, используйте `install_path=client`.

Чтобы в том же прогоне `compose` проверить загрузку закреплённого VAD, передайте `verify_vad=true` и настройте ограниченный `BRAI_CI_HF_TOKEN` в защищённом окружении `brai-clean-install`. Дополнительная задача сверяет манифест весов с кандидатом. Токен доступен только шагу скачивания. Замер Compose охватывает открытые модели, а размер VAD указан в отчёте отдельной задачи.
