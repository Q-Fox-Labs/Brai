# Эксплуатация клиентского сборщика

## Подготовка

Сборщик использует Python 3, rsync, Docker и закреплённый официальный образ
Duplicati. Код находится в этом каталоге; операторские роли установки — в Admin.
Общая роль brai_client_backup вызывается только при явном opt-in. Она не
запускает сервис, Google-задание или таймер и не заменяет прежние ключи.
Все программы, план и состояние доступны только root. Пользовательского UI/API
у этой реализации нет; обычный профиль не получает доступ к системной CLI.

План /etc/brai-backup/plan.json соответствует [схеме](plan.schema.json).
Семантические проверки выполняет recovery.py: права, инвентарь, границы,
покрытие записывающих процессов и согласованность не выводятся из JSON Schema.

- installation_manifest — защищённый manifest принятой установки с installed
  по средам и source_revisions. environment выбирает только свой экземпляр.
- components должен содержать ровно установленные компоненты. Каждый объявляет
  roots, postgres или причину отсутствия состояния rebuild.
- opaque_roots объявляет корни исходных файлов, которые нельзя преобразовывать.
  Для компонента artifacts все файловые корни автоматически считаются opaque.
- roots — непересекающиеся канонические абсолютные корни. Корень всех профилей
  включает будущих пользователей; подпапки, таблицы и поля не перечисляются.
- postgres — все выделенные клиенту кластеры: container, user, database для
  административного соединения, data_mounts для исключения физических страниц,
  dedicated=true и при необходимости socket. Имена БД обнаруживаются при каждом
  запуске. Кластеры с данными чужих экземпляров не поддерживаются и отклоняются.
- docker_scope — метки контейнеров своего экземпляра; systemd_scope — шаблоны
  имён его служб. Не объявлять всю машину общим клиентским экземпляром.
- snapshot задаёт enter/leave argv и полный список units/containers записывающих
  служб. Новая служба без покрытия останавливает копию. Для штатного адаптера
  snapshot.py дополнительно нужны ingress_socket и ingress_uid.
- exclude содержит точный path либо root + relative с отдельным компонентом *
  для всех профилей. Например */.cache/pip относится только к этому уровню,
  а не к одноимённой пользовательской папке глубже. Каждое исключение требует
  reason и proof: root-only файл с format=brai-rebuild-proof-v1,
  restored=true, recipe, software_revision, subject с точным селектором исключения
  и закреплённым SHA-256.
- destination — googledrive://<folder>/<subfolder> без токена в URL.
  duplicati.image задаётся immutable digest. Необязательный keep_versions
  и local_keep_versions выбирает администратор отдельно для удалённых и локальных
  поколений; удаление происходит только после проверенного
  скачивания и восстановления новой копии. Значения по умолчанию нет.

Штатный адаптер запускается как Python -B snapshot.py enter/leave. Он использует
протокол release.begin/status/resume ingress, проверяет UID Unix-собеседника,
останавливает объявленных активных писателей, а затем возвращает только их.
Изначально остановленные и paused-контейнеры не запускаются. Активные внешние
зависимости, неподтверждённый drain и изменённая пауза — явная ошибка.
Список писателей нельзя заменять неподтверждённым успешным exit code: enter
обязан вернуть свой operation_id и state=quiesced; leave — state=resumed.

Оператор передаёт независимый пароль архива в /etc/brai-backup/passphrase
и Google AuthID в /etc/brai-backup/google-drive.json с единственным полем authid.
Права — root:root 0600, родительские каталоги защищены от записи другими.
Оба входа можно передать через защищённые Ansible/Vault-переменные
brai_client_backup_passphrase и brai_client_backup_google_authid. Повторное
применение принимает прежние значения, но отказывается молча заменить их.
Единственную копию пароля нельзя оставлять на сервере.

Google AuthID получает администратор через штатный
[OAuth Duplicati](https://github.com/duplicati/documentation/blob/main/backup-destinations/file-synchronization-providers/googledrive-destination.md).
Подключение чужого аккаунта и его значения из примера не наследуются.
Для отдельного испытания допустим file:///absolute/remote; он никогда
не получает cloud_verified=true.

## Запуск и состояние

После подготовки и передачи плана оператор выполняет:

    brai-client-backup inspect
    brai-client-backup prepare
    brai-client-backup run
    brai-client-backup status

inspect только проверяет покрытие. prepare создаёт и проверяет локальный
снимок; это не внешняя копия. run всегда готовит новый снимок, шифрует его,
выполняет Duplicati test all, скачивает последнюю версию с новой локальной БД
Duplicati и повторяет проверку файлов и реальное восстановление PostgreSQL.
Только после этого записывается verified с ID, временем и digest плана.

Транспорт монтирует только готовый снимок read-only, закрытый файл параметров
и собственный каталог Duplicati. Рабочие профили, Docker socket и исходные тома
в контейнер не передаются. Контейнер не публикует порт или веб-интерфейс.
Пароль/AuthID отсутствуют в argv и открытых журналах.

В /var/lib/brai-backup сохраняются current, проверяемые build-поколения,
status.json и last-verified.json. Ошибка новой попытки не заменяет квитанцию
последней успешной. Смена плана снимает успешный статус для текущей конфигурации.
Временные права staging нормализованы для root-контейнера без DAC capabilities;
оригинальные UID, права и атрибуты возвращаются из manifest при restore.
Зависимости неподтверждённых Brai Files публикаций включаются даже при исключении
scratch-корня; несуществующий исходник делает снимок неполным.
Статус всегда относится к версии и времени, а не ко всем более поздним записям.

Операции сериализованы root-only lock. SIGTERM вызывает cleanup; после SIGKILL
ExecStopPost или явный brai-client-backup resume повторяет возврат собственного
hold, завершает только свой помеченный transfer-контейнер и убирает закрытые
временные параметры. Неизвестный исход Docker сохраняет журнал и блокирует
новую передачу до разрешения. Чужие контейнеры не удаляются.

Расписание передаётся явно через brai_client_backup_calendar. После успешного
первого run администратор отдельно включает brai-client-backup.timer.
Перед обновлением кода нужно выключить таймер и дождаться завершения job;
роль не заменяет код активного сборщика. Ошибка видна через failed systemd job
и status; доставка оповещений подключается к мониторингу оператора отдельно.

## Потеря сервера

1. Вернуть независимо сохранённые ключ архива и OAuth, установить совместимую
   версию программ из Git и операторского плейбука. Не открывать запись приложений.
2. Передать прежнее назначение и выполнить brai-client-backup fetch.
   Команда скачивает последнюю версию без исходных корней и прежней БД Duplicati.
3. Выполнить brai-client-backup verify --bundle /private/downloaded-bundle.
   Нужны исходные pinned PostgreSQL images из manifest; их загружает оператор.
   Проверка создаёт только собственные изолированные кластеры, сравнивает схемы,
   все строки, векторы, последовательности и large objects, затем удаляет их.
   Для более старой версии fetch принимает --version N (0 — последняя).
4. Выполнить brai-client-backup restore --bundle /private/downloaded-bundle
   --root /new/empty/restore-root. Root не должен существовать. Возвращаются
   файлы, штатные SQLite, права, расширенные атрибуты и ссылки. Команда не
   подменяет действующие корни, не запускает службы и не применяет SQL к DEV.
5. Оператор возвращает PostgreSQL штатными pg_restore из postgres/<cluster>/*.dump
   и globals.sql в новые изолированные подготовленные кластеры. Нельзя подавлять
   ошибки существующих ролей или применять dump поверх рабочей среды.
   Чистое bootstrap-соединение и исходный image позволяют проверить полный
   globals/--create путь; его использует postgres_store.isolated_verify.
   Исходные postgresql.conf, HBA/ident, включённые конфиги и postgresql.auto.conf
   сохранены в configuration с картой контейнерных путей; оператор возвращает их
   с учётом нового окружения, не подменяя конфигурацию действующей БД.
6. По операторскому протоколу сопоставить новые корни и БД установленным службам,
   проверить профили, права, Артефакты, переписку, память и квитанции и только
   затем открыть запись. Провести следующую резервную копию.

Это инструменты подготовки, доставки и контрольного восстановления. Автоматическое
переключение рабочего сервера на скачанные данные намеренно не выполняется.

## Проверки разработки

Обычные проверки на синтетических файлах и SQLite:

    python3 -B -m unittest discover -s deploy/backup/tests -p test_collector.py -v

Изолированный нативный прогон выполняется root через Ansible с явными
BRAI_BACKUP_NATIVE=1 и BRAI_BACKUP_TEST_POSTGRES_IMAGE=<immutable image>:

    python3 -B -m unittest discover -s deploy/backup/tests -p test_native.py -v

Он использует отдельный /run-каталог и собственные помеченные контейнеры без
сети и рабочих volumes. Google не подключается. Проверяются два поколения,
новые пользователи/папки/БД/таблицы/колонки, binary/NUL/FTS, реальные векторы,
остановка/возврат своего writer, полная потеря источников и локального каталога,
скачивание и восстановление. Успех стенда не подтверждает конкретный Google-аккаунт
или установку на чистую машину: эти этапы принимает администратор клиента.
