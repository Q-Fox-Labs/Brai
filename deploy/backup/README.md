# Резервирование и восстановление данных Brai

## Назначение и статус

Требование к клиентской установке: после полной потери сервера восстановить
приложения из Git и операторского плейбука, затем вернуть всё уникальное состояние
из резервной копии. Возвращаются все профили, их данные, права, память, переписка,
файлы и состояние операций на момент согласованного снимка.

Реализация сборщика, транспорта и проверок находится рядом с этим документом;
[эксплуатационный порядок](OPERATIONS.md) описывает план, CLI и приёмку.
Наличие исходников не подтверждает
работающий сборщик, расписание, копию на Google Drive или проверенное восстановление.
Реализация резервирования и её выпуск требуют отдельной приёмки. Перестройка
хранения MemOS и Диалогов в текущий объём не входит.

## Состав копии

Четыре области — логические группы. Переносить все данные в usercustom не нужно.

| Область | Что сохранять |
| --- | --- |
| Личные данные всех профилей | usercustom целиком с будущими подпапками; личные инструкции и навыки; конфигурацию, доступы, локальные БД, переписку и устойчивое состояние профиля, находящиеся вне usercustom; необходимое состояние авторизации браузера. Включать все сохранённые профили, в том числе отключённые, пока их данные не удалены штатно. |
| Артефакты | Все сохранённые файлы Артефактов и их метаданные в БД, включая связи и сведения о владельцах. Состояние незавершённых зарегистрированных публикаций вместе с необходимыми для их завершения файлами. |
| Базы и другое состояние служб | Полные штатные дампы всех БД экземпляра: пользователи, роли продукта и привязки, настройки, задания, расписания, память, переписка, история, квитанции и прочие данные. Для векторных хранилищ — сами векторы, исходные записи, связи и метаданные. Устойчивые очереди, журналы доставки и подтверждения также входят, даже если находятся вне БД. |
| Уникальные общие настройки и ключи | Реестр профилей и идентичностей, настройки экземпляра, которые нельзя получить из Git и плейбука, ключи шифрования и подписи, секреты и доступы, необходимые для восстановления. Они передаются только защищённым способом. |

MemOS и Диалоги выгружаются обычными дампами с текущим содержимым.
Повторяющиеся тексты, старые выдачи контекста, версии саммари и записи памяти
не вырезаются сборщиком. Их изменение — задача владельцев этих сервисов.
Векторы не заменяются обещанием заново вызвать модель.

## Исключения

Исключать можно только данные с проверенным способом восстановления из
зафиксированных исходников, плейбука или сохраняемых первичных данных.

- Код из Git, установленные зависимости, образы и модели, сборки и их кэши.
- Физические страницы БД и индексы при наличии полноценного штатного дампа;
  после восстановления индексы создаются штатным механизмом.
- Проверенные кэши браузера, отчёты о падениях Chrome и обычные диагностические
  логи, если они не содержат единственное свидетельство незавершённой операции.
- Временную рабочую область workspace/files/work. Она не является постоянным
  хранилищем. Файлы, на которые ссылается незавершённая зарегистрированная
  публикация, сохраняются как зависимости этой операции.
- Старые миграционные и аварийные архивы — только после доказательства, что
  актуальная копия содержит всё их уникальное состояние.

Не исключать каталог, таблицу или поле только по имени cache, log, archive,
migration или temp. Реестр исключений содержит точный объект, основание,
способ пересоздания и результат проверки. Новое исключение требует новой проверки.
Схемы, последовательности, версии миграций и служебные квитанции по умолчанию
сохраняются. Неизвестное состояние нельзя молча считать воспроизводимым.

## Автоматическое включение новых данных

Корни данных экземпляра, профили, хранилища Артефактов и принадлежащие экземпляру
БД определяются по доверенному инвентарю установки и фактическому состоянию.
Не использовать список нынешних пользователей, проектов, имён БД или таблиц
как постоянный состав бэкапа. Учитывать все обслуживающие экземпляр кластеры
и отдельные персональные БД служб; обход одного Supabase недостаточен.
Чужие экземпляры на общем сервере не включаются.

Каждый корень сохраняется рекурсивно: новые подпапки и файлы входят по умолчанию.
Каждая обнаруженная БД выгружается полностью: новые таблицы и поля не требуют
ручного добавления. Исключения должны быть явными и узкими.

Новый корень, отдельный контейнерный том или новый тип БД должны быть объявлены
у владельца компонента и в установке. Для нового типа хранилища до его принятия
нужны штатные выгрузка и восстановление. Универсальный дамп PostgreSQL
не резервирует автоматически отдельный векторный сервер или файлы его тома.

Обнаруженное хранилище без правила резервирования, недоступный корень,
непрочитанная БД или несовпадение инвентаря означают неполную копию.
Операция должна завершиться ошибкой с указанием пропуска, сохранив предыдущую
пригодную копию. Частичный результат не получает статус полной успешной копии.
До реализации этих проверок автоматическое включение не считается обеспеченным.

## Подготовка и передача

Управлять резервированием всей установки и восстановлением могут только admin
и creator. Роль проверяет доверенный сервер для каждого входа: UI, API, фонового
запуска и инструментов. Обычный пользователь не подключает Google Drive и не
меняет состав, расписание, ключи или назначения копий.

Предусматривается один системный сборщик, запускаемый администратором или таймером.
Он готовит закрытый каталог согласованного снимка из четырёх областей.
Duplicati запускается отдельным контейнером для каждой операции и получает подготовленный каталог
только для чтения. Его задача — шифрование, сжатие, хранение версий и передача
на Google Drive; сбор данных не зависит от инструкций или ответа Hermes.

Снимок создаётся штатными средствами: PostgreSQL — pg_dump/pg_restore или SQL-дамп
и штатное восстановление; SQLite — согласованная резервная копия средствами
SQLite; другие БД и устойчивые очереди — средствами их владельцев. Копирование
открытого файла БД без согласования с WAL не является резервной копией.
Специальный формат строк MemOS или Диалогов не вводится.

Владелец сборщика согласует записи в БД, файлы Артефактов и очереди: штатный
снимок либо согласованная приостановка записи на время фиксации данных.
Отдельные дампы разных БД сами по себе не образуют общий момент времени.
Читающий контейнер Duplicati не решает эту задачу.

Копия сопровождается перечнем БД и корней, версиями кода и схем, контрольными
суммами, размерами, исключениями и итогом каждого шага. Это описание снимка,
а не собственный формат данных БД. Подготовленная локальная копия и принятый
Google-токен не подтверждают внешнюю копию.

Расписание и срок хранения выбирает администратор; произвольные значения
в продукте не назначаются. Пароль шифрования хранится независимо от сервера
и доступен администратору при полной потере машины. Секреты не выводятся в
журналы и не попадают в Git. Сбой становится виден администратору.

## Восстановление и приёмка

1. Установить зафиксированную совместимую версию из Git операторским плейбуком,
   подготовить расширения БД и защищённые входы, не запускать обычную обработку.
2. Расшифровать выбранную копию и проверить её состав и контрольные суммы.
3. Восстановить БД, все профили, файлы Артефактов, устойчивые очереди, уникальные
   настройки и ключи штатными средствами. Вернуть владельцев и права файлов.
4. До открытия записи проверить пользователей и изоляцию профилей, память
   и векторы, переписку и саммари, доступность Артефактов, задания и квитанции.
   Завершённые действия не должны повториться из-за потери подтверждений.
5. Проверить запись новых данных и их попадание в следующую копию.

Проверка выполняется на отдельной установке без изменения рабочих данных.
Успех выгрузки не заменяет приёмку восстановления. После изменения схемы,
движка БД, путей, авторизации или способа шифрования приёмка повторяется
для затронутого сценария.
