# Пользовательские файлы Hermes

Все постоянные пользовательские байты принадлежат Artifacts. Локальные пути — временные копии. Служебные файлы, настройки, инструкции, навыки и внутренние базы остаются в штатном lifecycle. Движки экземпляров уже отдельные; адаптер их не разделяет и не копирует.

## Уточнения текущего поручения

Ход включает подготовку исходного сообщения после занятия guard адаптера, даже когда шлюз ещё ожидает публикацию файлов или выполнение входных плагинов. Текст, правки сообщений этого хода и готовые вложения в это время сохраняются как steer того же поколения и передаются исполнителю перед его первым запросом. Настоящий альбом сохраняет сборку и передаётся одним мультимодальным уточнением. Отмена подготовки освобождает эти входы и ожидания; следующий ход их не наследует.

Авторизованные пользовательские сообщения и готовые вложения, принятые до фиксации текущего финального ответа, передаются в тот же ход через steer. Уточнение не прерывает инструменты и не запускает отдельный ответ после финала. Правка сообщения текущего хода уточняет его; правка старого сообщения обновляет журнал без нового запуска агента. Служебные события Telegram сохраняются для диагностики отдельно от пользовательских поручений.

## Интерфейс и доверие

`publish_file`/`fetch_file` сохраняют совместимость. `files_get`/`files_list` используют owner-схемы Artifacts с фиксированным владельцем. `files_prepare({mode,items})` проверяет метаданные всего упорядоченного набора и возвращает `deliveryMarker`. Элемент содержит `artifactId`, необязательные `caption` и `presentation`; режим — `files` или `album`. Порядок и повтор одного файла сохраняются. Один ответ содержит один явный набор. Перед доставкой заново проверяются байты, размер, SHA-256, owner и готовность всех элементов.

Модель не задаёт owner, адрес сервиса или NATS subject. Private `files.configuration` передаёт bootstrap только root-owned конфигурацию без credentials и отсутствует в MCP модели. [OpenRPC](../trusted.openrpc.json) описывает private методы.

Внутренний `reference_metadata(reference)` возвращает ранее проверенные имя, ID и тип файла из aliases фиксированного владельца по старому пути либо явной ссылке `artifact:`. Он не обращается к сети, не скачивает байты и не создаёт пользовательский результат. Неизвестный локальный путь не сканируется. Поиск памяти вызывает этот порт только после проверки доступа к исходнику со ссылкой. Это сведения для нахождения документа: текущие ready/owner и байты по-прежнему проверяет штатное чтение Artifacts, а сохранённое имя не даёт права прочитать файл.

## Файлы изолированных пользователей Telegram

В режиме `BRAI_IDENTITY_MODE=telegram` общий ingress загружает только `transport.py`. Он не создаёт FileStore, не читает прежнюю конфигурацию owner и не использует `_brai_hermes_file_port`. Transport сохраняет исходные message/attachment IDs, подписи и ключ альбома до native объединения. Неописанные файловые и агентские операции завершаются `FILES_OWNER_REQUIRED`.

Личный worker устанавливает `_brai_identity_worker.call` до импорта движка. Bootstrap получает `files.configuration` через Unix broker. При наличии этого marker ни bootstrap, ни bridge не переходят к прежнему publisher. FileStore, SQLite, рабочая область, aliases и результаты находятся в собственном home. Broker определяет UID через SO_PEERCRED и повторно проверяет действующего пользователя Auth и registry. До активации профилю со статусом provisioning доступна только несекретная конфигурация его собственного home, сверенная с root-owned runtime mapping: это позволяет проверить startup до перевода в active. Остальные файловые операции, инструменты и память в provisioning закрыты; blocked/disabled не получают и bootstrap.

Worker вызывает `files.configuration {}`, `files.publish {path,requestId}`, `files.fetch {artifactId}`, `files.get`, `files.list`, `files.prepare`. Последние три метода сохраняют прежние параметры owner-схем Artifacts. Параметр owner или UID worker не принимает. Публикация и загрузка возвращают `artifactId,filename,mimeType,sizeBytes,sha256,localPath,markdown`; путь и Markdown указывают только на личный `home/results/<artifactId>/<filename>`. Inline-разметка сохраняет решение проверенного publisher.

Для публикации broker открывает каждый каталог и конечный inode без symlink, проверяет UID, единственную hardlink-ссылку и предел 64 MiB. Он копирует стабильный inode в root-owned staging, сохраняя basename. Root publisher получает только этот snapshot и owner из доверенного профиля. Перед выдачей копии broker проверяет точный root cache path, размер и SHA-256. Запись в личный каталог выполняется относительно закреплённых descriptors с атомарной заменой; произвольный root path от worker не принимается.

`runtimeProfilesPath` указывает на защищённый root-owned mapping UID → userId/profileId/home/stagingRoot/cacheRoot. Broker перечитывает mapping и сверяет привязку при файловом доступе, поэтому приглашённый профиль не требует перезапуска. При отсутствии этого пути допускаются только явно заданные индивидуальные `artifactCacheRoots`; общего cache fallback нет.

Trusted ingress после регистрации хода вызывает `ingress.prepare {uid,turnId,paths}`: broker копирует скачанные входящие файлы UID ingress из непересекающихся `ingressReadRoots` в media выбранного профиля. Исходящие файлы читаются через `ingress.open-artifact {uid,artifactId,turnId?,inputId?}`: после свежей проверки Auth, владельца Artifacts и текущего хода broker выдаёт один O_RDONLY descriptor исходного root-cache inode через SCM_RIGHTS существующего Unix socket. JSON-RPC результат содержит только artifactId, filename, mimeType, sizeBytes и sha256. Ingress проверяет descriptor и байты до Bot API; права каталогов не расширяются и дополнительная локальная копия не создаётся. Фоновая доставка использует тот же метод без turnId после проверки owner-bound маршрута. Worker не получает этот порт. Ограничения, отмена и закрытие FD описаны в [WORKER.md](../identity/WORKER.md#чтение-исходящих-вложений). Прежние `ingress.artifact` и `ingress.delivery-artifact` сохранены для совместимости старых ingress; только они используют `ingressDeliveryRoot`.

Broker не повторяет операции после обрыва или тайм-аута. `requestId` публикации сохраняет семантику идемпотентности Artifacts; неизвестный исход не означает отмены публикации. Автономная проверка `files/tests/identity.test.mjs` подтверждает запрет symlink/hardlink, проверку owner/cache/hash, сохранение исходных ID и отсутствие fixed-owner bootstrap. Живое взаимодействие worker, publisher и Telegram подтверждается отдельной приёмкой Ansible.

## Обязательные границы

Ansible применяет `native.patch` к закреплённому отдельному движку `517b5e10febd619ce30bb22580e29b160266eb43`. Для DEV переход проверяет неизменённость исходного выпуска и точный файловый delta; в PROD общий engine не допускается. Bootstrap читает защищённую конфигурацию своего экземпляра и использует его Node. Ошибка адаптера останавливает файловую операцию. Patch охватывает общий conversation loop, tool dispatch, read/write/patch, terminal/code execution cwd, final response и канальные отправки. CLI/API, cron и дочерние агенты используют ту же границу.

Gateway proxy пока не имеет подтверждаемого протокола файловых наборов и стабильного ключа операции: файловый вход через proxy останавливается до запроса с `FILES_PROXY_UNSUPPORTED`. Для поддержки необходим согласованный протокол proxy и удалённого движка; текстовые запросы сохраняют штатный путь.

CLI/API принимают локальные `@file:`/`@image:` и `artifact:<UUID>`; мультимодальные API-файлы сначала публикуются. Прямые удалённые/inline байты модели отклоняются. Канальные CDN-вложения скачиваются штатным SSRF/size-ограниченным загрузчиком, затем публикуются. Прерванный или неуспешный ход без текстового ответа сохраняет исходный результат и диагностику; файловая обработка не создаёт для него отправку и не заменяет причину ошибки. Результат conversation содержит `fileSets` со стабильными ID; каналы получают отдельные временные копии конкретного ответа.

Внутреннее inline-кодирование изображений для vision разрешено только для уже принятого набора и только в текущем вызове gateway. Прямой API не получает это разрешение. Если native builder не подготовил хотя бы одно изображение, набор не передаётся агенту как успешно принятый.

Промежуточные материалы в рабочей области автоматически не публикуются. Сохраняются явно выбранные результаты и выходы генераторов. Файловые изменения вне временной области и разрешённых служебных путей отклоняются. Терминал и code execution получают временный cwd; это правило приложения, не отдельная изоляция произвольного shell-кода.

Для авторизованного входа gateway рабочая область привязана к экземпляру, каналу, чату, теме, отправителю и сессии. Она сохраняется между ходами и перезапуском, включая время ожидания согласования; очистка другого хода и подтверждённой публикации её не удаляет. Файловые инструменты отклоняют путь в область другой беседы. Это локальные рабочие данные без автоматической публикации и отдельной гарантии резервного копирования: для постоянного результата по-прежнему нужен Artifacts. При отсутствии доверенного входа остаётся временная область операции. Автоматическое удаление областей бесед не выполняется; оператор учитывает их в хранении.

Штатное завершающее предупреждение проверяющего не передаёт пользователю внутренние пути и коды инструментов: вместо него отображается понятное сообщение о неудавшейся попытке. Остальной текст ответа сохраняется.

## Приём наборов

Identity файла включает owner, канал, экземпляр, чат, тему, отправителя, исходный message ID и attachment ID исходного сообщения. Позиция позднее объединённого массива в ключ не входит. Состав, подписи, происхождение, готовность и admitted-версия хранятся в служебной SQLite Hermes; байтов там нет.

Telegram публикует каждый готовый элемент в Artifacts после авторизации. При занятом ходе отдельный готовый файл сразу передаётся в steer. Настоящий Telegram-альбом с `media_group_id` сначала собирается целиком, затем передаётся в steer одной пачкой; готовый набор не ждёт завершения ответа. Принятая подготовка файла или альбома удерживает финал текущего хода. При свободной сессии применяется штатная сборка. Для альбомов и серий отдельных фотографий без `media_group_id` истечение окна ждёт завершения update этого чата, уже зарегистрированных в per-chat FIFO, включая медленные публикации; отмена прежнего таймера не отменяет FIFO. Серия отдельных фото сохраняет общий ключ набора до публикации каждого следующего файла, поэтому после перезапуска она восстанавливается одним набором с исходным порядком и подписями. Повтор Telegram-сообщения сохраняет ранее записанный ключ, даже если окно группировки уже закрылось. Группировка учитывает полный маршрут и media_group_id. Поддержаны фото/видео и документы. Повтор использует прежний ключ. Более поздний текст той же темы ждёт передачу ранее принятых фотографий и альбомов; другие темы и более поздние фото его не задерживают. При ошибке предыдущего набора текст сохраняется для повторной передачи. Перед агентом проверяется весь набор; неполный набор останавливает обработку. Поздний элемент становится дополнением; прежние элементы повторно не запускаются. Изображение Telegram, альбом, документ и дополнение к набору передаются в steer текущего незавершённого хода вместе с подписями и проверенными изображениями. Уже принятые элементы повторно не передаются. После перезапуска восстанавливаются принятые не переданные наборы и неопределённые публикации с прежними ключами. Admitted означает передачу в обработку, не успешное выполнение задачи. Восстановленный после перезапуска набор, включая одиночный файл, ждёт занятый ход и не прерывает новое пользовательское сообщение. Ошибка файлового доступа при фоновом восстановлении записывается в технический журнал и наблюдатель; она не создаёт уведомление об ошибке нового текстового хода. Явно присланное пользователем вложение сохраняет штатную видимую обработку ошибок. Обычный текст без файловых ссылок не обращается к Artifacts. При конфликте параллельно подготовленных версий канал запускает восстановление оставшихся элементов без перезапуска; старые версии не повторяются.

При первом запуске версии с исправленной группировкой ранее сохранённые, но не переданные Telegram-вложения требуют отдельной сверки: старый учёт не доказывает, был ли каждый файл уже использован в другом ходе. Их identity сохраняются в `legacy_recovery_review`; исходные записи и файлы остаются на месте, а автоматическое восстановление их не запускает. Количество записывается как `BRAI_FILES_LEGACY_REVIEW_REQUIRED`. Это только переход старых данных: новые незавершённые наборы восстанавливаются штатно. Решение о старых записях принимает оператор после сверки; повторная отправка файла пользователем получает новый message ID.

## Доставка и очистка

Набор получает проверенные копии и leases до первого вложения. Telegram отправляет совместимые группы по 2–10 через sendMediaGroup, большие наборы разбивает заранее, одиночный остаток отправляет отдельно. Фото/видео могут смешиваться; documents/audio группируются только со своим типом. Несовместимые сочетания, voice и animation идут по порядку отдельно с пояснением. Проверяются типы и размер. Подпись, не помещающаяся в файл, отправляется целиком отдельным сообщением или Rich Message; за границей Rich Message адаптер экземпляра выдаёт полный PDF. При отсутствии такой возможности отправка не разбивается. Чат и тема сохраняются. [Ограничения Bot API](https://core.telegram.org/bots/api#sendmediagroup).

Личный IPC-адаптер передаёт набор целиком через `send_file_set`: owner descriptors, исходный порядок, подписи, presentation, kind и явный fallback. Ingress проверяет все файлы до первого API-вызова и сохраняет native Telegram-группировку. Прямые voice/animation также публикуются в Artifacts. Успех голосового требует media receipt; текст после ошибки не считается доставленным голосом.\n\nПеред вызовом канала записывается unknown. Квитанции каждого элемента сохраняются; sent требует подтверждения всего набора. Потеря ответа оставляет unknown с известными квитанциями, без автоматического повтора или fallback. Другие каналы преобразуют тот же набор в поддерживаемое представление.

Временные копии ответа освобождаются после потребителя/доставки. Восстановление и публикация файла удерживают общий cache lock до проверки байтов и сохранения aliases; очистка другого хода не удаляет незавершённую загрузку. Leases защищают параллельные операции; после crash проверяется PID/start time. Неподтверждённые публикации и неизвестные доставки сохраняются для восстановления. Разрешение чтения каталога не даёт права удалить его содержимое: очистка ограничена объявленными временными путями.

## Переход и приёмка

`install.py` сохраняет UID/GID/mode/ACL движка и не запускает gateway. Прежние overlays проверяются после обратного применения только нашего delta на копии. Перенос старых материалов выполняет отдельный Ansible manifest: размер, SHA-256 и восстановление каждого файла проверяются до освобождения источников. Старые пути остаются в aliases. Служебные файлы, инструкции, навыки и секреты исключаются.

Автономные Python/Node проверки и проверка pinned patch не требуют модели. Живые CLI/API, cron, дочерний агент, Telegram и восстановление после очистки кэша входят в приёмку конкретной поставки. До принятия результата DEV не обновляется; миграция данных в этой задаче не запускается.

Текст и подписи к файлам преобразуются в формат Telegram, включая именованные ссылки; ошибка форматирования не вызывает отправку сырого текста. Автономная отправка файлов также проходит через Artifacts, прямой обход файлового адаптера отклоняется.

## Делегирование и завершение

Одноразовый приём входящего набора выполняет родитель. Дочерняя работа наследует доверенное происхождение и разрешённые файлы, но не право повторного приёма сообщения. Контексты восстанавливаются при выходе и ошибках; рабочие области дочерних сессий различаются. Точный временный каталог каждого хода передаётся модели через ephemeral system context; исходный пользовательский текст и общее окружение процесса не меняются. После выхода прежний контекст восстанавливается.

Перед остановкой основного хода готовые результаты помощников этого хода сохраняются в его контексте. Отметка потребления в существующем реестре делегирования ставится только после успешного сохранения сессии. Доверенная metadata записи контекста закрывает окно сбоя между сохранением и отметкой. При повторе или перезапуске уже включённый результат не создаёт нового ответа. Для ещё работающих задач сохраняется доставка между ходами; результаты другой сессии и исторические завершённые задачи не подмешиваются.

Ранние отказы отдельных помощников сохраняются для диагностики; родитель получает сводный итог. Автоматическое техническое уведомление о каждом отказе в Telegram не отправляется. Полезный новый результат обрабатывается обычным ходом, уведомление без новых сведений использует штатное намеренное молчание.

Диагностический footer проверки записи файлов фильтруется также на последней границе результата: движок добавляет его после раннего output transform. Пользователь получает последствия отказа по-русски; пути и коды остаются в сохранённых результатах инструментов.

## Гостевой текстовый артефакт

Private files.create-text принимает filename, content и requestId; без пути и ownerId. До 1 МиБ точных UTF-8 байтов. Публикация использует штатные staging/Artifacts и проверяет имя, размер и SHA-256; код в содержимом не исполняется. Ответ — bounded artifact descriptor с канонической artifact-ссылкой. files.read-text принимает только artifactId и возвращает filename/content после owner/size/hash проверки. Guest-публикация входного файла требует root-owned admission receipt для точного профиля, пути и байтов; общий files.publish модели не выдаётся. [Политика](../identity/ROLES.md), [OpenRPC](../identity/broker.openrpc.json).

Служебный bootstrap допускает только точные readonly `serviceRoots` за пределами HOME: `/opt/brai-profile/engine`, `/opt/brai-profile/runtime`, `/opt/brai-profile/instructions`, `/opt/brai-profile/skills`. Последний соответствует настоящему namespace mount общих навыков. Это не добавляет эти каталоги в пользовательские `readRoots`, `temporaryRoots` или `legacyRoots`; похожие имена и путь `/opt/brai-profile/system-skills` отклоняются.
