# Пользователи и границы Hermes

Этот каталог содержит адаптеры личных процессов Hermes и доверенные границы ввода, памяти и сети. Их наличие в исходниках не подтверждает включение в работающем экземпляре. Переключение требует завершённой установки, миграции и отдельной приёмки.

Личный голосовой инструмент `local_ai_invoke_synthesize` принимает короткий ввод `{text}` и вызывает `runtime.synthesizeVoice`, как обычный MCP. Этот обработчик добавляет доверенную модель, идентификаторы и срок выполнения; владелец определяется личным runtime. Полный внутренний DTO не является входом инструмента агента.

[Сетевая граница](EGRESS.md) описывает внешний доступ и прокси модели. Личный браузер использует собственный процесс Chrome и CDP в сетевом пространстве worker; его запуск и проверку готовности обеспечивает установщик.

Служебный Chrome предпочитает уменьшенную анимацию, чтобы декоративные WebGL-фоны не задерживали чтение страницы в headless-режиме. Настройка действует только в его процессе.

Chrome видит весь собственный HOME по каноническому пути. Каталоги профиля, кеша и временных файлов находятся в HOME/browser; чужие HOME и системные секреты скрыты. Подкаталог браузера не используется как привилегированный источник монтирования. Подготовка его состояния выполняется с личным UID, без root-записи в изменяемые пользовательские каталоги.

PM bootstrap с фактами зависимостей и родителями точки подключения venv входит в защищённую поставку softwareRoot/pm-bootstrap. Worker и ingress подключают его только для чтения; личный HOME/pm не является источником монтирования. Изменяемые личные файлы остаются в HOME и не используются как доверенные пути запуска.

Канонический PM получает отдельный личный файл `.install.lock` из каталога `pm-locks` рядом с `profiles`. Все родители этого файла и точки его подключения принадлежат root: пользователь может держать lock, но не может заменить источник монтирования. Факты зависимостей, bootstrap и venv остаются доступны только для чтения.

[Личный процесс и IPC](WORKER.md) описывает границу ingress/worker. Auth владеет постоянной идентичностью Brai, правами и сессиями; профиль не назначает себе владельца. Доверенный Telegram ingress определяет отправителя до обращения к личной истории и передаёт событие только связанному процессу. Поддерживается только личка боту; групповые сообщения не обрабатываются. Профиль и постоянная память привязаны к пользователю, поэтому переход из прежней группы в личку не требует нового переноса. Подтверждённая личная память сохраняется; неоднозначные записи прежнего переноса остаются в закрытом архиве. Попросите агента подключить второй личный Telegram-аккаунт: инструмент brai_telegram_link_account вернёт сведения, затем агент своими словами объяснит полный доступ к данным и запросит явное согласие без контрольной фразы. Смысл свободного ответа определяет агент, а broker сверяет полную точную копию нового человеческого сообщения, исходный аккаунт, тему, срок и выбранное действие; списка разрешённых положительных фраз нет. После нового подтверждения в той же личке агент объяснит переход на второй аккаунт; проверенная ссылка на бота придёт с объяснением, а одноразовая команда — отдельным копируемым блоком с кнопкой «Скопировать». Связанные аккаунты используют общий профиль, память и файлы, но отдельные беседы. Попросите агента отвязать этот или другой свой аккаунт: он назовёт аккаунт по имени и username, объяснит последствия и запросит подтверждение. Первый аккаунт тоже можно отвязать. Пользователь может отключить все аккаунты; у администратора должен оставаться хотя бы один канал связи. Профиль и данные сохраняются, входы на сайт отзываются. После отвязки всех аккаунтов Telegram-доступ прекращается.

Шлюз памяти запускает root: `python3 -B -m identity.memory_gateway --config /путь/к/config.json`. Конфиг root-owned с режимом 0600 содержит `registryPath`, `upstream` (HTTP на числовом loopback), `authorizationSocket`, `cursorKey` (32 случайных байта в 64 hex-символах), `socketPath` и `adminSocket`. Каталоги сокетов принадлежат root и не доступны на запись другим пользователям. При запуске шлюз проверяет реестр и наличие stream/index API, затем объявляет `READY` и поддерживает systemd `READY=1`. SIGINT и SIGTERM закрывают сокеты.

Подтверждение `/product/add` возвращает плагину логический куб запроса. Перед преобразованием шлюз требует непустые committed memory IDs и совпадение физического куба каждой строки с разрешённым профилем; неполное или чужое подтверждение отклоняется.

Для каждого профиля логический куб `cube` хранится как физический `profileId__cube`. Границы запросов и ответов проверяются по реестру и UID соединения; актуальный Auth проверяется через root broker до операции и до выдачи ответа. Административный сокет root-only, а полномочия администратора проверяет вызывающий Control. Изменение статуса во время операции не отменяет уже начатую запись, но не позволяет вернуть её результат пользователю.

Большое чтение сначала полностью проверяется в закрытом временном файле, затем передаётся с периодической проверкой Auth. Одновременно доступны два файла, каждый не более 2 ГиБ; превышение даёт ошибку без усечения. Необязательный `spoolDirectory` должен быть root-owned с режимом 0700. `quarantineProfile` задаёт отдельные `userId`, `profileId`, `homeScope`, `memoryEpoch` и список логических `cubes`; архив доступен только через административный сокет и каждая запись обязана содержать маркер карантина. Исходный автор архивной записи не подменяется.

Worker задаёт browser-harness короткий `BH_RUNTIME_DIR=/tmp/brai-browser` внутри собственного временного пространства. `BH_RUNTIME_DIR_SHARED=1` сохраняет отдельные IPC-сокеты именованных сессий, включая имена длиной 64 символа. Длинный HOME с UUID не участвует в пути Unix-сокета; снимки и рабочие файлы браузера остаются в личном профиле.

Административный список полностью проверяет каждый поток, но хранит в памяти только выбранную страницу и ограниченное число ключей. Подписанный непрозрачный cursor привязан к владельцу, профилю и поисковому запросу и продолжает после последней пары cube/id. После обновления шлюза старые cursor со смещением недействительны: список нужно открыть заново. JSON страницы ограничен 820000 байт; общий объём текстов может быть больше. Поле text содержит не более 2048 байт UTF-8, textTruncated явно указывает сокращение, totalMemoryBytes содержит исходный размер. Полное содержимое доступно при чтении записи.

Каждый процесс пользователя получает отдельные UID, HERMES_HOME и сетевое пространство. Общие credentials, чужие профили и внутренние сокеты ему недоступны. MemOS остаётся общим; gateway определяет область запроса по проверенному UID соединения. Прямой запрос к MemOS из кода пользователя запрещён системной границей.

Обычный запрос к агенту в личном Telegram-чате инициирует одноразовый вход. Секрет и точный адрес установки подставляет доверенная доставка, минуя память, модель и журнал содержимого. Кнопок выдачи кода нет.

Миграция сначала сверяет отправителей и происхождение старой памяти. Неоднозначные записи сохраняются в закрытом архиве. Запуск новой схемы до проверки изоляции и переноса всех пользователей запрещён.

[Управление идентичностью и выдача кода](CONTROL.md) описывает доверенные операции Auth, административного чтения и доставки кода.

Служебные ответы Telegram о привязке и приглашениях сохраняют тему исходного личного сообщения. Исход доставки записывается без текста, кодов и токенов; неподтверждённая отправка не вызывает повтор привязки или автоматический повтор сообщения.

Погашение команды привязки обрабатывается до модели. Машинное подтверждение показывает имена и usernames обоих подключённых аккаунтов и напоминает, что любой можно отвязать через агента. Имена читаются текущим Bot API getChat только для привязок, подтверждённых Auth. При отказе чтения имени успешная привязка не повторяется; сообщается, что имя недоступно. Полная доставка вопроса агента подтверждается ingress, включая последнее сообщение при разбиении ответа; промежуточный вывод и неуспешная доставка не открывают согласие.

## Общие возможности и личные настройки

Обычное обновление отдельного профиля использует существующий Root-only ingress socket.
`profile.release.try` и `profile.release.status` принимают `operationId`, `attemptId`,
`profileId`, `targetPayloadHash`, `workerPid`, `workerStartTime`; статус `ready`
подтверждает закрытый вход профиля и проверенный простой его исходного процесса.
`busy` означает открытый вход и подтверждённое отсутствие удержания источников;
ожидающий профиль продолжает работать и принимать подтверждения. `profile.release.resume`
дополнительно принимает `replacementPid` и `replacementStartTime`, ожидает реального
завершения восстановления и выдаёт сохранённую квитанцию о возобновлении. Клиент
проверяет привязку systemd и PID независимо; ingress проверяет UID, PID и время
запуска подключённого процесса. Неясный результат оставляет профиль закрытым.

До подтверждения Telegram каждый вход сохраняется в общем транспортном журнале
`identity-chats/00000000-0000-0000-0000-000000000000/telegram.sqlite3` вместе с
исходной классификацией Auth; зарезервированный UUID не может быть UUID профиля.
Зарегистрированные входы также сохраняются в SQLite журнала профиля с исходной
привязкой Auth и поколением беседы. После сбоя не переданное приглашение восстанавливается
как приглашение исходного отправителя, а не как новое сообщение созданного профиля.
Неизвестный
результат передачи не переигрывается автоматически; нативное подтверждение дубликата
не является доказательством выполнения действия. Метаданные схемы версии 2 и снимок
привязки добавляются без удаления прежних таблиц или строк. Откат к старому читателю
требует независимой проверки отсутствия незавершённых входов и удержаний.
SQLite использует существующий busy timeout журнала: ошибка блокировки прерывает
возврат пачки до подтверждения Telegram; это не ограничивает время работы агента.
Изолированный Root-only тест `tests/test_ordinary_uds_root.py` проверяет kernel UID,
PID и время запуска на отдельных синтетических процессах, включая потерянный ответ
resume. Его worker имитирует RPC и не подтверждает работу полного native engine;
пропущенный без Root тест не считается такой проверкой.

Установщик собирает единый readonly каталог из bundled-навыков закреплённого engine, продуктовых инструкций с их скриптами и справкой, а также общего brai-task-workflows. Все личные процессы подключают его как `/opt/brai-profile/skills` через native `skills.external_dirs`. Личные навыки создаются в `HERMES_HOME/usercustom/userdata/skills`; прежний личный каталог `HERMES_HOME/skills` остаётся доступен для совместимости и не становится общим.

Системные настройки возможностей берутся из принятого `server-defaults.json`. Provider диалога, память, credentials и пути привязываются к текущему пользователю отдельно. Нативный TTS использует `identity.synthesize`: одна owner-bound попытка Local AI, проверка Artifact ID, формата OGG и контрольной суммы перед созданием результата. Подписочный image provider использует личный relay; OAuth credential остаётся в доверенном egress. GIF сохраняют отдельный общий API-маршрут.

Личные `USER.md` и `SOUL.md` принадлежат пользователю и сохраняются при обновлении профиля. Отсутствующий USER создаётся пустым; SOUL получает общий начальный текст только при создании. Актуальные USER/SOUL читаются в личный контекст каждого хода; это не возвращает файловую память MEMORY.md или её фоновое ревью. Обязательные context.md, INDEX, BASE и инструкция GIF подключаются из readonly поставки к каждому ходу через `identity.instructions`, включая дочернюю работу. Удаление личного SOUL или ссылок в нём не отменяет системный контекст. Отсутствующий, изменяемый посторонним или пустой обязательный источник останавливает зависимый ход.

Общий набор включает публичные плагины поиска, памяти, Telegram Business и голоса; их credentials и состояние остаются личными либо в доверенном сервисе. Media launcher `yt-dlp`/`instaloader` из readonly `instructions/bin` использует закреплённый SDK с явным import path. Загрузки создаются в личном `workspace/downloads`; прежнее общее media-окружение не используется.
