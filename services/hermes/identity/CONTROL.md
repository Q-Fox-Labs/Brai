# Доверенный identity control

## Служебные операции Диалогов

Broker поддерживает приватный JSON-RPC `dialogues.authorize` без аргументов.
Он получает служебный UID от ОС и ищет его в root-only `dialoguesServicesPath`:
`{version:1, services: {UID: {workerUid,userId,profileId}}}`. UID worker и root
не являются служебными UID. Привязка сверяется с реестром и текущим Auth;
ответ содержит только `userId` и `profileId`. Отказ Auth закрывает доступ.
Приватный контракт находится в broker.openrpc.json. Метод dialogues.summarize-stream принимает только поток input, проверяет тот же служебный UID и текущий Auth до вычисления и выдачи. Кадры ограничены 64 КиБ; общий broker передаёт их с обратным давлением, не собирая весь исходник или сводку в своей памяти. Один фиксированный операторский исполнитель создаёт отдельный эфемерный модельный запрос. Общий параллелизм — один; busy переносит задание без расходования попытки. Исполнитель не получает доступ к БД Диалогов. Личные контейнеры не получают общий управляющий сокет Codex. Установка реестра и исполнителя проходит отдельно через операторский lifecycle.

Для `login.send` необязательный положительный целый `threadId` поступает только от доверенного ingress, фиксируется в ходе broker и передаётся в Bot API как `message_thread_id`. Код приходит в тему исходного запроса. Worker не может выбрать или изменить тему; ошибка доставки в тему не разрешает повторную отправку в общий чат.

Control проверяет текущую сессию администратора и вызывает Auth `admin-audit` до чтения. Успешный ответ содержит `status`, `body` и `setCookies`; отказ передаётся заголовками `Nats-Service-Error` и `Nats-Service-Error-Code`. Неверный Origin, отсутствующая сессия или неуспешный аудит запрещают чтение. Активный администратор может читать данные профиля в любом известном состоянии реестра: active, blocked, disabled или provisioning. Если данные ещё не созданы, источник возвращает ошибку или пустой список по своему контракту. Cursor подписан и привязан к пользователю, операции, запросу и размеру страницы.

Машинные контракты: [AsyncAPI](asyncapi.yaml), [схемы DTO](schemas/control.schema.json), [приватный OpenRPC](control.openrpc.json).

NATS Services: `brai_hermes_identity`, queue `brai_hermes_identity`, subjects `brai.hermes.identity.v1.admin-memory-list`, `admin-memory-get`, `admin-chats-list`, `admin-chats-get`, `admin-artifacts-list`, `admin-artifacts-get` и `admin-artifacts-download` с тем же префиксом. В запросе нужны `headers: {cookie,origin}` и `userId`. Чтение одной записи принимает `memoryId`, `chatId` или `artifactId`; списки и сообщения принимают `cursor` и `limit` от 1 до 100, по умолчанию 50. Поиск памяти принимает `query`.

Для `admin-chats-get` необязательный `order` принимает `asc` (по умолчанию, прежний стабильный снимок от начала) или `desc` (последние сообщения). В `desc` каждая страница читает свежую защищённую копию и сразу удаляет её; ответ остаётся хронологическим, `nextCursor` продолжает по ID к более ранним репликам и не истекает по сроку снимка. Новые записи не сдвигают эту границу; изменения уже прочитанных строк за пределами свежей страницы и удаление сообщений не синхронизируются. Подписанный cursor привязан также к порядку; для другого порядка историю открывают заново. При повторном чтении без cursor возвращается свежая последняя страница. Это режим наблюдения Web; прежняя админка сохраняет `asc`. В каждом запросе заново проверяются сессия, роль и аудит; новые NATS subjects не вводятся.

Сервис памяти вызывается через закрытый UNIX socket: POST `/admin/list` и `/admin/read`. Полная запись `admin-memory-get` передаётся последовательными частями `{userId,memoryId,snapshotId,offset,totalBytes,sha256,chunkBase64,nextCursor}`: до 450000 исходных байт на часть и 16 МиБ на запись. Каждая часть заново требует активного администратора и записи аудита; cursor связан с сессией, пользователем, записью, профилем и эпохой. Снимок действует до двух минут; одновременно сохраняется не более восьми снимков и 64 МиБ, выполняется не более четырёх чтений полных записей. Web проверяет последовательность, целостность и полный JSON до показа. При отказе, разрыве или истечении срока нужно открыть запись заново. Профиль и UID берутся из root-owned registry, не из запроса. Чаты читаются из копии `state.db` и WAL: исходные файлы открываются без перехода по symlink, владелец и inode проверяются до и после копирования. Путь пользователя не принимается через NATS. Отказ проверки или неподдерживаемая схема возвращает 503. Страницы чатов читаются из защищённой копии SQLite в течение пяти минут; на одну страницу возвращается до 100 записей и 900000 байт текста JSON. Одна запись, превышающая этот предел, даёт 503. Одновременно хранится до 20 копий, для создания сохраняется не менее 512 МиБ свободного места. Страницы артефактов используют offset owner API: при добавлении или удалении объектов между запросами записи могут повториться или пропуститься. Общего ограничения на число сообщений или артефактов нет. Артефакты проверяются по ownerId, внутренний URL не возвращается. `admin-artifacts-download` принимает `artifactId` и возвращает серверу Web descriptor: `artifactId`, `mimeType`, `filename`, `sizeBytes`, `sha256`. Control сверяет владельца, готовность, размер до 2 ГиБ и точный внутренний URL; сам URL и байты не входят в ответ. Web строит адрес из защищённой конфигурации, не передаёт его браузеру и потоково выдаёт байты без redirect, проверяя размер и SHA-256. Несовпадение обнаруживается к концу потока, уже переданные байты отозвать нельзя.

Только доверенный broker запускает `runtime.mjs --stdio` и передаёт строки JSON-RPC 2.0 `{jsonrpc:"2.0",id,method,params}`; ответ содержит `jsonrpc`, `id` и `result` либо `error:{code,message}`. Notifications не получают ответа; batch ограничен 64 запросами. Одновременно выполняется не более 64 запросов. Методы: `telegram.link`, `telegram.unlink`, `identity.link-redeem`, `identity.resolve`, `identity.invite-redeem`, `identity.revalidate`, `authorize`, `tools.list`, `tools.call`, `login.send`. Broker получает UID через SO_PEERCRED и не принимает его от worker. Привязки обрабатываются доверенным broker и Auth. Первый вызов brai_telegram_link_account через telegram.link не отправляет уведомление: phase=offer возвращает needs_consent, имена аккаунтов и проверенный botUrl. Агент сам формулирует предупреждение о полном доступе и вопрос. Broker открывает согласие на пять минут только после ingress.close с questionMessageId из подтверждённой полной доставки финального ответа. При разбиении берётся последний ID; промежуточный вывод, typing и неуспешная доставка не считаются вопросом. Новое человеческое сообщение должно быть строго новее исходной просьбы и всех частей вопроса, в том же личном аккаунте и теме. Ingress передаёт полный исходный accountAnswer (до8192символов; более длинный ответ непригоден и не обрезается). Словаря положительных фраз нет. Агент сам определяет, является ли новый ответ ясным разрешением именно этой операции, и вызывает инструмент с confirmation — точной полной копией ответа. Broker сверяет точное равенство полной строки, свежесть, аккаунт, тему, action/target и срок; он не классифицирует произвольный естественный язык. Модель не может выдумать человеческое сообщение или подтвердить действие прежним ответом. Любой следующий human input снимает offer, оставляя только однократного кандидата текущего turn; следующий input или новый offer не воскрешают этот ответ. Отдельный model eval проверяет, что отказ, условие, цитата и вопрос не приводят к исполняющему вызову. Короткие явные отказы дополнительно блокируются ingress. После перезапуска требуется новый вопрос.

После сверенного confirmation phase=command получает от broker только message со вступлением агента без ссылок, @имён и /start. Control добавляет адрес текущего бота из getMe. После подтверждённой доставки вступления выпускается код, затем отдельное сообщение содержит только /start link_CODE, entity pre и inline-кнопку copy_text. Секрет не возвращается worker или модели. Постоянная квитанция команды предотвращает автоматический повтор при unknown. Погашение обрабатывается до модели: identity.link-redeem возвращает user и максимум две подписи accounts={name,username}, прочитанные через getChat только для действительных привязок Auth. Ни ID, ни код не отображаются в подтверждении. Сбой чтения имён после успешной привязки не повторяет мутацию.

brai_telegram_unlink_account принимает только target=current|other. Первый вызов возвращает needs_consent, имя выбранного аккаунта и последствия; агент сам задаёт вопрос. Broker закрепляет точный ID внутри доверенной границы, не возвращая его модели, и принимает confirmation с полным новым ответом по тем же правилам доставки, свежести, аккаунта и темы. Срок кандидата проверяется ещё раз непосредственно перед исполнением. Вызов без confirmation всегда начинает новый offer и отменяет прежнего кандидата; смена target не переносит старое согласие. Второй вызов отзывает именно закреплённую привязку; первый аккаунт тоже можно отключить. Перед исполнением заново проверяется Auth. Прямого identity.unlink и команды /unlink нет. Администратор сохраняет хотя бы один канал связи, остальные могут отвязать все. Сейчас Auth учитывает Telegram; новые каналы должны дополнять эту проверку. Модель и worker не выбирают владельца, не подменяют подтверждение и не получают секрет. `login.send` допускается только для текущего проверенного личного события Telegram. Control сверяет исходный Telegram ID через Auth с каноническим пользователем реестра; код отправляется в исходный аккаунт, включая дополнительный. Код отправляется напрямую через Bot API и не возвращается worker; неизвестный исход не означает разрешение на повтор.

Зарезервированное значение `userId: "__quarantine__"` обозначает архив до разделения и допускается только в перечисленных административных операциях чтения. Оно не является пользователем и не даёт сессию, вход или доступ к инструментам. До чтения Auth проверяет активного администратора и записывает аудит с этим идентификатором. При отсутствующей или неверной конфигурации control возвращает 503. Обычный профиль в UID-реестре для архива не создаётся.

В защищённом конфиге `quarantineProfile` содержит `userId`, `profileId`, `homeScope`, `memoryEpoch`, `cubes`, `home`, `workerUid` и необязательный `authorId`. Для памяти используется `userId` этого профиля и отдельная конфигурация карантина memory gateway, для чатов — `home` и `workerUid`. `quarantineArtifactsOwnerId`, если задан, определяет владельца архивных артефактов; иначе используется `quarantineProfile.userId`. Эти значения не принимаются из пользовательских запросов. Memory gateway обязан проверять признак карантина и заданную область; если его поддержка или миграция ещё не установлена, наличие конфига control не подтверждает доступность данных.

Путь `BRAI_IDENTITY_CONTROL_CONFIG` указывает на root-owned JSON mode 0600. Настройки: `origin`, `cursorKey` не короче 32 байт, `registryPath`, `memorySocket`, `telegramToken`, `artifactsInternalBaseURL` и `nats` с `servers` и необязательными `user`, `password`, `credsFile`, `caFile`. Реестр также должен быть root-owned mode 0600; его родительские каталоги не должны разрешать запись группе или другим пользователям.

Сборка `startControl(config, adapters)` принимает `perUserRuntime`, `historyCall`, необязательный `onIdentityChanged` и доверенные порты `telegramSend` и `telegramInfo(method, telegramId)`. telegramInfo разрешает только getMe/getChat и не сохраняет метаданные в памяти профиля. Последний предназначен для изолированной проверки доставки; при отсутствии порта используется прямой Telegram Bot API. `perUserRuntime(profile)` возвращает объект с `listTools()` и `callTool(name,args,signal)`. `historyCall(profile,name,args,signal)` выполняет отдельное проверенное чтение истории; owner берётся из `profile`. `runStdio(adapters)` принимает те же порты. Без них инструменты недоступны. `tools.list` возвращает `{tools:[{name,description,inputSchema}]}` после проверки UID и роли. Интеграцию с реальными Auth, NATS, Telegram, memory gateway и личным runtime нужно проверять до включения; модуль сам не настраивает системные разрешения или ACL.

`identity.revalidate` повторно читает реестр и Auth через trusted identity-get по userId. Стабильный автор памяти в реестре не обязан оставаться подключённым Telegram-аккаунтом. При неактивной записи или изменении ранее подтверждённой роли вызывается `onIdentityChanged({userId,profileId,status,role})`. Broker сам запускает периодические проверки и при недоступности Auth, отсутствии записи или отрицательном результате останавливает worker и egress. Отзыв только web-сессий не меняет результат `telegram-resolve`; для немедленной остановки по этому событию требуется отдельный подтверждённый сигнал Auth.

`runtime.mjs --stdio` собирает персональные инструменты для broker. Root-owned `runtimeProfilesPath` читается перед каждым вызовом и содержит объект по UID с `{userId,profileId,home,toolsConfigPath,stagingRoot,cacheRoot}`. UID, userId, profileId и home сверяются с registry и Auth. Staging заканчивается UID; staging и cache принадлежат root, не допускают запись группы или остальных и не пересекаются с домашними областями. Cache равен publisher `resultRoot` данного владельца. Broker копирует готовые файлы в home и не раскрывает worker root-пути.

`toolsConfigPath` и publisher JSON принадлежат root и имеют mode 0600. `ownerId` обоих совпадает с userId, `allowedReadRoots` publisher содержит только staging данного UID. Рядом расположен защищённый `files.json` с ownerId пользователя: `stateRoot=<home>/workspace/files`, `resultRoot=<home>/results`, `readRoots` — ровно `<home>/workspace`, `<home>/media`, `<home>/results`. Изменение защищённых конфигураций закрывает старые подключения при следующем вызове.

Дополнительные private методы broker: `identity.profile-ready`, `files.configuration/get/list/prepare` и `artifacts.publish/fetch`. Publisher вызывается только broker после проверки UID и создания root snapshot; прямые `publish_file/fetch_file` worker не доступны. Для неподтверждённых owner bearer `gameCore`, `history` MCP и `transcription` должны быть ровно `{ "enabled": false }`; включение без проверки привязки завершает сборку отказом. `history_list/get` используют NATS web/RLS с userId из проверенного профиля. Три общих справочника History доступны через read-only NATS, без owner bearer. Необязательный root-only `sharedServicesConfigPath` в реестре профилей подключает семь инструментов Transcription через защищённый HTTP delegate; userId, profileId и актуальная роль берутся из Auth, а не из аргументов worker. Личные tools.json сохраняют эти сервисы выключенными: общие возможности добавляет только root runtime после проверки источника. Нужна сквозная приёмка Auth, broker, owner API и NATS ACL.

`ingress.profiles {}` возвращает `{profiles:[{uid,...profile}]}` только доверенному ingress UID для сопровождения активных личных процессов. Каждый профиль проходит свежую проверку Auth. Ответ не содержит переписку или credentials; worker не может вызывать этот метод.

Внешние `serviceRoots` ограничены тремя read-only путями worker: `/opt/brai-profile/engine`, `/opt/brai-profile/runtime`, `/opt/brai-profile/instructions`. Они разрешают внутреннее чтение, не публикацию или временные файлы. Личные инструкции остаются внутри собственного HOME.

Во время provisioning `health` подтверждает native runner и файловый адаптер до активации Auth. После активации `health` с `require_tools: true` также проверяет реальное обнаружение MCP и инструмента входа. Worker всегда выполняет эту проверку до обработки первого сообщения: модель не запускается без инструмента входа.

## Административная выдача и отзыв доступа

Auth владеет постоянными операциями доступа и их состоянием. Существующий root broker при наличии защищённого `accessCommand` последовательно запрашивает `identity.lifecycle-claim`, каждые 10 секунд вызывает `identity.lifecycle-renew` и завершает работу через `identity.lifecycle-complete`. Форматы NATS принадлежат [Auth](../../auth/README.md), приватные методы описаны в [OpenRPC](control.openrpc.json). Эти методы отсутствуют в Unix API ingress и личных worker.

Root entrypoint получает только user из Auth через stdin и использует фиксированный Ansible lifecycle. Подготовка начинается сразу после административной выдачи; готовый системный профиль сам по себе не открывает доступ, пока Auth не подтвердит актуальную операцию. Старое завершение после отзыва или смены поколения не активирует аккаунт.

Lease действует 45 секунд. Потеря lease или невозможность его продлить завершает собственный установщик вместе с дочерней Ansible-группой. Отмена подтверждается после остановки процесса. Неизвестный результат завершения сверяется следующим claim; постоянная операция и стабильные идентификаторы обеспечивают восстановление после перезапуска. Одна физическая операция ограничена 630 секундами, Ansible — 600; ожидаемые ошибки возвращаются как PROFILE_FAILED без системных путей.

Отзыв закрывает Auth, сессии и коды входа одной транзакцией. Затем Ansible останавливает и выключает автозапуск личных worker и браузера. Общие gateway остаются доступны другим людям. Реестр, Unix-аккаунт, HOME, переписка, память и файлы сохраняются; повторная выдача использует прежние userId и profileId.

Приглашения используют ту же постоянную очередь Auth. Ingress больше не запускает отдельный установщик и не активирует профиль через legacy profile-ready: он ожидает актуального состояния Auth до 660 секунд; внешний Telegram-вызов ждёт 700 секунд. Это покрывает 600 секунд Ansible, остановку дочерних процессов и подтверждение очереди. Поэтому старое приглашение не может снова включить отозванные службы.

При отзыве после остановки защищённый реестр сохраняет blocked, поэтому штатный resume не запускает отозванные службы. Восстановление под общим provision.lock переводит только точную прежнюю привязку в provisioning до startup и health. Используется прежний узкий порт files.configuration для provisioning; чтение данных и инструменты требуют active Auth.
