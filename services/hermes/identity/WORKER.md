# Личный процесс Hermes

Native `secure_parent_dir` сохраняет точный ACL личного HOME: owner=rwx,
именованный ingress=--x, group=---, mask=--x, other=---. Проверяются владелец,
UID ingress и отсутствие ссылок; иной ACL отклоняется. Подключение к worker
предшествует допуску входа: отказ подключения не резервирует новую беседу.

Обязательный `brai-telegram` включён в конфигурацию личного worker и поставляется
вместе с общими плагинами, принадлежащими root. Его регистрация сохраняется между bootstrap
и повторным подключением, чтобы новый адаптер получил существующий callback.
Завершение worker использует штатный native CLI tail: он сохраняет код выхода
и закрывает запись жизненного цикла перед выходом процесса.

Доверенный ingress принимает только личные Telegram-сообщения: тип чата private, chat ID совпадает с sender ID. Группы, supergroup и каналы молча отклоняются до обращения к Auth, загрузки вложений и запуска агента; приглашение в них не активируется. Подготовка события повторно требует native chat_type=dm и chat ID текущего подтверждённого Telegram-аккаунта до регистрации хода и копирования media.

Доверенный ingress проверяет Telegram sender, связывает его с Brai owner и передаёт событие в соответствующий worker по UNIX socket. Все связанные через Auth Telegram-аккаунты используют один worker. Один Bridge и одно IPC-соединение закреплены за UID; каждый исходный аккаунт допускается заново через Auth. expectedUid запрещает зарегистрировать ход в другом worker при смене привязки между resolve и admit. Доставка дополнительно сверяет текущую исходную беседу, даже если этому пользователю принадлежат несколько аккаунтов. В worker передаётся стабильный внутренний user_id автора памяти, а настоящий личный chat_id сохраняется: по нему различаются беседы и маршруты доставки. Исходный Telegram-аккаунт однозначно равен chat_id, проверенному до преобразования. Это сохраняет прежнего автора памяти и владельца файлов без копирования данных.

Worker и ingress проверяют UID собеседника через SO_PEERCRED. Один worker обслуживает одного владельца; его HERMES_HOME, сеть, UID и доступы задаются отдельно. В worker нет Telegram token и общей истории.

`identity/native.patch` направляет `TelegramAdapter.handle_message` в обработчик, установленный `ingress.install(runner, adapter, resolve_bridge)`, до общих session guards. Патч обязателен: при отсутствии marker или обработчика Telegram не начинает polling и не передаёт сообщение в общий agent. В режиме ingress общий cron выключен. Сначала broker проверяет отправителя или выполняет onboarding; затем native `_hm_admit_event` применяет проверку на этот sender в ограниченном контексте. Это version-specific интеграция с закреплённым Hermes; штатные правила разрешённых пользователей и plugins должны быть настроены на ingress. `resolve_bridge(source)` возвращает привязанный `Bridge`. `prepare_event(event)` подготавливает только разрешённые поля MessageEvent и переносит вложения в область владельца; `deliver(owner, action, payload)` проверяет принадлежность artifact владельцу и выполняет фактическую отправку, возвращая receipt. Ни один путь worker не передаётся ingress для открытия. Сохранение, владельца и операции файлов проверяет Artifacts. Код входа и связь Telegram с Brai owner не входят в этот канал.

## Расширение native Telegram

В штатной сборке nonce `scope_id` обязателен для встречного `send`. Порты delivery и UI подключаются до первого соединения с worker; затем их привязка не меняется. Они используют стабильного владельца, а фактический аккаунт заново проверяется при каждом действии.

Личный runtime выполняет полный штатный `start_gateway`: MCP, восстановление сессий и обязательств, watchers, cron и housekeeping. Подменяется только Telegram transport. Расписание перебирает только текущий HERMES_HOME. Bootstrap health доступен при provisioning; `health(require_tools=true)` после active Auth подтверждает полный запуск. Ingress держит отдельное постоянное соединение с каждым активным профилем и восстанавливает его после разрыва, поэтому фоновая работа не ждёт нового сообщения. Native restart передаёт exit 75; systemd создаёт новый процесс.

Доступны send, edit_message, send_typing, send_draft, send_file_set, send_image, send_animation, send_image_file, send_document, send_video, send_voice. Файловые действия принимают исключительно artifact descriptor. Входящий ход получает nonce `delivery_scope`; native tasks и executor сохраняют его. Поздний ответ закрытого хода отвергается. Намеренная фоновая доставка с null scope требует свежего Auth и ранее допущенного маршрута либо личного чата владельца. Root-only журнал хранит маршруты и message IDs без текста; edit/reply не могут обращаться к сообщениям другого профиля, включая после перезапуска ingress.

Личный adapter наследует native возможность асинхронной доставки: завершения дочерней работы и напоминания используют личный runtime. `send_draft` восстанавливает потоковый preview в личном чате и его ранее допущенных темах. Worker передаёт исходный текст, draft ID и scope; Root проверяет маршрут и вызывает свой native renderer с доверенной metadata. API preview не выдаёт message ID и не создаёт запись доставленного сообщения. При недоступном draft API возвращается ошибка, и native streaming использует обычные send/edit. В группах draft не включается; реакции и создание тем не активируются этим изменением.

Callback и inline update допускаются отдельно: проверяется настоящий отправитель, а для callback — принадлежность точного bot message. Root передаёт update и обязательный `actor_telegram_id` в native TelegramAdapter личного worker. Raw `query.from_user` не переписывается в автора памяти; native callback authorization допускает фактического actor только в контексте этого подтверждённого вызова. Ledger связывает права со стабильным владельцем и отдельным actual chat/thread. Отзыв аккаунта запрещает его callback, draft и последующую доставку; повторно проверяется именно этот канал. Supervisor подключает активный профиль по UID, поэтому отвязка первоначального аккаунта не останавливает runtime второго. Tokenless `telegram_api` разрешает только send/edit/delete сообщений и ответы на подтверждённые query; Bot token, polling, произвольный API и загрузка файлов недоступны. Native clarification, approval и меню используют прежние обработчики и личное pending state. Включение GameCore сохраняет отдельный операторский порядок; перевод профилей не включает заранее отключённый сервис.

Файловый модуль личного адаптера передаёт опубликованные descriptor в ingress, сохраняя исходные байты и квитанции. После повторной проверки owner и восстановления файла ingress вызывает native Telegram media primitives без повторной публикации в общий FileStore. Набор передаётся целиком с порядком, подписями и native album grouping; успех требует реальных receipts каждого элемента. Текст после ошибки voice не считается доставкой голоса. send_voice принимает необязательный boolean is_voice; true сохраняется до Telegram transport, который при необходимости выполняет штатное преобразование в OGG/Opus.

Worker обновляет send_typing каждые две секунды от подготовки инструментов до завершения полной native task, включая доставку текста и вложений. Внутренние pause и interrupt не гасят этот индикатор. Вызов ограничен 1,5 секунды; временный отказ не отменяет ответ. Завершение, отмена, ошибка подготовки или разрыв соединения прекращают обновление; Telegram убирает последний индикатор при ответе или по своему сроку действия.

Оператор может открыть дополнительное соединение того же доверенного ingress UID только для bootstrap `health` без `require_tools`. Оно не получает dispatch/cancel/interactive, не меняет основной peer и не останавливает native lifecycle при закрытии. Полная operational-проверка выполняется по основному duplex каналу. Native `/bg` и `/btw` снимают только истекающий turn scope при создании отдельной задачи; поздняя доставка заново проверяет владельца и сохранённый маршрут.


## Минимальный встраиваемый Bridge

Без подключённых портов native UI мост предоставляет базовый канал доставки. Ограничение callback в этом разделе относится к такому режиму; штатная сборка Brai подключает расширение, описанное выше.

Worker создаётся как `Worker(ingress_uid, user_id, telegram_id, publish_file)` и запускается `serve(path, worker)`. `publish_file(path)` публикует файл владельца и возвращает `{"artifact_id": "…"}`. Каталог сокета защищает оператор; сокет создаётся с mode 0666, а SO_PEERCRED допускает только UID ingress. При запуске требуется UID ingress с возможностью подключения и UID worker, отличный от него. Ingress всегда проверяет UID worker. Перезапуск не повторяет незавершённые вызовы.

JSON-RPC 2.0: UTF-8 JSON строка до 1 МиБ, не больше 64 одновременных запросов на соединение. `dispatch(owner, event)` возвращает `accepted` и случайный `turn_id` для нового хода (при steer он пуст): событие принято или отклонено; завершение фоновой обработки не подтверждается этим ответом. `cancel(owner, turn_id)` останавливает только ещё действующий выданный turn_id и возвращает `stopped`, `stopping` или `not_running`. Встречный `send(action, payload)` возвращает receipt доставки. `turn_ended(owner, turn_id)` сообщает ingress о завершении хода; потеря соединения оставляет исход уведомления неизвестным. Превышение срока ожидания или разрыв соединения означают неизвестный результат, а не отмену и не разрешение на автоматический повтор. Запросы, пакеты и уведомления следуют JSON-RPC 2.0; позиционные параметры не поддерживаются.

Доступны send, edit_message, send_typing, send_image, send_animation, send_image_file, send_document, send_video, send_voice. Файловые действия принимают исключительно artifact descriptor. Ingress допускает только ранее зарегистрированный исходный chat/thread владельца; edit разрешён лишь для message_id, полученного в собственном receipt. Callback, native-кнопки и другие методы пока не реализованы: их включение требует отдельного привязанного к владельцу и ходу обратного канала. Text fallback подтверждений должен обрабатываться worker как следующее входящее событие. Перед выдачей ответа и файла broker повторно проверяет действующую привязку исходного Telegram-аккаунта. Отзыв запрещает последующую доставку, но не отменяет уже начатые внешние действия. Одновременно один профиль сохраняет прежнее ограничение: пока выполняется ход в одной беседе, вход из другой отклоняется; он не становится уточнением чужой беседы. Все неподдержанные операции завершаются ошибкой.

Эта библиотека не включает установку systemd, миграцию, регистрацию профилей или реализацию доверенного брокера. До активации обязательна проверка на закреплённом установленном engine: lifecycle, busy/steer, stop, streaming/edit, восстановление файлов, ошибки и разрывы. Общая граница памяти сохраняется только при работающей изоляции UID, сети и файлов.

Worker CLI запускается `python -m identity.worker --config /абсолютный/путь/worker.json`; JSON строго `{"socketPath":"<HERMES_HOME>/control/worker.sock"}`. Нужны окружение `HERMES_HOME`, `BRAI_IDENTITY_INGRESS_UID`, `BRAI_IDENTITY_USER_ID`, `BRAI_IDENTITY_TELEGRAM_ID`, `BRAI_IDENTITY_EGRESS`, `BRAI_IDENTITY_BROKER`. На startup процесс запускает `identity.network.start_relay` на 127.0.0.1:18080 в своём PrivateNetwork. Брокер подтверждается SO_PEERCRED UID 0; `artifacts.publish` получает путь и requestId, открывает и проверяет файл на своей стороне и возвращает artifactId. `tool_client.py` обслуживает MCP stdio, а login.send выдаёт только статус: код и адрес в worker не передаются. При подтверждённой отправке ingress должен подавить обычный итог данного хода. Машинный контракт duplex RPC — `worker.openrpc.json`.

Telegram-аккаунты равноправны, максимум два. Стабильный authorTelegramId сохраняет автора памяти при отключении первого аккаунта; актуальный доступ определяют Auth и исходный аккаунт каждого события. Инструмент brai_telegram_unlink_account принимает только current/other и не позволяет модели подтвердить отвязку. Подтверждение точного ID из нового сообщения проверяет broker после доставленного предупреждения.

## Автоматическая тема уведомлений

Telegram не показывает предложение выполнить `/sethome`. В личном worker
домашний адрес определяется из конфигурации либо стабильного Telegram ID профиля;
старый номер домашней темы и переменные cron не закрепляют удалённую тему.
Бот должен поддерживать темы в личных чатах.

Фоновая отправка через IPC без исходной темы и reply получает внутренний маркер
`_brai_notifications=true`. Root принимает его только при явном `scope_id=null`,
проверяет актуальную Auth-привязку фактического аккаунта до создания и перед отправкой.
Обычные ответы, callback, typing, draft и явно адресованные беседы сохраняют маршрут.
У двух подключённых аккаунтов одного профиля разные темы; рассылки между ними нет.

Ingress создаёт тему «Уведомления» при первой доставке и сохраняет её в
`identity-delivery.sqlite`, отдельно по стабильному owner и chat.
Атомарная резервация в SQLite и локальная блокировка предотвращают параллельное
создание. Квитанция createForumTopic допускает новый маршрут в журнале прав.
Pending после таймаута, отмены, crash или некорректной квитанции не повторяется
автоматически: сначала требуется сверка внешнего исхода. Явный отказ Telegram
снимает резервацию и позволяет следующую попытку.

При ответе Telegram об отсутствующей теме текст без уже доставленных частей
получает новую тему и одну повторную отправку. Частично доставленный текст,
неопределённые сетевые исходы и остальные ошибки не повторяются.
Перед файловым набором сохранённая тема проверяется через editForumTopic;
удалённая тема заменяется до отправки. Уже начатый файловый набор целиком
не повторяется: он мог доставить подпись или часть сообщений.
Восстановление происходит при доставке; удалённая переписка не восстанавливается.

## Чтение исходящих вложений

Trusted Telegram ingress вызывает `ingress.open-artifact` по существующему
Unix JSON-RPC socket. Broker проверяет SO_PEERCRED, Auth, владельца Artifacts,
ready-байты, размер и SHA-256. Для текущего хода до и после получения файла
проверяются turnId, inputId и актуальная привязка аккаунта. Ответ содержит
метаданные и ровно один O_RDONLY descriptor через SCM_RIGHTS. Пути, credentials,
доступ к каталогу и право записи ingress не получает; права root cache не меняются.
Копия в `ingressDeliveryRoot` новому ingress не нужна.

Ingress проверяет root UID отправителя, соответствие RPC ID и artifactId,
тип и read-only flags inode, размер, стабильность и SHA-256, затем передаёт
открытый поток Bot API. Все потоки закрываются после отправки, ошибки или отмены.
При конвертации неподдержанного voice формата ffmpeg читает исходный FD через
stdin; ограниченный производный Ogg находится в памяти, оригинал не копируется.
До первого Bot API вызова проверяется весь набор и текущий маршрут.
Отзыв прав закрывает новые выдачи; уже переданный FD доступен получателю до его
закрытия. Как и уже прочитанные байты, его нельзя отозвать задним числом.

Метод поддерживает только одиночный запрос с id: notification не выдаёт FD,
batch для него недоступен. Результат ограничен 32 KiB, файл — 64 MiB;
получение — 120 секунд, запись ответа — 5 секунд. Отмена и ошибки закрывают
FD с обеих сторон; disconnect не означает отмену backend fetch и не запускает
повторную отправку. Старые `ingress.artifact` и `ingress.delivery-artifact`
оставлены только для совместимости старого ingress и требуют прежний каталог.
Новая версия не откатывается к копированию, если FD transport недоступен.

Диагностика отказа сохраняет имя операции, тип исключения, тип причины и errno;
текст исключения, содержимое сообщения и credentials в журнал не попадают.

Когда native финализатор обновляет уже отправленный текст без metadata, личный
адаптер наследует тему только из контекста того же dispatch и того же chat ID.
Параллельные dispatch сохраняют собственный контекст. Явно переданные metadata
не заменяются; принадлежность сообщения проверяет ingress. Успешное обновление
не вызывает повторную отправку текста; вложения доставляются отдельным путём.

Индикатор «печатает» проходит worker → ingress → native sendChatAction с темой
исходного запроса, в том числе во время ожидания инструментов. Отказ Bot API
не запускает повтор без темы. Журнал содержит тип ошибки, номер темы и только
заранее известную классификацию причины; произвольный текст ошибки не пишется.

## Guest

Перед GatewayRunner устанавливается native_policy; у guest используется readonly гостевой config и только trusted product plugins. MCP discovery остаётся включён. Каталог и dispatch проверяются раздельно. Guest operational readiness требует настоящего зарегистрированного create_text_file и отказа terminal/login. Bootstrap health содержит rolePolicyVersion:1 и роль, но не подтверждает полный операционный сценарий. [Политика](ROLES.md).

Разговорные согласования принимаются в `dispatch` после проверки владельца и
поколения, до native busy/idle и файлового steer. Один объект события обрабатывается
один раз; штатный STT и его cache сохраняются. IPC adapter связывает вопрос с
транспортной операцией до ожидания ответа и сохраняет только успешную квитанцию
с message ID. Завершение модельного хода для этого не используется.
