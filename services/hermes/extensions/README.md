# Расширения Hermes

Исходники расширений принадлежат Brai. Внешние Hermes, MemOS и окружение Python устанавливаются и обслуживаются отдельно оператором. Наличие этих файлов не включает расширения в экземпляре. Порядок применения patches и происхождение исходников указаны в `provenance.json`.

Каталог содержит код, тесты, локализации и начальные шаблоны, но не содержит пользовательских данных, памяти, переписки или секретов. Рабочие инструкции агента находятся в `docs/user-agent/instructions/hermes`. `profile/userdata` содержит только начальные шаблоны; подготовка профиля сохраняет существующие файлы.

Описание плагинов: [Groq Voice](plugins/groq-voice/README.md), [MemOS REST](plugins/memos-rest/README.md), [Telegram Business](plugins/telegram-business/README.md). Начальные шаблоны профиля: [маршруты](profile/userdata/ROUTING.md), [область бэкапа](profile/userdata/BACKUP_SCOPE.md).

## Состав и подключение

`patches/memory-recall.patch` расширяет native MemoryManager: внешний provider может задать положительный конечный `prefetch_timeout_seconds`. MemOS задаёт 180 секунд по умолчанию на весь поиск. Планирование, чтение кубов и параллельный отбор используют один уменьшающийся срок; вложенный запрос его не продлевает. Ошибка чтения или истечение ожидания попадают в контекст модели и в обычное уведомление recall, без текста исходного исключения. Патч применяется перед `turn-request-budget.patch` и проверяется вместе с остальными native bytes; обновление и откат выполняет тот же операторский lifecycle.

Патч также передаёт из `agent/turn_context.py` окно текущей модели и свободное место в hook памяти. Provider, который сам распределяет этот бюджет, объявляет `manages_context_budget`; native не усекает его результат вторым общим spillover. Необязательный `RecallStatus.summary` показывает отдельно найденные и переданные записи. Прежние provider сохраняют обычное ограничение spillover и прежний формат уведомления.

`manifest.json` перечисляет в `runtimeFiles` файлы расширений, которые входят в поставку. Внешний `artifact-manifest.json` закрепляет их SHA-256 вместе с самим manifest. Оператор проверяет поставку целиком; структурная проверка исходного дерева не удостоверяет происхождение файлов.

`tools/connect.py --check` проверяет структуру и при наличии внешнего manifest сверяет хеши. `--plan` показывает изменения профиля без записи; `--apply` применяет их. `--instructions-root` задаёт путь к каноническим инструкциям, по умолчанию используются инструкции из той же поставки. Для замены отличающихся файлов требуется явный `--overwrite`: прежнее содержимое сохраняется в резервную копию профиля. Патчи движка применяет операторский процесс отдельно.

Фактическое переключение экземпляра выполняет оператор. Прежний способ установки production сохраняется до отдельного выпуска. Границы сервиса описаны в [контракте Hermes](../CONTRACT.md), общие инструкции — в [документации пользовательского агента](../../../docs/user-agent/README.md).

## Документация навыков

`tools/skill_docs.py plan|apply|verify --system --profile-dir ...` обслуживает только тексты. Для plan/apply обязательны `--source-root` с Git-каталогом и `--revision` с полным SHA коммита. [Каталог навыков](../../../docs/user-agent/skills.md) описывает порядок обновления. Код из исходного коммита не выполняется; скрипты остаются в immutable поставке. Каталог skills/ может отсутствовать рядом с базовыми инструкциями: connect.py сохраняет отдельно установленные тексты.

Identity overlay передаёт подтверждение потоковой доставки обычного вопроса
в разговорное согласование. Отдельная повторная отправка вопроса не нужна:
ответ владельца привязан к доставленному сообщению, той же сессии и теме.
Предварительный текст, ошибка доставки и сообщение другого владельца согласие не открывают.

## Единственная постоянная память

`memory-recall.patch` также исключает файловую память Hermes: её флаги всегда выключены, инструмент записи недоступен, регистрация `/memory` и обработчики CLI/gateway удалены. Старые настройки профиля не возвращают эту возможность. Внешний provider MemOS и техническая группа инструментов `memory` сохраняются; группа нужна для подключения `memos_*`. Фоновые проверки навыков работают отдельно.

Idle-таблица gateway также исключает `memory`: она строится и для обычного текста, поэтому ссылка на удалённый обработчик останавливает любое новое сообщение до модели. `tests/test_native_memory.py` проверяет настоящую таблицу с отсутствующим memory-handler и сохранёнными `skills`/`model`.

Патч входит в manifest и воспроизводимую композицию каждого штатного обновления. Несовместимость с новой основой останавливает сборку до переключения. Установщик переводит управляемые флаги профиля в выключенное состояние; прежние файлы и ожидающие предложения не удаляются и не применяются.

## Разговорные согласования

conversational-approvals.patch подключает native/approval_conversation.py
из явного абсолютного HERMESCUSTOM_ROOT. Он применяется перед
memory-recall.patch. Настройки профиля: smart + conversation. Установленный
runtime вручную не патчится; состояние принадлежит профильному SessionDB.

test_conversation_approval.py проверяет ответы, однократность, перезапуск,
конкурентность и авторство. test_native_conversation.py требует
BRAI_NATIVE_ENGINE с изолированной копией закреплённого движка после полной
композиции. Тест не запускает модель или настоящий Telegram.
Полный контракт — в ../CONTRACT.md.

Перед включением DEV оператор отменяет прежние ожидания без выполнения,
снимает legacy кнопки по известным message IDs и проверяет тестовый диалог.
Отсутствующие сведения о старых сообщениях означают незавершённую приёмку.
PROD и принятый клиентский состав требуют отдельного выпуска.

## Ожидание и восстановление модельного запроса

`patches/turn-request-budget.patch` применяется последним. Один пользовательский
ход допускает не более двух дополнительных физических модельных запросов.
Успешная следующая итерация инструмента получает свой основной запрос, но общий
бюджет дополнительных попыток сохраняется при сжатии и автоматическом
восстановлении. Новый самостоятельный ввод создаёт новый бюджет.

Повтор одной операции сохраняет исходный монотонный срок. Уже переданный текст,
выполненные действия и неполные вызовы инструментов автоматически не переигрываются.
Исчерпание бюджета проходит через штатное сохранение незавершённого хода.
В диагностике остаются технические ID хода и попытки, этап и причина остановки.
Содержимое сообщений и credentials туда не добавляются.
