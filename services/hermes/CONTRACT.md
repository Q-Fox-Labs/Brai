# Инструменты Hermes

Владелец этой границы — `services/hermes`. Программа `tools.mjs` предоставляет MCP stdio по официальному SDK. Её входные схемы берутся из MCP владельца или опубликованных JSON Schemas соседей. Бизнес-данные и команды остаются у владельцев; служебные сведения файловых наборов и доставки принадлежат общему адаптеру Hermes. Историю изменений сохраняют владельцы; мост не создаёт дублирующих History фактов.

Отказ Game Core ограничивает операции, которым нужны его данные или решения. Независимая работа Hermes продолжается без вымышленных записей и без повтора записи с неизвестным исходом.

## Связи и доверие

| Вход Hermes | Порт владельца | Ограничение |
| --- | --- | --- |
| `game_core_*` | [game-core MCP](../game-core/CONTRACT.md) | Owner-bound endpoint; human claim/complete/fail модели запрещены. |
| `publish_file`, `fetch_file`, `files_get`, `files_list`, `files_prepare` | [publisher MCP stdio](../agent/PUBLISHER.md) | Независим от основного Agent. Metadata NATS, байты HTTP, owner/ready/SHA-256 проверяются publisher. |
| `timer_*` | [Timer v2](../timer/README.md) | Команды JetStream; чтение NATS Services; userId добавляет мост. |
| `history_list`, `history_get` | [History scoped queries](../history/CONTRACT.md) | Только user scope текущего owner, без SQL/произвольного scope. |
| Три инструмента справочника History | Готовый History MCP | Только categories_list, types_list, type_get; административные инструменты скрыты. |
| `alerts_*` | [Alerts owner API](../alerts/CONTRACT.md) | list/get/summary/read/read_all; user_id добавляет мост. |
| `transcription_*` | [Transcription MCP](../transcription/CONTRACT.md) | Trusted bearer с фиксированным principal; обычные локальные расшифровки идут через coordinator. |
| `local_ai_*` | [Local AI owner API](../local-ai/CONTRACT.md) | Каталог, install/state/configure/load/unload/remove, embed, synthesize, cancel/status. OwnerId добавляет мост. |

MCP-инструмент `local_ai_invoke_synthesize` принимает только `text` по ограничениям Local AI. Мост выбирает `tts.model` из доверенной конфигурации и голос `eugene`, создаёт разные request ID и operation ID и задаёт срок 180 секунд от текущего времени. Дополнительные поля, включая переданный моделью срок, отклоняются до вызова Local AI. Внутренний файловый адаптер `voice.mjs` продолжает вызывать owner API с полным контрактом. Полученный audioArtifactId принадлежит текущему владельцу; неизвестный исход не запускает повтор. `local_ai_operations_get` относится к установке моделей и не подтверждает исход синтеза.

Оба входа моста до вызова Local AI отклоняют текст вне кириллицы, пробелов и обычной пунктуации с ошибкой `VOICE_TEXT_REQUIRES_CYRILLIC`. Hermes заранее записывает английские слова и числа кириллицей и раскрывает значимые символы словами; после этой ошибки исправляет текст и повторяет запрос. Проверка не выполняет транскрипцию и не подтверждает, что агент сохранил все слова исходного ответа.

Поток файла: Hermes working file → publisher snapshot → Artifacts prepare → HTTP bytes → подтверждение ready/hash → неизменяемая локальная копия → представление нужного канала. Общая модель описана в [контракте адаптера](files/CONTRACT.md). Входящий Telegram файл проходит тот же publish; последующие потребители получают Artifact ID. Модель не получает произвольный NATS/SQL инструмент, upload URL или право читать чужой артефакт.

Запуск требует защищённого JSON и отдельного доверенного `BRAI_HERMES_OWNER_ID`. Они должны совпадать. NATS identity Hermes имеет только необходимые subjects и свой inbox; старые связи сервисов не меняются. Credentials не включаются в ошибки. Конфигурация экземпляра отвечает за owner binding GameCore endpoint и Transcription bearer. Подмена owner во входе отвергается.

## Голосовой вход через Transcription

`transcribe.mjs --input <absolute-audio-path> --output <absolute-text-path>` — файловый адаптер штатного command STT Hermes. Он использует существующий publisher и [Transcription MCP](../transcription/CONTRACT.md); собственного ASR runtime, ключа провайдера и долговечного хранилища текста нет. `config.stt.model` — полный selector по owner-схеме `ModelSelector`: `{modelId,revision,profileId}`. Неизвестные поля selector отклоняются. Owner берётся из защищённой конфигурации подключений, а не из CLI или запроса модели.

Вход должен быть непустым обычным файлом, допускаемым read roots publisher. После одного `publish_file` принимаются только MIME `audio/ogg`, `audio/wav`, `audio/flac`, `audio/mpeg` и UUID готового артефакта владельца. Штатный publisher автоматически распознаёт OGG/Opus или Vorbis, WAV и FLAC по байтам; MP3 пока не поддержан файловым мостом из-за отсутствия audio sniff в publisher. Произвольный `application/octet-stream` не принимается. Один `transcription_request_submit` получает новый `clientIdempotencyKey`, `audioArtifactId`, `{route:"local",selection:"required",modelId}` и абсолютный `deadlineAt`. API Transcription сам фиксирует revision/profile; мост проверяет все поля фактического selector против конфигурации. Схемы запросов и ответов принадлежат Transcription и не копируются в Hermes.

После submit читается только `transcription_request_get` с интервалом 250 ms. Когда task succeeded и result available, один `transcription_result_get` получает эфемерный текст и actual selector. Проверяются request ID, требуемая модель и owner DTO ответа. Непустой UTF-8 текст размером до 1 MiB записывается без изменения в новый output с правами `0600`; существующий путь не перезаписывается, в том числе если он появился во время вычисления. Groq-нормализация к этому тексту не применяется.

Общий срок publish/submit/poll/output — максимум 180 секунд; тот же абсолютный deadline передаётся Transcription. Тестируемая функция `transcribeFile` допускает более короткий `timeoutMs`, CLI его не переопределяет. Native command provider задаёт timeout 200 секунд для запаса на подключение и закрытие. Timeout не подтверждает физическую остановку вычисления; его deadline и lifecycle принадлежат Transcription/Local AI. Мост не выполняет автоматический повтор, resubmit, замену модели или удаление готовых артефактов.

`OUTCOME_UNKNOWN` означает потерю подтверждения изменяющего вызова, невалидный ответ submit либо явно неизвестный исход владельца. `MODEL_MISMATCH` запрещает принимать другую модель или result request ID. `RESULT_UNAVAILABLE` обозначает потерянный или истёкший результат; `EMPTY_TRANSCRIPT` — отсутствие распознанных слов. `INVALID_ARGUMENT`, `OUTPUT_EXISTS`, `RESULT_TOO_LARGE`, `DEADLINE_EXCEEDED` и безопасные ошибки владельцев завершают команду без нового compute. CLI выводит только безопасный код в stderr; stdout не содержит текст или служебный протокол. Нативный command STT читает output-файл. Настройка provider показана в [README](README.md#telegram-и-голос).

Сам мост не имеет fallback. До включения экземпляра нужно проверить, что fallback нативного gateway не может незаметно заменить выбранный сервис установленным альтернативным локальным backend. Это отдельная проверка runtime; настройка named provider сама по себе не доказывает отсутствие такого backend.

## Постоянная память агента

В поставке Brai постоянной памятью владеет внешний provider MemOS. Сохранение завершённых разговоров, выделение фактов и recall не зависят от файловой памяти Hermes. `USER.md` и `MEMORY.md` не загружаются как native память; инструмент `memory`, его фоновое ревью и команда `/memory` недоступны независимо от прежних настроек профиля. Поддержка навыков сохраняется.

Удаление файловой памяти закреплено в последнем `extensions/patches/memory-recall.patch` и проверяется вместе со всей композицией движка при установке и обновлении. Техническая группа `memory` остаётся для инструментов внешнего provider. Обновление не удаляет прежние файлы и очередь предложений, не выполняет их и не переносит старые записи автоматически.

## MemOS embeddings

`memos/embedding/adapter.mjs` предоставляет `POST /v1/embeddings` для закреплённой модели `embeddinggemma-2-q8` через публичный Local AI invoke.embed. Owner и selector берутся из доверенной конфигурации, назначение всегда `symmetric`; порядок входного пакета сохраняется. Настройка процесса описана в [MemOS README](memos/README.md).

JSON принимает только `model`, текстовый `input`, необязательные `dimensions` и `encoding_format`. `dimensions` допускает только целое число `768`; отсутствие поля означает ту же размерность, уменьшения вектора нет. `encoding_format` принимает `float` или `base64`, по умолчанию `float`. Ответ содержит соответственно массив чисел либо base64 точных little-endian float32 байт всех 768 элементов. Python OpenAI SDK по умолчанию запрашивает base64 и сам преобразует эти байты в массив чисел. Параметры формата не передаются в Local AI.

Другая модель, размерность, формат или неизвестное поле отклоняются HTTP 400 до вызова Local AI. Некорректный ответ владельца, включая неверную длину вектора, нечисловые/бесконечные значения либо переполнение float32 при base64, даёт HTTP 502. Ошибка транспорта Local AI даёт HTTP 503; автоматических повторов нет.

## Выполнение и неизвестный исход

Обычный NATS timeout — 12 секунд, конфигурируемый до 60 секунд. Долгие Local AI/MCP вызовы — до `longRequestTimeoutMs`, по умолчанию 300 секунд и максимум 30 минут. Publisher сохраняет собственный deadline до 30 минут. Переданный `deadlineAt` Local AI не переписывается. До 8 MCP вызовов исполняются одновременно; очереди нет, девятый получает `OVERLOADED`. Publisher дополнительно ограничивает собственные операции до двух. JSON вход ограничен 65536 байтами, NATS ответ — 1 MiB; DTO владельца могут иметь более строгие ограничения. Остановка закрывает собственные MCP/NATS подключения и дочерний publisher.

Команда Timer возвращает `{commandId,status:"stored",outcome:"unknown",nextTool:"timer_command_get"}` после PubAck. Это подтверждает только хранение команды. Итог читается по прежнему commandId. PubAck timeout не означает отсутствие команды. `Nats-Msg-Id` не используется: изменённая команда с прежним ID должна получить owner conflict, а не быть скрыта транспортной дедупликацией.

При возможной отправке mutation и потерянном/просроченном ответе мост выдаёт `OUTCOME_UNKNOWN`. Автоматического повтора записи нет. Caller сохраняет исходные параметры и ключ: Timer — commandId, publisher — requestId, GameCore claim — idempotency_key, revise — revision_id. Для planning build/apply сохраняются attempt_id и точный исходный кандидат; game_core_timeline_get возвращает result попытки, включая result.planning.candidate/candidate_sha256/applied. Caller сверяет именно эту попытку и текущую ревизию из graph до любого повтора. Для create заранее задаются устойчивые UUID; после неизвестного исхода читается graph. Local AI invoke не имеет гарантии однократности; новый вызов означает новую вычислительную попытку. Transcription после submit сверяется через request.get/result.get, без повторного compute. Подтверждённые бизнес-ошибки сохраняют безопасный код владельца.

MCP подключения открываются независимо. При отказе транспорта только явно разрешённые чтения повторяются не более одного раза в пределах исходного срока; ошибки владельца, отказ доступа и отмена не повторяются. Поздняя ошибка старого подключения не закрывает его замену. Недоступный сервис не скрывает инструменты остальных сервисов; его схемы добавляются после успешного чтения каталога, без вымышленных определений. Persistent plugin и учёт попыток не сбрасываются.

Для `game_core_planning_*` мост сохраняет безопасную диагностику нормативного `INVALID_ARGUMENT` из [контракта GameCore](../game-core/CONTRACT.md): `diagnostic:{phase,reason}`. Принимаются только известный этап, непустая строка причины до 500 символов и ровно эти два поля. Прочие поля upstream, произвольные сообщения исключений и диагностика других инструментов не передаются. Старые ответы без diagnostic остаются совместимыми; наличие причины не запускает автоматический повтор.

## Человеческие действия

Модель может создать Action и вызвать `game_core_request_human_action({moveId})`. Ответ содержит moveId, revisionId, targetId, title и следующий инструмент. Это чтение; оно не начинает и не подтверждает попытку. Для старого плана готового артефакта без явного `approval_required=true` ответ направляет к `game_core_result_review_skip`, а private prepare не создаёт новую human attempt. Агент сверяет исходное поручение: если отдельное принятие не требовалось, пропускает рассмотрение; если требовалось, уточняет или перепланирует с явным признаком. Уже начатое решение остаётся доступно для восстановления. Новые планы с явным признаком сохраняют подтверждение. При показе результата файлы доставляются через Artifacts, а текст преобразуется в формат Telegram без повтора сырым текстом при ошибке. `clarify` показывается как вопрос без кнопки; ответ владельца проходит через текущий Telegram MessageEvent и private `actions.feedback`, который завершает только текущий human Action с `metadata.stage=clarification`, `metadata.outcome=answered` и фактическим текстом/происхождением. Модель не передаёт текст ответа.

Доверенный Telegram плагин проверяет личный чат владельца, сохраняет случайный одноразовый callback token и вызывает `actions.prepare` до показа кнопки. Pending запись связывает token с точными moveId, attemptId, revisionId и stage. На click плагин атомарно поглощает token, сверяет private owner и передаёт точные связанные поля в private `actions.complete`. Данные решения формирует callback, а не текст модели. Обычный MCP ограничивает executor_kind до agent; перед complete/fail дополнительно читает graph и отклоняет human Action.

Доверие private RPC основано на вызывающем runtime. Само отсутствие метода в MCP не изолирует private CLI от terminal инструмента, работающего тем же Unix пользователем и читающего ту же конфигурацию. Для такой угрозы развёртывание должно отдельно ограничить shell и доступ к human credentials; секрет в доступном модели окружении не создаёт эту границу.

Private `actions.complete` проверяет текущую попытку, human, running и revision. Game-core атомарно проверяет статус попытки и актуальную planning revision, задаёт `confirmed_by` владельцу и сохраняет результат. Для review/final проверка revision в мосте является предварительной: текущий owner API не даёт общего атомарного CAS. Это известная граница, а не обещание блокировки параллельного редактирования.

Отмена и восстановление незавершённой отправки используют private `actions.cancel`: только та же текущая human/running попытка завершается через owner fail; Move снова planned. Прежний reason=expired остаётся совместимым с private API, но Telegram больше не задаёт срок решения и не отменяет доставленные кнопки по таймеру. При нажатии проверяются актуальные revision/attempt и отправитель; повтор callback не создаёт новую попытку. Неизвестный исход сохраняется как unknown; он не выдаётся за отказ или успешное решение.

`post_tool_call` сохраняет UUID только подтверждённых `game_core_move_claim` agent Операций и удаляет запись после успешного complete/fail. Native `on_session_end` и `agent_loop_stopped` завершают только terminal attempts; при plugin startup сохранённые exact claims проходят trusted recovery. Private `actions.fail_agent` повторно читает owner graph и вызывает `game_core_move_fail` только для того же всё ещё running agent attempt; уже заменённая попытка и human actions не затрагиваются. При неизвестном результате запись остаётся для следующего старта.

## Private stdio RPC

`trusted.mjs` использует JSON-RPC 2.0, UTF-8, один JSON документ на строку. Поддерживаются batch и notifications, строковый id рекомендуется. stdout содержит только ответы, stderr — безопасный код диагностики. Метод не принимает owner identity. Машинный контракт — [trusted.openrpc.json](trusted.openrpc.json).

| Метод | Вход |
| --- | --- |
| `files.publish` | `{path,requestId,title?}` по publisher контракту; requestId 1–256, файл до 2 GiB. |
| `files.fetch` | `{artifactId}`; возвращает проверенную копию владельца. |
| `actions.read` | `{moveId}`; текущие target/revision, move status, attemptId/status/executor, title/description, inputResourceIds. |
| `actions.prepare` | `{moveId,revisionId,idempotencyKey,inputResourceIds?}`; ключ 1–200; возвращает связанную human attempt и currentRevisionId. Если inputs не заданы, берёт текущие разрешённые owner API inputs. При claimed восстанавливает только точную текущую running попытку прежнего ключа, даже если revision уже сменилась; такой recovery используется для отмены после перезапуска. |
| `actions.complete` | `{moveId,attemptId,revisionId,stage,decision,comment?}`; stage planning/final/review, decision approved/success/changes/cancelled. |
| `actions.feedback` | `{elementId,revisionId,moveId?,decision,feedback}`; точное сообщение владельца, decision changes/cancelled; источник поставляет плагин. |
| `actions.cancel` | `{moveId,attemptId,revisionId,reason}`; reason expired/cancelled/declined. |

Files ответ — `{artifactId,filename,mimeType,sizeBytes,sha256,localPath,markdown}`. Markdown publisher сохраняется без изменения. Telegram распознаёт только настроенный resultRoot/UUID путь, повторно вызывает fetch и отправляет проверенные bytes нативным API.

RPC строка до 65536 байт проверяется до parse; oversized или неполная строка закрывает канал. Ответ до 1 MiB; превышение закрывает канал без усечения. Запросы идут последовательно с обратным давлением stdin/stdout. Разрыв/timeout не отменяет уже возможный эффект. Standard errors: -32700/-32600/-32601/-32602; owner failures — -32000 с безопасным `{code}`. Повтор после unknown применяется только по контракту владельца.

## Постановка game-core

После claim существующей agent Операции `plan`/`start` Hermes вызывает `game_core_planning_packet`. Пакет содержит только выбранные реальные входы, фактический уровень и версионированные правила. Сначала Hermes классифицирует обычное корневое поручение как `task`, `goal` или `quest`. Если начальный черновик создан с временным `task`, но пакет обосновывает иной уровень, Hermes вызывает `game_core_element_reclassify` до фиксации критериев. Эта команда доступна только безопасному начальному корневому черновику. Независимый проверяющий фиксирует критерии через `game_core_planning_bind` до кандидата; напарник составляет предметный план по пакету и передаёт `game_core_planning_build`. Тот же проверяющий проверяет кандидат; `game_core_planning_apply` принимает его SHA256 и проверку. Owner API атомарно сохраняет новую ревизию, Ходы, ресурс постановки и завершение исходной попытки. Повтор того же применения возвращает те же ID. Квесты и Цели планируются со своими уровнями. Повтор раскрывается `game_core_planning_expand_repeat` по фактическому ресурсу; неподдерживаемые дети и отложенные части останавливаются.

Все четыре инструмента наследуют user_id только из owner-bound runtime. Модель не подтверждает постановку за Игрока: Human Экшен проходит через session-bound web или доверенный Telegram. Фонового исполнителя эта интеграция не запускает; Hermes повторяет протокол по следующему явному поручению.


Telegram использует одну кнопку «Принять». Замечания и отмена поступают обычным
сообщением через brai_telegram_submit_feedback. Модель не задаёт текст и источник
решения. Отмена сохраняет выполненное и атомарно отменяет невыполненную ветку.
Практические Human Actions используют brai_telegram_submit_result только с точными
moveId/revisionId; текст и provenance берутся из текущего реального сообщения.
У одного итогового выхода отчёт может сохраниться отдельно до следующего явного
решения владельца, после чего завершается тот же Action. Несколько выходов требуют
JSON-сопоставления по точным названиям и отдельного решения. Кнопка не создаёт
свидетельств практической работы.
Параметр feedback у game_core_element_activate запрещён обычному MCP модели;
его передаёт только private порт. Подробности — в telegram/CONTRACT.md.

## Ограниченное чтение пакета постановки

`game_core_planning_packet_read({attempt_id,file_name?,offset?,limit?})` без file_name возвращает manifest с `file_sha256` каждого точного UTF-8 файла. Aggregate `inputs_sha256` сохраняет прежний смысл. Имя выбирается только среди ключей текущего owner `game_core_planning_packet`, не является путём файловой системы. Offset считает Unicode code points; limit 1–12000, next_offset=null означает конец. Каждый slice содержит тот же полный хеш, source revision и manifest. Читатель не выполняет код, не пишет файлы, не фиксирует baseline и не подтверждает план. Существующие owner/attempt/revision проверки выполняет upstream packet. Проверяющий читает весь пакет и записывает per-file map в baseline.inputs; bind/build/apply и проверка квитанции остаются штатными.

## Отключённый Game Core

`gameCore.enabled=false` в доверенном JSON выключает интеграцию Game Core.
В этом режиме url/ownerId Game Core не требуются; остальные обязательные порты
сохраняют проверки. Мост не открывает и не обнаруживает endpoint, не публикует
`game_core_*` и отклоняет прежние сохранённые вызовы кодом `GAME_CORE_DISABLED`,
включая private human actions. Telegram читает тот же переключатель: не
регистрирует workflow tools/callbacks и не восстанавливает прежние попытки.
Owner guard, файлы, наблюдение переписки и обычные ответы сохраняются. Прежние
задачи, попытки, решения и кнопки не изменяются и не выдаются за завершённые.
При отсутствии enabled сохраняется прежнее подключение для совместимости.
Рабочие инструкции обычного агента не требуют Game Core для выполнения поручения.

## Разговорные разрешения и имя Brai

Управляемый профиль использует `approvals.mode=smart` и
`approvals.interaction=conversation`. Overlay conversational-approvals.patch
загружает native/approval_conversation.py до выбора старого транспорта.
Terminal, execute_code и plugin approval используют общий gate. Старые
callback не выдают разрешений. Ошибка проверки не включает старый UI.
Терминал, Python и остальные инструменты сохраняются.

Проверяющий получает точные аргументы, cwd/backend, отпечаток окружения,
доступные bytes явно указанных скриптов, текущее поручение и до 32 подлинных
сообщений того же владельца в той же беседе. Авторство фиксирует gateway после
аутентификации. Перед каждой проверкой перечень читается заново: уточнения
работающего хода не теряются в снимке его начала. Текст модели, команды и результаты инструментов не выдают
полномочий. Ответ — строгий JSON: решение, известность эффектов, объект,
последствия и основание. Бюджет 2048 токенов, общий task timeout approval,
максимум один повтор в том же сроке. Неизвестные последствия требуют сначала
изучить действие доступными инструментами.

Различаются allow, needs_consent, policy_denied, review_unavailable.
needs_consent сохраняет операцию и возвращает обычный вопрос через controlled
halt, освобождая поток. Вопрос не содержит команд, внутренних путей или секретов.
Он принимается к ответу только после подтверждённой доставки.

Таблицы brai_consent и brai_consent_requests принадлежат профильному SessionDB.
Отдельного сервиса и публичного MCP выдачи согласия нет. Одно активное
согласование связано с владельцем, транспортом, беседой, темой и отпечатком
операции. Ожидание переживает перезапуск и не истекает через пять минут.
Разрешение атомарно поглощает один внутренний execution ID. Изменение
аргументов плагином, cwd или bytes скрипта требует новой проверки.
Повтор ответа не повторяет выполнение. Сбой после поглощения даёт неизвестный
исход; автоматический повтор запрещён. Сохранённый executing после перезапуска
трактуется как возможно уже начатое действие. Стоп/сброс отменяет ожидания,
а executing переводит в неизвестный исход.

Текстовое да/нет принимает доверенный вход gateway после авторизации или
локальный интерактивный CLI от своего Unix principal. Другой пользователь,
тема, ответ до доставки или на старый вопрос не разрешают действие.
Новое текстовое уточнение отменяет прежнее неиспользованное ожидание и
поступает в обычный диалог; история поручения сохраняется. Пустой голосовой
вход сам по себе не отменяет ожидание. Напоминание не меняет первую
подтверждённую доставку вопроса. Внутренний порт ответа позволяет проверить
ожидаемый ID вопроса в той же транзакции. Пока вопрос ожидает ответа, другая
операция проходит собственную проверку; безопасная работа не блокируется
старым вопросом. Новых session/always разрешений нет.
Дочерние потоки наследуют runtime context; непривязанный вызов закрывается
без технического запроса.

Пользовательское имя — Brai: Python i18n, desktop/web каталоги, запасные ответы
gateway и инструкции представления. Технические ключи, каталоги, команды,
URL и лицензии сохраняются. Порядок overlay закреплён provenance.json:
разговорный overlay перед последним memory-recall. Поставка кода не
переключает DEV/PROD. Реальный тестовый Telegram-диалог и снятие прежних
кнопок обязательны перед отдельным переключением DEV.

Вложенный вызов из согласованного execute_code получает от runtime точную
проверенную родительскую операцию и её последствия. Проверяющий разрешает
покрытый эффект без второго вопроса; модель не создаёт эту привязку.
Дополнительный непокрытый эффект не выполняется: родитель сохраняет неизвестный
исход, дочерняя операция становится единственным новым ожиданием.
Переписанные плагином аргументы проверенного действия останавливаются до dispatch.

## Голосовой вход из личного Unix-профиля

Для identity worker `identity.transcribe` использует существующие методы broker
`files.publish/files.fetch` и `tools.call(local_ai_invoke_transcribe)`. Уже принятый
артефакт проверяется через fetch без повторной публикации. Owner определяется
SO_PEERCRED и актуальным Auth. Shared Transcription bearer остаётся выключенным.
Публичный selector передаёт установщик из прежнего защищённого `stt.model`.
Нет selector — STT выключен. Вход — обычный собственный аудиофайл; Local AI
получает только ID опубликованного артефакта. Публикация и invoke используют общий
срок 180 секунд; requestId и operationId различаются. Неизвестный исход не повторяется.
Ответ проверяется по обоим ID и точному selector. Пустой текст и результат больше
1 МиБ отклоняются; усечения нет. Новый UTF-8 output имеет mode 0600, существующий
файл или symlink не заменяется. CLI пишет в stderr только безопасный код ошибки.
Общий однопользовательский профиль сохраняет прежний мост через Transcription.

## Общие системные и личные навыки

Все личные процессы читают один системный набор. Продуктовые .md/.txt устанавливаются оператором из точного Git-коммита через extensions/tools/skill_docs.py --system отдельно от payload и fingerprints кода. CLI plan не пишет файлы; apply требует Root, проверяет неизвестные изменения до записи, сохраняет backup и откатывает собственные записи при ошибке. verify отдельно проверяет квитанцию, байты и защиту файлов. Два apply одного каталога сериализованы; после ожидания план пересчитывается. Повтор с теми же байтами не обновляет файлы. Изменение только текстов не требует сборки или перезапуска Hermes.

Namespace worker подключает системную документацию и скрипты только для чтения. Системные корни выше личных и проектных; пользовательские external_dirs/create_dir не меняют их. Disabled и platform_disabled не отключают системные имена и пути. Неизвестный, отсутствующий или небезопасный обязательный системный источник останавливает работу. Обязательный context-gifs читается из независимого каталога; базовые политики остаются в кодовой поставке.

Штатный skill_manage создаёт личные навыки только в HERMES_HOME/usercustom/userdata/skills текущего владельца. Поддерживающие файлы добавляются write_file; установка не выполняет импортируемый код. Пользователь может редактировать и удалять свои навыки. Они не экспортируются в Git, общий каталог или другие профили и сохраняются при обновлении системы. При совпадении имени или пути системный навык сохраняет приоритет; для личной редакции требуется другое имя.

Встроенный каталог движка служит защищённым резервом; одноимённая системная редакция из документации имеет приоритет. Новое чтение видит атомарно заменённый файл, уже включённые в разговор байты могут оставаться в контексте. Обновление нескольких файлов не меняет контекст выполняемого хода целиком. Пользовательские данные, скрипты и исчезнувшие документы updater не удаляет.
