# Теневое наблюдение Hermes Telegram v1

Дата: 1 ноября 2026 года. Статус: закреплённый целевой контракт, НЕ реализован.
Этот документ не разрешает выпуск или включение наблюдения.
Действующее чтение переписки описано в [CONTRACT.md](CONTRACT.md).

## 1. Назначение и границы

Hermes остаётся единственным получателем Telegram updates, исполнителем ходов
и отправителем ответов. Потоковая выдача, typing, команды, callbacks, human
подтверждения, очереди, прерывания, STT, файлы и память сохраняют штатный путь.
Копии событий не управляют этими действиями и не являются условием их успеха.

Владелец захвата, нормализации Telegram и экспорта — Hermes. Экспортёр является
отдельной программой этого сервиса, не новым микросервисом. Приём владеет
[сценарием обработки копии](../../../intake/SHADOW_CONTRACT.md).
Артефакты и История остаются существующими владельцами данных.

В этой версии наблюдаются только новые разрешённые сообщения выбранного
бота/чата/темы после явной границы включения. Telegram Business, импорт старой
переписки, инициативные cron-отправки без известного обращения и переключение
маршрута агента не входят в этап. Выбор новых топиков или threaded mode не
выполняется скрыто при включении наблюдения.

## 2. Граф и изоляция отказов

~~~mermaid
flowchart TD
    TG[Telegram] <-->|Прежний рабочий путь и streaming| H[Hermes]
    H -.->|Ограниченный захват без ожидания| Q[Буфер наблюдений]
    Q --> J[Неизменяемый журнал Hermes]
    J -->|Read API| E[Отдельный экспортёр Hermes]
    E --> JS[JetStream: вход Приёма]
    JS --> I[Теневой сценарий Приёма]
~~~

В обработчике Hermes запрещены await записи наблюдения, сетевой вызов новых
сервисов, ожидание PubAck, fsync и ожидание освобождения места в буфере.
Захват выполняет только ограниченное копирование разрешённых полей и put_nowait.
Проверка размера ограничивает обход данных; ссылки на изменяемый native event
не сохраняются. Всё медленное выполняется вне gateway event loop.

Один фоновый writer записывает снимки. Ошибки захвата/SQL/экспортёра не меняют
возвращаемое значение, исключение, текст, SendResult, callback или lifecycle
основной операции. Нет добавленного ожидания writer при завершении хода или
shutdown gateway. Ошибка фоновой ветки не отправляет сообщение в Telegram.

Исходные значения для первого этапа, не результаты измерения:

| Ограничение | Значение |
| --- | --- |
| Буфер захвата | До 128 записей и суммарно 8 MiB; отказ без ожидания |
| Снимок и окончательный ingress event | Каждый до 128 KiB UTF-8; без усечения текста |
| Фоновый writer | Один; ожидание SQLite lock до 50 ms |
| Экспортёр | Одна публикация за раз; чтение до 16 записей |
| Сетевые сроки экспортёра | Read 2 s; PubAck 5 s |
| Хранилище наблюдений | Бюджет 256 MiB вместе с WAL; прекратить новый захват на 200 MiB либо при свободном месте менее 1 GiB |
| Exporter runtime | Начальные пределы 128 MiB RAM и 0.25 CPU; отдельный процесс |

Проверка диска выполняется writer вне gateway. Бюджет и свободное место
проверяются до записи, checkpoint выполняется вне gateway; это не утверждение
о файловой квоте ОС. Перед первым включением проверяют реальное поведение WAL
и запас места. Журнал и его WAL располагают вне БД, файлов и каталога состояния
рабочих сессий; новый writer не использует транзакции текущего UI-журнала.

Переполнение буфера, закрытый writer, превышение размера, ошибка диска или SQL
означают пропуск наблюдения. Ограниченные безопасные счётчики и последний код
диагностики не содержат текстов, имён, токенов и файлов. Они не пишутся в stdout
потока агента и не создают бесконечный журнал ошибок.

До COMMIT наблюдение может потеряться при crash. Надёжность переписки от этого
не зависит. Счётчики потерь до COMMIT могут быть только локальными текущему
запуску; после аварийного рестарта полнота coverage=unknown. Нулевой счётчик
не доказывает отсутствие потерь. Гарантия ровно всех исходных событий не
заявляется. Ненадёжный захват нельзя называть надёжным принятием события.

## 3. События и содержание снимка

Источник снимает два вида завершённых предметных наблюдений:

- incoming: разрешённое логическое сообщение после штатной сборки набора,
  перед передачей его агенту; включает исходный текст/подписи и состав файлов.
- outgoing: окончательный содержательный ответ либо содержательная отправка
  инструментом в рамках известного обращения; после штатного результата
  соответствующей отправки сохраняются содержание и фактическое свидетельство.

В text/подписях сохраняются исходные разрешённые данные после сборки набора,
до добавления ASR-текста, служебных artifact markers и инструкций модели.
Обогащённый prompt не выдаётся за исходное сообщение. Исходные поля удерживаются
в ограниченной native metadata на время сборки; повторно разбирать их из UI
журнала или из текста prompt запрещено.

Токены модели, промежуточные draft/edit потока, typing, технические ошибки,
команды управления и callbacks не создают отдельных message-пакетов.
Потоковая выдача не буферизуется ради теневого режима. Финальная запись появляется
после native terminal boundary. Частично выданный ответ при ошибке помечается
partial/unknown, а не выдаётся за полностью доставленный. NO_REPLY без отправки
не превращается в пустой message.outgoing.

Альбом уже собирает Hermes: один логический набор, упорядоченные вложения и
подписи, полный маршрут, media_group_id и IDs элементов. Позднее дополнение
сохраняет связь с прежним набором и содержит только новый native состав.
Экспортёр не вводит второй debounce и не повторяет прежние элементы.
Изменение содержания — новая ревизия наблюдения, не перезапись прежнего снимка.

Неизменяемый Observation содержит следующие закрытые поля:

| Поле | Содержание |
| --- | --- |
| version | 1 |
| id | UUID снимка, сохраняемый при повторе |
| epoch, seq | UUID жизни журнала и возрастающий безопасный integer |
| observedAt | UTC-время самого наблюдения, сохраняемое при повторе |
| direction | incoming или outgoing |
| logicalId, revision | Устойчивая идентичность материала и положительная ревизия |
| conversationId, turnId | Native беседа и ID хода; turnId может быть null до его назначения |
| sourceRef | botId, chatId, threadId; все Telegram IDs строки, отсутствующая тема null |
| sender | Для входа реальный human ID, наблюдавшиеся name/username/photoArtifactId; для выхода agent ID |
| text, attachments | Текст или null; упорядоченные имя/MIME/artifactId/подпись файлов; artifactId=null у неподтверждённого файла |
| origin | Для ответа точный ключ исходного наблюдения; для входа null |
| nativeRefs | IDs исходных Telegram messages, mediaGroupId или null; supplementOf или null |
| evidence | status=received/sent/failed/unknown/partial, Telegram IDs результата, attachmentState=ready/pending/failed/none |

Обязательность: перечисленные поля присутствуют; необязательные поля sender
могут отсутствовать. Unknown fields запрещены, кроме явно описанного nativeRefs.
Данные sender не восстанавливаются догадкой из имени; отсутствие username/фото
не означает null. Ссылку фото получают только если Hermes уже располагает
подтверждённым artifactId: синхронного Telegram API запроса ради наблюдения нет.

Bot ID задаёт доверенное подключение, owner определяется защищённой конфигурацией.
General нормализуется по конкретному профилю Telegram: нельзя универсально
заменить всякий threadId=1 на null. Сохраняется также исходный thread в nativeRefs
как отдельный rawThreadId для проверки преобразования.

sourceRef закрыт тремя перечисленными полями. nativeRefs закрыт полями
messageIds:string[], mediaGroupId:string|null, supplementOf:string|null,
rawThreadId:string|null, causalInputIds:UUID[]. IDs не преобразуются в числа.
logicalId/conversationId/turnId и строковые refs — до 255 символов; revision —
1..2147483647, seq — 1..Number.MAX_SAFE_INTEGER. observedAt — RFC 3339 UTC.
Элемент attachments закрыт полями filename:string, mimeType:string,
artifactId:UUID|null, caption:string|null. null artifactId никогда не готовый файл.

origin={epoch,id} указывает точно наблюдавшийся вход. При объединении нескольких
native входов origin указывает назначенный движком trigger, а nativeRefs хранит
causalInputIds всех известных входов. Связь по «ближайшему сообщению в чате» запрещена.
Отсутствующий trigger не выдумывается: выход получает origin=null и явную
диагностику ORIGIN_NOT_OBSERVED. Ответы старых ходов на границе включения допускают
именно этот случай.

id назначается до put_nowait и остаётся в native контексте хода для origin;
неуспешный захват не делает эту ссылку существующей записью. Журнал назначает
seq/revision атомарно с записью immutable snapshot; повтор того
же стабильного native identity/content возвращает прежнюю запись, конфликт
идентичности виден. Повторное совпадение текста без совпадения native identity
не является дублем. Поля исходного Telegram Update, не перечисленные здесь,
байты файлов, local paths и credentials не экспортируются.

Текущий messages/changes UI-журнал не является источником immutable Observation:
он объединяет изменения в текущую строку, не содержит отдельный username,
точное происхождение всех ответов и признак финальности streaming.
Новый журнал принадлежит тому же Hermes observer, но хранится отдельно;
существующие API и импорт истории не меняются.

## 4. Планируемый read API источника

Новый endpoint NATS Services: brai.hermes.telegram.shadow.v1.query.
Это целевой endpoint; действующий observer.v1.query его не предоставляет.
Сервис: brai_hermes_telegram_shadow, версия 1.0.0. Только доверенный exporter caller
с фиксированным owner/profile получает доступ через NATS ACL, без owner из request.
Программа чтения не получает Telegram token и не вызывает gateway.

Запрос до 4 KiB, ответ до 1 MiB, одна активная операция, срок 2 s.
Неизвестные поля закрыты; errors используют NATS Service API headers.

| Операция | Запрос | Ответ |
| --- | --- | --- |
| status | {action:"status"} | {epoch,lastSeq,captureEnabled,coverage,bootId,dropped,storageBytes,lastError} |
| read | {action:"read",epoch,after,limit?} | {epoch,items:Observation[],cursor} |

after — integer от 0 до Number.MAX_SAFE_INTEGER. limit=16, диапазон 1..16.
Страница содержит целые записи и прекращается до превышения ответа. cursor
равен seq последней включённой записи либо исходному after для пустой страницы.
Нельзя продвинуть cursor за невключённую запись. after больше lastSeq —
INVALID_CURSOR; иной epoch — SOURCE_EPOCH_MISMATCH. Прочитанное неизменяемо,
чтение не отмечает обработку и не удаляет данные.

coverage=complete/known_gaps/unknown описывает только окно текущего наблюдения,
не полноту Telegram или старой переписки. bootId — UUID запуска writer; dropped —
счётчик только этого запуска. Коды: INVALID_ARGUMENT/400, INVALID_CURSOR/409,
SOURCE_EPOCH_MISMATCH/409, BUSY/503, NOT_READY/503, RESPONSE_TOO_LARGE/413.
Повтор чтения безопасен. Epoch сохраняется между нормальными рестартами;
замена/утрата журнала создаёт иной epoch и требует явной новой границы включения.

## 5. Экспорт и передача ответственности

Экспортёр читает только API владельца; не читает чужие таблицы. Его собственный
checkpoint хранит epoch, cursor и точный замороженный pending ingress event.
На журнал и его source bindings работает один exporter; второй экземпляр
останавливается по локальной process lock до изменения checkpoint.
Он не является очередью заданий: долговечный backlog хранится в источнике,
передача после источника — в JetStream, выполнение — в Temporal.

Приём принимает копии как отдельный тип message.observed на существующие ingress
subjects ограниченных source identities. Конверт Event v1 принадлежит Приёму;
data={observation:Observation}. Новый тип поддерживается только будущим теневым
сценарием, старый runtime его отвергает и не запускает active message workflow. Вход бота и producer ответов имеют разные sourceId;
Каналы связывают bot с входным sourceId, а ответный source разрешают отдельно.
Исходный sourceId не подменяется ID сервиса или пользователя.

После чтения запись нормализуется один раз и сохраняется pending перед публикацией.
PubAck с постоянным msgID предшествует продвижению cursor. Потеря ответа после
COMMIT брокера повторяет тот же eventId, occurredAt и JSON; окно дедупликации
JetStream не заменяет постоянный source/eventId/hash Приёма.
Сбой checkpoint после PubAck безопасно повторяет публикацию.
Readiness новых сервисов не является readiness gateway.

Сеть восстанавливает штатный NATS SDK; цикл чтения только ждёт доступность
источника/брокера с ограниченной паузой 5 s. Новая очередь повторов не создаётся.
Ошибка конкретного DTO сохраняет безопасный отказ и останавливает checkpoint
на нём до явного исправления/пропуска с основанием; cursor не перескакивает молча.
Пропуск фиксируется отдельной операторской квитанцией, не успешным message.

Готовые artifact IDs передаются как есть. При missing/pending/failed вложениях
сохраняется неполнота: она не превращается в пустой полноценный message.
Публикация копий не загружает файлы повторно и не запускает ASR/ИИ.
Старую переписку не импортируют и не пересылают при первом включении.
Экспортёр не получает права dispatch, запуска хода, delivery или human решений.

## 6. Совместимость и отключение

Машинные схемы Draft-07 и AsyncAPI этого дополнения создаются при реализации
рядом с владельцем. Действующие схемы наблюдателя не рекламируют эти операции.
Ссылки на сообщения Приёма принадлежат Приёму; чужой runtime не импортируется.

Переключатели capture и export по умолчанию выключены и независимы.
Остановка экспортёра не останавливает gateway; отключение capture не закрывает
файловые leases, сессии, streaming или native observer. Изменение/ошибка конфигурации
дополнения отключает только дополнение, без отказа старта основного Hermes.
Запрещены PartOf/Requires зависимости gateway от новых программ.
Отключение или удаление shadow consumer не переводит копии в активный сценарий.
