# Нативный Telegram плагин Brai

Компонент `brai-telegram` подключается к штатному gateway Hermes через публичный plugin API закреплённой версии `517b5e10febd619ce30bb22580e29b160266eb43`. Каталог копируется целиком в `HERMES_HOME/plugins/brai-telegram`. Плагин не запускает polling, не заменяет Telegram adapter и сохраняет остальные инструменты Hermes.

## Конфигурация и границы

Защищённое окружение процесса задаёт следующие параметры:

| Переменная | Значение |
| --- | --- |
| `BRAI_TELEGRAM_OWNER_ID` | Обязательный положительный decimal Telegram **user ID** владельца. Не chat ID и не Brai owner. |
| `BRAI_TELEGRAM_CHAT_ID` | Необязательный signed decimal ID единственного рабочего чата. Отрицательный — группа/supergroup; положительный допустим только равный owner. Без значения используется прежний личный чат owner. |
| `BRAI_TELEGRAM_STATE_DIR` | Абсолютный профильный каталог с последним сегментом `brai-telegram`. Содержит private SQLite подтверждений. |
| `BRAI_HERMES_TRUSTED_ENTRY` | Абсолютный путь к `services/hermes/trusted.mjs`. |
| `BRAI_HERMES_NODE_EXECUTABLE` | Абсолютный путь к доверенному Node; окружение экземпляра задаёт `/usr/local/bin/node`. |
| `BRAI_TELEGRAM_RESULT_ROOT` | Точный абсолютный **файловый** `resultRoot` publisher, без завершающего `/`, кроме корня файловой системы. Это не HTTP URL. |
| `BRAI_HERMES_CONFIG` | Наследуемый защищённый JSON config private порта; формат принадлежит [Hermes tools](../CONTRACT.md). |

Состояние принадлежит плагину; Graph и Artifacts принадлежат своим сервисам. Связи: native ingress → owner/route проверка → publisher RPC → exact Markdown; model output → descriptor → fetch RPC → native MEDIA upload; model tool → human prepare → native кнопки → owner callback → read/complete или cancel. Точка сборки — `register(ctx)`, native bot и loop предоставляет factory `(app, adapter)`.

Factory ставит один штатный PTB `TypeHandler(Update, guard)` в группе `-100`, раньше native command/media/callback/inline handlers. Guard допускает только точные chat ID и `effective_user.id=owner`; anonymous `sender_chat`, Business и bot identities запрещены. Отказ через `ApplicationHandlerStop` происходит до download, команды, inline ответа и обработки кнопки; ответ чужому отправителю не отправляется. Для группы допустимы group/supergroup/forum, для owner DM — private/dm. Forum topic не является отдельным разрешением: маршрут охватывает заданный чат целиком. Нативный ответ сохраняет исходный thread; human кнопки и уведомления адресованы рабочему чату.

Runtime дополнительно задаёт native `TELEGRAM_ALLOWED_CHATS=chatId`, `TELEGRAM_GROUP_ALLOWED_USERS=owner`, `TELEGRAM_ALLOWED_USERS=owner`; `TELEGRAM_HOME_CHANNEL` при необходимости содержит route. `TELEGRAM_GROUP_ALLOWED_CHATS` и YAML `group_allowed_chats` не используются: в закреплённом Hermes они дают доступ всем участникам. Отрицательные chat ID запрещены в `TELEGRAM_GROUP_ALLOWED_USERS`: Hermes сохраняет legacy chat grant. Нет wildcard, allow-all, guest/observe или bot grants; adapter `allow_from/group_allow_from`, если заданы, содержат только owner. Один chat ID без обязательного user owner не активирует плагин. Секреты и пользовательские значения живут только в защищённом runtime, не в исходниках.

Сам Hermes считается доверенным ядром. Защита callback обеспечивает обычный маршрут MCP/Telegram. Она не изолирует private CLI от произвольного кода, запущенного native terminal тем же Unix пользователем с тем же окружением. Planning revision проверяется атомарно владельцем; для final/review доступны предварительные проверки private порта, общего атомарного CAS нет.

## Файлы

`pre_gateway_dispatch` выполняется до штатной авторизации и повторяет owner/route проверку. События других платформ проходят без изменений. Telegram допускается только для `source.user_id=owner`, точного рабочего `source.chat_id` и соответствующего типа чата, без bot identity, anonymous sender или Business connection. Другие Telegram события получают `skip`.

До десяти уже загруженных native вложений публикуются последовательно через `files.publish`. `requestId=tg:<chatId>:<messageId>:<zero-based-index>` сохраняется при повторной доставке. Publisher проверяет разрешённый read root, owner, ready и SHA-256; его предел — 2 GiB. Точный возвращённый Markdown добавляется к тексту через `rewrite`. Ошибка публикации закрывает весь вход для дальнейшей обработки; владелец получает native сообщение об ошибке, если Telegram доступен. Успешно опубликованные до ошибки файлы не удаляются; повтор использует прежние ключи.

`transform_llm_output` работает только для Telegram. Распознаются publisher descriptors `[label](<resultRoot/UUID/filename>)` и `![label](<...>)`, включая экранированные скобки, Unicode и пробелы. UUID должен быть каноническим lowercase. Посторонние URL и пути не вызывают fetch. Каждый artifactId восстанавливается через `files.fetch` один раз. Проверяются идентичность, DTO metadata, точный путь `resultRoot/artifactId/filename`, канонический realpath без symlink и обычный файл. Только после этого descriptor заменяется на quoted `MEDIA:"<localPath>"` для штатной отправки. Ogg/Opus добавляет штатный `[[audio_as_voice]]`. Число вложений — до десяти, общий deadline преобразования — 20 секунд, ниже стандартного 30-секундного hook timeout Hermes. Ошибки остаются видимыми как «Файл не отправлен».

Native MEDIA parser поддерживает пробелы, Unicode и скобки в quoted path. Пути с double quote, backtick, backslash, control characters или `MEDIA:` отклоняются с видимой ошибкой; плагин не копирует файл и не изменяет descriptor произвольно. Преобразование подготавливает native upload; оно не утверждает, что Telegram уже принял байты. Фактический результат отправки принадлежит gateway.

`transform_tool_result` обрабатывает только успешный JSON `image_generate` в текущем Telegram session context с точными owner/chat/type. Штатный hook получает `tool_name`, `args`, `result`, `session_id`, `tool_call_id`, `turn_id`, `api_request_id`; platform/chat/user читаются через native `gateway.session_context.get_session_env`, не из аргументов модели. Допускается только обычный файл без symlink непосредственно в активном `HERMES_HOME/cache/generated/images`, с расширением PNG/JPEG/WebP/GIF. Пустая session/tool-call identity, чужой контекст или путь закрывают успешный результат явной ошибкой без нового вызова генератора.

Один hook вызывает `files.publish` один раз с `requestId=tg-image:SHA256([owner,chat,sessionId,toolCallId])`. Повтор доставки той же identity использует прежний publisher key; неоднозначная ошибка не вызывает автоматический повтор. Проверяются exact descriptor и publisher DTO/канонический файл той же проверкой, что для исходящих артефактов. Успешный JSON сохраняет provider/model/prompt и прочие metadata, заменяет `image` и имеющиеся native path aliases на опубликованный `localPath`, добавляет точные `artifactId` и `markdown`. Native autoappend получает опубликованную копию; Markdown поддерживает обычную quoted MEDIA отправку. Literal `MEDIA:` внутри metadata кодируется JSON Unicode escape, чтобы native scanner не принял текст prompt за вложение; JSON-содержимое metadata сохраняется. При ошибке возвращается `success:false,image:null,error_type:artifact_publication_failed` без исходного cache path. Другие tools, неуспех image_generate и другие платформы не преобразуются. Успешное вычисление не означает успешную публикацию или upload.

Runtime должен разрешать publisher читать узкий `cache/generated/images`, а native `gateway.media_delivery_allow_dirs` — каталог `results` с опубликованными копиями. Publisher read roots сами по себе не разрешают native delivery из `/var/lib`. Public Bot API допускает входящие документы до 20 MiB и исходящие файлы до 50 MB; publisher 2 GiB не расширяет Telegram limits. Native фото может сжаться; документ отправляется отдельным native методом. Проверка upload, STT/vision и кнопок в живом чате остаётся отдельной DEV-приёмкой.

## Подтверждения

Единственный model tool — `brai_telegram_request_confirmation({moveId,revisionId,stage?})`; stage по умолчанию `planning`, также доступны `final` и `review`. Он не принимает решение, owner или attemptId. Точный публичный API Hermes: `ctx.register_tool(..., handler(args, **kwargs), is_async=True)`. Factory захватывает native loop; вызов из worker loop передаётся через `run_coroutine_threadsafe`, все bot операции выполняются на loop приложения.

Перед `actions.prepare` транзакция SQLite сохраняет случайный opaque token, owner, chatId, move/revision/stage и срок 15 минут. Этот token служит стабильным idempotencyKey prepare. Допускается одна незавершённая запись на move и не более 100 незавершённых записей на профиль. Claim создаёт human attempt до показа кнопок; attemptId сохраняется до native отправки. Перед отправкой дополнительно читаются актуальные move status, attemptId, revisionId, human/running. Сообщение показывает title, доступные target title/description, moveId, targetId, revisionId и stage. В SQLite закрепляется фактический messageId.

Scoped `CallbackQueryHandler(pattern="^brai:")` не перехватывает остальные кнопки Hermes. Callback data не превышает 64 байт. Допускаются только owner, точный исходный chatId/messageId и сохранённый token. Token атомарно поглощается один раз **до** внешнего эффекта. Подмена, повтор, чужой чат или пользователь не подтверждают действие. `planning/review` допускают approved/changes/cancelled; `final` — success/changes/cancelled. Старая revision/attempt не завершается. Cancel и cleanup обращаются только к прежней текущей human/running attempt; новую попытку не отменяют. Изменившаяся revision допускает отмену прежней attempt для освобождения Action.

Поглощение и успешное завершение сохраняются отдельно. Ошибка/timeout complete не повторяет approval и не выдаётся за успех. Кнопки снимаются; пользователь видит неопределённый исход и необходимость проверить Action. Cleanup читает текущую точную attempt и при необходимости отменяет её, после чего возможен новый запрос кнопок. Сбой native отправки также отменяет связанную attempt.

Native asyncio timer погашает истёкший token и вызывает `actions.cancel(reason=expired)`. После перезапуска восстанавливаются ожидающие таймеры; consumed-but-unresolved записи очищаются сразу. Прежняя SQLite схема мигрирует chatId в owner DM. При смене route/owner старые tokens немедленно погашаются и очищаются без approval; сообщения с тем же messageId в новом чате их не подтверждают. Cleanup уведомляет сохранённый исходный чат, не переносит старую кнопку или её контекст в новый. Reservation без сохранённого attemptId восстанавливается **тем же** prepare key исключительно для отмены, без повторного approval и без новых кнопок. Private порт гарантирует восстановление прежней running attempt этого ключа, в том числе после смены revision; чужой ключ не может присвоить claimed move. Это закрывает crash между claim и записью attemptId. Crash после успешного complete определяется чтением; уже завершённая/заменённая attempt не отменяется, сообщение остаётся нейтральным.

Если cleanup не подтверждён, native task повторяет проверку через 60 секунд. Каждый повтор сначала читает состояние; complete никогда не повторяется. При недоступном владельце невозможно гарантировать немедленное освобождение attempt: token уже неактивен, статус остаётся неизвестным до успешного чтения/cleanup. `ctx.on_unload` снимает только собственные handlers и tasks, SQLite остаётся для следующего запуска.

## Private RPC и проверки

Схемы операций принадлежат [trusted.openrpc.json](../trusted.openrpc.json). Один вызов запускает отдельный private процесс: одна UTF-8 JSON-RPC 2.0 строка → один ответ с тем же строковым id → выход. До двух процессов одновременно; semaphore ожидание входит в 15-секундный deadline. Запрос до 65536 байт, stdout до 1 MiB. Проверяются версия, id, взаимоисключение result/error и object result. stderr и сырые ошибки не передаются владельцу или модели. Timeout завершает всю собственную process group, включая publisher child; уже возможный удалённый эффект считается неизвестным. Автоматического повтора публикации/complete нет; повтор доставки publish применяет стабильный requestId, recovery prepare — прежний idempotencyKey.

Локальная проверка: `python3 -m unittest discover -s services/hermes/telegram/tests -v`. Зависимости не устанавливаются, живой бот не используется. Stubs проверяют native API и thread/loop переходы; SQLite и stdio child processes реальные. При наличии read-only `tmp/hermes-pinned-telegram` отдельные тесты сверяют API и точный MEDIA parser закреплённого исходника. Полный Telegram/Artifacts/game-core сценарий требует отдельной DEV-приёмки с доступным ботом.
