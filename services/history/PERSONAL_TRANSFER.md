# Перенос подтверждённых личных событий

Операторский CLI принадлежит History и использует отдельную учётную запись
владельца его БД. Он не опубликован через HTTP, NATS или MCP. Runtime app/web
не получают owner credentials и не могут менять журнал переноса или привязки.

Перенос добавляет область чтения в `history.personal_event_bindings`.
Исходный `history.events` сохраняет все 11 полей, ID, JSONB-числа и даты.
Ответ API возвращает исходный DTO, включая первоначальный scope. Запись
с `scope_id IS NULL` в таблице привязок относится к закрытому архиву.
Пользовательская RLS её не открывает. Административный просмотр архива должен
проходить через отдельный удостоверенный порт с аудитом.

Перед apply внешний оператор закрывает вход, останавливает производителей,
делает согласованные резервные копии и закрепляет реестр аккаунтов/профилей.
Scope выводится из подтверждённого profileId по публичному Auth helper.
Владелец определяется по проверенному отправителю, исходному запросу или
однозначной цепочке связанных записей. actor_id, имя, упоминание и общий
технический owner не являются доказательствами.

CLI проверяет структуру и хеш доказательства; содержательную проверку внешнего
доказательства и его связи с закреплённым реестром выполняет оператор до создания
закрытого входного файла. Недоверенные пользовательские поля не становятся
таким файлом. Одно событие назначается не более чем одному личному scope.

## Фазы

Для CLI нужны `HISTORY_OWNER_DATABASE_URL` и `HISTORY_OWNER_ROLE`.
Текущая SQL-роль обязана совпадать с указанной ролью и владельцем целевой БД.
Входные JSON-файлы — обычные файлы своего UID с одним hardlink и правами 0600.
Выход создаётся через exclusive create с правами 0600; существующий файл
не перезаписывается. Пароль не передаётся аргументом команды.

```text
node dist/personal-transfer.js inventory - /protected/inventory.json
node dist/personal-transfer.js plan /protected/assignments.json /protected/plan.json
node dist/personal-transfer.js apply /protected/plan.json /protected/applied.json
node dist/personal-transfer.js verify /protected/plan.json /protected/verified.json
node dist/personal-transfer.js rollback /protected/plan.json /protected/rollback.json
```

inventory возвращает ключи и SHA256 PostgreSQL JSONB-текста исходных строк.
Содержимое события не проходит через Node JSON.parse/JSON.stringify. Снимок
содержит не более 100 000 событий; превышение останавливает операцию целиком.

Вход plan содержит id переноса (UUID), sourceHash просмотренного inventory
и assignments. Каждое назначение содержит source, id, scopeId и proofSha256.
Scope имеет вид brai-personal-v1:<64 hex>, proofSha256 закрепляет проверенное
внешнее доказательство. Дубли, неизвестные ключи, произвольный scope и отсутствие
доказательства отклоняются. Каждая оставшаяся строка включается в план как архив.
Уже личные данные не принимаются для нового переноса.

apply блокирует исходные таблицы и сверяет свежий sourceHash. Привязки и
квитанция сохраняются одной транзакцией. Отказ посередине не оставляет часть
назначений. Повтор и параллельный apply одного плана используют одну квитанцию;
другой план с тем же ID отвергается. JSON-порядок полей не влияет на хеш плана.

verify сверяет неизменность всех исходных строк, каждую привязку, план и баланс
«назначено + архив = исходные строки». Это проверка при закрытом входе.
Команды, outbox, JetStream и события не воспроизводятся и не публикуются.

rollback удаляет только привязки данного переноса и сохраняет квитанцию возврата.
Любая новая строка или изменение исходника запрещает возврат. После открытия
пользовательского входа внешний оператор дополнительно запрещает возврат к общей
системе, даже если History ещё не получил новых событий. Повтор rollback безопасен;
повтор apply отменённого плана не восстанавливает доступ автоматически.

SQL-проверка `tests/integration/personal-transfer.test.mjs` использует настоящий
синтетический PostgreSQL: точность чисел/микросекунд, два владельца, закрытый архив,
RLS, повторы, отказ посередине и запрет возврата после новой пользовательской записи.
