# Контракт сервиса истории

Сервис service_history владеет неизменяемыми событиями и системными справочниками категорий и типов. Контракты данных находятся в [schemas](schemas/); маршруты NATS описаны в [AsyncAPI](asyncapi.yaml). JSON-схемы используют Draft-07. Сервис не зависит от admin и не копирует начальные строки справочников в документацию: актуальные категории и типы возвращают MCP-инструменты.

## Модель события

Событие содержит ровно 11 полей:

| Поле | Тип | Правило |
| --- | --- | --- |
| id | UUID | Источник создаёт ID до отправки и сохраняет для безопасного повтора. |
| source | строка, до 64 символов | Код источника: строчная латиница, цифры и _, начинается с буквы. Пара (source,id) уникальна. |
| type_id | целое положительное | Ссылка на тип; категория определяется через справочник типов. |
| occurred_at | timestamp | Время события у источника; RFC 3339 с явной временной зоной и не более чем шестью знаками долей секунды. |
| recorded_at | timestamp | Назначает PostgreSQL при записи; ответы возвращают UTC с шестью знаками долей секунды. |
| actor_id | строка или null | Необязательно; заявленный инициатор без внешнего ключа. |
| scope_type | строка, до 32 символов | Вид области, например user или system. |
| scope_id | строка, до 255 символов | Идентификатор области. |
| object_type | строка до 64 символов или null | Вид объекта в источнике. |
| object_id | строка до 255 символов или null | Идентификатор объекта в источнике. |
| data | JSON-объект | Дополнительные данные, по умолчанию {}. |

BetterAuth и другие строковые идентификаторы не преобразуются в UUID. object_type и object_id передаются вместе или оба равны null. Входные необязательные actor_id, object_type, object_id и data сохраняются с явными значениями null, null, null и {}. Сервис сохраняет occurred_at в UTC, не теряя точность микросекунд. Лишние поля в DTO запрещены. Секреты и избыточные персональные данные в data не передаются.

data не имеет фиксированной предметной схемы. Источник может описывать там необходимые ему этап, результат, связь операции и изменения, например phase, outcome, operation_id и changes. Учитывайте, что scope всего события распространяется и на каждое значение внутри data. Не добавляйте секреты, токены, IP-адреса, содержимое писем или лишние персональные сведения. retry как тип события означает новую попытку бизнес-операции; повторная доставка того же события — транспортный повтор, который использует тот же (source,id) и те же данные.

Размер полного JSON события после UTF-8 сериализации не превышает 65 536 байт. Строки ограничены схемой common.schema.json: source — 64, scope_type — 32, actor_id/scope_id/object_id — 255, object_type — 64 символа. Код справочника — до 64 символов, имя — до 128, описание — до 512. Строковые идентификаторы допускают любые непустые значения этих размеров; NUL запрещён реализацией БД.

## Выбор категории, типа и данных

Перед записью запросите актуальные строки через history_categories_list и history_types_list; history_type_get помогает прочитать выбранный тип. Выберите категорию и тип по фактическому смыслу события. Не нужно использовать все начальные типы или записывать событие на каждое внутреннее изменение. Если подходящего типа нет, создайте минимально нужный тип в существующей категории; новую категорию создавайте только при отсутствии подходящей. Для уже существующего кода меняйте только имя и описание.

Дополнительные сведения источника помещайте в data: используйте phase для этапа, outcome для результата, operation_id для связи попыток и changes для нужных изменений. Это примеры полей, а не общая схема. Не дублируйте в data значения, уже представленные полями события. Исправляющее событие должно ссылаться на исходные source и id. Область видимости относится ко всему событию, включая data; храните только данные, которые допустимо видеть получателям этой области.

## Запись, повторы и исправления

Пара (source,id) уникальна. При повторе с тем же нормализованным содержимым сервис возвращает исходное событие и его первоначальный recorded_at. Для сравнения он исключает назначенный БД recorded_at и не учитывает порядок ключей JSON. Повтор того же ID с другим содержимым отвечает EVENT_ID_CONFLICT. Параллельные одинаковые запросы дают один сохранённый результат.

Запись неизменяема. Роли приложения не могут менять, удалять или очищать события. Исправление — новое событие со ссылкой в data на исходные source и id; заменять или удалять прежнее событие нельзя. Сервис не обещает строгий глобальный порядок между источниками.

У NATS имя источника берётся из части subject brai.history.v1.append.<source>; тела JSON поле source не содержат. NATS ACL связывают доступный отправителю subject с его кодом источника. MCP передаёт source в запросе, но это заявленное значение, а не удостоверенная личность. source=service_history допустим для обычного события, кроме зарезервированных записей аудита справочников: общий append отвергает сочетания source=service_history с object_type=sys_categories или object_type=sys_types. Только внутренний код аудита создаёт такие события.

## Чтение web

Web сначала проверяет сессию BetterAuth и передаёт user_id только из серверного контекста. NATS endpoint brai.history.v1.query.list принимает listRequest: user_id, необязательные filters, limit и cursor. brai.history.v1.query.get принимает getRequest: user_id, source и id. Схемы расположены в schemas/messages.schema.json (listRequest, listResponse, getRequest, getResponse). Веб-контракт не принимает scope_type или scope_id; сервис всегда задаёт scope_type=user и scope_id=user_id.

Фильтры списка — только source, category_id, type_id, actor_id, object_type, object_id, occurred_from и occurred_to. Нельзя передавать произвольные JSON-фильтры или SQL. Даты фильтра — RFC 3339 с временной зоной и точностью не выше микросекунд. Сервис возвращает только пользовательскую область; отсутствующее и чужое событие для get одинаково дают NOT_FOUND. Категория и тип разрешаются через справочник; сортировка по recorded_at, source и id убывает.

Страница по умолчанию содержит 50 событий, допустимый limit — 1–100. Курсор непрозрачен и подписан HMAC с ключом сервиса; он связан с нормализованными фильтрами, областью и последним ключом сортировки. Изменённые фильтры/область, неверная подпись или повреждённый курсор дают INVALID_CURSOR. Следующая страница использует строгое условие после последней возвращённой записи. Новые записи выше уже пройденной границы не сдвигают курсор; курсор не обещает снимок всей истории.

Списки MCP для категорий и типов используют тот же размер страницы и форму ответа {items,next_cursor}, но сортируются по ID по возрастанию. Курсор типов связан с category_id, если фильтр задан; несовпадение фильтра даёт INVALID_CURSOR.

Ответ списка ограничен 524 288 байтами. Если полный набор не помещается, сервис уменьшает страницу и формирует next_cursor по последнему фактически возвращённому событию. Он не пропускает просмотренные, но не возвращённые строки. Если отдельный результат не помещается в ограниченный ответ, ответ — RESULT_TOO_LARGE. Ответ одной записи — объект с полем event.

## NATS Services

NATS Service имеет имя service_history, предметную версию 1.0.0, уникальный ID экземпляра и queue group service_history. Он поддерживает PING, INFO и STATS. Это подтверждает обнаружение экземпляра; готовность требует успешных проверок PostgreSQL и NATS.

| Subject | Запрос | Успешный ответ | Эффект |
| --- | --- | --- | --- |
| brai.history.v1.append.<source> | appendRequest | appendResponse | Сохраняет событие или возвращает первоначальный результат повтора. |
| brai.history.v1.query.list | listRequest | listResponse | Читает ограниченную пользовательскую страницу. |
| brai.history.v1.query.get | getRequest | getResponse | Читает событие по (source,id) в пользовательской области. |

Endpoint `brai.history.v1.append.<source>` также принимает Core NATS publish без reply: проверяет и сохраняет тот же `appendRequest`, но отправитель не получает результата и не может считать публикацию подтверждением сохранения. Отсутствие reply не отклоняет запрос и не меняет проверки источника или данных. Режим применим к фактам, для которых источник допускает потерю и не обещает доставку.

Вход и успешный ответ — UTF-8 JSON без JSON-RPC envelope. Ответ направляется на нативный reply subject запроса; клиент не задаёт replyTo в теле. Ошибки передаются стандартными заголовками Nats-Service-Error (код ошибки) и Nats-Service-Error-Code (числовой HTTP-подобный статус); клиент проверяет их до чтения тела. Тело ошибки соответствует common.schema.json#/definitions/error и содержит code, безопасное message и retryable.

| Код | Статус | Значение |
| --- | ---: | --- |
| INVALID_ARGUMENT | 400 | Некорректный JSON, поля или сочетание полей. |
| INVALID_CURSOR | 400 | Курсор повреждён или не соответствует фильтрам/области. |
| NOT_FOUND | 404 | Событие отсутствует или скрыто областью доступа. |
| EVENT_ID_CONFLICT | 409 | (source,id) уже занят другим содержимым. |
| REQUEST_TOO_LARGE | 413 | Тело запроса или событие больше 65 536 байт. |
| RESULT_TOO_LARGE | 413 | Отдельный результат не помещается в ограниченный ответ. |
| BUSY | 503 | Одновременно заняты 8 операций и заполнена очередь из 64 запросов. |
| DATABASE_UNAVAILABLE | 503 | PostgreSQL не отвечает или отклонил соединение. |
| DEADLINE_EXCEEDED | 504 | Операция превысила 10 секунд. Для append результат может быть неизвестен; повтор безопасен только с тем же ID и тем же содержимым. |
| INTERNAL | 500 | Непредвиденная ошибка без раскрытия SQL, данных события или секретов. |

Запрос не превышает 65 536 байт, успешный ответ — 524 288 байт. Срок операции — 10 секунд; одновременно выполняются не более 8 операций, очередь — не более 64. Переполнение получает BUSY. При тайм-ауте ответ может завершиться до транзакции, но занятый слот удерживается до остановки SQL, чтобы не превысить предел параллелизма.

Для новых источников NATS request-reply сам по себе не подтверждает фиксацию события в чужой БД и не заменяет их гарантию доставки. Первый выпуск не вводит JetStream или outbox: собственный аудит сервиса записывается атомарно с изменением справочника.

При `HISTORY_GAME_CORE_EVENTS_ENABLED=true` сервис подключает durable consumer `history_game_core_events` к stream `BRAI_GAME_CORE_EVENTS_V1` и принимает envelope GameCore. Категория и тип разрешаются по `data.history_category_code` и `data.history_type_code` в собственном справочнике; числовые ID GameCore не передаёт. ACK следует после COMMIT. Повтор использует `(source=service_game_core,event_id)` и то же содержимое.

## Справочники и собственная история

Системные справочники находятся в таблицах sys_categories и sys_types. Префикс sys_ обозначает поставляемый сервисом системный каталог; коды строк сохраняют исходные семантические значения. ID, code и связь type с category имеют стабильную семантику и после создания не меняются. Имя и описание можно править через MCP; удаление запрещено. Миграция содержит исходный каталог и комментарии БД, атомарно добавляет отсутствующие строки и audit events, не перезаписывая имена, описания и новые строки. Несовпадение закреплённых ID/code/category завершает миграцию явной ошибкой.

Собственная история справочников записывается в той же транзакции, что и изменение. Новый audit event описывает исходный запрос и старые/новые значения; если аудит не сохранён, транзакция откатывается. Повтор миграции не создаёт повторные события аудита.

## Внутренний MCP

MCP работает через Streamable HTTP по /mcp на loopback или доверенной внутренней сети. Нет публичного маршрута, пользовательской авторизации или OAuth. Сервер проверяет Host и Origin, ограничивает число сессий конфигурацией и закрывает ресурсы при завершении. MCP роль имеет явный доступ читать все области и управлять двумя справочниками. actor_id в MCP — заявленное поле, а не удостоверенная личность агента. Инструменты вызывают те же прикладные операции; адаптер не вводит собственную бизнес-логику.

Входы и выходы MCP принадлежат schemas/tools.schema.json. Помимо десяти инструментов MCP предоставляет два read-only ресурса: brai://history/CONTRACT.md — документация сервиса; brai://history/schemas/common.schema.json — общие структуры и схема события. Успешный вызов инструмента возвращает owner DTO в structuredContent и content=[]. Ошибка имеет isError=true и единственный JSON-текст в content, соответствующий owner DTO {code,message,retryable}; structuredContent для ошибки отсутствует. Вызовы используют structured JSON output официального MCP SDK.

| Инструмент | Вход | Выход | Действие |
| --- | --- | --- | --- |
| history_categories_list | categoriesListRequest | categoriesListResponse | Постранично читает категории из БД. |
| history_types_list | typesListRequest | typesListResponse | Постранично читает типы, при необходимости по category_id. |
| history_type_get | typeGetRequest | typeGetResponse | Читает тип по ID. |
| history_append | appendRequest | appendResponse | Добавляет или идемпотентно повторяет событие. |
| history_get | getRequest | getResponse | Читает событие по (source,id) из любой области. |
| history_search | searchRequest | searchResponse | Ищет по фиксированным фильтрам и постранично читает события всех областей. |
| history_category_create | categoryCreateRequest | mutationResponse | Создаёт категорию и её аудит атомарно. |
| history_category_update | categoryUpdateRequest | mutationResponse | Меняет только имя и описание категории и записывает аудит. |
| history_type_create | typeCreateRequest | mutationResponse | Создаёт тип и его аудит атомарно. |
| history_type_update | typeUpdateRequest | mutationResponse | Меняет только имя и описание типа и записывает аудит. |

Входной JSON-RPC envelope ограничен 65 536 байтами; весь UTF-8 JSON-RPC response envelope — 524 288 байтами. Общий предел 10 секунд отсчитывается от начала HTTP-запроса и включает чтение тела, ожидание места в очереди и выполнение ядра. Общий предел нагрузки: 8 активных операций и очередь до 64; слот остаётся занятым до остановки SQL даже после deadline.

Изменение справочника принимает стабильный event_id и необязательный заявленный actor_id. Отсутствующий actor_id нормализуется в null. Audit data имеет точную форму {operation, request, old, new, result}: operation — имя одного из четырёх MCP инструментов изменения; request — нормализованный вход вместе с event_id и actor_id; old равен null при создании и прежней записи при изменении; new — сохранённая запись после операции; result — исходный результат операции (созданная/изменённая категория или тип). Повтор того же event_id, operation и нормализованного request возвращает первоначальный result без второго изменения; иной запрос или операция с тем же ID даёт EVENT_ID_CONFLICT. Для проверки используется существующая запись аудита; отдельной таблицы команд нет. Ответ mutation содержит {result, audit_event}; при replay audit_event — та же исходная audit запись. Код, ID и категория созданного типа неизменяемы; удаления нет. Если аудит не сохранён, изменение откатывается.

События аудита имеют source=service_history, область system/service_history, type_id=101 для create и type_id=102 для update. Событие create/update с одинаковым event_id различается именем операции, поэтому replay сверяет его вместе с исходным запросом. Для категории используется object_type=sys_categories, для типа — object_type=sys_types; object_id равен строковой форме ID записи. Результат повтора принимается только при совпадении source, scope, type_id, object и исходного запроса в audit data. Запрос общего append для пары source/object_type выше отклоняется, чтобы не подменить маркер или содержимое аудита. Начальные строки и их аудит создаёт миграция атомарно; её повтор не добавляет новые audit events.

## Граница, роли и восстановление

Поток web начинается с BetterAuth в web: сервер передаёт проверенный user_id через NATS, ядро вызывает PostgreSQL-адаптер с веб-ролью, а RLS ограничивает транзакцию этим пользователем. Внутренний MCP передаёт запросы тому же ядру через отдельный app-пул; чтение доступно по всем областям, а изменение каталога и его аудит проходят в одной транзакции.

Отдельный владелец БД запускает миграции и не входит в runtime; HISTORY_OWNER_ROLE должен совпадать с владельцем целевой БД. App и web — разные роли без SUPERUSER, CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS, членства в других ролях и владения таблицами history или public. App-роль не может выполнять DDL, менять или очищать events; запись в системные справочники ограничена разрешёнными полями. Web-роль имеет только чтение событий с RLS и получает user_id локально внутри транзакции. Приложение не хранит owner credentials.

Секрет HMAC курсора передаётся через HISTORY_CURSOR_HMAC_KEY_FILE и должен оставаться прежним после выпуска и восстановления: смена ключа делает уже выданные курсоры недействительными. Значения секретов не попадают в логи. Порядок сборки, запуска, резервного копирования и восстановления описан в [DEPLOYMENT.md](DEPLOYMENT.md). Запуск процесса не применяет миграции. Откат образа не удаляет БД и не очищает историю; восстановление БД и стабильного ключа выполняют отдельно по эксплуатационной процедуре.

Переход на game-core выполняется при остановленных производителях и потребителях. Миграция владельца сохраняет UUID и данные: ожидающие outbox-события получают новый subject, History и Alerts — источник `service_game_core`; отметки прочтения сохраняются. Конфликт идентичности прерывает транзакцию. До запуска нового транспорта оператор переносит сохранённые JetStream-события; повторная доставка использует прежние UUID.
