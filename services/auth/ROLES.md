# Роли и применение доступа

Auth — единственный владелец назначенной роли. `IdentityUser.role` принимает `creator`, `admin`, `user`, `guest`; неизвестное значение запрещает доступ. Миграция расширяет ограничение без изменения существующих ролей, userId, profileId и аккаунтов. Нулевое число creator допустимо.

| Операция | creator | admin | user | guest |
| --- | --- | --- | --- | --- |
| Личные диалоги, память, собственные артефакты | Да | Да | Да | Да |
| Веб-вход | Да | Да | Да | Нет |
| Прежние административные операции продукта | Да | Да | Нет | Нет |
| Приглашения user/guest | Да | Да | Нет | Нет |
| Назначить admin/user/guest | Да | Кроме изменения creator | Нет | Нет |
| Назначить или изменить creator | Да | Нет | Нет | Нет |

Первый владелец по умолчанию admin. Защищённый owner-bootstrap JSON может явно содержать `role:"creator"`. Для ранее настроенного владельца нужны те же подтверждённые идентификаторы и отсутствие другого creator; переход ставится в lifecycle с неизменным операторским requestId. Сетевой identity-provision не назначает creator/guest; новые гости проходят очередь приглашения или users-add. Восстановление сохраняет роль, а явный конфликт users-add возвращает `ROLE_CONFLICT`.

`invite-create` и `users-add` принимают необязательную роль user/guest; отсутствие означает user для нового профиля. Роль хранится в приглашении и не принимается при его погашении. Повтор погашения использует текущую учётную запись, не отменяя административное решение.

## Смена роли

`role-set({userId,role,requestId?})` возвращает `{user,operation}`. Для надёжного повтора нужен стабильный requestId. Существующая очередь prepare/stop, аренда и порядок блокировок не меняются. Повтор прежних параметров возвращает ту же операцию; конфликт даёт `REQUEST_CONFLICT`. Аудит хранит автора, цель, old_role/new_role, requestId и generation без содержимого пользователя.

applied_generation фиксирует подтверждённое поколение runtime. No-op сохраняет его, хотя журнал и сессии переходят в новое lifecycle_generation. Bootstrap связывается с конкретной подготовленной ролью и поколением.

Новая операция повышает lifecycle_generation, отменяет прежнюю pending/running работу, отзывает коды, команды привязки и несовместимые сессии. Обычный профиль переходит в provisioning до подтверждения worker. Единственный управляющий защищён по совокупности creator/admin. Переход между управляющими ролями сохраняет active-управление и действующие сессии, переводя их в новое поколение; личный runtime перестраивается отдельно. Admin не изменяет creator также через users-add, статус и отзыв сессий.

Worker с `rolePolicyVersion:1` получает новые операции. Старый worker их не захватывает. Новый worker подтверждает фиксированную JSON-квитанцию установщика с версией политики и ролью; пустой ответ старого установщика не считается успехом. Только актуальные generation/lease завершают операцию. Failed остаётся видимым и требует новой административной попытки; неизвестный исход сначала сверяют по requestId.

Коды Telegram, существующие cookie и SSO сверяют active-роль creator/admin/user и поколение. В email-режиме обычные аккаунты без identity сохраняют прежний вход. Для привязанного профиля действуют те же ограничения; поколение email OTP захватывается до вызова официального движка и условно подтверждается после создания сессии. Понижение и последующее повышение не оживляют старые credentials.

## Порядок совместимого обновления

1. Подготовить новый установщик и поддерживающие политику readonly runtime assets. Не назначать новые роли старым потребителям.
2. Применить расширяющую миграцию Auth; сохранить существующие данные и роли.
3. Установить согласованные Auth, Hermes и Web из принятого состава. Проверить policy version, каталог и прямой dispatch до назначения guest.
4. Роли применять очередью с проверкой остановки старого worker/browser и потомков. Сначала запрещаются прежние вызовы, затем готовится новый профиль, и только после подтверждения открывается доступ.
5. При сбое оставить provisioning/blocked и failed-операцию. Восстановить совместимую поставку и повторить с новым requestId после сверки. Откат на runtime без гостевой политики не открывает гостю исполнение; старые сессии и задания не восстанавливаются автоматически.

Роль не выдаёт root, системный Docker, исходники сервера или будущий исполнитель разработки. Установку контролирует lifecycle, а не текст пользователя. [Политика инструментов Hermes](../hermes/identity/ROLES.md).
