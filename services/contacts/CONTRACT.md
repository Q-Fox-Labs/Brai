# Контракт Контактов v1

Статус: согласованный целевой контракт от 31 октября 2026 года. Самостоятельный
сервис, миграции, машинные схемы и адаптер Приёма пока не реализованы.
Операции ниже описывают обязательства будущей реализации, а не действующие endpoints.
Сохранение контракта не разрешает выпуск или изменение рабочего Telegram.

Потребитель: [Приём](../intake/CONTRACT.md). Соседние границы:
[Каналы](../channels/CONTRACT.md), [Артефакты](../artifacts/CONTRACT.md),
[История](../history/CONTRACT.md).
AsyncAPI и JSON Schema Draft-07 добавляются при реализации у владельца;
потребители используют их как объявленную зависимость поставки без копирования
определений и импорта внутренней реализации Контактов.

## 1. Ответственность и идентичность

Контакты сопоставляют внешний аккаунт, хранят актуальный профиль и неизменяемый
результат наблюдения конкретного поступления. Контакт не является доказательством
того, что несколько внешних аккаунтов принадлежат одному человеку.

Ключ идентичности — (ownerId, namespace, externalId). В v1 namespace равен telegram,
externalId — Telegram User ID положительной десятичной строкой.

- Один Telegram User ID через разных ботов одного владельца получает один contactId.
- Разные владельцы получают отдельные контакты даже для одинакового Telegram ID.
- sourceId, бот, чат и тема описывают происхождение, но не входят в ключ идентичности.
- Имя, username и фотография не участвуют в сопоставлении.
- Поддерживается только namespace=telegram. Другой namespace отклоняется явно.
- Каждый новый внешний аккаунт создаёт отдельные контакт и идентичность атомарно.
  Присоединения произвольного аккаунта к существующему контакту в API v1 нет.
- Merge/split, перенос между владельцами, ручные псевдонимы, сущности людей и
  автоматическое объединение разных аккаунтов или платформ в v1 не входят.

Владелец данных, отправитель, инициатор и создатель материала различаются.
creatorRef из правил Каналов не заменяет фактического отправителя.
Автор ответа Hermes — агент; контакт исходного человека не становится его автором.
Инициатор может быть связан через исходное сообщение.

Контакты не вызывают Telegram, не хранят файлы или токены, не определяют канал,
не запускают ИИ и не владеют сценарием обработки сообщения. Самостоятельный сервис
состоит из одной программы Node.js/TypeScript с PostgreSQL и NATS Services.
Миграция запускается отдельно. Собственных Temporal worker, retry scheduler,
очереди доставки и фонового получения фотографий нет.

## 2. Транспорт, доверие и общие форматы

Целевой NATS Service: service_contacts, предметная версия 1.0.0, уникальный ID
экземпляра, queue group service_contacts, поддержка PING/INFO/STATS.
PING не подтверждает готовность PostgreSQL.

Subjects, кроме status: brai.contacts.v1.<operation>.<callerId>.
Реальная NATS identity получает только разрешённые subjects. Runtime binding
связывает callerId с операциями, ownerId и sourceId; суффикс и поля запроса
не создают полномочий. Запись требует разрешённых операции, владельца и источника.
Чтение требует явного разрешения на владельца. Дополнительный синхронный вызов
Каналов внутри Контактов не нужен: проверку источника и канала выполняет Приём.

Операции чтения не ограничиваются ботом, через который был впервые обнаружен
контакт: это нарушило бы единую Telegram-идентичность владельца. Доступ к чтению
контактов владельца выдаётся отдельно; право записи от одного источника само по
себе такого доступа не даёт.

Все DTO закрытые; неизвестные поля отклоняются. Секреты, raw updates, тексты
сообщений и байты файлов в контракт не входят.
Идентификаторы собственных сущностей и packetId — UUID. Сравнение UUID учитывает
эквивалентность регистра; новые ID возвращаются канонически. ownerId и
operationId — непустые строки до 255 символов; sourceId/callerId — строчная
латиница, цифры и _, начало с буквы, длина до 64. operationId Приёма для resolve
равен packetId + "/contact".

Время — RFC3339 с timezone, до 6 дробных знаков, ответы UTC. observedAt означает
время наблюдения доверенным вызывающим участником, не время завершения RPC.
Приём передаёт receivedAt своего зарегистрированного пакета. Для позднего
уточнения передаётся время соответствующего наблюдения.

Нормализованный запрос включает все поля предметной операции. Хеш — SHA-256
канонического JSON: рекурсивная сортировка ключей объектов, сохранение порядка
массивов, UTF-8 без дополнительных пробелов. Отсутствие и null различаются.
Времена нормализуются в UTC до хеширования. NUL, непарные суррогаты и не конечные
числа недопустимы.

Ошибка NATS Services передаётся заголовками Nats-Service-Error и
Nats-Service-Error-Code, тело — {code,message,retryable}.
Тексты безопасны: без SQL, профилей, содержимого пакетов, секретов и чужих данных.

## 3. Наблюдение и результат

Identity: {namespace:"telegram",externalId:string}.

ProfileObservation — объект только из наблюдавшихся полей:

| Поле | Значение |
| --- | --- |
| name | Непустая строка до 255 символов или null |
| username | Непустая строка до 255 символов или null |
| photoArtifactId | UUID или null |

Пустое наблюдение допустимо для resolve: устойчивая идентичность достаточна,
чтобы создать или найти контакт. profile.observe требует хотя бы одно поле.
Строки профиля не участвуют в сопоставлении и не приводятся к другому регистру.

Отсутствующее поле означает «не наблюдалось»: актуальное значение не меняется.
Явный null означает подтверждённое отсутствие и может очистить актуальное значение.
Ошибка получения фотографии не является наблюдением отсутствия.

Snapshot: {name:string|null,username:string|null,photoArtifactId:UUID|null,
observedFields:массив name/username/photoArtifactId без повторов}.
observedFields возвращается в порядке name, username, photoArtifactId.
Внешняя идентичность всегда присутствует рядом в обязательном identity.
Значение не наблюдавшегося поля — null, но его нет в observedFields.
Наблюдённый null также равен null, а поле входит в observedFields.

ContactResolution имеет ровно поля:
contactResolutionId, operationId, packetId, ownerId, sourceId, observedAt,
contactId, identityId, identity, senderSnapshot, historyEvents.

senderSnapshot строится только из данного наблюдения. Актуальные значения,
известные по другим сообщениям, в него не подставляются. Поэтому поздний пакет
может иметь старое имя в собственном снимке, не откатывая актуальный профиль.

ProfileObservationReceipt имеет ровно поля:
operationId, ownerId, sourceId, observedAt, contactId, identityId, identity,
profile, changedFields, committedAt, historyEvents.
profile — первоначальное наблюдение, changedFields — действительно изменённые
значения актуального профиля в том же фиксированном порядке полей.

Contact: {id,ownerId,createdAt,identities:[CurrentIdentity]}.
CurrentIdentity содержит id, contactId, ownerId, namespace, externalId,
name, username, photoArtifactId, fieldOrigins, firstObservedAt, lastObservedAt.
fieldOrigins содержит для каждого известного поля его observedAt, sourceId,
callerId и operationId; отсутствие наблюдения представлено null.
Явно наблюдённый null имеет происхождение, как любое другое значение.

## 4. Операции

Во всех строках subject начинается с brai.contacts.v1.
Все поля запросов обязательны, кроме явно помеченных.

| Операция / suffix | Запрос | Результат и эффект |
| --- | --- | --- |
| resolve.<callerId> | {operationId,packetId,ownerId,sourceId,identity,observedAt,profile} | ContactResolution; создать/найти контакт, применить наблюдение, сохранить первоначальный результат |
| profile.observe.<callerId> | {operationId,ownerId,sourceId,identity,observedAt,profile} | ProfileObservationReceipt; обновить уже известную идентичность без создания контакта |
| contacts.get.<callerId> | {ownerId,contactId} | Contact с актуальным профилем; чужое/отсутствующее — NOT_FOUND |
| contacts.list.<callerId> | {ownerId,namespace?:string,externalId?:string,limit?:integer=50,cursor?:string|null=null} | {items:[Contact],nextCursor:string|null} |
| operations.get.<callerId> | {ownerId,operationId} | {operation:"resolve" или "profile.observe",result:первоначальный результат}; только операция того же caller |
| status | {} | {ready:boolean,database:boolean,configuration:boolean,contractVersion:"1"} |

profile.observe неизвестной идентичности возвращает NOT_FOUND без создания записи.
Для list externalId разрешён только вместе с namespace. Фильтр namespace также
принимает только telegram. Других фильтров, fuzzy-поиска и поиска по username нет.

limit — 1..100. Сортировка — по стабильному id контакта. Непрозрачный HMAC-курсор
связан с caller, владельцем, нормализованными фильтрами и последним возвращённым
ID. Ключ HMAC стабилен после перезапуска и восстановления. Cursor не является
полномочием, не переносится в другой scope и не обещает снимок всех страниц.
При достижении предела ответа страница уменьшается без пропуска элементов.

## 5. Транзакции, повторы и порядок наблюдений

Общий ключ обеих изменяющих операций — (callerId,ownerId,operationId).
После проверки текущих полномочий точный повтор возвращает первоначальный
сохранённый результат. Другой запрос или вид операции с прежним ключом даёт
REQUEST_ID_CONFLICT. Права проверяются и при повторе. operations.get не даёт
доступ к квитанциям другого caller.

Изменение контакта, идентичности, профиля, первоначальный результат и готовые
факты Истории сохраняются одной транзакцией. Ошибка до COMMIT не оставляет
частично принятой операции. Потеря ответа после COMMIT разрешается повтором
того же запроса с прежним ключом, а не созданием нового operationId.

БД защищает уникальность (owner_id,namespace,external_id).
Конкурентные первые поступления создают ровно один контакт и идентичность.
Транзакционные блокировки берутся сначала по ключу операции, затем по ключу
идентичности; операция затрагивает одну идентичность.

Актуальные поля выбираются независимо. Побеждает большее observedAt; при
равенстве — лексикографически большее (sourceId,callerId,operationId), сравнение
строк по UTF-8 байтам, без locale-зависимого порядка. Окончание RPC не влияет
на выбор. Даже если наблюдение старее, его собственный результат сохраняется.
firstObservedAt — минимум времени принятых наблюдений, lastObservedAt — максимум.

Если победившее наблюдение подтвердило прежнее значение, обновляется происхождение,
но это не считается изменением значения и не создаёт update-факт Истории.
Не наблюдавшиеся ранее поля остаются null с null-происхождением.

## 6. Хранилище и роли

Собственная схема contacts, три таблицы:

| Таблица | Поля и назначение |
| --- | --- |
| contacts | id, owner_id, created_at; устойчивая запись контакта |
| contact_identities | id, owner_id, contact_id, namespace, external_id; актуальные name, username, photo_artifact_id; field_origins, first_observed_at, last_observed_at |
| contact_operations | caller_id, owner_id, operation_id, operation, input_hash, request, result, committed_at, history_events; неизменяемое наблюдение и первоначальная квитанция |

Имена SQL-полей и их ограничения закрепляются миграцией владельца; DTO не зависят
от внутреннего SQL. Таблицы и колонки получают комментарии PostgreSQL.
Внутренние связи защищены FK, принадлежность идентичности владельцу контакта
проверяется БД. Внешних FK на таблицы Приёма, Артефактов или Истории нет.

Полных версий профиля, таблицы очереди, отдельного журнала повторов и справочника
типов каналов нет. Актуальный профиль — изменяемая проекция наблюдений;
исторические операции — неизменяемые записи. Приём и будущие Входящие дополнительно
сохраняют снимок отправителя рядом с поступлением.

Миграции выполняет отдельная owner-роль. Runtime получает только необходимые
чтение/вставку и обновление актуальной проекции; не может менять существующие
контакты, принадлежность и внешний ключ идентичности, квитанции, выполнять DDL
или удалять данные. Физического удаления и автоматической очистки в v1 нет.
Owner credentials не входят в runtime.

## 7. Фотография и связь с Приёмом

Контакты принимают только непрозрачный artifact ID, без Telegram file ID, URL,
токена, файлового пути или байтов. Вызывающий участник передаёт только проверенный
готовый артефакт того же владельца. Контакты не проверяют файл скачиванием и не
создают обязательного синхронного вызова Артефактов.

Приём готовит и сохраняет ContactRequest до RPC:
1. Берёт подтверждённые identity/source/owner и receivedAt пакета после Каналов.
2. Подготавливает необязательную ссылку фотографии через API Артефактов.
3. Если фото недоступно, не добавляет photoArtifactId в наблюдение; сохраняет
   диагностический результат подготовки и не задерживает сообщение.
4. Сохраняет неизменяемый запрос; все повторы используют его без повторного
   выбора доступных полей по текущему состоянию соседей.

Неподтверждённая ссылка не попадает в проверенное представление отправителя.
Оригинал пакета не переписывается. Ошибка не превращается в photoArtifactId=null.
Проверка аватара выводится из обязательной подготовки файлов сообщения.

Позднее фото передаётся отдельным profile.observe с собственным operationId
и временем наблюдения. Снимки прежних сообщений не меняются. Автоматическое
получение фото из Telegram и его запуск относятся к последующему этапу адаптера.

Приём заменяет общий contact-конверт узким ResolveRequest по схеме владельца.
Принимая результат, проверяет структуру и пределы, все UUID, packetId, ownerId,
sourceId, identity, observedAt и точное соответствие снимка сохранённому наблюдению.
Сохраняет полный ContactResolution неизменяемо, затем передаёт отдельно от
оригинала в prepared вместе с каналом, assignments и fieldOrigins.

Старые неполные contact-контексты не дополняются нынешним профилем: несовместимое
продолжение явно останавливается. В диагностике сохраняется безопасный предметный
код ошибки. Временные ошибки повторяет существующая Activity Temporal.
Ответ агента и generic event.recorded не получают обязательного вызова Контактов.
Граф workflow и фиксированные message-сценарии этим этапом не расширяются.

## 8. История

Источник фактов — service_contacts, область — user соответствующего ownerId.
Используются существующие типы 101 create и 102 update категории object.
На создание контакта с первой идентичностью формируется один create-факт;
на фактическое изменение профиля существующего контакта — один update-факт.
Повтор, чтение, неизменившиеся значения и проигравшее старое наблюдение
не создают дополнительных фактов.

Факт содержит постоянный ID, время принятого изменения, ссылки на контакт/
идентичность/операцию и имена изменённых полей. Значения name, username и фото
в аудит не копируются. Сам результат resolve может содержать профиль:
его наличие не означает разрешения выводить payload в технический журнал.

historyEvents — массив готовых append-запросов по контракту Истории.
Subject доставки: brai.history.v1.append.service_contacts; source определяется
транспортной привязкой, не полем append body. ID, время и содержимое факта
создаются вместе с квитанцией и при повторе не пересобираются.

COMMIT Контактов не подтверждает доставку в Историю. Вызывающий долговечный
сценарий обязан доставить факты с исходными ID/содержимым. В связке с Приёмом
это делает существующая Activity подготовки: сохраняет ContactResolution, затем
доставляет его факты до зависимых шагов. Потеря ответа Истории повторяется с тем
же ID. Отдельные NATS credentials/ACL разрешают публикацию от service_contacts.
Произвольному producer это право не выдаётся.

Другой вызывающий profile.observe также обязан иметь долговечный координатор;
простой одноразовый publish не обеспечивает гарантию. Собственный outbox или
административный координатор доставки внутри Контактов в v1 не добавляется.

## 9. Ошибки и пределы ресурсов

| Код | NATS код | retryable | Условие |
| --- | --- | --- | --- |
| INVALID_REQUEST | 400 | false | Неверные поля, типы, значения или сочетания |
| UNSUPPORTED_NAMESPACE | 400 | false | Профиль идентичности не поддерживается |
| FORBIDDEN | 403 | false | Caller не разрешены операция, владелец или источник |
| NOT_FOUND | 404 | false | Доступная сущность или операция не найдена |
| REQUEST_ID_CONFLICT | 409 | false | Ключ уже принят с другим запросом/операцией |
| INVALID_CURSOR | 400 | false | Курсор повреждён или не соответствует области/фильтрам |
| REQUEST_TOO_LARGE | 413 | false | Запрос превышает предел |
| RESULT_TOO_LARGE | 413 | false | Один результат не помещается в предел |
| BUSY | 503 | true | Заняты все активные слоты |
| DATABASE_UNAVAILABLE | 503 | true | БД или соединение недоступны |
| DEADLINE_EXCEEDED | 504 | true | Истёк срок, результат COMMIT может быть неизвестен |
| INTERNAL | 500 | false | Непредвиденная ошибка без раскрытия внутренних данных |

Запрос — до 65 536 байт UTF-8 JSON, успешный ответ — до 131 072 байт.
Активных операций — до 8, пул PostgreSQL — до 4 соединений.
Дополнительной прикладной очереди ожидания нет: переполнение возвращает BUSY.
Общий deadline — 5 секунд, включая ожидание соединения; SQL получает оставшийся
срок. После timeout слот удерживается до прекращения SQL и освобождения ресурсов.
Потеря БД не должна завершать процесс необработанным событием ошибки клиента.

## 10. Совместимость и приёмка

В v1 сохраняются неизменяемые оригиналы поступлений и результаты прежних операций.
Никакое обновление профиля не является пересчётом старого senderSnapshot.
Наличие контракта не меняет текущий generic contact port Приёма: переход
выполняется отдельной реализацией и общей проверкой.

Приёмка требует реальных PostgreSQL/NATS и процесса Контактов, минимальных прав,
конкурентного create/resolve, проверки порядка наблюдений, повтора после COMMIT,
отказов и сроков. Общая изолированная цепочка использует реальные Приём, Каналы,
Контакты, Temporal и API Артефактов/Истории; отсутствующие получатели остаются
тестовыми. Контакты также запускаются без Приёма, Temporal и Telegram.

После реализации необходимы независимая проверка, успешные упаковка/CI и отдельное
подтверждение уборки стенда. Подготовка роли и рецептов не включает компонент
в действующий установочный состав. Живой Telegram остаётся на прежнем пути;
выпуск возможен только позднее в составе принятого полного комплекта.
