# Измерение ресурсов local-ai

`observe.py` — source-only Linux `/proc` observer для будущего узко ограниченного запуска через Ansible 5. Он принимает явные PID лидера, PGID, `starttime` лидера в ticks, длительность окна и интервал. Лидер обязан быть отдельной session (`pid == pgid == sid`), а переданный `starttime` должен совпасть до начала сбора. Wrapper снимает starttime с непосредственного дочернего PID сразу после собственного spawn и передаёт его явно. Наблюдатель перечисляет numeric procfs entries только для отбора точного заданного PGID/session; посторонние строки не сохраняет и не выдаёт. Он прекращает учитывать PGID, когда в нём больше нет ранее подтверждённой пары PID+starttime. PID reuse не продолжает старую CPU дельту. Потомок, который намеренно покинул process group, сюда не попадёт; Ansible wrapper должен исключить detach либо применить отдельный cgroup v2 сбор.

Запуск ничего не создаёт, не посылает сигналов и не завершает процессы. Он не читает command line, environment, stdout/stderr, модели, аудио или пользовательский текст. В отчёт попадают только PID/starttime участников, process/thread counts, sampled RSS, CPU ticks, интервалы и агрегаты. Длительность ограничена 0.1–300 секунд, интервал — 50–5000 ms, procfs scan и число отчётных identity тоже имеют верхние пределы. При deadline наблюдатель возвращает уже собранные образцы с `terminationReason=deadline_reached`; это не доказывает завершение группы. Владелец Ansible отдельно обязан выполнить ограниченную очистку своей группы: проверить исходную PID/starttime identity, отправить TERM только своей выделенной группе, ждать в пределах резерва, затем при необходимости KILL той же проверенной группе и отдельно подтвердить её исчезновение. Наблюдатель сам не выполняет cleanup.

`aggregateSampledRssBytes` — сумма RSS всех видимых процессов группы в каждом снимке, а `peakAggregateSampledRssBytes` — максимум только среди этих снимков. Это не kernel high-water mark и не физически уникальная память: общие страницы могут считаться несколько раз, а короткие пики между снимками могут быть пропущены. CPU delta складывает только изменения `utime + stime` для той же пары PID+starttime между соседними снимками. Первый снимок задаёт baseline; первый и последний неполные интервалы и процессы, исчезнувшие между снимками, могут не попасть в delta. Process/thread counts — значения `/proc` на последовательном обходе, а не атомарный системный snapshot. Члены, остановленные как zombie, могут оставаться в count до того, как их reaper соберёт.

`resource-report.schema.json` описывает только фактические измерения. Observer не генерирует рекомендуемые production limits, profile или вывод о приемлемости. Значения `threads=4`, текущие timeout/decode параметры и прежние parent-only RSS receipts не являются whole-group ресурсными пределами. Short GigaAM уже показал parent-only sampled RSS 1,923,850,240 и 1,924,022,272 bytes; эти числа нельзя переименовывать в group RSS или kernel peak. Longform и clean baseline ещё не измерялись; принимаемые профили остаются `null` до реальных групповых receipts, host-condition записи, ревью и freeze.

Для полного accounting кратковременных children Ansible 5 может отдельно подготовить одну transient, выделенную cgroup v2 на каждый запуск до старта runner/FFmpeg. Подготовка должна подтвердить unified cgroup v2 и активные `memory` и `cpu` controllers; создать новый пустой systemd scope с accounting этих controllers; запустить runner, FFmpeg и всех детей внутри scope; зафиксировать точный cgroup path из принадлежащего Ansible unit/scope; и проверить, что в scope нет чужих процессов. Отдельный optional read-only helper получает только этот path, проверяет его каноническое расположение внутри `/sys/fs/cgroup` и открывает только `memory.peak` и `cpu.stat` через проверенную границу, сохраняя `memory.peak` bytes и `usage_usec`. Требуются отдельные права чтения; observer выше cgroup не создаёт и не меняет, не пишет в control files и не читает произвольные cgroup-файлы. `memory.peak` на свежем пустом scope даёт kernel high-water для этой cgroup, `cpu.stat usage_usec` — суммарное CPU usage её процессов; эти поля могут появиться в evidence только после такого отдельного Ansible-подготовленного сбора. Без него отчёт остаётся sampled process-group evidence с описанными ограничениями.

Локальные stdlib-проверки запускаются из каталога runner:

```sh
python3 -m unittest discover -s services/local-ai/runners/resources -p 'test_*.py'
```

Тесты используют synthetic procfs fixture и только свои короткоживущие child processes с отдельной process group и bounded cleanup. Они не загружают модели и не изменяют серверные cgroups.
