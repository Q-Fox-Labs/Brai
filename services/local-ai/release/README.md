# Подготовка portable image context

`prepare-portable-runtime.py` — source candidate для Ansible-подготовителя runtime inventory из уже существующих roots. Он проверяет точный Node 24.22.1, 98-пакетную CPU closure по product lock, pinned llama OCI manifest и FFmpeg package version; материализует CPython 3.12.3, stdlib/lib-dynload, relocatable venv site-packages, Node executable и production-only Node dependency closure, llama app/system и `ffmpeg`/`ffprobe`. Парсер lock учитывает extras в именах requirements, включая `fsspec[http]`, как обычную запись пакета `fsspec`. Разрешённые worktree package symlinks разворачиваются только из общего Brai dependency store после сверки lock version. Для ELF объектов он использует `ldd`, отвергает неразрешённые зависимости и конфликтующие SONAME, а glibc/loader из host не упаковывает: они должны прийти из закреплённой Ubuntu 24.04 base. Из TorchCodec wheel сохраняются все locked bytes, но ABI closure проверяется только для трёх FFmpeg-6 библиотек; девять fallback-библиотек FFmpeg 4/5/7 остаются учтёнными, но не активируются. Из контекста исключаются точные scipy/pyannote test audio и неиспользуемые vision metric weights. Пять файлов SentencePiece data и `distutils-precedence.pth` разрешены только по полному пути, размеру и SHA-256. Выходной manifest хранит source/destination, размер, режим и SHA-256 каждого файла и исключённого asset, а также active/inactive TorchCodec ELF, связывая их с source revision, lock, base и llama image. Llama extraction manifest проверяется отдельно и не включается в image payload. Не запускайте producer до отдельного Ansible review; этот код пока не проверен на prepared host inputs и не доказывает ABI в image.

`prepare-image-context.py` — product-owned сборщик Docker-контекста. Его вызывает отдельный Ansible playbook после подготовки входов; он не устанавливает пакеты, не загружает данные и не запускает Docker. Он требует чистый checkout на полном `HEAD`, компилирует TypeScript из этого checkout в staging locked TypeScript 5.9.3 и проверяет runtime inventory, четыре model source files; затем создаёт dynamic-module cache из локального model snapshot через managed CPU venv в offline-режиме. Выходной каталог должен отсутствовать. Он содержит копии трёх release-файлов, `payload/app`, `payload/runtime`, `payload/hf-modules-cache`, SHA-256 inventory payload и provenance inventory.

Ansible передаёт полный Git revision, portable runtime root, приватный staging-каталог и канонический GigaAM model directory. Runtime inventory имеет поля `sourceRevision`, `pythonLockSha256`, `llamaImage`, `cachePythonExecutable` и массив `files`. Каждый элемент массива задаёт `source` внутри runtime root и канонический `destination` в контексте, а также `bytes`, `sha256` и `mode`; provenance индексируется исходным runtime-путём. Fixture прогоняет именно этот producer/consumer переход через context verifier. В context builder разрешены назначения только внутри runtime, `app/services/local-ai/node_modules` и отдельно создаваемого HF module cache. Симлинки, абсолютные и выходящие за root пути, неизвестные destinations, несовпадения хеша/размера/режима и повторный output path отклоняются. Инвентарь должен покрывать Node production dependency closure, Python interpreter/stdlib/venv/libs, FFmpeg и pinned llama app/system; каждый файл переносится обычной копией.

Context builder сам вызывает `prepare-transformers-cache.py` через `cachePythonExecutable`, используя только CPU venv, локальный четырёхфайловый model snapshot и offline flags. Cache генерируется в staging-каталоге image context; credentials удаляются из окружения, а HF Hub и Transformers переводятся в offline режим. Шаг копирует только dynamic Python source, не исполняет модель и не включает веса в образ. `verify-image-context.py` сверяет полный набор payload-файлов, SHA inventory, source revision и отсутствие model/audio/credential artifacts перед Docker build.

Portable runtime inventory обязан быть создан подготовителем на той же Ubuntu 24.04 / glibc 2.39 ABI и привязан к тому же source revision. Для Native Audio closure активны только точные TorchCodec и `torio` FFmpeg-6 библиотеки; fallback-версии остаются в payload и inventory, но не входят в ABI closure. У torchaudio сохраняются и хешируются два core ELF и отдельная lazy SoX-пара; SoX backend намеренно не активируется, так как требует отсутствующую `libsox.so`, тогда как продуктовые аудиопути декодируют через FFmpeg/TorchCodec. Runtime factory должен явно передать дочернему процессу `LD_LIBRARY_PATH` с `runtime/system-libs`, `runtime/python/lib`, `runtime/python/lib/python3.12/lib-dynload`, `runtime/gigaam_pytorch/.venv/lib/python3.12/site-packages/torch/lib`, `.../torchcodec`, `.../torio/lib`, `.../torchaudio/lib` и закреплёнными llama `app`/`system`; он также задаёт приватные `HOME`, `HF_HOME`, `HF_MODULES_CACHE` и временные каталоги. ELF preflight использует общий 60-секундный deadline на весь активный набор и после его истечения не запускает следующие проверки. До отдельной проверки relocation нельзя считать host venv или `ldd` host closure достаточным доказательством переносимости. Подготовитель также обязан отвергать `.env`, credentials, audio/test fixtures, внешние модели и неразрешённые пакеты. Этот контекстный сборщик сверяет входной inventory, но не доказывает импорт Python в готовом image или runtime acceptance.
