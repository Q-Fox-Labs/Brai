# Теневое подключение Приёма v1

Дата: 1 ноября 2026 года. Статус: закреплённый целевой контракт, НЕ реализован.
Это дополнение к [действующему контракту](CONTRACT.md), не описание готового API.
Код, DTO и схемы этого дополнения вводятся будущей реализацией вместе.
Выпуск и включение рабочего DEV сейчас не разрешены.

## 1. Смысл этапа

Приём, Каналы и Контакты обрабатывают копии реальных событий независимо от Hermes.
Hermes сам принимает сообщения, сохраняет файлы, выполняет ход, транскрибирует
нужное аудио и отправляет потоковые ответы прежним способом.
Теневой контур не может вызвать ход или отправку и не управляет правами Hermes.

Остановка любого нового сервиса, worker, БД, NATS или Temporal не должна
менять поведение gateway. Общие CPU, RAM, диск и БД не дают физической гарантии
нулевого влияния: ресурсы фоновой ветки ограничивают и измеряют до включения.

Не требуются Входящие, Понимание, их память, тестовые получатели или пустые
успешные задания. Текущий полный intakeMessageV1 не используется для копий
и не изменяет свою семантику завершения.

## 2. Владельцы и поток

~~~mermaid
flowchart TD
    TG[Telegram] <-->|Без изменений, включая streaming| H[Hermes]
    H -.-> O[Hermes: ограниченный захват и свой журнал]
    O --> E[Hermes: отдельный экспортёр]
    E --> JS[JetStream]
    JS --> I[Приём: регистрация копии]
    I --> W[Temporal: intakeObservationV1]
    W --> C[Каналы: настоящий resolve]
    W --> K[Контакты: настоящий resolve для человека]
    W --> A[Артефакты: проверка готовых ID]
    W --> HI[История: факты регистрации и Контактов]
    W --> R[Сохранённый результат наблюдения]
~~~

Исходные события и их экспорт принадлежат
[Hermes observer](../hermes/telegram/observer/SHADOW_CONTRACT.md).
Приём не читает SQLite Hermes. Каналы и Контакты доступны только по их API,
схемы владельцев используются без runtime-импортов и без копирования DTO.
Байты файлов не передаются через JetStream или Temporal.

## 3. Вход и доверие

Добавляется тип Event v1 message.observed. Это отдельный вариант схемы Приёма;
действующий runtime пока его не принимает. Нет флага shadow в пользовательском
message.incoming/outgoing, способного изменить способ исполнения.

| Поле Event | Смысл |
| --- | --- |
| version | 1 |
| eventId | Строковый Observation.id, неизменный при публикации/повторе |
| source | Доверенный sourceId экспортёра, совпадает с ingress suffix |
| type | message.observed |
| occurredAt | Сохранённый observedAt исходного наблюдения |
| correlationId | Observation.conversationId |
| causationId | null; внешняя origin-ссылка находится внутри Observation |
| data | Закрытый объект {observation:Observation} по схеме Hermes |

Observation и пределы захвата определяет владелец Hermes. Поставка Приёма включает
только необходимую схему владельца. Приём дополнительно проверяет согласованность
direction/source binding, id/eventId, observedAt/occurredAt, conversationId/
correlationId, целостность origin и валидность JSON. Unknown fields запрещены.
Размер окончательного Event — не более 128 KiB UTF-8.

У input- и output-источников отдельные NATS identities и allowlist типов,
ограниченная роль direction=incoming/outgoing, owner из защищённой конфигурации.
NATS ACL ограничивает subjects, а тип payload и direction проверяет Приём.
Для этих source bindings запрещены message.incoming, message.outgoing,
operation.result и processing.resume; ACL дополнительно запрещает dispatch. Подмена source/owner/бота/направления отвергается.

Подключение Каналов связывается с input sourceId бота; producer ответов получает
явное replySourceIds разрешение. Нельзя создать второй channel connection того же
бота ради теневого режима. При первом заведении готовят настоящий адрес и правила
выбранного DEV-маршрута до границы включения наблюдения. Нет wildcard, автосоздания
каналов или автоматического расширения human allowlist.

Неподдерживаемое/повреждённое событие сохраняет безопасный rejection до ACK,
по общему контракту Приёма. Оно не перенаправляется в активный сценарий.

## 4. Регистрация и самостоятельный Temporal-сценарий

Для нового типа неизменяемо фиксируются mode=temporal, scenario=observe.v1,
executionProfile=shadow.v1, оригинал Observation, receivedAt брокера, source,
owner и hash всего Event. Материал идентифицируется epoch/logicalId; revision
берётся из наблюдения. Точный source/eventId/hash возвращает прежний пакет,
иной JSON с тем же ключом — EVENT_ID_CONFLICT.

Первый запуск создаёт intakeObservationV1, workflow ID intake/observation/v1/packetId,
в отдельной task queue и отдельном worker entrypoint. ACK ingress следует за
подтверждённым запуском. Разрыв COMMIT/start и потеря ACK восстанавливаются прежним
механизмом JetStream. Existing intakeMessageV1 и его пакеты не переписываются.
Копия не может сменить профиль после рестарта, изменения config или отключения.

Шаги intakeObservationV1:

1. Сохранить receive-факт регистрации 1105 в независимой ветке Истории.
2. Разрешить назначение через настоящие Каналы.
3. Для human incoming сохранить ContactRequest до вызова, получить настоящий
   ContactResolution. Для agent outgoing контакт не создаётся.
4. Проверить готовые artifact IDs по owner/ready; необязательное фото —
   по тем же правилам, что у действующего Приёма.
5. Сохранить неизменяемые snapshots и результат проверки.
6. Доставить сохранённые Contact historyEvents через настоящий API Истории;
   повтор использует прежние UUID/JSON и полную owner appendResponse валидацию.
7. После успешных обязательных шагов закончить state=observed.

Нормализация запроса Каналов переводит incoming/outgoing Observation в
eventType=message.incoming/message.outgoing и direction владельца. mode/scenario
Resolution проверяются относительно этого направления, а не observe.v1.
Схема Resolution не расширяется. Вход передаёт только факты текста/модальностей,
источник, автора и sourceRef; байтов, текста и произвольных hints в Каналах нет.

У outgoing Приём сопоставляет origin={epoch,id} с собственным входным пакетом
того же owner/подключения. Input source определяется доверенной связью бота.
Пакет может прийти раньше обработки входа: временная неготовность его Resolution
повторяется. Связь сохраняется отдельно от immutable original как originPacketId
и originResolutionId. Мнимый inboxRef/messageId не создаётся; готовность Входящих
не проверяется. Исторический маршрут ответа берётся из исходного Resolution.

origin=null, отсутствующий/чужой вход, неверная беседа или противоречащий origin
дают ORIGIN_NOT_OBSERVED/ORIGIN_CONFLICT и needs_attention. Связь не угадывается
по последнему сообщению или текущей сессии. Отказ Каналов/Контактов сохраняет
безопасный предметный код; он не меняет уже состоявшуюся отправку Hermes.
Historical policy выбирается на receivedAt копии: это теневой расчёт, не
доказательство того, что Hermes применял эти правила при исходной отправке.

Состояния нового профиля: registered, processing, needs_attention, observed.
observed означает проверенное и зафиксированное наблюдение, не передачу команды
или доставку Telegram. Read API и его schema явно поддерживают новый вариант.
Свидетельство native доставки хранится отдельно как observation evidence;
sent принимается только как заявленное источником свидетельство с ID сообщений,
не как эффект Приёма. Проверять подлинность Telegram через новые запросы не нужно.

Для shadow-пакета jobs всегда пусты, inboxRef отсутствует. Программный guard
и NATS ACL запрещают hermes, deliver, inbox, understand, memory и dispatch.
Запрещены вызывающие эффекты при resume, redelivery, любом неизвестном outcome
или смене конфигурации. Старые API get/resume применяются только после проверки
профиля; общий resume не умеет активировать shadow-пакет как обычное сообщение.

## 5. Вложения, порядок, ошибки и аудит

Файлы уже публикует штатный Hermes. Приём не делает prepare/PUT, не скачивает
Telegram файлы, не повторяет публикацию, не вызывает STT/ИИ.
Неподтверждённый artifactId=null, attachmentState=pending/failed, неизвестный owner
или неполный состав сохраняются как неполнота и needs_attention, а не как готовый
пакет без файлов. Позднее полное наблюдение — новая immutable revision;
прежний снимок не исправляется задним числом.

Нет самостоятельной проверки delivery.check, обязательной для observed:
теневая ветка ничего не доставляет, и проверка текущих прав позднее не доказывает
их состояние в момент фактической native отправки. Реальный delivery.check
остаётся обязательным для будущей активной интеграции перед её эффектом.

Порядок источника определён epoch/seq, но завершение разных workflow может
переставляться. Это не меняет очередь и session ordering Hermes. Связанные
исходящие пакеты ждут только исходный снимок, а не завершение его аудита.
Нет ожидания ответа агента, завершения другого пользовательского хода или записи памяти.

Transient ошибки Каналов, Контактов, Артефактов и Истории повторяет Temporal
без занятой ожиданием Activity. Неповторяемый предметный отказ создаёт
needs_attention. Авторизованный retry шага сохраняет исходный запрос и snapshots,
не пересчитывает правила и не запускает бизнес-попытку Hermes.
Технические повторы не увеличивают номер ревизии наблюдения.

Для новой ветки используется receive 1105 как факт регистрации, плюс реальные
Contact historyEvents. Факт deliver 1106 не пишется: обязательной передачи
бизнес-получателям нет. observed ожидает подтверждение этих фактов; недоступная
История задерживает только теневое завершение. Новые типы Истории не требуются.

Ресурсы worker: одна Activity одновременно, до двух Workflow Tasks, cache до 8;
пулы API/worker до 4 соединений каждый, 1 активный ingress handoff в теневом
экземпляре. Сроки owner API не расширяются. Начальные лимиты API 256 MiB/0.5 CPU,
worker 512 MiB/0.5 CPU; не измеренные минимумы. Namespace, task queue, БД/роли,
NATS identities и ресурсы broker изолированы от рабочих очередей Hermes.
На существующем DEV NATS используется отдельный shadow account с собственными
streams/consumer и этими же ingress subjects. Связи к существующим Artifacts.get
и append.service_intake/service_contacts History объявляются узкими service
exports/imports; произвольный доступ к основному account запрещён. Ни второй
NATS server, ни импорт команд Hermes не нужны. Проверка accounts/ACL входит
в операторскую приёмку до включения и сохраняет прежние credentials.
Достигнутый предел оставляет фоновые события ждать, не тормозит gateway.

## 6. Проверяемый результат и совместимость

Read API показывает packet/event/Observation identity, профиль, стадийные
состояния, snapshots, проверенные artifact IDs, native evidence, reason и
audit pending. Сводка без содержимого сообщений показывает зарегистрировано/
observed/needs_attention, backlog, возраст старейшей записи, экспортированный
cursor, coverage и ошибки зависимостей. Имена и тексты не попадают в метрики.

Этот этап подтверждает реальную регистрацию копий, Каналы, Контакты,
идемпотентность, связи ответов и чтение Артефактов/Истории. Он НЕ подтверждает
управление ходами, полноту захвата при crash, активную Telegram-доставку,
Входящие, Понимание, память либо безопасность будущего переключения маршрута.

Схемы/AsyncAPI/миграция нового Packet-варианта и конфигурация появляются при
реализации. Действующий get/schema не объявляется совместимым до этой проверки.
Компоненты остаются самостоятельными. Полный message workflow сохраняет
прежние 75 локальных и 34 интеграционных проверки как базу без пропусков.

Переход в активный маршрут требует отдельного контракта, проверок и принятия.
Нет флага, который превращает сохранённые shadow-копии в команды на исполнение.
Ни принятие этого документа, ни commit/push не разрешают включение DEV.
