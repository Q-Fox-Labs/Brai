# Bug Hunt

Отдельный сервис регистрации наблюдений о сбоях. PostgreSQL хранит обращения,
карточки, первоначальные квитанции и аудит ручного разбора. MCP и NATS Services
вызывают одно предметное ядро. Web предоставляет список и карточку.

[Контракт v1](CONTRACT.md), [систематизация v2](SYSTEMATIZATION.md), [машинные DTO](schemas/messages.schema.json),
[проверка наблюдений v3](VERIFICATION.md),
[credential helper и его закрытый RPC](owner-rpc/README.md),
[установка и восстановление](DEPLOYMENT.md).

Подключённый агент постоянно получает только строку-подсказку.
bug_hunt_help({}) читает правила и пример из публичного
[agent-guide.json](contracts/agent-guide.json), без регистрации и обращения к БД.
Схемы полей остальных инструментов опубликованы отдельно.

## Сборка и запуск

С готовыми зависимостями из корня: `npm run build:bug-hunt`,
`npm run test:bug-hunt`. Отдельная проверка типов: `npm run typecheck:bug-hunt`.
Миграции запускаются отдельно командой `npm run migrate:bug-hunt` с owner URL,
`BUG_HUNT_OWNER_ROLE` и `BUG_HUNT_APP_ROLE`.
Runtime получает только app URL через защищённый JSON
`BRAI_BUG_HUNT_CONFIG`; запуск: `npm start --workspace=@brai/bug-hunt`.
Готовность: `npm run health:bug-hunt`.

Поля конфигурации: databaseURL, installationId, cursorKey (не менее 32 байт),
nats (servers, inboxPrefix и необходимые credentials), mcp (host, port,
allowedHosts, allowedOrigins, principalsFile, maxConnections до 32),
maxReports (до 1000000), reportsPerMinute (до 6000), maxDatabaseBytes
(порог приёма, минимум 16 МиБ) и artifactsEnabled. Все значения задаёт экземпляр.
Конфигурация и реестр principal — обычные закрытые файлы без symlink,
с владельцем root либо UID процесса и без группового или общего доступа.

Реестр Codex содержит массив {tokenSha256, ownerId, principalId, enabled}.
Credential не хранится в реестре в открытом виде. Стабильный principalId
сохраняется при ротации токена. Каждый HTTP-запрос заново читает реестр и Auth.

## Проверки

Unit-проверки не требуют инфраструктуры. Интеграционные проверки принимают
только явные loopback URL отдельной БД brai_bug_hunt_test и своего NATS.
Начальная схема fixture находится в tests/integration/init.sql.
Ни установленный DEV, ни пользовательские обращения не используются для тестов.

Наличие исходников или успешная сборка не означают подключение компонента
в текущей установке. Поиск, обратимые группы и фоновые предварительные метки
описаны в SYSTEMATIZATION.md. Worker по умолчанию выключен; intake v1 не ждёт
моделей. Систематизация v2 не подтверждает баги. Опциональное расследование v3 описано
в [VERIFICATION.md](VERIFICATION.md); исправление программы в него не входит.

## Систематизация

Миграции 002/003/004 добавляют собственные производные таблицы поверх схемы 1.
Оператор заранее готовит pgvector; runtime не выполняет DDL.
processing — необязательная защищённая конфигурация с флагами, dailyLimits,
intakeReserveBytes/maxDerivativeBytes и внешними очищенными проекциями.
Её проверка и точные значения принадлежат src/config.ts и контракту v2.
targetGeneration готовит embedding рядом с active, без повторного Jev/local.
Переключение требует отдельной operator-only activate-generation с CAS и полным
покрытием; status показывает оба поколения. Старые векторы и квитанции сохраняются.
Установка передаёт те же стабильные installationId и cursorKey.

Обычный test не обращается к моделям. Изолированные integration tests используют
отдельные PostgreSQL/NATS fixture; model-quality.mjs запускается только явно
с отдельным UUID и синтетическими текстами. Replay этого UUID не вызывает inference.

Автоматическая классификация включается защищённой политикой
processing.externalProjectionPolicy=technical-fields-v1 и явным
externalAllowedOwners. Сервис готовит технические поля новых и накопленных
обращений сам; ручной список externalProjections не требуется.
Точные правила исключений, ограничения и аудит описаны в SYSTEMATIZATION.md.

## Расследование v3

Для диагностики сервера есть отдельный путь через [Ansible и MCP](#диагностическое-расследование). Он сохраняет вывод и отметку в карточке. Путь v3 ниже описывает прежний исполнитель и его исторические данные.

Отдельные verification-worker и verification-runner поставляются тем же
компонентом. Worker использует Temporal, собственный приватный stdio-процесс
Codex и существующего credential owner через private UDS helper. Новые login,
копия auth.json и изменения ядра/egress Hermes не нужны. Providers выбирается
отдельно, без автоматического fallback при отказе Codex.

До фазы выбирается последняя стабильная Sol/high из настоящего каталога той же
авторизации. Startup-проекция меняет только tool_mode выбранной модели на direct.
Native state имеет стабильную generation; checkpoint отдельно закрепляет
catalog/source/account/binding. Refresh того же account меняет binding и
закрывает прежнюю фазу. Потерянный ACK не разрешает повторять inference вслепую.

Runner исполняет только принятые recipes в физической изоляции: начальный набор
проверяет настоящую собранную identity-функцию reviewer и DTO schemas. Применимость
требует точного совпадения source commit и observation registry; результат нельзя
переносить на другие обращения. Область доказательства и recovery описаны в
[VERIFICATION.md](VERIFICATION.md).

Dispatch по умолчанию выключен. Ограниченная порция допускается раз в шесть часов
или по явной команде только после приёмки фактического состава. Native/helper/runner
имеют отдельный lifecycle, который обеспечивает Root через общую роль обоих
операторских установщиков. Сборка и unit tests не подтверждают приёмку DEV;
до принятой целевой квитанции admission остаётся закрытым.

## Диагностическое расследование

BB, Codex и терминал используют один MCP. Hermes получает тот же результат через свой доверенный broker. Расследования запускает собственный фоновый цикл Bug Hunt с существующим владельцем авторизации OpenAI по схеме Диалогов. [Подключение и установка](DEPLOYMENT.md#оператор-диагностики)

В MCP Codex и у доверенного broker Hermes ответы `report` и `get` дополнены объектом `investigation`. Квитанция `report` остаётся неизменной при повторе с тем же входом. Объект `investigation` вычисляется при чтении. Web сохраняет прежний контракт. Вывод v3 остаётся доступным через отдельные инструменты.

- `state` принимает `pending`, `running`, `failed`, `processed` или `unavailable`. Ошибка чтения дополнительного итога после успешной регистрации даёт `unavailable` вместе с принятой квитанцией.
- `applicability` принимает `investigated` для своего завершённого расследования, `exact` для применимого итога другой карточки того же владельца и установки, `similar` для ссылки на похожий разобранный случай в группе или `none`. `exact` требует совпадения сигнатуры и подтверждённой версии. Чужой или изменённый ручным разбором результат недоступен. Отображение готового итога для похожей карточки не помечает её обработанной.
- `result` содержит вывод (`confirmed`, `expected_behavior`, `fixed` или `insufficient_evidence`), уточнённое описание, проверенную версию, факты и необязательную подсказку (`correct_path`, `workaround` или `stop`). `stop` передаёт совет без изменения разрешений или выполнения действий.

Управление заданиями доступно только MCP principal из `mcp.investigators` для собственных карточек. `bug_hunt_investigation_claim` принимает UUID `request_id` и необязательный `case_id` и `component`. Без `case_id` сначала берётся новая карточка, затем карточка с известным техническим отказом. Активные задания и завершённые расследования этой ревизии не запускаются повторно. Повтор того же запроса возвращает прежнюю квитанцию. Другое содержимое повтора даёт `IDEMPOTENCY_CONFLICT`. `bug_hunt_investigation_complete` принимает `request_id`, `investigation_id` и `result`. `bug_hunt_investigation_fail` принимает те же ID и завершает известный технический отказ без вердикта. Завершение сверяет владельца, исполнителя и ревизию, сохраняет новую запись в истории и возвращает свой ID. Чужой ID даёт `NOT_FOUND`, ручное изменение карточки — `REVISION_CONFLICT`. Неизвестный исход остаётся у выданного задания, а повтор `claim` не запускает второй ход.

Служебный обработчик среды использует отдельное закрытое значение
`mcp.installationInvestigatorSha256` и `installation_queue: true` в своём профиле.
Его credential открывает только `investigation_list`, `investigation_card` и
операции с попытками. Он не открывает пользовательские `report`, `get`,
`list` или ручной разбор. План содержит технические признаки; очищенная
проекция выдаётся после захвата. Результат привязывается к исходному
владельцу карточки. Прежние клиентские права действуют без изменения.

Оператор запускает служебную очередь с одной блокировкой на среду. Под ней
`investigation_recover` закрывает незавершённые попытки прежнего пакетного
процесса с кодом `BATCH_INTERRUPTED`, сохраняя их в истории. Попытки старого
формата проверяются и закрываются адресно. Общая блокировка авторизации
отражается как `blocked` и `blocked_code` в результате пакета. План без
попыток остаётся read-only.

Ручной пакет использует эти же операции. Он фиксирует верхнюю границу времени регистрации, обходит все страницы своей очереди и берёт только ожидающие карточки прежней ревизии. Готовый точный итог сохраняется без модели. Карточки с одной точной сигнатурой выполняются последовательно, чтобы следующее расследование могло переиспользовать результат предыдущего. Число независимых групп в работе задаёт оператор. Данные Ansible читаются один раз на службу за пакет, с отдельной сводкой журнала для интервала каждой карточки. Пакет разбирает карточки любых компонентов. Если Ansible не собрал факты, исполнитель разбирает доступное техническое описание и записывает `insufficient_evidence` с конкретными недостающими сведениями. Без читаемого описания карточка получает запрос на обезличенное описание операции, результат и свидетельство сбоя. Новый вызов модели для уже выданного задания с неизвестным исходом не выполняется.
