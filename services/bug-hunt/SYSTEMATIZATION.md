# Систематизация наблюдений v2

Владелец — bug-hunt. Это добавочное расширение [v1](CONTRACT.md).
Исходные report, case, mutation и review, их IDs, содержимое и квитанции
не переписываются. verification_status остаётся unverified. Совпадение
проявлений не устанавливает общую причину и не подтверждает баг.

[Закрытые DTO](schemas/v2.schema.json), [операторские DTO](schemas/processing-v2.schema.json),
[NATS Services](asyncapi-v2.json), [поставка и восстановление](DEPLOYMENT.md).

## Входы и права

Subject имеет префикс brai.bug_hunt.v2. Пользовательские вызовы принимают
прежний доверенный envelope {context,input}. Auth и реестр credentials
проверяются заново; owner, installation и reviewer не являются аргументами модели.

| Операция | Результат |
| --- | --- |
| search | Буквальный и полнотекстовый поиск с фильтрами, фрагментом, методом и покрытием |
| similar | Cosine-поиск по сохранённым частям доступного case_id без нового inference |
| enrichment | Группа, предварительная классификация, ручная поправка, предложения и состояния ветвей |
| groups-list | Страница групп; optional case_id выводит владельца из доступной карточки |
| groups-get | Независимые страницы состава и неизменяемого аудита группы |
| membership-update | Атомарный перенос/отделение выбранных case IDs с revisions всех затронутых групп |
| proposal-resolve | Принятие или отклонение предложения с объяснением |
| classification-override | Новая неизменяемая ручная предварительная метка с revision |

Обычные чтения ограничены владельцем. Проверяющий Web может прочитать выбранную
чужую карточку, её группу, историю и похожие случаи; область выводится из
доступного ID, а не из свободного owner-флага. Общий список первого этапа
сохраняет отдельный operator-list. Поиск без выбранной карточки остаётся личным.
Ни одна группа или связь не соединяет разных владельцев или установки.

Модель получает только help/report/get/list и новые read tools
search/similar/enrichment/groups_list/groups_get. MCP stateless; административных
команд в каталоге модели нет. Постоянная подсказка остаётся одной строкой.

## Проекции, поиск и группы

Оригинал неизменен. Полная локальная поисковая проекция содержит title,
operation, expected, observed, steps, diagnostic_text, компонент, версии
и код ошибки. PostgreSQL simple/russian tsvector и буквальный параметризованный
поиск охватывают весь разрешённый корпус без окна последних N записей.

Точная сигнатура версии 1 включает owner/installation, известный компонент
и хотя бы одну известную версию/commit/deployment, operation, error_code,
expected, observed, steps, diagnostic_text и упорядоченные Artifact IDs.
Явное unknown не является известной версией. Нормализуются только CRLF.
Title и транспортные IDs исключены. После SHA-256 сравнивается canonical.
Неизвестный контекст не даёт права на автоматическую группу.

Новая регистрация сохраняет собственные report/case/receipt. Производная
группа не меняет title, review_state или revision исходной карточки.
Одна карточка имеет не более одной активной группы; пустая группа сохраняет
ID и аудит. Точные конкурентные проявления выбирают одну группу под scoped lock.

Перенос требует request_id, explanation и expected_revisions всех старых
и целевой групп. Revisions, membership, аудит и исходная квитанция фиксируются
вместе. Повтор прежнего входа возвращает прежний результат с replayed=true;
иной вход того же ключа даёт IDEMPOTENCY_CONFLICT. Конфликт revision не переносит
часть карточек. Отделение по умолчанию оставляет сохраняемый запрет на
автоматическое присоединение. Снять его можно явным ручным решением.

Страницы по умолчанию 20, максимум 50. HMAC cursor связан с видом чтения,
владельцем/проверяющим, фильтрами и поколением. Изменение состава группы
или векторов, которое меняет продолжение, даёт CURSOR_STALE.
has_more/next_cursor ограничивают страницу, а не рассматриваемый корпус.
Покрытие относится ко всем разрешённым отфильтрованным report. Отсутствующий
embedding исходной карточки даёт INDEX_NOT_READY; неполный исходный embedding
оставляет результат partial даже при полном покрытии выбранных соседей.
Предложения исключают канонически идентичные случаи и участников одной группы
до ограничения top-20; локальный индекс должен быть готов до материализации.

## Модели

Embedding selector закреплён:
embeddinggemma-2-q8 / bfcd298762cc34d0357ece5ebdd31791a3a374d8 /
embeddinggemma2_llama_cpp, purpose symmetric, 768 измерений, mean/L2.
Используется только публичный Local AI invoke.embed; другая модель,
инфраструктурный runtime и fallback запрещены. Каждая часть проверяется
на точный selector, 768 конечных значений, ненулевую L2-норму с допуском 0,001.
В БД vector(768) также проверяет норму. Поиск точный, без HNSW/IVFFlat.

Локальный embedding использует разрешённый поисковый текст своего владельца;
URL остаётся текстом, по нему не открывается ресурс. Artifact bytes не читаются.
Части сохраняют UTF-16 offsets и hash, не разрезают surrogate-пару:
до 1200 UTF-8 байт, 64 частей и 64 КиБ. Неполное покрытие явно partial.
Готовая часть сохраняется до следующего вызова. Generation
gemma2-symmetric-v1 отделяет модель, purpose и chunking. Миграция 004 хранит
точный selector, projection_version, chunking_version, purpose, dimensions
и pipeline_version в неизменяемом embedding_generation.

Jev вызывается только через Providers v1: typesafe/jev-1.13.0,
questions bug-hunt-jev-1. Закрытые choice/noul ответы задают предполагаемый
тип, влияние, достаточность описания и признаки дефекта. Сохраняются точные
answers, confidence, usage либо null, requested/actual model, версии,
operation ID, исключённые поля и machine_suggestion. Ручная поправка имеет
приоритет; поздняя модель не меняет её и не архивирует карточку.

Разрешение внешней классификации по умолчанию отсутствует.
Защищённые externalAllowedOwners задают владельцев, чьи технические обращения
допущены к внешней обработке. Для автоматической подготовки требуется также
externalProjectionPolicy=technical-fields-v1. Политика выбирает title,
operation, expected, observed, steps, component_id, component_version,
commit_sha, deployment_revision и error_code. Diagnostics, ссылки на переписку,
Artifact IDs и bytes не передаются. Поле с обнаруженным credential, URL,
email, Telegram handle, телефоном, IP, UUID или ID владельца исключается целиком;
исключённые поля и версия политики входят в неизменяемый intent и результат.
Оригинал не меняется. Подготовка детерминирована и применяется также к новым
обращениям без ручного внесения текстов в конфигурацию.

Это ограниченная техническая проекция, а не гарантия анонимности произвольного
свободного текста: известные формы не покрывают все имена и секреты. Защищённый
список владельцев явно разрешает внешнюю обработку подготовленных технических
полей по этой политике; сам report разрешения не даёт. Необязательные
externalProjections по точным ownerId/inputHash остаются приоритетными ручными
исключениями. Без политики/исключения или при пустом подготовленном тексте —
blocked_policy. Слишком большой текст даёт input_too_large без отправки.
Политика и Auth проверяются перед dispatch повторно; изменение проекции
останавливает отправку. Чтение прежнего operationId после unknown не создаёт
новую отправку и сохраняет проекцию исходного intent.

## Устойчивая обработка и ресурсы

В intake-транзакции нового report создаются три обязательства pipeline 2:
local, embedding и classification. Replay новых jobs не создаёт.
Ограниченный anti-join reconcile находит старые и поздно закоммиченные report,
включая принятые старым runtime. Watermark регистрации не используется.

Worker находится в том же сервисе, выключается отдельно и имеет свой pool
максимум 2. Claim, lease, heartbeat и fencing generation защищают от stale writer.
Модели вызываются после закрытия SQL-транзакции и освобождения соединения.
До двух jobs и одного вызова каждой модельной ветви; каждый четвёртый claim
отдаёт место исторической работе. Между владельцами действует чередование.

Сохранённый intent в dispatching сохраняет место в допуске, пока задание ждёт
ответа провайдера. GET прежнего operationId имеет приоритет и не требует нового
места, включая разбор очереди, накопленной прежней версией. Свежие задания
допускаются в оставшиеся места. Этот предел относится к отслеживаемым вызовам:
unknown не доказывает физическую остановку вычисления у внешнего провайдера.

До dispatch атомарно сохраняются точный body/hash/operationId/deadline и резерв
суточного per-owner/global бюджета. Unknown остаётся возможным расходом.
После потери Providers reply выполняется только GET прежнего operationId.
NOT_FOUND, resultExpired и неизвестный результат не разрешают новый invoke.
После возможной отправки Local AI нет автоматического повторного вычисления.
Только доказанные BUSY/OVERLOADED not_sent получают до трёх технических попыток.
При исчерпании суточного бюджета задание ждёт следующих UTC-суток без нового
business attempt; возможный расход unknown сохраняется в прежнем дне.
Отключённые модельные ветви не занимают выборку локальной работы.
Явная новая business attempt требует оператора, нового ID, причины и аудита.

Ресурсные настройки processing защищены файлом runtime. По умолчанию все
ветви выключены; daily limits embedding owner/global 100/1000,
classification 20/100, reserve для intake 64 МиБ, derivative limit 256 МиБ.
Физический объём производных таблиц/индексов и размер всей БД проверяются
также перед локальным индексом. Фон не заполняет резерв оригиналов/ручных решений.
Это admission limits, не файловая квота ОС. Оригиналы и ручной аудит не очищаются.

Автоматическая подготовка проекции не резервирует вызов Jev и не обходит
дневные лимиты. Когда лимит владельца или всей установки исчерпан, задание
получает budget_exhausted / DAILY_CALL_LIMIT и ждёт следующего дня UTC.
Это относится и к новым обращениям: приоритет новых заданий не гарантирует
оставшийся бюджет. Локальная обработка, Gemma и Jev имеют отдельные состояния;
успешный индекс не означает готовую классификацию, а лимит Gemma не запрещает
Jev работать в пределах своего бюджета. Приёмка должна проверять каждую ветвь.

Flags, разрешения, очищенные проекции и бюджеты перечитываются перед dispatch.
Смена lease/connection settings требует штатного перезапуска.
Status/health не вызывают модели. V1 status сохраняет прежнюю форму;
операторский processing.status отдельно показывает jobs, паузу,
производные bytes, зарезервированные calls и действующие лимиты.
generations содержит active, build, activation_revision и два покрытия:
active_coverage/build_coverage {total_reports,indexed_reports,state}.
Оператор видит весь корпус установки; внутренний неревьюерский вызов считает
только своего владельца. Части partial не входят в indexed_reports; при наличии
таких частей state=partial, даже если полностью готовых report ещё нет.

processing.status принимает {}. processing.pause принимает
{request_id,paused,reason}; processing.retry —
{request_id,job_id,business_attempt_id,reason}. Доступ только по operator ACL,
без model context. Эти мутации также сохраняют идемпотентную квитанцию.
Новый retry не пересчитывает сохранённые части без причины.

## Подготовка и активация поколения

processing.targetGeneration — защищённое имя build, по умолчанию
gemma2-symmetric-v1. Формат: 1–64 символа, первый a–z/0–9, остальные также
точка, дефис и подчёркивание. Оно не выбирает другую модель, purpose,
размерность или произвольные метаданные. Selector и алгоритмы закреплены кодом;
новое имя с тем же selector позволяет отдельный проверяемый пересчёт.

embedding_generation_control хранит активный указатель независимо от build.
При upgrade и первом intake active инициализируется исходным поколением один раз.
Последующая смена build не переключает указатель и не удаляет старые данные.
Конфликт уже зарегистрированных метаданных имени — GENERATION_METADATA_CONFLICT,
а не перезапись. Миграция подготавливает указатели существующих установок;
выключенный worker не скрывает их прежние векторы.

Intake и reconcile создают embedding obligation с отдельным index_generation.
Local и Jev сохраняют прежний стабильный ключ и business attempt; новый build
не требует их повторного вычисления. Enrichment показывает три текущие ветви,
а операторский status учитывает также сохранённые старые jobs. Каждая текущая
ветвь enrichment возвращает job_id и index_generation; оператор получает ID
для явного retry через доступную карточку, без прямого чтения БД.
Перед reservation и каждым dispatch проверяются build, pause и Auth.
Job старого build не отправляет новый вызов. Его уже сохранённый intent
восстанавливается по прежним правилам без повторного invoke.

Старая embedding attempt с неизвестным исходом или dispatching текущей business
attempt запрещает автоматический вызов нового поколения того же report:
blocked_policy/PREVIOUS_GENERATION_UNKNOWN. Оператор может явно retry именно
новый job с новым business_attempt_id и reason; аудит такой попытки разрешает
новый возможный расход. Исторический unknown не блокирует новые поколения
после успешной текущей business attempt старого job. Старые intent не меняются.

Similar читает только active: selector, projection и pipeline берутся из
сохранённых метаданных этого поколения. Векторы разных поколений не соединяются.
Build не меняет signed cursor активного поколения. Активация или откат меняют
activation_revision; прежний cursor получает CURSOR_STALE, в том числе после
возврата на прежнее имя поколения.

Отдельный operator-only subject:
brai.bug_hunt.v2.processing.activate-generation. Закрытый вход:
{request_id,generation,expected_active_generation,reason}. Owner, selector,
метаданные и model context запрещены. Команды нет в MCP, Web и Hermes.

Активация сериализуется с подготовкой, проверяет expected active (CAS) и полное
покрытие всех report установки по metadata/pipeline целевого поколения.
Job должен завершиться с complete, с сохранёнными полными частями точного
selector/projection/input hash. Частичное или отсутствующее покрытие даёт
INDEX_NOT_READY; неверный expected — REVISION_CONFLICT.
Возвращается {generation,previous_generation,activation_revision,total_reports,
indexed_reports,replayed}. Квитанция v2_mutation и неизменяемый
embedding_generation_activation фиксируются вместе с указателем.
Повтор request_id возвращает исходную квитанцию, даже если затем был откат;
иной вход того же ключа даёт IDEMPOTENCY_CONFLICT.
Откат — такая же явная covered CAS-активация сохранённого поколения.

## Качество и ограничения

Восьмипримерный RU/EN synthetic baseline проверил настоящий путь обеих моделей:
8 embeddings, 8 классификаций, 24 завершённых jobs, 0 изменений оригиналов.
Типы 8/8, высокое влияние 2/2, недостаток сведений 2/2; gold-пара заняла первое
место с cosine 0,9609. Повтор сохранил 16 attempts без новых вычислений.

При эвристическом пороге предложений 0,90 на этом наборе одно из двух
предложений оказалось ложным: precision 0,5. Предложения требуют человека,
не объединяют разные проявления автоматически и не подтверждают баг.
Малый набор не доказывает калибровку или качество на всех реальных ошибках.

Изменение вопросов/проекции/purpose/model/chunking требует явных версий и
ограниченного принятого пересчёта. Явная смена targetGeneration готовит отдельные
embedding jobs; dispatch требует включённого worker и принятых бюджетов,
а переключение active всегда требует отдельной команды оператора.
Предыдущие исходники и производные поколения сохраняются для отката.

Нагрузочная приёмка SQL-ядра на отдельной синтетической области: 520 report,
1560 jobs, 50 replay без новых строк, одна точная группа, исходные hashes
сохранены. После добавления lifecycle поколений при смешанной нагрузке p95 intake
304 мс, search 388 мс, group 218 мс, reconcile 263 мс; foreground pool 4, background pool 2.
Это один прогон в общей тестовой среде, без моделей и без обещания production SLA.
