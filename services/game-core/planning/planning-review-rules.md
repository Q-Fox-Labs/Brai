# Независимая проверка постановки

Версия 1.3. Проверка выполняется внутри Операции постановки. Это не Ход и не замечания Игрока.

## Два этапа

1. Новый проверяющий получает только пакет и правила. До чтения плана сохраняет `requirements`: независимые результаты (`result`) и условия (`condition`), с ID и точной цитатой. Этапы выделяет из исходного поручения; черновик задаёт границу, но не подменяет разбор. В Цели и Квесте результаты относятся к прямым детям; в Задаче — к Ходам и одному наблюдаемому свойству `state: {object, property, value}`. Для результата указывает зависимости `after`, для пообъектного Хода — `each: true`.
2. Тот же проверяющий получает план и сборку. Каждый независимый результат связывает ровно с одним узлом `chain`; разные этапы требуют разных узлов. Условия связывает с узлами, работой, ребёнком или обоснованным раскрытием неизвестного продолжения. Проверяет сохранение зависимостей и повторений, затем шесть условий [общего алгоритма](game-planning-rules.md).

Оригинал поручения, границы и выделенные ресурсы у автора и проверяющего одинаковы. Не требуй отсутствующих во входах сведений. Если факт уже есть в пакете, не объявляй его новым вопросом Игроку.

Отдельно проверяй ограничения и обеспечение ресурсами. Для каждого нужного ресурса найди подтверждение его доступности и достаточности во входах либо предшествующий Ход, который их обеспечит; допустимость использования этого не подтверждает. Сохрани эти проверки отдельными условиями в baseline.

Критерии фиксируются до сборки и сохраняются при исправлениях. Новый чистый проверяющий получает те же входы и зафиксированный baseline; повторно критерии не придумывает. Если ошибочен сам baseline, останови участок и сообщи причину. Не меняй критерии под кандидата.

Возвращай только существенные нарушения: потеря смысла или известной работы, выдуманные основания, неверный исполнитель, недоступный вход, неверный порядок либо решение. Для ошибки укажи нарушенное условие, место, причину и исправление. Качество заголовка и формулировок записывай в `notes`; оно не блокирует работоспособный план.

Сначала сверяй поручение с цепочкой, затем цепочку с карточками. Ищи самостоятельные состояния, скрытые внутри общей «готовности»; одно упоминание не подтверждает отдельный этап. Проверяй лишнюю работу и полноту плана. Неизвестный параметр не оправдывает перенос известного действия. Механическая сборка не доказывает смысловую корректность.

## Файловый протокол

Команды выполняются с корнем прогона; пути относительны этому корню.

- `python3 planning-system.py bind КОРЕНЬ ПАКЕТ BASELINE` фиксирует независимые критерии. `build КОРЕНЬ ПАКЕТ КАНДИДАТ ПРЕФИКС` проверяет ссылки и создаёт неизменяемые `.json`, `.md`, `.manifest.json`.
- `python3 planning-system.py release КОРЕНЬ MANIFEST BASELINE ОТВЕТ КВИТАНЦИЯ` разрешает выпуск только принятой неизменившейся версии.
- `python3 planning-system.py child КОРЕНЬ КВИТАНЦИЯ КЛЮЧ_РЕБЁНКА ПАКЕТ` собирает дочерний пакет. Контекст и правила наследуются без пересказа; ресурсный набор выбирается явно.

`baseline` — независимый результат первого этапа:

```json
{"inputs":{"путь":"sha256"},"requirements":[{"id":"r1","kind":"result","text":"Необходимое состояние","state":{"object":"Объект","property":"Свойство","value":"Ожидаемое значение"},"after":[],"each":false,"source_file":"input.md","quote":"Точная цитата"}]}
```

`inputs` вычисляется функцией `packet_inputs` из `planning-system.py`: пакет, исходные контекстные файлы и правила. Проверяющий сам записывает эти хеши. Во втором этапе он возвращает:

```json
{"baseline_sha256":"...","candidate_sha256":"...","verdict":"accept","coverage":[{"requirement":"r1","items":["ссылка result узла цепочки"]}],"errors":[],"notes":[]}
```

Для `condition` допустимы результаты, ключи работы или детей и `expand:КЛЮЧ_ХОДА`; `after` пуст, `each` ложь. При неясном поручении используй `system:clarify`. При `revise` укажи `{condition, path, reason, fix}`; автор исправляет постановку. Новый проверяющий использует прежний baseline. Исчерпание бюджета не означает принятия.

Квитанция связывает входы, план, сборку, baseline и ответ хешами. Изменение любого файла или принятого предка блокирует продолжение. Квитанция проверяющего не подтверждает план за Игрока и не делает ожидаемые ресурсы доступными.

Система блокирует выпуск при склейке независимо выделенных этапов, пропущенной зависимости или повторении, даже при `accept`. Предыдущие протоколы сохранены в исторических прогонах.
