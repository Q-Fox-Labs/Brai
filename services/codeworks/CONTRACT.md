# Codeworks

Codeworks — вспомогательный сервис рабочих деревьев, веток и выпусков.
Агент использует обычные инструменты Codex. Сервис не запускает агента,
не меняет его разрешения, не исполняет его команды и не управляет чатами.
Владелец данных — существующая схема PostgreSQL `codeworks`.

## Работа с задачей

Чтение и диагностика доступны независимо от Codeworks. Новая область создаётся при допуске первой поддерживаемой файловой записи через hook. Публичный prepare продолжает только существующую область; он не создаёт новую область заранее.
Область задачи имеет стабильный
workspace_key, UUID, тип, исходный коммит, ветку, путь и состояние подготовки.
Файлы области редактируются напрямую; коммиты создаются обычным Git.
Для новой области workspace_key — осмысленное название задачи: до 64 строчных
латинских букв и цифр с дефисами, начинается с буквы; UUID и хэш коммита не
подходят. Ветка получает настроенный префикс типа и это название, например
feature/codeworks-auto-cleanup или hotfix/login-timeout. Занятое название
не присваивается: для другой задачи нужен новый ключ. Существующие области
с прежними ключами и именами продолжают работать без переименования.
Идентификатор чата помогает найти прежнюю область, но не является правом доступа.

Фича: origin/dev → рабочая ветка → dev → установка DEV.
Хотфикс: фактически установленный PROD, совпадающий с origin/main →
рабочая ветка → main → установка PROD → перенос в dev → установка DEV.
Тип и база области неизменны. Promotion не поддерживается.

Клиент release передаёт подтверждённый своей процедурой commit.
Порядок получения человеческой приёмки задаётся внешним процессом.
Codeworks не распознаёт текст сообщений и не проверяет человеческое решение
через ядро, токены или отдельную систему подтверждений. Изменение рабочего коммита меняет принимаемый артефакт.

## API v2

NATS Services: `service_codeworks`, queue `service_codeworks`,
subjects `brai.codeworks.v2.<executor>.<method>`.
Executor задают broker ACL; он не идентифицирует writer и не ограничивает инструменты агента.
Форматы — [api.schema.json](schemas/api.schema.json), subjects/replies —
[asyncapi.json](asyncapi.json).

| Метод | Параметры помимо project_id | Результат |
| --- | --- | --- |
| prepare | workspace_key, kind=feature или hotfix, request_key | продолжение существующей области: operation_id, workspace_id, path, branch |
| status | workspace_id, workspace_key или operation_id; для списка offset и limit до 500 | область, операция и Git либо список и next_offset |
| sync | workspace_id, commit_sha, request_key | идентификаторы операции и области |
| release | workspace_id, commit_sha, request_key | идентификаторы операции и области |
| cleanup | workspace_id, request_key | идентификаторы операции и области |
| lifecycle.status | workspace_id | задача, workflow, блокировки и безопасное состояние обязательства cleanup |
| release.close | workspace_id, release_operation_id, request_key, reason | идентификаторы закрывающей операции и области |
| workspace.cancel | workspace_id, request_key, reason | идентификаторы операции закрытия и области |
| workspace.transfer | workspace_id, request_key, evidence | идентификаторы операции переноса и области |

Внутренние write.begin/admit/finish/stop учитывают конкретный native вызов записи и не входят в пользовательский список CLI/MCP. Их subjects используют ту же проверку executor. Они сохраняют идентификаторы, хэши и цели, а не исходный текст инструмента.

Служебные project.register/get задают конфигурацию репозитория, существующий
подготовщик, контуры и GitHub. Регистрация разрешена только административному
executor; конфигурация не расширяет полномочия Codex. При несовпадении
конфигурации регистрация возвращает CONFLICT.

CLI принимает один JSON через stdin либо `--request-json`; поле action — имя метода.
`--help` и `--schema` доступны без сервиса. Запрос ограничен 64 KiB,
NATS ожидает ответ 10 секунд. Тайм-аут не отменяет принятую операцию.
Мутацию повторяют с прежним request_key и неизменными аргументами; состояние
смотрят через status. Неизвестный метод или лишнее поле дают INVALID_ARGUMENT.
Если проверка дерева недоступна или обнаружила чужое владение, status сохраняет
сведения об области и операции, возвращая git=null и безопасный inspection_error.

## Git, CI и установка

При первой записи Codeworks сохраняет намерение до создания ветки и дерева. Подготовщик подключает
готовые зависимости и выполняет --check; установка пакетов не выполняется.
Ошибка сохраняет дерево. Повтор с новым request_key после failed позволяет
повторить подготовку прежней области, сохраняя её тип и базу.

sync отправляет чистый точный HEAD обычным push и создаёт/находит рабочий PR.
Он не выполняет слияние и установку. Повтор сверяет удалённую ветку и существующий PR.

release закрепляет чистый точный HEAD. Сначала требуются успешные обязательные
проверки этого коммита, затем слияние, проверки итогового коммита и установка
соответствующего ему проверенного состава. GitHub App, Actions attempt,
исходники и immutable digest проверяются существующим CI verifier.
Механизмы кешей и переиспользования описаны в [CI](ci/README.md).
Рабочие ветки native Codex с префиксом codex/ проходят тот же workflow,
что и feature/; это не запускает слияние или установку.

Сборка, проверки и упаковка имеют отдельные ключи. Изменение общего Git SHA
не заставляет пересобирать всё. Изменения зависимостей, рецепта, платформы
или базового образа учитываются в затронутых компонентах.
Установка использует существующий Ansible adapter; сравнение artifact digest
определяет изменившиеся компоненты. Установка самого Codeworks выполняется
внешним Ansible, без управления процессами Codex.

PostgreSQL сохраняет операцию, request_key и команду доставки одной транзакцией.
Ответ мутации подтверждает сохранённое поручение. Недоступность Temporal оставляет
его в очереди. Один workflow ведёт область от prepare до очистки или безопасной
отмены. Его ID и terminal tombstone сохраняются в PostgreSQL независимо от retention
Temporal; завершённый workflow повторно не запускается.

После успешного CI рабочего SHA выпуск занимает постоянную FIFO очередь проекта
и контура. База закрепляется после получения очереди. Контур занят до проверенной
установки. Ожидание не удерживает соединение БД или Git lock. Хотфикс освобождает
PROD после подтверждённой установки и только затем занимает DEV; успех PROD
сохраняется при незавершённом переносе. Проектный Git lock защищает короткий проход,
но не отзываёт доступ у агента. Ошибки локальны: awaiting_ci,
awaiting_deployment, awaiting_reconciliation или failed с причиной.
При succeeded существующая операция cleanup автоматически ставится в очередь
в одной транзакции с завершением выпуска. Повтор и восстановление выпуска не
создают вторую очистку. Статус выпуска содержит cleanup_operation_id; агент
дожидается статуса этой операции. Её ошибка не отменяет успешную установку.
Неудачная установка завершает запрос выпуска ошибкой DEPLOYMENT_FAILED.
Повтор с прежним ключом возвращает ту же операцию. Для новой явной попытки
агент вызывает release с новым request_key и прежним принятым SHA: сохраняются
выполненные слияния, исходный проверенный состав и связь retry_of установки.
Фоновый опрос сам повторную установку после ошибки не создаёт.
Ошибка после слияния удерживает контур. release.close закрывает указанную попытку
после проверки отсутствия работающей установки и неопределённых внешних действий.
Закрытие освобождает очередь и сохраняет задачу, ветку и дерево для доработки.
Если результат неизвестен, закрывающая операция ждёт сверки и контур остаётся занят.
Закрытие попытки не завершает задачу и не запускает её очистку. Если позднее другой
успешный выпуск установил результат feature в DEV, явный запрос cleanup может
зафиксировать завершение задачи на основании проверенной доставки. Сервис сверяет
закрытую failed попытку, актуальную установленную версию и доверенное подтверждение
установки после закрытия, а также включение всех существующих Git heads в этот
установленный commit. Исходная попытка остаётся failed. Грязное дерево, новый HEAD,
незавершённые операции или неизвестная запись не разрешают такую очистку; перед
удалением доказательства и ресурсы проверяются повторно.
Блокировку доверенных записей установленной версии и evidence выполняет узкая
функция владельца `lock_publication_evidence(project, installed_operation, evidence)`
из миграции 012. Она использует фиксированный `search_path` и возвращает boolean;
приложению разрешён только её вызов. Права приложения на изменение доверенных
записей не расширяются. Проверка и блокировка выполняются в прежней транзакции
Codeworks, без отдельного сервиса или оркестратора.
workspace.cancel фиксирует решение закрыть задачу и создаёт обязательство очистки; незавершённые операции и неизвестные исходы сначала разрешают. Неподтверждённые изменения сохраняются. workspace.transfer заявляет перенос результата и требует проверяемое evidence: полный диапазон изменений исходной области, целевой commit и соответствия файлов. Проверка сверяет чистоту, доверенный целевой репозиторий и его origin из `project.transfer_destinations`, постоянную ветку, blobs и режимы; список назначений задаётся отдельно от разрешённых Codeworks репозиториев; недоказанный перенос блокирует очистку. Выполненные слияния и установки не откатываются.

После исчерпания ограниченных повторов SDK команда остаётся pending с сохранённым retry_at. Следующий технический раунд сверяет фактические результаты прежнего ID; новая бизнес-попытка не создаётся. Предметная ошибка не перезапускает workflow целиком.
Успех установки и результат cleanup учитываются отдельно: ошибка очистки оставляет
workflow открытым для команды повтора. Подробности — [TEMPORAL.md](TEMPORAL.md). Приём сохраняет команду короткой
транзакцией после внешних проверок. Независимые области исполняются параллельно;
медленный GitHub/CI/Ansible не удерживает общий замок Git или приёма проекта.
Очередь одного контура сохраняется до подтверждённой установки либо безопасного закрытия.

Результат задачи (`outcome`) отдельно от очистки: released, cancelled,
transferred или unused. При закрытии lifecycle переходит в closing, а сохранённое
обязательство ведёт проверку и удаление ресурсов. Неиспользованная область может
получить outcome unused только после проверки отсутствия активной или неизвестной
записи и других незавершённых команд. Неизвестный исход не означает отсутствие записи.

Очистка сверяет фактическое владение, изменения, refs и индекс перед действиями.
Чужие или недоказанные ресурсы сохраняются с причиной ожидания решения. Remote
удаляется с точным SHA lease; dev и main не удаляются. После удаления дерева и
локальных refs удаляется только подтверждённый индекс владельца, затем проверяется
отсутствие ресурсов. Временные ошибки повторяются через сохранённое обязательство;
повтор сверяет уже выполненные действия. Успех выпуска не отменяется ошибкой очистки.
removed_at означает подтверждённое отсутствие ресурсов, а не только принятое решение.

Для исторической очистки оператор может представить доказательство архива: локальный
защищённый Git bundle, SHA-256 и список закреплённых refs и OID. Разрешённые
каталоги задаёт `project.cleanup_archive_roots`, владельца каталога и файла —
`project.cleanup_archive_uid`. Проверка восстанавливает bundle в пустой bare
репозиторий, проверяет все головы и целостность. Архив сохраняет историю, но не
является живой рабочей веткой. Он не разрешает удалять активную задачу или ресурсы
с незавершённой записью или операцией. После подтверждённого архивирования outcome
остаётся cancelled; refs и индекс проверяются до подтверждённого отсутствия.
Публичный workspace.cancel доказательство архива не принимает.

Проверенный оператором manifest может дополнительно содержать
`filesystem_preservation: {receipt_path, receipt_sha256}` для конкретного
относительного каталога, включая игнорируемые Git файлы. Защищённая root расписка
закрепляет архивные байты, копию для проверки и метаданные указанного дерева.
Перед удалением рабочей области свежий снимок без перехода по ссылкам сверяет
содержимое, типы и режимы под существующими защитами писателя и исполнения и Git
flock. Изменение снимка останавливает удаление с TARGET_CHANGED. Перед окончательным
подтверждением отсутствия ресурсов архив проверяется повторно. Поле включают в
manifest до закрепления его digest при создании Git-архива.

Это доказательство относится только к объявленному пути: оно не подтверждает
сохранность других игнорируемых файлов и не исключает произвольного внешнего
писателя ОС. При closing Codeworks не допускает своих управляемых писателей.

Историческое обязательство может относиться только к Git ref ветки, без рабочей
области. Такой scope не создаёт фиктивный путь или UUID дерева и не удаляет индекс.
Он проверяет принадлежащие ветке refs и архивное доказательство, а также защиту
активных и ожидающих задач. `lifecycle.status` для известной области показывает
состояние её обязательства и причину ожидания без внутренних доказательств и токенов;
исторический workflow сохраняет свой ID.

Для исторической области с removed_at и без workflow registry существующий
проектный reconciler может создать обязательство только после подтверждения
связанного успешного выпуска. Он выполняет две полные последовательные проверки
отсутствия Git-ресурсов и индекса по настроенным профилям feature и hotfix и
сохраняет оба снимка и время проверки. Найденный ресурс или неполный снимок
оставляет обязательство в ожидании решения; ошибка backend повторяется. Этот
аудит только читает ресурсы: он не удаляет их и не восстанавливает прежний
workflow. Один removed_at не доказывает ни успешный выпуск, ни отсутствие
ресурсов. Проверка индекса охватывает настроенные профили, а не неизвестные
исторические namespaces. Исторические promotion и release refs допускаются
только для отдельной read-only проверки, не для расширенного удаления.

## Хук Codex

Инструкция агенту — основной способ соблюдать рабочий процесс. PreToolUse hook
распознаёт один `git -C '<репозиторий>' apply --whitespace=nowarn <<'PATCH'` с литеральным unified diff на stdin. Он создаёт область из этого фактического вызова записи и меняет только аргумент каталога. Команда выполняется штатным командным инструментом Codex с обычной проверкой доступа; Codeworks не исполняет её и не расширяет права. При `native_file_writes: false` файловые вызовы `apply_patch`, `Write` и `Edit`, включая вложенные, отклоняются до begin/admit с `WORKSPACE_WRITE_TRANSPORT_REQUIRED`. Это исключает создание области с неизвестным файловым писателем при отказе sandbox или ранней проверке патча. Динамический shell, дополнительные команды, абсолютные пути diff, переименования, binary patch и изменение ссылок не поддерживаются этим транспортом.

По умолчанию действует `native_file_writes: false`, включая переключение runtime до обновления hook.json. Совместимый прежний режим с явным `native_file_writes: true` распознаёт native файловые вызовы apply_patch, Write и Edit. Для
однозначной записи в защищённую основную копию он сохраняет вызов, ждёт готовности
области ограниченное время, переписывает пути в дерево и допускает тот же вызов.
При PREPARE_PENDING запись отклоняется: проверь status и повтори её после готовности.
Неоднозначные цели и смешение владельцев отклоняются. Shell кроме описанного литерального Git patch не
создаёт область и не переписывается. В готовой области hook до подключения и допуска проверяет, способен ли подтвердить завершение потенциальной shell-записи. Неподдерживаемые формы команд, динамические аргументы и фоновые вызовы отклоняются с WRITER_COMPLETION_UNSUPPORTED; используй распознаваемую foreground команду. Чтение без записи проходит без этого допуска. Хук не гарантирует распознавание любых программ, а write_stdin уже открытого
процесса не является новой проверкой PreToolUse.

Штатный `PostToolUse` передаёт метаданные завершения файлового вызова или распознанной foreground shell-команды. Hook сначала сохраняет уведомление в `completion_spool` и синхронизирует файл и каталог. Доставка удаляет запись спула только после фиксации входящего уведомления в БД. `write.finish` принимает точные идентификаторы, имя инструмента, SHA-256 исходного JSON и канонического JSON входа и исход success/error. Ответ pending означает сохранённое уведомление, а finished — завершённую проверку; changed возвращается при наличии результата. Temporal повторяет внутреннюю проверку под защитой области. Фактическое изменение активирует область и first_write_at. `write.admit` может закрепить канонический SHA-256 фактического переписанного входа; для прежних вызовов используется raw digest. Текст patch и вывод инструмента не сохраняются. Спул принадлежит тому же UID исполнителя и не является защищённой root-аттестацией источника. Недоступный спул выдаёт видимую ошибку и блокирует соответствующую запись до создания области. `write.begin` может закрепить канонический digest исходного входа. В `write.finish` необязательный `execution_status` по умолчанию равен completed; not_started допускается только с outcome error. Для not_started сверяется исходный или переписанный канонический digest, а для completed — переписанный. Подтверждённый not_started закрывает только совпавший вызов без осмотра Git и активации области; последующий admit отклоняется. Если begin ещё не создан, сохранённый fence под той же блокировкой сессии запрещает позднему begin создать область; ответ содержит state not_started, null write_call_id и receipt_sha256. Stop, отмена или timeout не доказывают, что выполнение не началось. Новые уведомления спула версии 2 включают execution_status; версия 1 читается как completed. Большой Post разбирается с ограничением памяти, а восстановление частичного временного файла не должно блокировать соседние уведомления. Stop,
SubagentStop, Interrupt и SessionEnd фиксируют остановку. Отсутствующий Post или
ранее допущенные вызовы без надёжного подтверждения, включая фоновые процессы и потерянный Post, оставляют исход неопределённым: очистка ждёт независимой сверки и не считает вызов завершённым. Поддерживаемые foreground команды включают литеральные перенаправления, `cp` с двумя литеральными путями и `rm` с поддерживаемыми фиксированными флагами и литеральными целями; произвольный shell и фоновые команды не получают такого подтверждения. Позднее подтверждение последнего писателя атомарно возобновляет только обязательство с причиной WRITER_OUTCOME_UNKNOWN, без потери пробуждения при одновременной постановке ожидания. Чтение и диагностика доступны.

Если штатный Post потерян и вызов относится к поддерживаемому набору, оператор с правами owner может проверить конкретный native журнал Codex и создать защищённую root-owned расписку: `write-completion-attest --call <UUID> --source <абсолютный путь журнала> --receipt <абсолютный путь расписки>`. Затем `write-completion-import --receipt <абсолютный путь расписки>` проверяет её и вызывает обычное завершение записи. Аттестация сопоставляет точные идентификаторы проекта, области, сессии, хода и вызова, а также digest исходного и допущенного ввода. Для журнала дочернего потока проверяется однозначная одношаговая связь с логической сессией по обоим признакам родителя и глубине; конфликтующие, отсутствующие или чужие родители отклоняются. Расписка сохраняет логическую сессию, native thread и подтверждённую связь; ход, вызов и digest по-прежнему должны совпадать. Поддерживается конкретное завершение foreground Bash; произвольное сообщение агента не является подтверждением. Журнал доступен на запись агенту и не является криптографически подписанным доказательством исполнителя: owner отвечает за выбор и проверку источника. Для отдельного исторического failed nested `apply_patch` owner может вручную проверить конкретные исходные данные и создать root-owned receipt версии 2 с типом `operator_reviewed_nested_patch`, исходом error и закреплёнными идентификаторами и digest входа, вывода, manifest и префикса источника. Это решение оператора, а не автоматическая аттестация журнала; оно не содержит выдуманного exit code и не создаёт Post. Импорт использует приватную проверку под защитой области и Git inspection. Публичный RPC не принимает такой proof. Не подменяй Post и не меняй состояния напрямую через SQL или по истечении времени. Неизвестные писатели продолжают защищать ресурсы до подлинного подтверждения. Не для каждого потерянного Post или долгой сессии существует доступный способ восстановления; автоматического выпуска расписки, контроллера команд ОС и завершения по TTL нет.

Тела here-document не интерпретируются как shell-команды: HTML и код на stdin
не создают целей записи. Явные записи в заголовке команды и после разделителя
проверяются. Поддерживаются литеральные разделители без кавычек, в одинарных
и двойных кавычках, несколько here-document и `<<-` с табуляцией.
Нераспознанный или незавершённый here-document остаётся вне разбора shell.
Защищённый проект определяется путём распознанной записи, а не проектом чата.
Пути вне `projects[].repo_path` не запускают подготовку и не требуют доступности
Codeworks. Причина запрета содержит ID и корневой путь затронутого проекта.
Codeworks использует штатные события Codex и не требует изменения его исходников или собственного бинарника. Потерянное подтверждение не заменяется предположением о завершении инструмента. Изменение определения штатного hook требует проверки и доверия через /hooks:
Codex пропускает недоверенные пользовательские хуки. Синтаксис и ограничения —
в [официальной документации](https://learn.chatgpt.com/docs/hooks).

CODEWORKS_HOOK_CONFIG указывает публичный JSON:
`{"projects":[{"id":"brai","repo_path":"/absolute/project","documentation_paths":["docs","AGENTS.md"],"excluded_paths":[".git","node_modules",".env"]}]}`.
Список исключений берут из согласованной конфигурации проекта.
credsFile в публичных настройках CLI указывает существующий защищённый NATS
options JSON с servers, user, pass, inboxPrefix либо стандартный .creds.
Сервис читает тот же формат через CODEWORKS_NATS_CONFIG или
CODEWORKS_NATS_CREDS_FILE; CODEWORKS_NATS_URL задаёт необязательный адрес поверх файла.
Это сохраняет существующие broker identities и их ACL.
CODEWORKS_WORKSPACE_KEY необязательно явно выбирает задачу; без него сервис повторно использует сохранённую область сессии или выбирает осмысленное имя по целям записи. CODEWORKS_WORKSPACE_KIND=hotfix явно выбирает маршрут до первой записи; по умолчанию используется feature. Неоднозначный выбор и несовместимость с существующей областью вызывают конфликт. После перенаправления hook сообщает путь, ветку и ID области; дальнейшую работу продолжай в этом дереве. Хук устанавливается вместе с RTK без его замены.

Для полностью отсутствующего Post проектный reconciler может читать штатный API существующего исполнителя через `CODEWORKS_EXECUTOR_SOCKET`. Адаптер выполняет только initialize, thread/read и thread/turns/list, не возобновляет и не изменяет чаты. Socket принадлежит UID службы и находится в закрытом каталоге; адрес задаётся только операторской конфигурацией. Сверяется точный session/turn/tool ID и terminal commandExecution либо fileChange. Исчезновение события, завершение всего хода и истечение времени не доказывают завершение записи. Исторические вызовы без terminal item требуют проверенного решения owner. Свидетельство API хранится отдельно от Post и от ручной расписки: только хэши и тип/состояние item, без вывода. Страницы и ошибки повторяются через прежний Temporal reconciler; курсор сохраняется. Импорт использует общий workspace guard, повторную проверку admission и фактического Git. Новые native файловые вызовы в режиме Git transport не допускаются, поэтому ранний failed nested apply_patch не создаёт новых неопределённых писателей.

Адрес физического потока передаётся необязательным `executor_thread_id` в write.begin и хранится как метаданные вызова. Имя transcript используется только как подсказка адреса: перед чтением дочернего потока API проверяет всю цепочку до session_id: на каждом ребре совпадают parentThreadId и source.subAgent.thread_spawn.parent_thread_id, depth убывает на единицу и заканчивается на 1. Циклы, разрывы, несовпадающие глубины и более 32 рёбер отклоняются. Публичный RPC не принимает proof API. Все допущенные незавершённые вызовы существующих областей сверяются независимо от стадии задачи, включая активную SYNCHRONIZED область без выпуска или очистки. Проход ограничен восемью вызовами; updated_at обеспечивает продвижение между вызовами, курсор — между страницами. Неопределённый писатель виден в lifecycle.status как WRITER_OUTCOME_UNKNOWN ещё до начала очистки.

Доказанный отказ создания shell-процесса без terminal item может завершаться отдельной root-owned распиской `operator_reviewed_process_start_failure` по защищённой проверке owner. Она связывает точный допуск, оба digest входа, исходный вызов и ответ с ошибкой, хэши проверенного префикса журнала и манифеста. Только `Bash/error`, без exit code и без выдачи ручного решения за native событие; штатный импорт сохраняет guard и проверку фактических изменений. Само отсутствие item, Stop, timeout, чистота дерева или успех последующего sync такой распиской не являются. Автоматическая сверка сохраняет ограниченный код причины ошибки либо `EXECUTOR_ITEM_MISSING`, не сохраняя вывод и не освобождая неизвестного писателя.

Поздний generic Bash Post может сообщать успешный возврат самого инструмента без exit code команды. Если точный вызов уже закрыт по проверенному API/owner свидетельству, совпавший Post подтверждается без новой ожидающей доставки и без изменения сохранённого исхода. Проверки ID, инструмента и входных digest сохраняются; к файловым вызовам это исключение не относится.

Миграция 008 добавляет владельца исполнения, реестр workflow, команды и очередь

владения требует остановки прежнего исполнителя и сверки внешних действий.
Удалённые области не запускаются; открытые сохраняют ID, базу, ветку и дерево.
После передачи прежний recovery scanner отключён; откат не возвращает ему области.
legacy_writer и legacy_attachments — только исторические данные. Старые promotion
области доступны для просмотра. Старые программы Codex-proxy удалены.
Оставшиеся Hermes-исходники отложены, codeworks-agent retired и не поставляется.

Обычные проверки:
`node --test --test-isolation=none services/codeworks/tests/*.test.mjs services/codeworks/components/*.test.mjs services/codeworks/ci/*.test.mjs`.

Сценарий конкурентного UPDATE от verifier проверяет фактическую блокировку; unit fixture с расширенными правами этого не подтверждает.

Настоящий Temporal, SIGKILL, Continue-As-New, Ansible A → B и backup/restore

не доказывают реальный Actions или установку. Для приёмки нужны отдельные

Рабочие службы и глобальные hooks не включаются проверками исходников.

## Необязательный индекс рабочей области

`CODEWORKS_CODE_INDEX_CONFIG` указывает операторский JSON: `engine` — абсолютный
путь закреплённого SocratiCode, `socraticodeConfig` — путь к его runtime JSON
либо объект путей `{feature, hotfix}` для настроек соответствующего контура,
`sources` — объект `{project_id: {feature: DEV_PATH, hotfix: PROD_PATH}}`.
Политика проекта `code_index_policy: {enabled: false}` должна быть явно задана до работы: тогда новый индекс не создаётся. Отсутствие политики означает неизвестное историческое состояние и требует доступного backend для проверки очистки; недоступный backend не доказывает отсутствие индекса. Публичный prepare не принимает настройки движка.
Все писатели этих индексов должны находиться на одном сервере: locks SocratiCode локальны.

Temporal после подтверждённой первой записи в области раз в 60 секунд пытается скопировать готовый
индекс, граф импортов и граф символов. Источник должен соответствовать `base_sha`,
не иметь незавершённых записей и содержать актуальные хеши и графы. Проверка
готовности читает источник; embeddings и графы при переносе не пересчитываются.
Если родитель ушёл на другой SHA, область продолжает работу без копии. После
копирования штатный update обрабатывает изменения файлов worktree, включая
незакоммиченные. Векторы обновляются по отличиям; графы могут строиться целиком.

`workspace.code_index` содержит identity, source_path, source_sha, state,
last_success_at и безопасный код error. Состояния: waiting, copying, ready,
updating, error, skipped, removed. `ready` подтверждает последний успешный проход,
а не отсутствие новых правок после него. Эти состояния не меняют готовность
worktree или успешность выпуска. Между проходами данные могут отставать до
следующего обновления; при недоступном backend — до его восстановления.

Один общий index guard ограничивает тяжёлое обслуживание одной операцией.
Оно исполняется параллельно командам области, без Git lock. Перед закрытием или очисткой workflow отменяет и дожидается своего прохода.
Cleanup сначала выполняет прежние проверки и удаление Git-ресурсов, затем удаляет
только индекс доказанного владельца; marker владения удаляется последним.
Ошибка очистки индекса сохраняет незавершённый cleanup, не отменяя выпуск.
Миграция не копирует данные индексов: этим занимается фоновый проход workflow.

Storage-адаптер поддерживает SocratiCode 1.16.0, index format 2 и symbol schema 2;
неизвестная версия отклоняется. Для чтения обновлённых графов из открытого MCP
требуется поставляемое Admin исправление межпроцессного кэша. Области используют
path-based identity и явный projectPath; общий конфиг Codex не меняется.

## Основная локальная копия DEV

После подтверждённой установки DEV выпуск сохраняет ссылку на установку и ждёт отдельную Activity `synchronizeCheckout` того же workflow. Activity выполняется до освобождения очереди DEV и создания обязательства очистки. Она останавливает собственную индексацию, проверяет отсутствие незавершённых писателей и вызывает зарегистрированный оператором подготовщик под общим Git lock.

Подготовщик обновляет основную копию только до закреплённого merge SHA и подтверждает lock и внешний граф зависимостей. Несовпадение SHA, чужие tracked изменения или несовместимая используемая установка возвращают видимую причину ожидания. Изменения не уничтожаются и не прячутся. Вызов повторяется тем же workflow через durable таймер; исчерпание коротких повторов не завершает выпуск. Потерянный ответ после фактического FF требует новой сверки, а не повторного слияния или отката установки.

Квитанция `releaseLeg.local_checkout` хранит только commit SHA и digests lock/графа. Зависимости подготавливает существующая операторская граница; новые версии ставятся в отдельные поколения, а уже работающие деревья сохраняют прежние пакеты. Подготовка обычной области использует тот же операторский путь, если требуется восстановить отставшую основу; установка выполняется по закреплённому lock в отдельном поколении. Codex, его разрешения и глобальные hooks не меняются.

## Тип первой записи

Литеральный Git transport поддерживает git -C <repo> -c codeworks.kind=hotfix apply --whitespace=nowarn с quoted heredoc. Тип является частью фактического вызова записи и digest, а не переменной окружения Codex. Операторская политика projects[].workspace_kind может закрепить hotfix для PROD-путей. Конфликт с закреплённым типом или уже открытой областью возвращает WORKSPACE_KIND_CONFLICT до допуска записи. Неподдерживаемые формы git apply с inline env не должны исполняться в основной копии.

База сверяется со свежим upstream; отсутствующие Git objects загружаются без изменения checkout и FETCH_HEAD, tracking ref меняется через CAS. Для хотфикса по-прежнему требуется совпадение base SHA с доказанной установленной версией PROD. Если основная копия или зависимости заняты, подготовка остаётся в существующем workflow и повторяется через durable таймер, не становясь failed из-за временного локального конфликта.

Успех самостоятельного rollout и освобождение его очереди сохраняются одной
транзакцией. Workflow не завершается с успешной операцией и занятой ею очередью.
Проектный Temporal reconciler восстанавливает прежние успешные standalone rollout:
под execution guard и блокировкой контура он сверяет точные request, квитанцию,
состав и сохранённое deployment evidence. Он освобождает только подтверждённую
запись, не запускает завершённый workflow и не меняет результат операции.
Работающие, неуспешные, неподтверждённые и принадлежащие release установки
сохраняют блокировку. Старый bootstrap helper не завершает операции после
передачи проекта Temporal.
