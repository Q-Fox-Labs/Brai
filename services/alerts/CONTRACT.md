# Контракт alerts v1

Владелец — `service_alerts`. Сервис хранит уведомления в собственной PostgreSQL-БД. Он не читает базы истории, пользователей или сервисов-источников. Публичные Draft-07 определения находятся в [messages.schema.json](schemas/messages.schema.json), валидаторы — в [contracts](contracts/index.mjs), фактические subjects — в [AsyncAPI](asyncapi.yaml). Другие компоненты используют определения владельца без копирования.

## Данные и область

Вход `ingest`: `id` UUID, `service_id` непустая строка до 255 символов, `type_id` положительное целое, `scope_type=user|system`, `scope_id`, `title` до 256 символов, `text` до 8192 символов, необязательный JSON-объект `data` (по умолчанию `{}`), `occurred_at` RFC3339 с явной зоной и до шести знаков доли секунды. `recorded_at` назначает PostgreSQL. Вход не принимает `recorded_at`, категорию, тип или прочтение. NUL и лишние поля запрещены.

Для личной записи `scope_type=user`, `scope_id` — строковой ID пользователя без преобразования в UUID. Для общей записи — только `system/global`. Одна общая строка доступна каждому вошедшему пользователю, в том числе зарегистрированному после её записи. Вся запись, включая `data`, относится к её области. Источник не передаёт секреты или сведения, которые запрещено показывать этой аудитории.

`service_id` — заявленный ID, а не удостоверенная identity: реестра источников пока нет. Доступ к входному subject разрешается только доверенным источникам через NATS ACL. Привязки ID к источнику или проверки существования пользователя нет.

Пара `(service_id,id)` уникальна. Повтор с тем же нормализованным содержимым успешен: сохраняется первоначальный `recorded_at`, новой записи или сигнала нет. UUID приводится к нижнему регистру, время — к UTC с микросекундами; порядок ключей JSON не учитывается. Другое содержимое той же пары вызывает terminal `EVENT_ID_CONFLICT`. Сервис не рассчитывает на дедупликацию брокера. Записи неизменяемы, исправление приходит новым ID.

Полный JSON входа и нормализованного события с `recorded_at` ограничен 65 536 байтами UTF-8. Поэтому событие на пределе входа может быть отклонено после нормализации. Полный ответ — до 524 288 байт. JSON должен сериализоваться и проходить валидатор; чрезмерная вложенность не должна приводить к бесконечным повторам malformed сообщения.

## Справочники

`sys_categories(id,code,name,description,color,importance)` и `sys_types(id,category_id,code,name,description)` принадлежат alerts. ID, code и category_id типа сохраняют смысл после создания. Владелец БД меняет имя, описание, цвет и важность отдельной миграцией; публичного API изменения нет. Имя до 128 символов, описание до 512, цвет `#RRGGBB`, важность `1|2|3`. Цвет не заменяет числовую важность или текст.

| Категория | ID | Имя | Цвет | Важность |
| --- | --- | --- | --- | --- |
| critical | 1 | Критические | #FF3B30 | 3 — высшая |
| important | 2 | Важные | #FFC107 | 2 |
| standard | 3 | Стандартные | #22C55E | 1 |

| Тип | ID | Категория |
| --- | --- | --- |
| failure | 1 | critical |
| unavailable | 2 | critical |
| attention_required | 3 | important |
| limit_approaching | 4 | important |
| completed | 5 | standard |
| information | 6 | standard |

Повтор начальной миграции сохраняет ручные названия, описание, цвета и важность. Несовпадение закреплённых ID/code/category завершает миграцию ошибкой. Таблицы и колонки имеют SQL-комментарии. Справочники не копируются в web.

## NATS Services

Identity `service_alerts`, версия `1.0.0`, уникальный ID экземпляра, queue `service_alerts`; SDK предоставляет PING, INFO и STATS. PING не подтверждает readiness БД и JetStream.

| Subject | Вход | Ответ |
| --- | --- | --- |
| brai.alerts.v1.query.list | `{user_id,limit?,cursor?}` | `{items,next_cursor}` |
| brai.alerts.v1.query.get | `{user_id,service_id,id}` | `{notification}` |
| brai.alerts.v1.query.summary | `{user_id}` | summary |
| brai.alerts.v1.command.read | `{user_id,service_id,id}` | summary |
| brai.alerts.v1.command.read_all | `{user_id}` | summary |

Только доверенная identity web может отправлять эти запросы с произвольным `user_id`. Web предварительно удостоверяет пользователя, берёт ID из сессии и не принимает его от браузера. Передача ID по NATS сама по себе не является авторизацией. Доступ к query и command должен быть закрыт другим NATS-клиентам.

`notification` содержит нормализованный вход, `recorded_at`, полные `category` и `type`, `read_at` (timestamp или `null`). Необязательное `data` становится обязательным `{}` в ответе. `list` сортирует по `recorded_at DESC,service_id DESC,id DESC`; строковой ID источника сравнивается по PostgreSQL collation C. Размер страницы по умолчанию 50, максимум 100. HMAC-курсор связан с пользователем и хранит точные микросекунды. Курсор нельзя изменить или перенести другому пользователю. При достижении бюджета ответа страница может содержать меньше заданного limit; продолжение сохраняется в `next_cursor`.

Чтение get/list/summary не создаёт отметок. Недоступная личная запись не отличается от отсутствующей и возвращает `NOT_FOUND`. `read` добавляет неизменяемую индивидуальную отметку, повтор успешен и сохраняет первоначальное время. `read_all` одним `INSERT SELECT` отмечает только записи, доступные на начало SQL-оператора; запись, закоммиченная позже, остаётся непрочитанной. Общие уведомления не клонируются для каждого пользователя. Параллельные команды прочтения безопасны через уникальный ключ `(user_id,service_id,id)`.

Summary: `{unread_count,category}`. `category` — `null` при нуле либо `{id,code,name,color,importance}` категории непрочитанной записи с наибольшей важностью. При равной важности выбирается самая новая по полному порядку списка. Count и выбранная категория используют один SQL snapshot. `read` и `read_all` возвращают итог после своих изменений в той же транзакции; concurrent ingestion может добавить новые доступные записи до итогового оператора summary.

Лимиты: 8 активных операций, 64 ожидающих, срок 10 секунд от получения сообщения, включая очередь. После срока ответ может завершиться ошибкой, но слот остаётся занят до окончания SQL и освобождения соединения. Истёкшие SQL откатываются до COMMIT. Подтверждённая команда прочтения безопасно повторяется при неопределённом сетевом ответе.

## Ошибки

Ошибка содержит оба заголовка: `Nats-Service-Error=<code>`, `Nats-Service-Error-Code=<status>`. Тело `{code,message,retryable}`; message — безопасный код, без SQL, адресов, текста, `data` или пользователя.

| Code | Status | retryable |
| --- | --- | --- |
| INVALID_ARGUMENT, INVALID_CURSOR, UNKNOWN_TYPE | 400 | false |
| REQUEST_TOO_LARGE, RESULT_TOO_LARGE | 413 | false |
| NOT_FOUND | 404 | false |
| EVENT_ID_CONFLICT | 409 | false |
| BUSY, DATABASE_UNAVAILABLE | 503 | true |
| DEADLINE_EXCEEDED | 504 | true |
| INTERNAL | 500 | false |

Клиент проверяет заголовки до успешного DTO. Неполученный ответ NATS допускает повтор безопасной команды. Клиент задаёт timeout немного больше сервисных 10 секунд; для UI без ответа сверка восстанавливает актуальное состояние.

## Долговечный вход и сигналы

`brai.alerts.v1.ingest` — JetStream `BRAI_ALERTS_INGEST_V1`, file storage, WorkQueue retention, без expiry, лимит 256 MiB, `DiscardNew`, максимум сообщения 65 536 байт. Producer сохраняет ID/содержимое до успешного PubAck и при отказе заполненного stream повторяет позже. PubAck подтверждает хранение у брокера, а не COMMIT alerts. Потеря неотправленного события между чужой БД и брокером остаётся ответственностью источника; новый outbox не введён.

Durable `alerts_ingest`: pull, filter ingest, explicit ACK, deliver all, `ack_wait=30s`, `max_deliver=-1`, `max_ack_pending=8`. Runtime запрашивает максимум одно сообщение за раз и проверяет готовую конфигурацию, не создаёт stream или consumer. ACK следует только после COMMIT. При отказе БД, BUSY, deadline или неожиданной внутренней ошибке — NAK с задержкой 1,2,4,8,16,30 секунд, затем до 30 секунд без конечного числа попыток. При malformed input, конфликте ID или неизвестном типе — TERM без повторов. Это удаляет terminal сообщение из work queue; отдельная DLQ не нужна. Безопасный журнал содержит код, номер доставки, stream sequence и длительность, не содержимое. Поток не гарантирует строгий глобальный порядок, а recorded_at назначается фактической записью.

`brai.alerts.v1.changed` — Core NATS после вставки или новых отметок COMMIT. Payload только `{user_id:string|null}`; `null` — общая запись. Сигнал не содержит ID, заголовка или данных уведомления и не является долговечной доставкой. При replay или повторном read без изменений сигнала нет. Web обновляет собственное состояние при сигнале, после reconnect и каждые 15 секунд. Потерянный сигнал восстанавливается этой сверкой.

## Роли и внешние связи

Поток: источник → JetStream → чистое ядро → app PostgreSQL; web session → NATS Services → чистое ядро → web PostgreSQL с локальным `app.user_id` → ответ. После COMMIT ядро вызывает явно подключённый Core-сигнал. Сборка выполняется в `main.ts`; доменное ядро не импортирует PostgreSQL или NATS.

Owner — отдельный владелец собственной БД и таблиц. App/web — разные роли без суперправ, CREATE, BYPASSRLS, членства в других ролях или владения таблицами. App имеет INSERT выбранных колонок notifications, SELECT каталогов/уведомлений/marks; web имеет RLS SELECT own+global и INSERT собственных marks для доступных notifications. Runtime не получает owner URL, не делает DDL, не изменяет или удаляет записи. Web-пул устанавливает пользовательский контекст локально в каждой транзакции; без него нет ни личных, ни общих записей. Миграция проверяет владельца БД и роли, закрывает PUBLIC и grants.

История: alerts не публикует отдельные business events в history для ingestion/read; они не требуются текущему поведению. Его данные и индивидуальное прочтение принадлежат alerts. Будущее подключение источников и аудит требуют отдельного контракта. Нынешний выпуск не подключает существующие источники.
