# Контракт сервиса таймера

Сервис `brai_timer` владеет глобальным секундомером, закрытой историей интервалов и журналом результатов команд. Внешний контракт — [AsyncAPI](asyncapi.yaml); переиспользуемые DTO определены в `schemas/`. Все тела сообщений — UTF-8 JSON. Предельный размер сообщения задаётся конфигурацией NATS; приложение не должно трактовать обрезанное или некорректное JSON как команду.

## Версии и маршруты

Предметная версия wire-контрактов — `v1` в subject. Версии NATS Service API (`1.0.0`) и реализация пакета выпускаются отдельно и не меняют форму DTO. Команда использует `brai.timer.v1.command.start` или `.stop`; событие — `brai.timer.v1.event.started`, `.stopped` или `.rejected`. Запросы NATS Services используют `brai.timer.v1.query.snapshot`, `.history`, `.command`. Имена streams: `BRAI_TIMER_COMMANDS` (subjects команд, durable consumer `timer_commands`) и `BRAI_TIMER_EVENTS` (subjects событий, durable consumer `web_events`). Имя NATS Service — `brai_timer`; reply inbox командного сервиса — `_INBOX.brai_timer.>`, сервиса web — `_INBOX.brai_web.>` согласно ACL. Сервис объявляет имя, версию `1.0.0`, уникальный ID экземпляра, три endpoints, и поддерживает стандартные PING, INFO, STATS. Ответ NATS Service направляется на нативное поле reply входного NATS message; AsyncAPI описывает динамический reply channel и документирует отображение через `x-nats-reply-subject: message.reply`. Клиент не должен добавлять JSON/HTTP-заголовок `replyTo`. Для ошибок endpoint он устанавливает `Nats-Service-Error` и `Nats-Service-Error-Code`; клиенты проверяют заголовки прежде тела ответа. PING подтверждает ответ экземпляра, но не готовность БД/JetStream.

## DTO и семантика

`StartCommand` содержит UUID `commandId`, неотрицательный целый `expectedVersion` и `startedAt` не содержит: время начала ставит сервис. `StopCommand` добавляет UUID `timerId`; время остановки также назначает сервис. В обоих типах `commandId` уникален в журнале сервиса. Полное исходное содержание для идемпотентности — subject/type плюс каноническое JSON-тело целиком, включая `commandId`; повторная доставка сравнивает его до проверки версии. Повтор с тем же ID и тем же содержанием возвращает неизменный первоначальный event/result. JetStream задаёт transport key `streamName:streamSequence`. Он сохраняется для malformed и конфликтной доставки. Повтор с тем же ID и тем же содержанием использует первоначальную ledger entry и исходные eventId/result без отдельной записи для каждой повторной доставки. Тот же ID с иным subject или любым иным полем тела возвращает `COMMAND_ID_CONFLICT`, не заменяет основную ledger entry и не меняет секундомер; конфликтный результат сохраняется по transport key, поэтому повтор именно этой доставки возвращает тот же eventId и результат. Новая конфликтная доставка с другим stream sequence получает собственную запись отказа.

Текущая версия — монотонное целое, увеличивается ровно на единицу только при успешном старте/остановке. START допустим лишь при отсутствии активного интервала; STOP — только если активный `timerId` совпадает. Успешный START сразу сохраняет активную запись интервала, создаёт UUID timerId и событие `started`; STOP закрывает ту же запись интервала и публикует длительность в целых миллисекундах. Даты RFC 3339 UTC, нормализованы к `Z`; durationMs вычисляется сервисом. Успешный переход атомарно сохраняет state/version, завершённую запись и ledger result в одной DB-транзакции. Отклонённая валидная команда фиксирует результат без изменения состояния и версии и публикует `rejected` с уникальным eventId. Ошибки инфраструктуры не записывают отказ как окончательный результат.

В одной транзакции обработчик сначала блокирует единственную строку состояния, затем проверяет ledger по commandId и полному содержимому (повторный поиск после блокировки обязателен для конкурентных доставок). Если запись найдена, он возвращает сохранённый результат. Иначе сравнивает expectedVersion и проверяет активный timerId. Устаревшая версия даёт `VERSION_CONFLICT`; неактивный или чужой timerId — `TIMER_NOT_ACTIVE`; повторный START — `TIMER_ALREADY_ACTIVE`. Эти результаты неизменны при повторах. Если БД commit прошёл, сервис публикует ровно сохранённый eventId и payload в JetStream, ждёт PubAck и только затем ACK-ает входную команду. При потере PubAck/сбое до ACK повторная доставка находит ledger и снова публикует тот же eventId/payload без повторного изменения БД. Потребитель последователен, `MaxAckPending=1`, команды сохраняются без MaxAge с WorkQueue, DiscardNew и лимитом 256 MiB; переполнение явно отклоняет публикацию, команда не вытесняется. Временные ошибки повторяются без лимита попыток с задержкой не более 30 секунд. Некорректный вход, который невозможно исполнить, получает явный `rejected` event и ACK после PubAck; потеря ACK безопасна. События хранятся семь дней, предел 64 MiB, Limits policy. Установка `replicas=1` отражает один NATS server. Секреты и произвольные данные не включать в DTO.

Malformed-команда может не иметь валидного commandId. JetStream stream sequence доступен даже для невалидного payload: сервис сохраняет отказ по transport key `BRAI_TIMER_COMMANDS:<streamSequence>` и публикует `rejected` с устойчивым UUID eventId, `commandId: null` и `correlationId`, равным этому transport key. Повторная доставка публикует сохранённый результат. Эта запись не меняет state, version или history и не требует валидного commandId. Тот же ключ обеспечивает стабильный результат конфликтной доставки commandId. Не использовать клиентский `Nats-Msg-Id` для идентичности доставки. Если сообщение не попало в stream, это не обработанная команда.

## Запросы и ответы

Snapshot возвращает active (объект с timerId/startedAt либо null), version, serverTime, nextCursor и ровно до 50 последних завершённых интервалов по startedAt убыванию с timerId как tie-breaker. `state`, version, history и serverTime формируются из одного read-only DB snapshot/read transaction; при конкурентном переходе читатель получает целиком состояние до или после него. Активный интервал включён только в active, не дублируется среди завершённых. `nextCursor` — непрозрачный курсор после последних возвращённых записей, либо null, если более старых записей нет. Он построен сервисом в той же read transaction; клиент передаёт его в HistoryRequest без собственного кодирования.

History содержит только завершённые интервалы в неизменяемом порядке `(startedAt DESC, timerId DESC)`. Запрос принимает limit от 1 до 100 и cursor (opaque base64url). Ответ возвращает items и nextCursor либо null. Курсор кодирует последнюю пару ключей страницы; следующие страницы используют строгое лексикографическое условие после неё. Новые завершения, появившиеся после первой страницы, не меняют cursor и не сдвигают уже пройденную границу; элемент, закрытый между запросами, может появиться далее, если его ключ находится после границы. Курсор не является снимком всей истории и не обещает исключить позднее закрытый интервал; этот выбор исключает пропуски/дубли из-за вставки более новых ключей. Недопустимый курсор или limit — `INVALID_ARGUMENT` через service error headers.

Command lookup по commandId возвращает сохранённый исходный результат, если команда завершена, либо `NOT_FOUND`. `NOT_FOUND` означает только отсутствие завершённой записи в ledger и не доказывает, что команда отсутствует в JetStream или не обрабатывается.

## Хранилище и доступ

Минимальные логические данные: одна строка state с version и optional active timer; неизменяемые записи завершённых интервалов; ledger с уникальным `commandId` для первой валидной команды, subject/type, полным исходным JSON, исходом и сохранённым событием; для malformed и конфликтных доставок результат уникален по `(streamName, streamSequence)`. Это может быть одна таблица с nullable commandId и отдельным уникальным delivery key. Обычные повторы команды не создают новых записей. DB constraints запрещают более одного активного интервала и повтор commandId. Только сервис таймера читает и меняет эти таблицы; web общается через описанные subjects и не импортирует внутренние функции/схемы реализации. Приложение использует роль `timer_app` без DDL и без доступа к чужим данным. Не удалять автоматически историю, ledger или завершённые интервалы.

Схемы покрывают валидные wire DTO; broker-delivered bytes, не соответствующие схеме, обрабатываются как malformed и приводят к явному `rejected`, а не к ошибке, которую можно бесконечно повторять. `rejected` валидной команды и инфраструктурная service error различаются: первое — окончательный сохранённый результат команды; второе — транспортный ответ с обоими стандартными заголовками ошибки. Не выдавать обещание exactly-once доставки; гарантируется идемпотентный эффект и повторная публикация одного сохранённого eventId.
