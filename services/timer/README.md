# Контракт сервиса таймера

Сервис `brai_timer` владеет личными секундомерами, закрытой историей интервалов и журналом результатов команд. Внешний контракт — [AsyncAPI](asyncapi.yaml); переиспользуемые DTO определены в `schemas/`. Все тела сообщений — UTF-8 JSON. Предельный размер сообщения задаётся конфигурацией NATS; приложение не должно трактовать обрезанное или некорректное JSON как команду.

## Граница владельца v2

Все команды, запросы, события и успешные ответы требуют верхнеуровневый userId — строку Better Auth длиной 1–128. Web добавляет владельца после проверки сессии; ACL разрешают команды только web. Принятый владелец неизменен при выходе и redelivery. Состояние, timerId, commandId, история и курсоры разделены владельцем. Чужой cursor отклоняется, чужой результат отсутствует. Анонимные subjects v1 не обслуживаются. Вход без допустимого владельца получает NATS TERM без эффекта и события.

Миграция 002 требует предварительной отдельной очистки прикладных данных v1 и отказывается удалять их сама (TIMER_V1_DATA_REQUIRES_EXPLICIT_RESET). Сохраняется timer.migrations. До перехода оператор останавливает старые producers/consumer и очищает только старые timer streams. Повтор миграции не очищает данные v2.

## Версии и маршруты

Предметная версия wire-контрактов — `v2` в subject. Версии NATS Service API (`2.0.0`) и реализация пакета выпускаются отдельно и не меняют форму DTO. Команды используют `brai.timer.v2.command.start`, `.stop`, `.edit` и `.delete`; события — `brai.timer.v2.event.started`, `.stopped`, `.edited`, `.deleted` и `.rejected`. Запросы NATS Services используют `brai.timer.v2.query.snapshot`, `.history`, `.command` и `.statistics`. Имена streams: `BRAI_TIMER_COMMANDS_V2` (subjects команд, durable consumer `timer_commands`) и `BRAI_TIMER_EVENTS_V2` (subjects событий, durable consumer `web_events`). Имя NATS Service — `brai_timer`; reply inbox командного сервиса — `_INBOX.brai_timer.>`, сервиса web — `_INBOX.brai_web.>` согласно ACL. Сервис объявляет имя, версию `2.0.0`, уникальный ID экземпляра, четыре endpoints, и поддерживает стандартные PING, INFO, STATS. Ответ NATS Service направляется на нативное поле reply входного NATS message; AsyncAPI описывает динамический reply channel и документирует отображение через `x-nats-reply-subject: message.reply`. Клиент не должен добавлять JSON/HTTP-заголовок `replyTo`. Для ошибок endpoint он устанавливает `Nats-Service-Error` и `Nats-Service-Error-Code`; клиенты проверяют заголовки прежде тела ответа. PING подтверждает ответ экземпляра, но не готовность БД/JetStream.

## DTO и семантика

Новый `StartCommand` содержит UUID `commandId`, клиентский UUID `timerId` и `startedAt`; новый `StopCommand` содержит `commandId`, `timerId` и `stoppedAt`. `expectedVersion` в этих вариантах отсутствует: вкладка может поставить START/STOP/START в FIFO до обработки первой команды. Время новых намерений — канонический UTC ISO `YYYY-MM-DDTHH:mm:ss.sssZ`, ровно три цифры миллисекунд, секунды 00–59. Сервис не нормализует входное body. STOP до начала и повтор timerId другого START дают окончательный `INVALID_ARGUMENT`; длительность равна stoppedAt − startedAt, задержка очереди её не увеличивает.

Авторизованные CAS-команды START `{userId,commandId,expectedVersion}` и STOP `{userId,commandId,expectedVersion,timerId}` используют серверное время. Анонимные тела v1 запрещены. В обоих типах `commandId` уникален в журнале владельца. Полное исходное содержание для идемпотентности — subject/type плюс каноническое JSON-тело целиком, включая `commandId`; повторная доставка сравнивает его до проверки версии. Повтор с тем же ID и тем же содержанием возвращает неизменный первоначальный event/result. JetStream задаёт transport key `streamName:streamSequence`. Он сохраняется для malformed и конфликтной доставки. Повтор с тем же ID и тем же содержанием использует первоначальную ledger entry и исходные eventId/result без отдельной записи для каждой повторной доставки. Тот же ID с иным subject или любым иным полем тела возвращает `COMMAND_ID_CONFLICT`, не заменяет основную ledger entry и не меняет секундомер; конфликтный результат сохраняется по transport key, поэтому повтор именно этой доставки возвращает тот же eventId и результат. Новая конфликтная доставка с другим stream sequence получает собственную запись отказа.

`EditCommand` принимает `{userId,commandId,timerId,expectedVersion,startedAt,stoppedAt}`; `DeleteCommand` — `{userId,commandId,timerId,expectedVersion}`. Оба значения времени edit задаются клиентом в том же каноническом UTC формате с точностью до миллисекунд, что и новые start/stop intentions. Длительность после правки вычисляет сервис как `stoppedAt − startedAt`.

EDIT и DELETE доступны только для принадлежащего владельцу завершённого интервала, который ещё входит в историю. Отсутствующий, чужой, удалённый или активный `timerId` даёт `NOT_FOUND`. Для edit начало должно быть раньше конца; итоговый интервал не должен пересекаться с другими завершёнными интервалами владельца и открытым активным интервалом, который для этой проверки продолжается до бесконечности. Пересечение даёт `INTERVAL_OVERLAP`. DELETE помечает проекцию интервала удалённой и исключает её из истории, сумм и статистики. Исходные результаты START/STOP и результаты новых EDIT/DELETE остаются отдельными неизменяемыми ledger-записями; сервис не переписывает журнал ради новой проекции.

Текущая owner version — монотонное целое, увеличивается ровно на единицу после успешного START, STOP, EDIT или DELETE. `expectedVersion` обязателен для EDIT/DELETE и legacy CAS-вариантов START/STOP; новые намерения START/STOP сохраняют FIFO без этого поля. Устаревшее переданное значение даёт сохранённый `VERSION_CONFLICT` в `rejected.error` с текущей `currentVersion`. START допустим лишь при отсутствии активного интервала; STOP — только если активный `timerId` совпадает. Успешный START сразу сохраняет активную запись интервала, использует клиентский timerId (для legacy создаёт UUID) и событие `started`; STOP закрывает ту же запись интервала и публикует длительность в целых миллисекундах. Даты RFC 3339 UTC, нормализованы к `Z`; durationMs вычисляется сервисом. Успешный переход атомарно сохраняет state/version, проекцию истории и ledger result в одной DB-транзакции. Отклонённая валидная команда фиксирует результат без изменения состояния и версии и публикует `rejected` с уникальным eventId. Ошибки инфраструктуры не записывают отказ как окончательный результат.

В одной транзакции обработчик сначала блокирует строку состояния владельца, затем проверяет ledger по commandId и полному содержимому (повторный поиск после блокировки обязателен для конкурентных доставок). Если запись найдена, он возвращает сохранённый результат. Иначе при наличии сравнивает expectedVersion, затем проверяет цель команды и ограничения перехода. Неактивный или чужой timerId для STOP даёт `TIMER_NOT_ACTIVE`; повторный START — `TIMER_ALREADY_ACTIVE`; отсутствие подходящего завершённого интервала для EDIT/DELETE — `NOT_FOUND`; наложение после EDIT — `INTERVAL_OVERLAP`. Эти результаты неизменны при повторах. Если БД commit прошёл, сервис публикует ровно сохранённый eventId и payload в JetStream, ждёт PubAck и только затем ACK-ает входную команду. При потере PubAck/сбое до ACK повторная доставка находит ledger и снова публикует тот же eventId/payload без повторного изменения БД. Потребитель использует один owned pull iterator `consume(max_messages=1)`, обрабатывает сообщения последовательно, `MaxAckPending=1`, команды сохраняются без MaxAge с WorkQueue, DiscardNew и лимитом 256 MiB; переполнение явно отклоняет публикацию, команда не вытесняется. Временные ошибки повторяются без лимита попыток с задержкой не более 30 секунд. Некорректный вход, который невозможно исполнить, получает явный `rejected` event и ACK после PubAck; потеря ACK безопасна. События хранятся семь дней, предел 64 MiB, Limits policy. Установка `replicas=1` отражает один NATS server. Секреты и произвольные данные не включать в DTO.

Malformed-команда может не иметь валидного commandId. JetStream stream sequence доступен даже для невалидного payload: сервис сохраняет отказ по transport key `BRAI_TIMER_COMMANDS_V2:<streamSequence>` и публикует `rejected` с устойчивым UUID eventId, `commandId: null` и `correlationId`, равным этому transport key. Повторная доставка публикует сохранённый результат. Эта запись не меняет state, version или history и не требует валидного commandId. Тот же ключ обеспечивает стабильный результат конфликтной доставки commandId. Не использовать клиентский `Nats-Msg-Id` для идентичности доставки. Если сообщение не попало в stream, это не обработанная команда.

## Запросы и ответы

Snapshot возвращает active (объект с timerId/startedAt либо null), version, serverTime, totalCompletedMs, nextCursor и ровно до 50 последних завершённых интервалов по startedAt убыванию с timerId как tie-breaker. `totalCompletedMs` — сумма durationMs всей завершённой истории владельца в целых миллисекундах, до округления для показа; активный интервал в неё не входит. `state`, version, сумма, history и serverTime формируются из одного read-only DB snapshot/read transaction; при конкурентном переходе читатель получает целиком состояние до или после него. Активный интервал включён только в active, не дублируется среди завершённых. `nextCursor` — непрозрачный курсор после последних возвращённых записей, либо null, если более старых записей нет. Он построен сервисом в той же read transaction; клиент передаёт его в HistoryRequest без собственного кодирования.

Новый сервис всегда возвращает totalCompletedMs; машинная схема допускает его отсутствие для прежних producers v2. Клиент старого ответа дочитывает страницы до конца, объединяет их по timerId и лишь затем показывает итог. Последовательный новый STOP увеличивает owner-сумму один раз; повторы SSE/ledger и устаревшие snapshots её не увеличивают. Новое чтение snapshot заменяет итог. Загруженные страницы не увеличивают итог нового сервиса.

History содержит только завершённые неудалённые интервалы в порядке `(startedAt DESC, timerId DESC)`. Запрос принимает limit от 1 до 100 и cursor (opaque base64url). Ответ возвращает items, nextCursor либо null и `historyRevision`. Курсор связывает владельца, historyRevision и последнюю пару ключей страницы; курсор другого владельца отклоняется. Следующие страницы используют строгое лексикографическое условие после неё. После START/STOP новая завершённая запись не меняет revision, cursor и уже пройденную границу; после успешного EDIT/DELETE revision увеличивается, прежний cursor даёт `HISTORY_CHANGED`, и клиент начинает чтение с первой страницы. Старые курсоры без revision считаются revision 0 и принимаются только до первого успешного EDIT/DELETE. `historyRevision` необязателен в SnapshotResponse/HistoryResponse для совместимости с прежними producers v2, но новый сервис всегда его возвращает. Курсор не является снимком и может показать закрытый STOP-ом интервал, если тот появился после первой страницы и его ключ расположен дальше границы. Недопустимый формат cursor или limit — `INVALID_ARGUMENT`; изменение истории после выдачи cursor — `HISTORY_CHANGED` через service error headers.

Command lookup по commandId возвращает сохранённый исходный результат, если команда завершена, либо `NOT_FOUND`. `NOT_FOUND` означает только отсутствие завершённой записи в ledger и не доказывает, что команда отсутствует в JetStream или не обрабатывается.

Statistics принимает `{userId}` и читает всю историю владельца одним snapshot запроса; limit или cursor не ограничивают расчёт. Ответ содержит общую сумму `totalCompletedMs`, `version`, `serverTime`, `timeZone` и дневную разбивку `daily`. Сервис включает каждый ненулевой день полной истории и все 28 дней челленджа, включая нулевые. Интервалы разделяются по календарным полуночам `Europe/Moscow`; активный интервал и удалённые интервалы исключены. `targetMs` каждой строки дня равен 28 800 000 ms, `percent = completedMs / targetMs * 100` без ограничения сверху, а `achieved` истинен при выполнении дневной цели.

Параметры единственного челленджа хранятся сервисом в `sys_challenge`: `Europe/Moscow`, начало 2026-10-04, 28 дней и 8 часов в день. Миграция добавляет начальные параметры и не перезаписывает существующую конфигурацию; runtime читает её. Конец — exclusive `2026-11-01`, полная цель — 806 400 000 ms. В `challenge.daily` сервис возвращает ровно 28 строк дня для графика и суммирует только завершённые интервалы, попавшие внутрь соответствующих challenge dates. `completedMs` и `remainingMs` — миллисекунды; `remainingMs = max(targetMs - completedMs, 0)`. `percent` не ограничен 100; `achieved` означает `completedMs >= targetMs`. `closedDays` — число дней, достигших дневной цели. `remainingDays` равно 28 до начала, в период челленджа считает даты от текущей локальной даты включительно до `endDateExclusive`, а после конца равно 0. `requiredDailyMs = remainingMs / remainingDays`, либо 0 при достигнутой общей цели или нуле оставшихся дней. Статистика не меняет таймер и не создаёт побочных эффектов.

## Хранилище и доступ

Минимальные логические данные: одна строка state на userId с `version`, `historyRevision` и optional active timer; проекция завершённых интервалов с `deleted_at`; неизменяемые исходные факты в `timer.interval_facts`, уникальные по `(userId,timerId)`, с исходными `startedAt`, `stoppedAt` и `durationMs`; immutable ledger с уникальным `commandId` для первой валидной команды, subject/type, полным исходным JSON, исходом и сохранённым событием; для malformed и конфликтных доставок результат уникален по `(streamName, streamSequence)`. Миграция 003 без очистки заполняет `interval_facts` исходными фактами всех уже завершённых интервалов. Новый STOP атомарно добавляет исходный факт вместе с переходом состояния и результатом ledger. Перед EDIT или DELETE сервис добавляет отсутствующий исходный факт из текущей проекции через `ON CONFLICT DO NOTHING`; повторный вызов не перезаписывает факт. Runtime имеет для `interval_facts` только `SELECT` и `INSERT`, без `UPDATE` и `DELETE`. Исходные START/STOP ledger results не переписываются; edit/delete добавляют свои записи и меняют только проекцию. Параметры челленджа хранятся в owner-only таблице `sys_challenge`; миграция не заменяет сохранённое значение, runtime имеет к ней только доступ чтения. Обычные повторы команды не создают новых записей. DB constraints запрещают более одного активного интервала и повтор commandId на userId. Только сервис таймера читает и меняет эти таблицы; web общается через описанные subjects и не импортирует внутренние функции/схемы реализации. Приложение использует роль `timer_app` без DDL и без доступа к чужим данным. Не удалять автоматически историю, ledger или завершённые интервалы.

Схемы покрывают валидные wire DTO; broker-delivered bytes, не соответствующие схеме, обрабатываются как malformed и приводят к явному `rejected`, а не к ошибке, которую можно бесконечно повторять. `rejected` валидной команды и инфраструктурная service error различаются: первое — окончательный сохранённый результат команды; второе — транспортный ответ с обоими стандартными заголовками ошибки. Не выдавать обещание exactly-once доставки; гарантируется идемпотентный эффект и повторная публикация одного сохранённого eventId.


## Запуск и миграции

Установить зависимости из корневого lockfile: `npm ci`. Собрать сервис: `npm run build:timer`. Запускать из `services/timer`: `npm start` (`node dist/main.js`). Для поставки нужны `dist/`, `schemas/`, `migrations/`, `package.json` и production зависимости npm workspace. Процесс не читает `admin` или файлы секретов; окружение передаёт оператор. Миграции при запуске приложения не выполняются.

Обязательные переменные: `DATABASE_URL` (прямое подключение прикладной роли к отдельной БД) и `NATS_URL`. Для защищённого NATS задаются `NATS_USER`, `NATS_PASSWORD`, `NATS_INBOX_PREFIX`; таймер использует собственный inbox `_INBOX.brai_timer`. URL и пароли не включать в логи и публичные настройки. `TIMER_COMMAND_MAX_BYTES` (по умолчанию 268435456), `TIMER_EVENT_MAX_BYTES` (67108864), `TIMER_EVENT_MAX_AGE_MS` (604800000), `TIMER_ACK_WAIT_MS` (30000) позволяют оператору явно задать пределы. При запуске сервис создаёт или обновляет только свои два streams и командный consumer. Событийный stream использует `DiscardOld`; командный — `DiscardNew`.

Оператор отдельно создаёт БД, её владельца и прикладную login-роль без SUPERUSER, CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS и членства в привилегированных ролях. Роль приложения не является владельцем БД или schema. Миграционный entrypoint — `node dist/migrate.js` или `npm run migrate` из `services/timer`: `DATABASE_URL` здесь принадлежит владельцу БД, `TIMER_OWNER_ROLE` и `TIMER_APP_ROLE` задают явные разные имена существующих ролей. Мигратор проверяет владельца и флаги runtime роли, применяет необходимые `migrations/001.sql`, `002.sql`, `003.sql` и `004.sql` в транзакции и выдаёт только CONNECT, schema USAGE, нужные SELECT/INSERT и UPDATE отдельных столбцов. PUBLIC лишается доступа к БД и schema; runtime не получает CREATE, DELETE, UPDATE журнала или доступ к миграциям. Повтор миграции безопасен. Учётную запись владельца не передавать процессу приложения. Права прикладной роли на другие БД и отсутствие наследуемых привилегий обеспечивает оператор.

Выпуск Web и timer требует согласованного переключения: приостановить оба сервиса, отдельно применить owner-миграции, переключить принятые образы и проверить готовность перед открытием правки и удаления. Старый Web строго проверяет DTO и отклоняет новые Snapshot/History с `historyRevision`; смешанный запуск старого Web и нового timer не поддерживается. Перед использованием EDIT/DELETE обновить ранее открытую браузерную вкладку, чтобы загрузить совместимую клиентскую модель.

После успешного DELETE прежний timer снова включит мягко удалённые строки в историю и суммы, поскольку не фильтрует `deleted_at`. Для восстановления после использования EDIT/DELETE сохранять совместимый новый timer и применять исправляющий выпуск либо Web с совместимым timer-адаптером. Добавленные таблицы и столбцы при откате приложения сохраняются; старый мигратор не запускать, поскольку он отзовёт новые права runtime.

`npm run health` (`node dist/health.js`) проверяет настоящее подключение к таблице состояния и JetStream account info с runtime окружением. Код 0 означает доступность зависимостей; ненулевой — неготовность. Эта команда не создаёт streams и не меняет данные. NATS Services PING служит discovery, не заменяет эту проверку. Завершение SIGTERM прекращает приём чтений и pull iterator, завершает текущую команду и закрывает соединения. Уже буферизованная следующая delivery получает NAK, чтобы новый процесс не ждал AckWait. Idle/resume сохраняют inbox итератора: секундное истечение pull-запроса не закрывает клиентскую подписку и не теряет принятую доставку. `durationMs` в operational log измеряет обработку от получения сообщения до event PubAck/ACK, `queueDelayMs` фиксируется до обработки; ожидание пустой очереди в duration не входит. Чтения ограничены тремя одновременными запросами; перегрузка получает `503 INTERNAL` с `retryable: true`, сохраняя слот БД для команды.

## Проверки реализации

`npm test --workspace=@brai/timer` собирает сервис и проверяет прикладные переходы и порядок commit → PubAck → ACK. `npm run typecheck:timer` проверяет типы. Интеграционные тесты используют настоящий PostgreSQL и NATS с теми же прикладными ACL; production queues и БД для них не подходят.

Из корня репозитория поднять отдельный стенд: `docker compose -f services/timer/tests/integration/compose.yml up -d --wait`. Его пароли синтетические и опубликованы в конфигурации, хранение — временное; использовать этот файл только для тестов. По умолчанию PostgreSQL доступен на loopback 15439, NATS — на 14239. Порты можно переопределить через `TIMER_TEST_PG_PORT` и `TIMER_TEST_NATS_PORT`.

Передать в `npm run test:integration --workspace=@brai/timer` три явные переменные:

- `TIMER_TEST_OWNER_URL=postgresql://timer_owner:fixture-owner@127.0.0.1:15439/brai_timer_test`
- `TIMER_TEST_DATABASE_URL=postgresql://timer_app:fixture-app@127.0.0.1:15439/brai_timer_test`
- `TIMER_TEST_NATS_URL=nats://127.0.0.1:14239`

Тест отказывается работать без явных URL и имени БД `brai_timer_test`. После проверки удалить стенд: `docker compose -f services/timer/tests/integration/compose.yml down -v`. Каждый запуск требует свежей тестовой БД и очередей.

Проверяются конкурентные команды и повторы, полный JSON и конфликты ID, откат до commit, реальная durable redelivery после commit и PubAck до ACK, согласованный snapshot и страницы истории, NATS Services discovery/error DTO, ограничение чтений, сохранение очереди при выключенном сервисе, отказ заполненного stream без вытеснения, права runtime и повтор миграции. Отдельный subprocess запуск проверяет сборку main, health и сохранение активного интервала после SIGTERM и перезапуска процесса. В рабочем коде нет специальных fault hooks.
