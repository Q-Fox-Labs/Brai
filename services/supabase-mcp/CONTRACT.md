# Контракт Supabase MCP v1

Владелец — `services/supabase-mcp`. Машинные схемы: `src/contracts.ts`; транспорт — стандартный MCP Streamable HTTP `/mcp` официального SDK 1.30.0. Сервер поддерживает редакцию MCP `2025-06-18`. Прямые внутренние вызовы не создают отдельного RPC.

## Адресация и каталог

Конфигурация задаёт экземпляры `{id,host,port,user,passwordFile?,bootstrapDatabase,tls}` и `defaultInstance`. HTTP-клиент передаёт только идентификатор экземпляра и имя БД. Ввод DSN, хоста или пароля через инструменты запрещён схемой. `list_instances` возвращает только `id` и `isDefault`.

Имена БД, схем и таблиц — строки, без enum объектов. Перед каждым вызовом БД сервер читает `pg_database` выбранного экземпляра через `bootstrapDatabase`, закрывает служебное соединение и открывает целевую БД. Один общий lease ограничивает оба последовательных подключения. Отсутствующая БД даёт `DATABASE_NOT_FOUND`; `datallowconn=false` — `DATABASE_CONNECTION_DISABLED`. Переименование или удаление между проверкой и подключением может дать безопасную `DATABASE_ERROR`.

`list_databases` и `list_migrations` используют keyset cursor, сортировку `COLLATE "C"`, `limit` от 1 до 100 (по умолчанию 50). Cursor кодирует последний ключ и привязку к экземпляру/БД/фильтрам. Изменение этой привязки даёт `INVALID_CURSOR`; `limit` можно менять. Пагинация не является snapshot: изменения каталога между страницами отражаются по обычным правилам keyset. Шаблоны БД исключены по `datistemplate`, если `includeTemplates` не включён. `name` — регистрозависимая подстрока. Значение `datallowconn=true` не обещает сетевой доступ или права подключения.

## SQL и пределы

Вызов выполняется один раз в отдельном соединении. Открытая пользователем транзакция не переносится в следующий вызов: закрытие соединения откатывает незавершённую транзакцию. Сервер не подменяет SQL и не добавляет LIMIT. Допустимы несколько statements, любые CRUD и DDL в пределах прав серверной роли. COPY с клиентским потоком не поддерживается.

Результат statement содержит `statementIndex` (с нуля), `command`, упорядоченные `columns{name,dataTypeID}`, массивы `rows`, `rowCount`, `truncated`. Bigint PostgreSQL возвращается десятичной строкой; даты — ISO, bytea — base64; NaN/Infinity — строками. Число строк ограничено суммарно на вызов. Сериализованный JSON `data` ограничен `limits.bytes`; отсутствующие результаты отмечаются `omittedResults`. Слишком большой несокращаемый ответ даёт `RESULT_TOO_LARGE`; исполненный SQL при этом не повторяется.

Бюджет `connections` действует на весь экземпляр, включая каталог; `queue` ограничивает ожидающие вызовы. Переполнение даёт `BUSY` до SQL. Deadline включает очередь, соединение, каталог и SQL. Соединения открываются по требованию и закрываются после вызова; пулов на каждую БД нет. HTTP sessions также ограничены и истекают после idle timeout; активные calls не удаляются по idle timeout.

## Миграции

Журнал — только `supabase_migrations.schema_migrations(version text PRIMARY KEY,statements text[],name text)`. Совместимость проверяется по именам и типам трёх столбцов и единственному первичному ключу `version`. `list_migrations` возвращает версии и имена; отсутствие журнала даёт `{available:false,migrations:[],nextCursor:null}` без записи.

`apply_migration` требует `version` из 14 цифр и snake_case `name`. Уже существующая версия даёт `MIGRATION_VERSION_EXISTS`; повтор по имени разрешён для другой версии. Advisory transaction lock последовательно выполняет проверку, первоначальное создание журнала, SQL и запись версии. Несовместимый журнал даёт `INCOMPATIBLE_MIGRATION_JOURNAL` без изменения таблицы.

SQL выполняется через динамический EXECUTE внутри PostgreSQL DO/SPI. PostgreSQL запрещает COMMIT, END, ROLLBACK и вложенный transaction control в этом контексте. Ошибка SQL, журнала или nontransactional DDL откатывает всю транзакцию. Исходный SQL сохраняется одним элементом массива `statements`. Nontransactional DDL выполняют через `execute_sql`; истории миграций других компонентов сервис не читает и не изменяет.

## Ошибки, отмена и доступ

Envelope: `{ok:true,data}` либо `{ok:false,error:{code,sqlstate?,outcome}}`; ошибочный вызов помечается MCP `isError`. Ошибки не содержат message/detail PostgreSQL, SQL или параметры подключения. `outcome:not_started` означает отказ до целевого SQL. `outcome:unknown` консервативно означает возможный эффект записи; сервис не повторяет SQL автоматически. Ошибка получения результата не доказывает rollback уже совершённого commit.

Отмена MCP, разрыв HTTP-ответа, deadline и shutdown закрывают соединение и освобождают lease. Это не распределённая гарантия отмены: SQL мог успеть завершиться до закрытия. Клиент проверяет фактический исход до ручного повтора.

Пароли читает сервер по файлу. Логирование ограничено событиями запуска и общей ошибкой запуска. SQL намеренно может читать данные в пределах прав роли; сервис не обещает скрыть секреты, которые пользователь сам запросил SQL. Host/Origin проверяются, loopback — значение bind по умолчанию. HTTP-авторизацию и границу доверия задаёт конфигурация экземпляра при последующем выпуске.
