# Планирование Элемента

Версия 9.2. Рабочая модель. Первый принцип — [радикальная простота](AGENTS.md). Один алгоритм применяется к Задаче, Цели и Квесту.

## Шесть условий

1. **Опирайся на входы.** Не придумывай факты, обещания, доступы и выполненную работу. Исследователь сам находит источники. Личные сведения получает Игрок; неизвестное сохраняй явно.
2. **Выбирай минимальный уровень.** Задача даёт один самостоятельный итог. Цель объединяет 2–6 Задач, Квест — 2–6 Целей. Границы определяет [классификатор](element-classification-rules.md).
3. **Сначала результаты, затем Ходы.** Выдели состояния из порученной работы. В Задаче узел фиксирует одно наблюдаемое свойство объекта и получает Ход одного исполнителя. Если одно полученное состояние пригодно без другого, нужны разные узлы; общая «готовность» не заменяет их. Проверка и фиксация того же состояния входят в его получение. В Цели и Квесте узел обозначает итог отдельного ребёнка.
4. **Известную работу планируй сейчас.** Неизвестный параметр требует его получения. При неизвестном перечне задай шаблон отдельного Хода на объект; система раскроет его по фактическому перечню. Откладывай только работу с неизвестным составом: укажи недостающие данные, границу и результат, после которого появится Операция её постановки.
5. **Каждый вход имеет источник.** Ход получает нужные сведения, средства и полномочия до использования. Неизвестную готовность обеспечь предыдущим Ходом; проверь доступность и достаточность до расходования. Порядок не переносит ресурсы: между Элементами передавай только выделенные входы и принятые итоги.
6. **Решение относится к конкретному Элементу.** Подтверждение постановки отделено от исполнения. Последний рабочий Экшен может включать итоговое решение Игрока; подтверждать собственное исполнение ещё раз не нужно. Приёмка ждёт решение именно по своему Элементу.

Элемент организует работу ради результата. Операция — Ход агента. Экшен — Ход Игрока. Ресурс пригоден для дальнейшего использования; артефакт хранит его содержание или подтверждение.

## Операция постановки

Она уже существует. Выполни внутри неё три этапа:

1. Определи итог и границы. Запиши цепочку результатов и зависимостей; затем создай соответствующие карточки.
2. Верни предметный план по [формату](game-planning-format.md). Система соберёт полные карточки. Существующую Операцию не переписывай.
3. Пройди [независимую проверку](planning-review-rules.md). Исправления выполняй внутри этой Операции. До принятия не раскрывай детей.

Автор и проверяющий получают один пакет: исходное поручение, границы Элемента, выделенные ресурсы и общие правила. Исходное поручение — основание фактов; оно не открывает доступ к внутренним ресурсам других Элементов.

## Что делает система

- Добавляет отдельный Экшен подтверждения постановки. В Задаче затем идут предметные Ходы. В Цели и Квесте — постановка и приёмка каждого ребёнка, затем рассмотрение общего итога.
- Создаёт приёмку результата. Родитель владеет постановкой и приёмкой ребёнка: это общие записи в двух представлениях. Без родителя обе Операции принадлежат самому Элементу.
- Связывает подтверждения и решения с ID Элемента. Создаёт UUID, порядок, статусы и полные карточки. Модель не повторяет эти шаблоны.
- В Задаче допускает только последовательные Ходы и одну активную попытку. Независимые Задачи могут выполняться параллельно. Номер для показа вычисляется; связь хранится через предшественника.

## Изменение плана

Замечания — результат Экшена, а не итоговое решение. После реальных замечаний система вставляет два Хода: доработку затронутого результата и повторное рассмотрение. Смешанные замечания обслуживает одна пара; предварительный выбор не отменяет требование доработки. До замечаний эти Ходы не создавай.

При итоговом решении, включая отмену, система снимает ненужное продолжение и открывает приёмку по имеющимся результатам. При техническом сбое создаёт попытку того же Хода. История сохраняется. Опровержение гипотезы не равно автоматически провалу.

Текущая файловая проверка строит успешную предварительную цепочку. Она не исполняет Ходы и не моделирует отказы детей. Реализация этого прототипа — [planning-system.py](planning-system.py); это ещё не подключённый runtime game-core.
