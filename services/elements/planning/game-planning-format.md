# Формат предметного плана

Версия 9.2. Модель возвращает JSON предметного плана. [Система](planning-system.py) создаёт UUID, служебные Ходы и человекочитаемые карточки. Ресурс определяется один раз.

## Поля Элемента

У Элемента и черновиков детей одинаковые 12 полей. Неизвестные тексты — пустая строка, списки — пустой список.

| Ключ | Поле и назначение |
| --- | --- |
| title | Заголовок: короткий итог, предмет и конечное состояние; без статуса. |
| summary | Короткое описание: зачем нужен итог. |
| inputs | Ссылки на выделенные входные ресурсы. |
| context | Известные факты, влияющие на план. |
| scope | Границы работы и отделение соседних результатов. |
| constraints | Обязательные условия. |
| preferences | Пожелания Игрока без выдуманных дополнений. |
| unknowns | Что пока неизвестно и влияет на работу. |
| hypothesis | Коротко: «Если [предметное условие], то [результат Элемента]». Назови конкретное свойство предмета, которое Ходы могут опровергнуть. |
| expected_result | Итог и проверка его достаточности. |
| result_types | Только «Выбор», «Артефакт» или оба. Тип относится к порученному итогу, не к вспомогательному отчёту или приёмке. |
| outputs | Ссылки на конечные ресурсы Элемента. |

Если порученный итог неясен, оставь title, hypothesis, expected_result пустыми, result_types и outputs — пустыми списками. Не создавай детей и работу; запиши необходимые questions. Система создаст уточнение и обновление постановки, а не исполнение неподтверждённого плана.

## JSON одной постановки

- `fields`: 12 полей текущего Элемента.
- `resources`: новые определения `{key, name, content}`. Это ожидаемые ресурсы; имя и содержание хранятся один раз.
- `chain`: узлы `{result, after}` в порядке получения. `result` — ссылка на основной ресурс этапа; `after` — ссылки на предыдущие узлы, чьи выходы используются. Каждый узел имеет своего производителя: Ход или ребёнка. Карточки следуют цепочке; вспомогательные выходы отдельного узла не требуют.
- `children`: черновики `{key, kind, fields}`. В Задаче список пуст. В Цели дети — Задачи, в Квесте — Цели. Собственные Ходы детей здесь не создавай.
- `work`: собственная предметная работа Задачи; в остальных уровнях список пуст. Каждый Ход: `{key, title, actor, description, instruction, inputs, outputs, criteria}`. `title` — короткое действие; `actor` — `player` или `agent`; `criteria` — список наблюдаемых признаков. Инструкция описывает работу до одного самостоятельного результата.
- `completion`: ресурсы, на основании которых приёмка создаст конечные ресурсы Элемента.
- `questions`: только необходимые личные вопросы при подтверждении постановки.
- `deferred`: неизвестные продолжения `{after, missing, scope}`. `after` — ключ предметного Хода, который получит недостающие данные. Система добавит после него Операцию постановки этой части. Она не заменяет карточки известной работы и потребует подтверждения нового плана.

Для повторения добавь узлу `each`: ссылку на входной перечень объектов. Связанный `work` описывает один объект. До получения перечня это неисполняемый шаблон. Функция `expand_repeat` создаёт последовательные Ходы с устойчивыми ID и сбор общего результата; пустой перечень не создаёт фиктивной работы.

`key` — локальная ссылка, не номер и не запись UUID. Во входах и выходах используй эти ключи либо переданные UUID. Система заменяет ключи UUID. Источник нового ресурса определяется единственным производителем: предметным Ходом, приёмкой ребёнка или приёмкой текущего Элемента. Не определяй заново переданный ресурс.

Пакет постановки содержит `element`, `operation`, `finish`, `draft`, `resources`, `context_files` и `rules`. У дочернего Элемента сохрани выделенные `inputs` и `outputs` из `draft`. Его Операция уже создана родителем. Саму Операцию и приёмку модель не возвращает.

Исходное поручение доступно как основание фактов во всех пакетах; остальные ресурсы передаются только явными ссылками. `context_files` и `rules` наследуются системой без пересказа. Автор и проверяющий получают один пакет. Наличие будущего контракта не подтверждает фактическую готовность ресурса.

## Системная сборка

Система проверяет структуру, ссылки, единственного производителя, порядок получения ресурсов, число и тип детей. Затем создаёт подтверждение постановки, парные граничные Операции детей, рассмотрение общего итога и приёмку. Итоговое решение привязано к UUID Элемента. Если последнюю практическую работу выполняет Игрок, решение входит в этот Экшен.

Полная карточка Хода сохраняет прежние 12 авторских полей: временный ID, заголовок, тип, роль, описание, предыдущий Ход, входные ресурсы, инструкция, границы, ожидаемый выход, критерии завершения, условие запуска. При сборке ресурсные ссылки разрешаются в имена. Служебные исходы Экшенов задаются системой, без трёх копий одних названий в ответе модели.

Состояния Хода: `planned`, `claimed`, `succeeded`, `cancelled`. Готовность вычисляется по предшественнику, ресурсам, подтверждению плана и отсутствию другой попытки в Задаче. Номер показывается только в представлении. Системные поля и фактические результаты модель не заполняет.

Планировщик файлов не исполняет Экшены, не подтверждает постановку за Игрока и не создаёт действующие ресурсы из ожидаемых.
