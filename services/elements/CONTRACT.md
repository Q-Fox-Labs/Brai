# game-core

Сервис владеет Элементами, ревизиями, Ходами, попытками и текстовыми ресурсами в одной собственной БД. Канонические записи находятся в схеме `game_core`. Развёртывание, npm workspace, MCP-имена и NATS Service `service_elements` сохраняют прежние технические имена Elements для совместимости инфраструктуры. Второго экземпляра сервиса или канонического хранилища нет. Старые команды заменены согласованной моделью; старый domain/storage не подключён к предметным операциям. Миграция запрещает переход при непустых прежних Elements: сначала нужен явный перенос их данных.

## Данные и доступ

Восемь таблиц: `elements`, `element_revisions`, `moves`, `move_attempts`, `resources`, `attempt_resources`, `element_resources`, `outbox`. Собственные ID и ссылки — UUID. Внешний user ID остаётся исходной строкой Auth. Каждая связь проверяется в области владельца, включая составные FK. Web передаёт только ID проверенной сессии. MCP фиксирует владельца конфигурацией и игнорирует входной `user_id`. NATS доступен только доверенным внутренним потребителям с ACL.

Элемент имеет тип `level|mission|quest|goal|task`, необязательного родителя и текущую неизменяемую ревизию. Корневые Цели и Задачи разрешены. Указанный родитель следует иерархии Level → Mission → Quest → Goal → Task. Ревизия содержит title, description, fields (структурированные авторские поля). Ожидаемые результаты не заменяют фактические ресурсы. Геометрия полотна хранится отдельно в браузере.

Ход имеет `element_id` владельца, `target_element_id`, `previous_move_id`, тип `operation|action`, назначение `work|plan|start|accept|finish|confirm|review|final`, title, instructions, fields и conditions. Числового порядка исполнения нет. Внутри Задачи допускается только одно продолжение одного предшественника. Выше Задачи независимые ветки допустимы, автоматическое слияние ресурсов не поддерживается. Один владелец не может одновременно запускать разные Ходы одной Задачи.

Попытка фиксирует запуск, исполнителя, ключ безопасчного повтора, входы, результат и ошибку. `attempt_resources` содержит только входные пары; выходы определяет `resources.created_by_attempt_id`. `element_resources` имеет роли `input|output`. Ресурс не копируется при повторном использовании. Исторические даты могут быть null; `recorded_at` обозначает запись реконструкции, а не дату прошлого события.

## Транспорт

Сохраняются subjects `brai.elements.v1.query.{graph,element,timeline,moves}` и `brai.elements.v1.command.{create,revise,activate,claim,complete}`. Добавлены `command.fail` и `command.link`. MCP предоставляет соответствующие `elements_*` инструменты; точные схемы — [messages.schema.json](schemas/messages.schema.json) и `toolInputs` в адаптере MCP. NATS Services поддерживает PING/INFO/STATS и queue `service_elements`. Ошибки передаются `Nats-Service-Error` и `Nats-Service-Error-Code`.

- `create`: `{user_id,elements:[{id?,revision?,kind,parent_id?,title,description?,fields?,initial_resources?:[{id?,title,content,metadata?}]}],moves:[{id?,element_id,target_element_id?,previous_move_id?,kind,purpose?,title,instructions?,fields?,conditions?}]}`. Пакет атомарен. Родители и предшественники создаются до зависимых записей. Создание с уже занятым ID возвращает CONFLICT без частичных изменений.
- MCP также создаёт отдельный Элемент или Ход с теми же полями. `elements_structure_create` публикует для `elements[].items` и `moves[].items` те же схемы, что standalone create: обязательные поля, UUID, enum и запрет неизвестных полей видны в каталоге/describe. Element требует kind/title; Move — element_id/kind/title/instructions/result_schema. Для связей внутри batch вызывающий заранее задаёт UUID `id` создаваемых записей и повторяет их в ссылках; родители и предшественники стоят раньше. Ссылки на существующие записи используют их реальные UUID. Подтверждение плана создаётся как kind=action,purpose=confirm; executor_kind, stage и status не являются полями create. Owner по-прежнему фиксирует MCP, а семантику связей и атомарность проверяет game-core.
- `revise`: `{user_id,element_id,revision_id,title,description?,fields?}`. `revision_id` — ключ безопасного повтора. Повтор той же версии возвращает её; другая сущность или заголовок с тем же ID — CONFLICT. Завершённые Элементы не редактируются.
- `activate`: `{user_id,element_id,cancel?}`. Без cancel активирует черновик. `cancel:true` отменяет незавершённую ветку, её ненужные Ходы и активные попытки без ожидания приёмки. Завершённые результаты сохраняются.
- `claim`: `{user_id,move_id,idempotency_key,executor_kind,input_resource_ids:UUID[],target_input_resource_ids?:UUID[],executor_id?,attempt_id?}`. Operation исполняет agent/system; Action — human. Повтор ключа с прежними исполнителем и списками возвращает первоначальную попытку; изменённые списки дают CONFLICT. Входы выбирает вызывающий из доступных целевому контексту; только они записываются в attempt_resources. Старое поле input отвергается. Предшественник проверяет порядок и успешную попытку, но не передаёт ресурсы. Последующие изменения не переписывают снимок.
- `complete`: `{user_id,attempt_id,result:{resources:[{id?,title,content,metadata?,artifact_ids?}]}}`. Создаёт текстовые выходы и завершает попытку атомарно. Повтор успешной попытки возвращает прежний результат без новых ресурсов. Файлы остаются в Artifacts: каждый artifact ID проверяется через его get-контракт, ownerId и ready; байты здесь не хранятся.
- `fail`: `{user_id,attempt_id,error_code}`. Сохраняет технический сбой и возвращает тот же Ход в planned. Новый ключ claim создаёт новую попытку; история сохраняется.
- `link`: `{user_id,after_move_id,before_move_id,moves:[operation,action]}`. После подтверждённых человеческих замечаний вставляет ровно доработку и повторное рассмотрение. Имена и ID старых записей сохраняются; меняется предшественник продолжения. Повтор уже применённой вставки отклоняется без новых записей.

`conditions.required_resources` содержит известные UUID необходимых входов. `conditions.decisions` содержит `{element_id,stage,outcome?}`. Для planning требуется подтверждение текущей ревизии и outcome approved. Для final — success. Решение создаётся только успешной человеческой попыткой с metadata `{element_id,revision_id?,stage,outcome}`; сервис проверяет целевой Элемент и записывает confirmed_by. Постановка не подтверждает доступы и деньги автоматически.

Рабочие Ходы Задачи и start ребёнка ждут подтверждения актуальной постановки владельца. Accept и finish всегда ждут финального решения именно по целевому Элементу. Finish дополнительно ждёт завершения или отмены детей. Accept сам закрывает ребёнка и связывает созданные итоги как output; закрытие не является отдельным ресурсом. Start фиксирует только явно выбранный target_input_resource_ids, являющийся подмножеством входов попытки. Этот список может быть пустым; он не наследует подтверждение или все материалы родителя. План и внутренние Ходы создаёт вызывающий через API; автономный планировщик не добавлен.

`graph` принимает `{user_id}` и возвращает полную личную карту BoardData: `elements` (id,kind,parentId,status,revision,title,description,fields,provenance,input,output), `moves` (id,ownerId как UUID Элемента,targetId,previousId,kind,purpose,title,status,attemptId,executor,instructions,fields,conditions,input,output), `resources` (id,attemptId,title,content,metadata,artifactIds), `attempts`, `revisions`, `links:[]`. Чужие записи не входят в ответ. `element` выбирает запись по element_id; `moves` — доступные Ходы; `timeline` — до 100 последних попыток, без курсора. Дальнейшую пагинацию не обещаем.

## Гарантии и ограничения

Изменения сериализуются транзакционной advisory-блокировкой владельца; SQL timeout 10s. Предметное изменение и outbox записываются одной транзакцией. Доставка использует прежний JetStream `BRAI_ELEMENTS_EVENTS_V1` и consumers History/Alerts; PubAck предшествует отметке published. Повтор использует прежние ID и содержимое. Outbox не является вторым общим журналом. События не содержат текст ресурсов и секреты. Категории execution/execute, exchange/import подтверждены через актуальный History MCP.

Пределы транспорта: запрос 65536 bytes, ответ 524288 bytes; входная очередь 64, активных запросов 8, deadline 10s. Ошибки: INVALID_ARGUMENT (400), NOT_FOUND (404 для отсутствующей и чужой записи), FORBIDDEN (403), CONFLICT/INVALID_STATE (409), BUSY/DATABASE_UNAVAILABLE (503), DEADLINE_EXCEEDED (504), INTERNAL (500). Слишком большая карта возвращает ошибку; потоковый обход не реализован.

CLI `dist/import-snapshot.js <private-json>` принимает снимок и владельца из защищённой среды. Частный набор не входит в публичный репозиторий. Импорт атомарен; повтор не перезаписывает существующие записи, частичный или чужой набор отклоняется. Событие фиксирует именно импорт реконструкции сегодня. Исторические даты, реальные сайты, телефон и секреты не восстанавливаются догадкой.

## Ручные статусы DEV

`brai.elements.v1.command.dev-status` принимает `{user_id,kind,id,status,request_id}`. kind — element или move; id и request_id — UUID. Возможность включена только при одновременных BRAI_ENVIRONMENT=dev и ELEMENTS_DEV_STATUS_ENABLED=true. Во всех остальных конфигурациях команда возвращает FORBIDDEN. Владелец проверяется по записи; web подставляет его из сессии и требует правильный Origin.

Элемент допускает draft, active, completed, cancelled. Ход допускает planned, claimed, succeeded, cancelled. Команда меняет только status одной записи. Она не каскадирует отмену, не создаёт успешных попыток, ресурсов, решений или outcome. Обычные команды исполнения сохраняют прежние проверки. Ручной статус служит тестированию и сам по себе не подтверждает работу.

Смена атомарно записывает outbox event element.status_overridden или move.status_overridden с прежним/новым статусом, human actor и manual=true/environment=dev. UUID request_id является UUID события; точный повтор не создаёт второго события, изменённый запрос с тем же UUID получает CONFLICT. History принимает аудит существующим durable путём. Ответ содержит id,status,event_id,changed.

## Границы ресурсов

Обычному Ходу доступны явные element_resources input, результаты успешных Ходов с этим target_element_id и принятые outputs непосредственных детей. Выходы постановки ребёнка относятся к ребёнку. Внутренние материалы ребёнка не доступны родителю автоматически. Принятые output доступны самому Элементу и его непосредственному родителю, но не братьям. Приёмка имеет контекст target ребёнка; постановка выбирает входы из контекста родителя и явно передаёт их ребёнку. Для start/accept target обязан быть непосредственным ребёнком владельца; остальные Ходы работают со своим Элементом. Происхождение в graph остаётся отдельно читаемым и не является входом попытки.

query.moves возвращает готовые Ходы и available_resource_ids — каталог допустимых ссылок, не содержимое контекста агента. При claim обязательные required_resources и нужные решения должны присутствовать в выбранном наборе. Возможность прочитать ресурс владельца через graph не даёт права включить его в чужой контекст: claim проверяет границу.

При create корневого Элемента initial_resources создаёт только новые внешние текстовые входы без попытки и связывает input. metadata.stage запрещена: внешним входом нельзя подделать решение. Для дочернего Элемента initial_resources запрещены; он получает выбранные существующие ссылки через start. Записи ресурсов не копируются. Создание и смена входов подчиняются прежним owner checks, транзакции и outbox.

Каждая операция берёт shared maintenance advisory lock; явный административный сброс использует exclusive lock и остановку только Elements на время резервного копирования/сброса. Runtime не выполняет сброс, seed или bootstrap при запуске. Новые таблицы не добавлены.

## Принятый планировщик

Пакет `planning/` содержит неизменные семь файлов `planning-9.2-review-1.3` и их SHA256. Это общий алгоритм, формат, классификатор, правила Цели/Квеста, проверка 1.3 и сборщик. `planning/runner.py` вызывает сборщик, не меняя его алгоритм. Runtime требует Python 3.11+ стандартной библиотеки; `Dockerfile` объявляет эту зависимость поверх явно выбранного Node image. Процесс ограничен 4 секундами и 512 KiB на вход/выход; временные файлы удаляются. Нового сервиса и хранилища нет.

Первая корневая Операция имеет purpose `plan`, сохраняет ID и может стартовать без собственного будущего подтверждения. `start` сохраняет прежние права и идентичность общей постановки ребёнка. Интегрированное применение сейчас поддерживает одну Задачу с последовательными Ходами. Дети, repeat, deferred и уточнение неизвестного итога останавливаются `INVALID_ARGUMENT` до применения; шаблон не считается выполненным.

Owner-bound MCP/Hermes путь:

1. Создать исходный draft и `plan` либо взять существующий `start`. `claim` сохраняет явно выбранные реальные входы. При возобновлении прочитать текущую попытку из графа.
2. `elements_planning_packet({attempt_id})` / `command.planning-packet` возвращает `files`, `source_revision`, `inputs_sha256`, `baseline_id`. Карточка существующей Операции и пакет — единственные входы автора и независимого проверяющего. `files` содержит точный `packet.json`, тексты выбранных входов и нормативные правила.
3. Независимый проверяющий до чтения кандидата составляет baseline по проверке 1.3. `elements_planning_bind({attempt_id,baseline})` фиксирует его в попытке. `inputs` — SHA256 точных UTF-8 байтов каждого файла. Критерии нельзя менять под кандидат.
4. Автор возвращает предметный JSON по формату 9.2. `elements_planning_build({attempt_id,candidate})` вызывает нормативный build и возвращает stage, Markdown, manifest, baseline_sha256 и candidate_sha256. Исправления разрешены при прежних критериях.
5. Тот же независимый проверяющий читает кандидат и сборку и возвращает review по протоколу 1.3. `elements_planning_apply({attempt_id,candidate_sha256,review})` повторно собирает и выпускает квитанцию нормативным release. Наличие квитанции не является человеческим подтверждением.

Bind/build не завершают попытку. Apply атомарно создаёт ревизию, Ходы и ссылки, сохраняет фактический ресурс плана, завершает существующую попытку и пишет outbox `plan.applied`. Операция и уже существующая общая приёмка сохраняют ID и владельца. Ожидаемые ресурсы остаются в fields ревизии/Ходов. `resources` не заполняется будущими выходами. Повтор точного apply возвращает прежние ID; другой digest/review, изменённая ревизия или назначенные входы дают CONFLICT. Ошибка SQL/сборки откатывает всю транзакцию. Независимость смысловой проверки обеспечивает вызывающий агентный процесс; API фиксирует неизменность критериев и проверяет нормативное покрытие, но не удостоверяет личность модели-проверяющего.

`conditions.required_outputs` содержит `{move_id,output_key,revision_id}`. Сервис разрешает ключ в один фактический выход успешной попытки именно этого производителя и ревизии. До выхода Ход не готов. `query.moves.required_resource_ids` даёт минимальные реальные ссылки для claim; `available_resource_ids` остаётся каталогом допустимых ссылок. Предшественник не переносит ресурсы. `complete` интегрированного Хода принимает явные `resources[].output_key` по `fields.planning.output_contracts`; при единственном выходе ключ можно опустить. Пустое/пропущенное/повторное или чужое определение отвергается. Metadata происхождения выставляет сервис. Плановые контракты не доказывают смысловую достаточность результата.

Все решения интегрированного плана требуют точные element_id/revision_id и текущую ревизию в снимке попытки. Доверенные web/Telegram каналы владеют human claim/complete; Hermes model bridge не получает эти права. После реальных финальных замечаний интегрированного Action сервис вставляет ровно Операцию полной доработки и Action повторного рассмотрения, связывает продолжение с новыми выходами и сохраняет общую приёмку. Технический fail создаёт новую попытку прежнего Хода. Замечания к постановке сохраняются и блокируют работу; автоматическое перепланирование новой ревизии пока не поддержано.

Web `/api/elements/workflow`: POST сохраняет только исходный draft/вход/первую Операцию; PUT начинает постановку или исполняет доступный Action. Origin и текущая Auth-сессия обязательны; user_id/executor/stage/metadata не принимаются от клиента. Результаты практического Action и обоснование решения обязательны по карточке. Отправка формы и повтор после reload читают game-core. Это действительное исполнение, независимо от DEV ручных статусов. Автономный генератор плана и фоновый исполнитель не добавлены: напарник проходит воспроизводимый MCP протокол выше.
