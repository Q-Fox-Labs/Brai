# Разовые операции и диагностика

Этот справочник загружай для явного управления/расследования. Не запускай процедуры на обычном ходе, который уже обслуживается провайдером.

## Найти и объяснить воспоминание
1. Установи область: технический user, нужные кубы, проект/автор/даты.
2. Используй provider search, если доступен и известен его контракт; иначе scoped REST search. Запрос должен быть конкретным, top_k ограничен.
3. Извлеки ID, текст, provenance, время и статус. При противоречии предпочитай подтверждённое актуальное уточнение; укажи старую версию, не скрывай конфликт.
4. Если пусто: сначала scoped get/list по точному ID, затем переформулируй запрос, проверь тип памяти/порог/top_k и сравни rerank/dedup. Не считай отключённый rerank универсальным диагностическим режимом: он меняет отбор и оценку кандидатов. Если проба отсутствует в первых результатах большого куба, расширь top_k в пределах известного count, прежде чем заключать, что индекс сломан. Не объявляй данные удалёнными по пустому semantic search.

## Записать дополнение
Обычные ходы вручную не записывай повторно. Для специальной записи сначала проверь дубликаты, затем add с точной областью и источником. Клиент использует sync-fast: это сохранение текста, не LLM-факт extraction. Для fine/async используй живой контракт; параметры задавай явно. Успех: read-back каждого ID плюс тематический recall. После timeout проверь запись по источнику/ID/task_id до повтора.

## Исправить факт
- Прочитай конкретную старую запись, выясни новое значение, автора и момент актуальности.
- Составь feedback_content однозначно: что было неверно, что актуально, какие факты не менять.
- POST /product/feedback: user_id, writable_cube_ids, retrieved_memory_ids, history с полезным фрагментом диалога, session_id, async_mode; corrected_answer=false, если нужен только update. Пустая history в резервном клиенте годится для явного полного уточнения, не для контекстного «нет, завтра».
- Не обещай строгую одиночную замену: LLM-коррекция может затронуть связанные записи. Для массового переименования сначала согласуй список/область, backup и ожидаемые изменения.
- Проверь IDs/текст/статус старого и нового факта, работу recall и очередь. Сохрани provenance и возможность объяснить версию.

## Забыть сведения
Для точечного удаления: до операции прочитай IDs в согласованном кубе, после — проверяй отсутствие в активной выдаче и семантику результата по локальному backend. Scoped delete: writable_cube_ids + memory_ids; не использовать голый user_id, session_id, пустой filter или delete_all.

Для многокубового факта найди все копии по общему logical ID и источнику; удаляй и проверяй каждую разрешённую привязку, иначе другая копия продолжит вспоминаться. Физическое удаление исходных сообщений, raw-files, mirrors, архивов и backups — отдельная область. Не утверждай «забыто навсегда» после удаления одного memory node. В schema есть delete/recover by record_id, но описание помечено internal; не выдумывай record_id и не обещай rollback любого удаления.

## Просмотр и экспорт
Используй get_memory с page/page_size; без пагинации контракт допускает весь экспорт. Собирай страницы в файл, дедуплицируй по ID, проверяй total_nodes/всю область и итоговый count программно. Не показывай содержимое всех записей в групповом чате. Экспорт JSON записи не включает автоматически relationships, embeddings, original files и queue state; для восстановления нужен план backup используемого backend. Созданные экспорты содержат личные данные и должны храниться в согласованной области.

## Почему память не вспоминается
Проверяй по слоям:
1. /health — доступен ли API; ошибки HTTP отдельно от ошибки логического code.
2. hermes memory status — выбран ли provider; это не тест его соединения.
3. Writer — передан ли turn нужного session/author, принят ли add, есть ли task_id/очередь и read-back.
4. Storage — найден ли точный ID в нужном кубе, активен ли status, корректны ли metadata.
5. Index — совпадают ли embedding модель и размерность, не был ли индекс перестроен частично.
6. Retrieval — какой mode/filter/threshold/top_k/rerank/dedup, не исключены ли нужные типы/архивы.
7. Injection — получил ли провайдер результат и был ли он добавлен в контекст, не обрезан ли бюджетом; cached agent может продолжать старую конфигурацию.

Не выводи полные секретные env-файлы или systemd Environment при диагностике. Запрашивай только конкретные несекретные значения и маскируй токены. Не перезапускай gateway другого агента без согласования.

## Очередь и скорость
GET /product/scheduler/status?user_id=... [&task_id=...]: waiting/in_progress/completed/failed/cancelled. Queue-status показывает backlog; allstatus шире и может раскрывать сведения других пользователей. Не смешивай принятие задания и completed. Даже completed проверяй read-back.

Сначала измерь задержку отдельных health/search/add и проверь backlog. LLM fine/feedback, embedding, reranker, DB и adapter — разные возможные источники задержки. Fast не проверяет LLM extraction. Не переключай fine на fast ради зелёного теста, не меняя описание того, что проверено.

## Изменение настроек
Объясни компромисс скорости/качества, влияние на recall и необходимость переиндексации. Перед изменением user/cube mapping, retention, embedding модели или БД подготовь снимок несекретных настроек, минимальный проверяемый тест и план восстановления. Резервируй пользовательские данные только если это совместимо с согласованной политикой; при требовании уничтожения не оставляй их в rollback-копии. Настройки Hermes меняй штатным hermes config set после запроса; конфигурацию внешнего плагина — через его проверенный механизм. Согласуй с параллельным владельцем интеграции затрагиваемые файлы и перезапуск.

## Создать и проверить несколько кубов
1. Прочитай живой `/openapi.json` и составь явный каталог ID/назначений. Отдели список необходимых кубов от уже зарегистрированных; не создавай проектные кубы по случайным именам в тексте.
2. Создавай через `POST /product/create_cube` с `cube_id`, `cube_name`, `owner_id`. После неизвестного результата прочитай реестр, а не повторяй создание вслепую. Если требуется локальный read-only резервный путь, внутри установленного API-контейнера `UserManager().get_user_cubes(owner_id)` возвращает зарегистрированные кубы; проверяй установленный код и не выводи личное содержимое.
3. Для каждого куба выполни scoped get, sync-fast add нейтральной пробы, read-back ID/маркер источника, чтение другого куба для проверки изоляции, semantic search и delete собственных ID. Cleanup выполняй в `finally`; после него проверь отсутствие ID.
4. Складывай по одной строке результата на куб и программно сравни количество уникальных cube IDs с каталогом. Для populated cube не требуй попадания новой пробы в top-5: это проверка ранжирования, а не существования. Проверяй известный ID в расширенной выборке или в изолированной тестовой области.
5. Затем отдельно испытывай маршрутизатор на пограничных примерах, разбиении смыслов, нескольких сферах, авторстве и проекте. Сохранённый оригинал или зелёные unit tests не доказывают классификацию работающего writer.
6. После активации проверь реальный lifecycle: новый вход → очередь → классификация → scoped записи → read-back → recall. Не перезапускай gateway до завершения зависимых фоновых задач: его остановка может оборвать весь исполнительный контекст.

## Наблюдаемость длительной фоновой работы
Telegram «печатает…» относится к обработчику ответа: после завершения ответа его refresh прекращается, даже если делегированный исполнитель продолжает работу. Не используй наличие или отсутствие этого индикатора как доказательство состояния задачи. Проверяй состояние исполнителя и давай различимые этапные статусы: в работе, что проверено, что ещё не активировано, готово либо конкретная ошибка. Постоянный статус или периодические уведомления требуют отдельной реализации и проверки; не обещай их по одному описанию. Перед ожиданием фонового результата соблюдай handoff: закончи независимые действия и заверши ход, не имитируй активность опросами артефактов.

## Очистка и передача другому пользователю
Это требования к процедуре и приёмке, не утверждение о наличии реализованной команды handoff.
1. Раздели сохраняемые код/нейтральную таксономию/каталог и уничтожаемые данные подготовки. Зафиксируй owner, профиль, managed cubes и границы local history, вложений, журналов и backup; не удаляй другие профили или несвязанные данные.
2. Приостанови приём/доставку записей и дождись завершения активного writer. Проверь, что уже работающие процессы действительно учитывают блокировку, а не только новый конфиг на диске.
3. Перечисли и удали целевые записи во всех managed cubes; убери связанные pending jobs и receipts после остановки writer. Очисти встроенные USER/MEMORY и остальные источники только в согласованной области. Не оставляй экспорт этих воспоминаний ради rollback.
4. Смени generation/epoch и установи границу старых сессий, чтобы on_session_end, checkpoint, retry и зеркалирование не восстановили уничтоженный материал. Одной очистки `main` недостаточно, пока живы копии и задания.
5. Проверь пустую область по хранилищу и recall, отсутствие старых queue payloads, затем попробуй воспроизвести stale job/session hook: он не должен вернуть старые записи. После передачи новый вход должен архивироваться в новой области.
6. Отчитайся раздельно о логическом/физическом удалении активного хранилища и очистке источников. Не обещай уничтожение WAL, внешних резервных копий, Telegram-сообщений или провайдерских журналов без отдельного подтверждения.
