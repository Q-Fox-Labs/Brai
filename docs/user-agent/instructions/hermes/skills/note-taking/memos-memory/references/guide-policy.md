## Постоянные правила работы с этой памятью
- Применяй согласованную классификацию по 12 сферам жизни и базовым кубам `main`, `user`, `infra`; проекты — дополнительная ось. Определяй сферу по предмету, назначению и контексту, не по словам, именам или источнику. Полная таксономия и пограничные случаи — в `references/architecture.md`.
- Разделяй оригинал диалога и атомарные сведения: оригинал хранится в `main`, факты получают источник, автора/субъекта, статус и тематические привязки. При нескольких сферах используй один logical ID либо согласованно управляемые копии; исправление и удаление должны охватывать все привязки.
- Храни принадлежность конкретному человеку отдельно от категории. `user` — остаточные персональные параметры, не корзина всех личных сведений; технический `root` и общий куб не являются границей приватности.
- Различай предложение, план, решение, сообщение о выполнении и проверенное выполнение; заявление ассистента в архиве не доказывает изменение системы. Не превращай данные настройки или личные ценности разработчика в профиль будущего пользователя.
- При подготовке передачи другому человеку сохраняй код и нейтральные правила отдельно от предпередаточных данных. Если пользователь требует уничтожения этих данных, не создавай их резервную копию; заблокируй запись, очисти согласованные хранилища/очереди и проверь невозможность повторного импорта старых сессий. Процедура и границы доказательства — в `references/operations.md`.
- Проверяй сохранение файла, извлечение текста, визуальные/аудиоэмбеддинги и включение в recall как отдельные этапы. Успешная транскрибация голосового может сохраняться обычной текстовой памятью без аудиоэмбеддингов; доказывай это сквозным тестом установленного пути.
- Объявляй отдельно: кубы созданы, маршрутизатор реализован, активный runtime использует его, запись/поиск проверены, данные очищены. Ни один этап не доказывает остальные.
