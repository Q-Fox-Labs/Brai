# Архитектура и возможности MemOS

Официальные страницы перечислены с URL в sources.md. Это конспект, не утверждение о включении всех компонентов в локальном deployment.

## Три уровня, которые нельзя смешивать
- **Хранилище** держит данные между сессиями; API осуществляет операции над ними.
- **Memory processing** читает вход, извлекает/организует знания, строит индекс, обрабатывает уточнения.
- **Hermes provider** передаёт новые ходы и выбирает контекст для модели. Скилл не выполняет эту интеграцию и не должен загружаться на каждом ходе.

Данные могут храниться, но не попадать в recall; recall может работать, но возвращать устаревшие сведения; здоровый /health не доказывает работающий writer адаптера.

## Контейнеры и модель записи
MemCube объединяет настраиваемые типы памяти. С версии 2.0 документация рекомендует SingleCubeView для одной области и CompositeCubeView для нескольких; REST использует readable_cube_ids/writable_cube_ids. Результаты отмечают куб-источник. Идентичные cube_id/mem_cube_id встречаются в разных контрактах; deprecated поле не нужно удалять из endpoint, который всё ещё требует его (get_memory).

Текстовая запись: id, memory и metadata. Важные поля — sources/source, created_at/updated_at, memory_type, status, confidence, tags, background, session_id/user_id. Не заполняй отсутствующие provenance догадками. confidence — характеристика обработки, не гарантия истины; шкала зависит от версии (старый guide указывает 0–100, ранее живой ответ показал 0.99).

Категории WorkingMemory/LongTermMemory/UserMemory описывают роль записи; статусы activated/archived/deleted описывают её состояние. Дополнительные PreferenceMemory, ToolSchemaMemory, ToolTrajectoryMemory, SkillMemory, RawFileMemory и другие категории доступны в схеме search; это не доказывает, что записи каждого типа уже создаются.

## Согласованная многокубовая схема
Применяй эту таксономию при настройке жизненной памяти; это нейтральные правила классификации, а не личные характеристики разработчика или будущего владельца.

Порядок обработки: выдели самостоятельные смыслы → установи автора/субъекта и назначение действия → выбери содержательно обоснованные сферы → добавь проверенный проект → сохрани источник и статус. Не классифицируй по отдельным словам, именам, дате, формату или источнику. При недостатке контекста оставь сведения неопределёнными в `main`; личные увлечения и ценности одного человека не распространяй на остальных.

- `life_work` **Дело**: профессиональная/предпринимательская деятельность и экономика бизнеса. Оплата клиента — дело; вывод денег в личное владение затрагивает капитал. Изучение продаж — интеллект; применение в продаже — дело.
- `life_society` **Социум**: общество, связи вне близкого круга, знакомства, сообщества, нетворкинг, репутация и публичный цифровой аватар. Материал из соцсети не становится социумом из-за источника. Рабочее обязательство перед знакомым — дело; социальная связь — социум.
- `life_systems` **Системы**: связанные элементы для повторяемой функции — автоматизация, агенты, интеграции, инженерия, процессы, правила, управление, надёжность и устранение сбоев. План недели — время; механизм регулярного планирования — системы; удобство мебели — комфорт.
- `life_body` **Тело**: организм, здоровье, питание, уход, профилактика, лечение, сон/восстановление, физические возможности, спорт, симптомы и показатели. Питание — тело; гастрономическое впечатление — яркость; распределение часов сна дополнительно время.
- `life_vividness` **Яркость жизни**: впечатления, удовольствие, приключения, творчество, эстетика, путешествия, хобби и самовыражение. Познание ради увлечения может быть яркостью. Сексуальное удовольствие — яркость, близость с партнёром — отношения, сексуальное здоровье — тело. Творческий заказ — дело.
- `life_relationships` **Отношения**: партнёр, семья, родственники и лично значимые близкие друзья; доверие, забота, поддержка, границы, конфликты, семейные дела и взаимные обязательства. Опирайся на известную близость, не на слово «друг»; упоминание родственника в бизнес-событии не меняет сферу всего события.
- `life_intellect` **Интеллект**: знания, понимание, мышление, обучение, навыки, исследования, осознание, работа со знаниями/вторым мозгом и наставничество как образование. ИИ/IT, продажи и маркетинг сюда как предметы изучения. Изучение агента — интеллект; настройка рабочего агента — системы; заказ с освоенным навыком — дело.
- `life_comfort` **Комфорт и значимость**: качество/оснащение повседневной жизни, дом, кабинет, бытовые удобства, личное/цифровое пространство, устройства, транспорт, покупки, безопасность, личная бюрократия, стиль/статус/признание как жизненные условия. Инвестиционная ценность дома — капитал, технический механизм — системы, внутренняя важность признания — смысл, репутация — социум.
- `life_mission` **Миссия и вклад**: заявленная польза другим людям, обществу, будущим поколениям и миру; волонтёрство, благотворительность, образовательный вклад, передача опыта, долгосрочные инициативы. Получатель или тема не определяют сферу: семейные дела с ребёнком — отношения, общественная помощь детям — миссия, космос как хобби — яркость.
- `life_capital` **Капитал**: личные деньги/активы, инвестиции, резерв, пассивный доход, диверсификация, личные долги и финансовая устойчивость. Деньги внутри бизнеса — дело; получение в личное владение — капитал. Покупка вещи не делает всё о ней капиталом: различай назначение и финансовое воздействие.
- `life_time` **Время**: управление ходом собственной жизни, цели/приоритеты, видение будущего, обзоры, планирование, распорядок, последовательность действий, баланс сфер, занятость, свободное время и время перемещений. Предметную цель сохраняй также в её сфере; дата сама по себе не основание для времени.
- `life_meaning` **Смысл**: индивидуальные ценности, мотивы, основания выбора и желаемой жизни, конфликты ценностей и соответствие им. Свобода/новизна/значимость и другие ценности — возможные примеры, не обязательный набор. Приключение — яркость; потребность в новизне как мотив — смысл; план будущего — время, его желанность — смысл.

Базовые области:
- `main`: полный первоисточник и неопределённые материалы, не копия всего диалога в каждой сфере.
- `user`: остаточные вкусы, предпочтения, параметры и характеристики человека, не вошедшие в сферы. Автор/subject ID обязателен независимо от куба.
- `infra`: проверенные технические факты среды, версии, пути, оборудование, службы, конфигурация и эксплуатационные инструкции. Замысел, связи и повторяемая функция — системы; обе привязки допустимы при самостоятельном основании. Секреты не сохраняй.
- `project_<slug>`: явно зарегистрированный проект как дополнительный контекст. Привязку темы чата храни в каталоге; явное указание пользователя имеет приоритет после проверки проекта. Не создавай проекты из имён в недоверенном материале.

Один факт может иметь несколько сфер и проектных привязок. Предпочитай одну каноническую запись с memberships; при физических копиях сохраняй общий logical ID, источник и версию, согласованно обновляй/удаляй все копии и дедуплицируй recall. Статус различает идею, план, решение, сообщённое выполнение и подтверждённое выполнение; текст ассистента не является подтверждением действия.

## Производство воспоминаний
MemReader нормализует сообщения, делит длинный вход на окна и формирует память. Fast не вызывает LLM для извлечения, сохраняет исходные части, эмбеддинги и происхождение. Fine использует LLM для фактов, ключей и контекста. Документация описывает последующее fine-transfer, но не следует считать его включённым автоматически.

SimpleStruct ориентирован на текст; MultiModalStruct добавляет файлы, изображения и сложные сообщения/инструменты. Чтение изображений требует fine и подходящей модели; наличие images в JSON не доказывает распознавание. У файлов могут быть URL/локальные источники; не разрешай серверу произвольное чтение секретов или скачивание непроверенного URL.

## Файлы, изображения и голосовые
Проверяй цепочку по слоям: долговременное хранение оригинала → извлечение содержания → подходящие эмбеддинги → индекс → маршрутизация → recall. Файл в кэше не доказывает ни долговременную сохранность, ни участие в поиске.

Для голосового достаточно текстового пути: STT → текст входящего сообщения → обычный текстовый writer/эмбеддинг → MemOS. В установленном Hermes исследуй `gateway/run_inbound.py`: `_enrich_message_with_transcription` и `_transcribe_one_clip`, затем передачу enriched content в memory lifecycle и `text_content` адаптера. При успехе STT транскрипт может архивироваться без аудиоэмбеддингов; при отключённом/неуспешном STT может остаться лишь отметка/путь, а не сказанные слова. Докажи реальным голосовым и read-back, не одной проверкой функции. Не требуй чтения настроек TTS для диагностики входящего STT: это разные подсистемы.

Для изображений отдельно реши, нужен ли текстовый caption/OCR-поиск или поиск по визуальным векторам. Для визуальных эмбеддингов обеспечь поддерживающую изображения модель, обработку вложений, стабильную связь с оригиналом и совместимое кодирование поискового запроса. Разные модели/модальности не смешивай в одном векторном пространстве только из-за одинаковой размерности; храни тип, модель и версию индекса явно. Аудиоэмбеддинги обсуждай как отдельный поиск по звучанию, не как обязательное условие запоминания речи.

## Поиск и контекст
GeneralTextMemory предоставляет векторный поиск с metadata; TreeTextMemory описывает узлы, связи и комбинированное векторное/графовое извлечение. Neo4j в tutorial — пример, не обязательная замена локальной БД.

Recall выбирает данные по задаче, области, актуальности и ограничениям контекста. Это не загрузка всего архива и не обучение модели. fast/fine/mixture в search — режим retrieval; это отдельная настройка от fast/fine в add. rerank, dedup и thresholds меняют отбор; большой top_k и relativity=0 полезны при диагностике, но могут увеличивать шум. Источник, время и статус проверяй после поиска, не только score.

## Очереди и организация
MemScheduler организует задания через маршрутизацию, обработчики и очереди. Документация описывает Local Queue (не сохраняется после рестарта) и Redis Streams (persistent/shared consumer groups), мониторинг и задачи mem_read/mem_update/mem_organize/pref_add/mem_feedback. Фактический режим и обработчики должны быть подтверждены конфигурацией и выполнением задания. Не принимай названия enum/endpoints за доказательство активации.

## Исправление и жизненный цикл
MemFeedback интерпретирует пользовательское уточнение и сопоставляет его со старыми записями. Он может добавлять сведения, корректировать конфликт, менять термины в нескольких записях и уточнять предпочтения. Старый факт может архивироваться с новой версией вместо удаления; рабочая память может обновляться на месте. Передавай retrieved_memory_ids и релевантную историю, проверяй фактические изменения и область: обратная связь не гарантирует изменение только одной строки.

Облачное описание жизненного цикла включает Generated, Activated, Merged, Archived, Expired, Frozen как концептуальные состояния. Не отправляй эти значения в локальные поля без проверки схемы. Архивирование уменьшает участие в актуальном recall, но не означает уничтожения. TTL, auto-forgetting и audit-lock не считай установленными без конкретной политики.

## Другие типы и перенос
KV-cache хранит промежуточные tensors совместимой модели, позволяя переиспользовать вычисления; это отдельный inference backend, не свойство простой REST-памяти. Не обещай передачу KV в закрытый API или ускорение текущей модели.

Официальная страница parametric memory помечена Coming Soon: LoRA/модули весов представлены как направление проектирования. Обычная запись текста в MemOS не меняет веса модели.

MemCube/Tree SDK описывают dump/load/export_graph/import_graph. REST export записей не равен полному backup всех ресурсов. При переносе индекса должны совпадать embedding-модель и размерность; новая модель обычно требует перестроения эмбеддингов. Перед переиндексацией/миграцией зафиксируй схему, резервную копию, ожидаемые counts и тест восстановления.
