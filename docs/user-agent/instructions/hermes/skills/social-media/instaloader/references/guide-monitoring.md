## Мониторинг и ежедневная сводка

Это отдельный запрашиваемый сценарий, а не автоматическое последствие создания скилла или авторизации.

1. Согласуй владельца, выбранные аккаунты/подписки, виды контента, тематические фильтры, время, часовой пояс и получателя. Сначала предложи небольшой набор аккаунтов; все подписки обрабатывай лишь по явному запросу.
2. При наличии разрешённой сессии получи список через `Profile.from_username(loader.context, owner).get_followees()`. Список подписок и состояние мониторинга храни отдельно для каждого владельца.
3. Создай и реально проверь небольшой сборщик. Перед планировщиком выполни один ограниченный проход и покажи тестовый дайджест. Не объявляй мониторинг готовым лишь на основании команд в этом документе.
4. В конфигурации зафиксируй owner ID, account IDs/usernames, источник сессии, фильтры, типы материалов, lookback, максимальный объём, часовой пояс и точный адрес доставки. Секретное содержимое в конфигурацию не включай.
5. Первый запуск — точка отсчёта с ограниченным согласованным lookback, не вся история. Для каждого аккаунта сохраняй контрольную отметку успешного сбора и идентификаторы уже доставленных материалов.
6. Обходи выбранные профили, а не считай `:feed` полным журналом подписок. Проверяй posts/Reels отдельно, если версия и доступ этого требуют. Не останавливайся по дате единственного поста: закреплённые публикации могут нарушить порядок.
7. Дедуплицируй по media ID или shortcode; фиксируй UTC-время, автора, permalink, подпись и пути медиа. Используй небольшой перекрывающийся интервал для поздно обнаруженных материалов. Не продвигай checkpoint аккаунта после ошибки или неполного прохода.
8. Stories могут исчезнуть между ежедневными проверками; не обещай полный суточный архив. При необходимости предложи более частый отдельный сбор с согласованным объёмом.
9. Дайджест: аккаунт → что нового → краткая суть → оригинал. Тематическую релевантность оценивай по реально полученным данным, сохраняя список исходных ссылок.
10. Различай «нового нет», «получено частично» и «проверка не выполнена». Сохраняй число проверенных и пропущенных аккаунтов с причинами.
11. Для расписания вызови `skill_view(name='hermes-agent')`, затем `skill_view(name='hermes-agent', file_path='references/background-systems.md')`; при необходимости сверяй официальные docs. Используй доступный `cronjob_manage`, не выдумывай его схему. Укажи расписание, владельца/конфигурацию и получателя явно; в группе не выбирай `origin` для личной сводки по умолчанию.
12. Проверь созданную задачу чтением её точного ID и настройками доставки. Уже доставленные ID отмечай только после подтверждения отправки; при неопределённом результате учитывай риск дубля и не обещай exactly-once. Прекращение мониторинга должно удалять/отключать конкретную задачу, а не другие задания.
