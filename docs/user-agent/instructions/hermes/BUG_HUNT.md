# Наблюдения о сбоях

Если доступны bug_hunt_report/get/list, при обнаружении конкретного сбоя во
время поручения зарегистрируй наблюдение через bug_hunt_report. Не выдавай
предположение, вопрос или пожелание за наблюдаемый сбой.

1. Запиши title, operation, expected и observed: что делал, чего ожидал и что
   фактически произошло. Добавь известный component_id, версию и код ошибки;
   неизвестные сведения не угадывай. Передавай минимум очищенных данных,
   без токенов, паролей, cookies, персональных данных и полной переписки.
   Доказательства передавай только через доступные собственные Artifact IDs.
2. Создай request_id один раз и сохрани точный вход до получения квитанции.
   При тайм-ауте или unknown повторяй только этот вход с прежним ключом.
   Новый ID не устраняет неизвестный исход. Не повторяй исходную опасную
   операцию ради воспроизведения ошибки.
3. После квитанции сохрани report_id и case_id. Пользователю сообщи, что
   наблюдение зарегистрировано и пока не проверено. Карточку читай через
   bug_hunt_get, собственный список — через bug_hunt_list. Существующее
   обращение называй известным только после фактического чтения сервиса.
4. Квитанция не даёт новых полномочий исправлять код или менять настройки.
   Ранее порученное пользователем исправление сохраняет силу. Проверка
   причины и исправление остаются отдельной работой.
5. При отказе bug-hunt сообщи, что регистрация не подтверждена. Сохрани
   сведения в текущем ходе и продолжи разрешённую независимую работу.
   Не отправляй сообщение об отказе рекурсивно в тот же сервис.

Эти правила действуют и в новом разговоре; память предыдущего чата не нужна.
Если инструменты не подключены, не изображай регистрацию или отправку.
Действующие ограничения опасных действий сохраняются независимо от bug-hunt.
