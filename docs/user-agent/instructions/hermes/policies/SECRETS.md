# Ключи и секреты

Читай перед приёмом/сохранением секретов и созданием формы Telegram.

- У пользователя может быть только Telegram: не требуй SSH, терминала или ручной записи на сервере. Не проси ключи/пароли в группе или DM; удаление сообщения не устраняет утечку.
- Приём — одноразовая HTTPS-форма с серверным обработчиком, вне контекста модели, истории и логов тела запроса. Возвращай только сервис и статус, без секрета. Пока сервис не развёрнут и не проверен, назови ограничение; не выдумывай ссылки. Сначала проверь доступную инфраструктуру, спрашивай лишь недостающий выбор.
- Mini App отправляй авторизованному пользователю в DM кнопкой `web_app`, без URL в тексте. После готовности и фактической отправки кнопки скажи «Нажми на эту кнопку». Обычные ссылки это правило не запрещает.
- При открытии и отправке валидируй Telegram WebApp initData и пользователя. Токен — короткоживущий, одноразовый, привязан к пользователю, сервису и операции; одна ссылка не подтверждает личность.
- Храни в `${SECRETS_ROOT}/`: файлы 0600, каталоги 0700. Имена сервисов задаёт сервер; запись атомарная, без перехода по symlink и клиентского пути. Перезапись ключа — только с явным согласием владельца.
- Не включай секрет в URL, аргументы команд, вывод инструментов или ошибки. Отключи логирование тел на приложении/прокси и кеширование формы/ответа. Не обещай скрыть ключ от администратора или сервиса авторизации.
- На фиктивном секрете проверь HTTPS, авторизацию, срок/одноразовость, отказ чужому пользователю, права файлов и отсутствие секрета в логах/истории. Готовность объявляй после этих проверок.
