# Наблюдения о сбоях

ID: `bug-hunt`. Включение зависит от установки.

## Возможности

Постоянная подсказка агента — одна строка. При сбое bug_hunt_help возвращает
подробные правила и пример по запросу, не создавая обращение.

Агент сообщает конкретное несоответствие ожидаемому результату и получает
квитанцию сохранения. Пользователь видит свои обращения в разделе
«Наблюдения». Проверяющий может разобрать, архивировать или вернуть карточку
в работу с обязательным объяснением.

Каждое обращение остаётся непроверенным наблюдением. Архивирование не доказывает,
что дефекта нет. Отдельно включаемая проверка v3 не изменяет исходные наблюдения и не исправляет программу.
При потере ответа агент сохраняет request_id и повторяет тот же запрос.

Поиск находит свои наблюдения по словам и кодам. Одинаковые проявления можно
собрать в обратимую группу, сохранив каждое обращение и его ручное состояние.
Похожие случаи и предварительные метки Jev помогают разбору, но не подтверждают
ошибку. Пользователь видит источник метки, ограничения и неполное покрытие.
Ручное решение сохраняет приоритет. Фоновая обработка включается отдельно.

## Связи и ограничения

Данные пользователей раздельны; права проверяет Auth. Личный Hermes сообщает
через доверенный broker. Необязательные доказательства — только собственные
готовые файлы Artifacts. Тексты диагностики не исполняются и не открывают пути.

[Технический README](../../services/bug-hunt/README.md).
[Индекс компонентов](README.md).

Классификация Jev может автоматически готовить технические поля новых
обращений по защищённой политике и разрешениям владельцев. Ручная подготовка
каждого обращения не требуется. Исходники сохраняются; результат остаётся
предварительной меткой, без подтверждения бага.

При исчерпании дневного лимита модели обращение сохраняется и ждёт следующего
окна обработки. Это возможно и для новых обращений. Готовый поиск и готовая
классификация проверяются отдельно; отсутствие метки не означает отсутствие бага.

## Проверка реальности ошибки

Диагностическое расследование показывает применимый итог в обычном `report` и `get` из Hermes, BB, Codex и терминала. Оно может добавить проверенный обход, объяснение ожидаемого поведения или совет остановиться. Фоновый цикл Bug Hunt выполняется без открытых клиентских сеансов. Ручной пакет просматривает всю очередь владельца, переиспользует общую диагностику и распределяет независимые разборы между исполнителями. [Контракт диагностики](../../services/bug-hunt/README.md#диагностическое-расследование)

При включённом этапе v3 раз в шесть часов проверяется ограниченная порция
случаев; можно явно запросить проверку своей карточки. Простая регистрация
модель не запускает. Вывод различает подтверждённый дефект, опровержение
конкретного предположения и недостаток данных, с версией, условиями и
доказательствами. Отдельный проверяющий и серверный валидатор проверяют пакет.
Отсутствие воспроизведения само по себе не опровергает ошибку.
Отдельный приватный процесс Codex использует существующую авторизацию через
закрытый helper, без нового login и копирования auth.json. Он выбирает последнюю
стабильную Sol с high из настоящего каталога; версия CLI или фиксированный список
моделей не задают выбор. Providers включается явным выбором, без автоматического
переключения при отказе Codex.

Проверка сохраняет версию исходников, условия, связь аккаунта и доказательства.
Смена подключения, включая refresh того же аккаунта, закрывает прежнюю фазу.
Неизвестный исход не разрешает слепой повтор. Начальные recipes проверяют
конкретные synthetic сценарии identity/DTO, а не любое похожее наблюдение.

V3 включается только после отдельной приёмки установленного маршрута; наличие
исходников и успешных локальных тестов не означает, что проверка включена в DEV.
[Контракт проверки](../../services/bug-hunt/VERIFICATION.md) и
[установка и откат](../../services/bug-hunt/DEPLOYMENT.md).
