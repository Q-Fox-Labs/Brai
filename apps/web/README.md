# Веб-интерфейс Brai

Next.js показывает вход по почте и шестизначному коду, личный таймер и страницу агента `/agent`. Сервер обращается к auth, timer и agent через NATS. Браузер использует HTTP/SSE; веб-приложение не читает БД или внутренний код сервисов. Схемы принадлежат [auth](../../services/auth/README.md), [timer](../../services/timer/README.md) и [agent](../../services/agent/README.md).

## Запуск и конфигурация

Из корня: `npm ci`, `npm run build:web`, `npm run typecheck:web`, `npm run test:web`. Из `apps/web`: `npm start` или `npm run dev`. Версии закреплены в package.json и lockfile.

Сервер получает `NATS_URL`, `NATS_USER`, `NATS_PASSWORD`, `NATS_INBOX_PREFIX` (по умолчанию `_INBOX.brai_web`) и `WEB_ORIGIN` — канонический публичный HTTPS origin без пути. Для локального прямого запуска origin берётся из URL запроса. Эти переменные не имеют префикса NEXT_PUBLIC. Приложение не читает секретные .env файлы самостоятельно.

`WEB_TRUST_PROXY` по умолчанию выключен. Включать значением `true` можно только при закрытом ingress за доверенным reverse proxy, который заменяет недоверенный X-Forwarded-For. Тогда сервер передаёт auth только последний адрес XFF, проверенный как IP. Без этого настройки XFF не передаётся; ограничение частоты auth использует общий fallback.

## Вход и выход

POST `/api/auth/send-code` принимает `{email}`. POST `/api/auth/verify-code` принимает `{email,otp}`; otp — строка ровно из шести цифр. JSON ограничен 2048 bytes; дополнительные поля отклоняются схемой владельца. GET `/api/auth/session` возвращает только `{user:{id,email}}`; отсутствие или истечение сессии, а также отказ владельца со статусом 401/403 дают 401. Ответ владельца с временным отказом (429/5xx), неожиданным статусом или некорректной оболочкой ответа по схеме владельца даёт 503 `{code:"AUTH_UNAVAILABLE",outcome:"not-published"}`. POST `/api/auth/sign-out` отзывает текущую сессию и после подтверждения закрывает её SSE. Все мутации требуют совпадающего Origin. Каждый Set-Cookie auth передаётся отдельным заголовком; session token не возвращается в JSON.

Отправка кода и вход выполняют по одному NATS request-reply с timeout 10 секунд без автоматического повтора. Неопределённый исход проверки кода восстанавливается проверкой текущей сессии. Неудачный выход не показывается как успешный. Интерфейс прекращает запросы/SSE перед выходом; при неудаче снова открывает клиент прежнего аккаунта. Проверка текущего аккаунта каждые две секунды обнаруживает выход или вход в другой вкладке.

## Личный HTTP/SSE контракт

Все операции таймера требуют текущей сессии Better Auth. Каждый HTTP запрос клиента передаёт `X-Brai-User` с ID аккаунта документа; SSE использует query `expectedUserId`. Сервер сравнивает это ожидание с проверенной сессией; отсутствие или несовпадение даёт 401 до чтения и публикации. Эти поля не предоставляют полномочий. Сервер добавляет доверенный userId в v2 DTO только после проверки сессии; тело браузерной команды с userId запрещено. Это исключает перенос очереди прежнего аккаунта под cookie другого аккаунта при смене входа в соседней вкладке.

| Метод | Запрос | Успешный ответ |
| --- | --- | --- |
| POST `/api/timer/start` | `{commandId,timerId,startedAt}` | 202 `{commandId,status:"queued"}` после PubAck |
| POST `/api/timer/stop` | `{commandId,timerId,stoppedAt}` | такой же 202 |
| GET `/api/timer` | нет | SnapshotResponse |
| GET `/api/timer/history?cursor=…&limit=50` | limit 1..100, непрозрачный cursor | HistoryResponse |
| GET `/api/timer/commands/{commandId}` | commandId | CommandLookupResponse |
| GET `/api/timer/events?expectedUserId=…` | ID аккаунта документа | SSE snapshot/change/heartbeat |

POST принимает JSON до 2048 bytes. Схемы, временные метки и идемпотентность принадлежат таймеру. Ответы не кешируются. Ошибка `{code,outcome}` различает отказ до публикации (`not-published`), неизвестный исход PubAck (`unknown`) и чтение (`query`). 404 NOT_FOUND результата не доказывает отсутствие команды в очереди. Принятая команда сохраняет userId владельца при выходе, повторе и обработке; новая сессия её не переназначает.

Один процесс владеет pull durable `web_events` в `BRAI_TIMER_EVENTS_V2`. Общая durable между несколькими web процессами не поддерживается. Hub отправляет события только соответствующему userId. Подписка присоединяется до snapshot; bootstrap и transport очереди ограничены 64 событиями, клиентов не более 128. Переполнение или gap версии закрывают поток; свежий snapshot восстанавливает состояние. ACK означает bounded fan-out, а не получение браузером.

Перед каждым frame сервер заново проверяет сессию и совпадение её ID/владельца. Каждые две секунды heartbeat выполняет ту же проверку, даже если таймер не меняется. Потеря сессии или ошибка auth закрывают поток; успешный выход немедленно закрывает все потоки этой сессии в процессе. Уже переданные transport bytes нельзя отозвать. SSE не воспроизводит события v1.

## Агент: HTTP/SSE

Транспортный слой агента обращается к NATS только от имени web-сервера. DTO и их проверки принадлежат [контракту agent](../../services/agent/README.md) и пакету `@brai/agent/contracts`; используйте его `validateDto`, `validateEventEnvelope` и `validateAguiEvent`. Не копируйте схемы в web. NATS subjects и DTO перечислены в README владельца.

Все HTTP-маршруты ниже требуют действующую сессию Better Auth и `X-Brai-User` с ID аккаунта текущего документа. Сервер сравнивает заголовок с проверенной сессией; отсутствие или несовпадение даёт 401. Заголовок не является полномочием. До запроса к agent сервер проверяет сессию; agent проверяет projectId по собственной конфигурации. Web не хранит второй реестр проектов или их путей. POST дополнительно требует совпадающий `Origin`; при несовпадении возвращается 403. Поля `userId` нет в DTO agent и его нельзя добавлять в NATS-запрос.

SSE-маршрут использует проверенную сессию и `expectedUserId` в query; `X-Brai-User` для SSE не требуется. Отсутствующий или несовпадающий `expectedUserId` даёт 401. Список разрешённых проектов и их пути принадлежат agent.

| HTTP | Суффикс subject (`brai.agent.v1.`) | Вход → владелецкий DTO | Успех → владелецкий DTO |
| --- | --- | --- | --- |
| GET `/api/agent/projects` | `query.projects` | пустой объект → `ProjectsRequest` | 200 `ProjectsResponse` |
| GET `/api/agent/status` | `query.status` | пустой объект → `StatusRequest` | 200 `StatusResponse` |
| GET `/api/agent/threads?projectId=…&cursor=…&limit=…` | `query.threads` | параметры → `ThreadsRequest` | 200 `ThreadsResponse` |
| GET `/api/agent/threads/{threadId}?projectId=…` | `query.thread` | параметры → `ThreadReadRequest` | 200 `ThreadSnapshot` |
| GET `/api/agent/threads/{threadId}/history?projectId=…&cursor=…&limit=…&turnId=…` | `query.history` | параметры → `HistoryRequest` | 200 `HistoryResponse` |
| POST `/api/agent/threads` | `command.thread.create` | `ThreadCreateRequest` | 202 `ThreadCreateResponse` |
| POST `/api/agent/turns/start` | `command.turn.start` | `TurnStartRequest` | 202 `TurnMutationResponse` |
| POST `/api/agent/turns/steer` | `command.turn.steer` | `TurnSteerRequest` | 202 `TurnMutationResponse` |
| POST `/api/agent/turns/interrupt` | `command.turn.interrupt` | `TurnInterruptRequest` | 202 `TurnMutationResponse` |
| POST `/api/agent/requests/respond` | `command.request.respond` | `RequestRespondRequest` | 202 `RequestRespondResponse` |
| GET `/api/agent/events?projectId=…&threadId=…&expectedUserId=…` | `event` (подписка) | SSE | 200: `ThreadSnapshot` и `EventEnvelope` |

GET может загрузить проекцию треда или восстановить upstream-соединение. GET не создаёт тред или ход и не прерывает выполнение. Открытие страницы/чата, чтение истории, переподключение SSE и отмена HTTP/SSE не запускают новый ход и не останавливают текущий. Новый ход запускает только явный `turn/start`. Изменение активного хода делает только явный `turn/steer` с текущими `generation` и `expectedTurnId`; прерывание — только явный `turn/interrupt` с текущими `generation` и `turnId`. Ответ на форму отправляется отдельно с текущими `generation`, `requestId` и `kind`.

Отказы проверки сессии/ожидаемого аккаунта (401) и Origin (403) принадлежат существующему auth-gate web и не являются `ErrorResponse` agent. Ответы agent проверяются владельческим валидатором. Ошибки agent имеют `ErrorResponse` с владельческими `code` и `outcome`: неверный ввод — 400, устаревшее поколение/ход/запрос или конфликт — 409, слишком большой запрос/элемент — 413, исчерпание ёмкости — 429 либо 503 с объяснением, недоступность — 503, тайм-аут — 504, отсутствие — 404, неподдерживаемая операция — 501. Ошибки чтения имеют `outcome: "query"`. Для мутаций `not-sent` означает, что отправка не состоялась; `unknown` означает неопределённый результат. При `unknown`, timeout или разрыве связи клиент не отправляет мутацию повторно автоматически и не объявляет её неудачной. Чтения имеют предел 10 секунд, принятие мутации — 12 секунд; `accepted` подтверждает только местное принятие, не завершение выполнения.

SSE сначала подписывается на события и ставит их в ограниченную очередь до 64 элементов, затем получает свежий `ThreadSnapshot` с водяным знаком `seq`. Snapshot передаётся как событие `snapshot`, а событие владельца — как `agent` с проверенным `EventEnvelope`; `EventEnvelope.event` передаётся в `AbstractAgent.connectAgent`. Поле SSE `id` имеет вид `generation:streamEpoch:seq`. После снимка клиент отбрасывает буфер до включённой границы и принимает только непрерывные номера той же эпохи. Пропуск, смена generation/streamEpoch, сигнал resync или переполнение очереди требуют свежего снимка; Core NATS не воспроизводит пропущенные события. Перезагрузка браузера не меняет живую эпоху. Новое upstream-подключение создаёт новое поколение.

Каждый SSE frame и двухсекундный heartbeat повторно проверяют ту же сессию и `expectedUserId`, что и обычный запрос. Потеря/смена аккаунта закрывает поток. Ограничения владельца действуют и для SSE: не более 128 клиентов, 64 событий очереди на клиента, 1 MiB на исходящий кадр; снимок и страница истории — не более 768 KiB каждый. Клиент также ограничивает свою очередь и при перегрузке переподключается со свежим снимком.

Снимок показывает текущие сообщения, активный ход и формы ожидания. `command-approval`, `file-change-approval`, `permissions` и `question` отображаются как нативные формы. `unsupported` показывается компактным состоянием с причиной и доступностью явного прерывания; для него нельзя отправлять ответ. При двух вкладках первое принятое решение побеждает, поздний ответ получает `STALE_REQUEST` и не подтверждается интерфейсом.

Пример потока: клиент явно отправил `TurnStartRequest` для уже существующего треда. POST отвечает `TurnMutationResponse` с `outcome: "accepted"`; затем SSE передаёт `RUN_STARTED`, `TEXT_MESSAGE_START`, `TEXT_MESSAGE_CONTENT`, `TEXT_MESSAGE_END` и финальное `MESSAGES_SNAPSHOT` в `EventEnvelope`, после чего `RUN_FINISHED` с `outcome: {"type":"success"}` и новый снимок. Прерывание завершает run как `RUN_FINISHED` с `outcome: {"type":"cancelled"}`; это не означает, что POST сам по себе уже подтвердил фактическое состояние Codex. Форма вопроса остаётся в том же открытом run: ответ на неё не вызывает новый `turn/start`.

После подключения к активному run SDK не считает сообщения и toolCalls из снимка открытым lifecycle. Перед первой наблюдаемой post-cut дельтой или END уже существующего сообщения клиент локально восстанавливает TEXT_MESSAGE_START по проверенному ID/role; для TOOL_CALL_ARGS или TOOL_CALL_END восстанавливает TOOL_CALL_START по сохранённым ID/name/parentMessageId. Это события только браузерного SDK, без Codex turn/start, новых SSE seq и повторной подачи текста/аргументов из снимка. TOOL_CALL_RESULT использует свой проверенный payload и не требует фиктивного открытия уже завершённого вызова. Локальный bootstrap должен сохранять содержимое снимка и не создавать дубликатов.

Фаза сообщения использует отдельный [контракт agent](../../services/agent/README.md#фаза-сообщения): snapshot.messagePhases для сохранённых сообщений, HistoryItem.trace.phase для истории и CUSTOM brai.agent.message.phase для живого обновления. Web хранит карту фаз отдельно от SDK messages, заменяет её свежим снимком и удаляет записи вместе с удалёнными сообщениями. SDK callback не перезаписывает метаданные; отсутствие/null означает неизвестную фазу, terminal не подставляет final_answer.

## Страница агента

Слева расположены настроенные проекты и их чаты, в центре — сообщения и раскрываемые действия, снизу — ввод задачи и управление ходом. Вход, выход и проверка аккаунта каждые две секунды общие с таймером. Страница поддерживает узкий экран и управление формами с клавиатуры.

История читается страницами от старых элементов к новым. Лента сохраняет её native order; свежий элемент с тем же ID заменяет содержимое на прежнем месте. Новые сообщения идут в порядке SDK. Действие с ID вызова инструмента располагается рядом с его родительским сообщением; остальные новые действия идут в порядке ограниченной проекции. Исторический order и live seq не сравниваются.

CUSTOM output.text и diff.diff полностью заменяют ограниченное содержимое данного itemId, а не добавляются к нему. Завершённый элемент и история с тем же ID также заменяют содержимое. Интерфейс показывает признаки усечения и реальные фазовые метаданные, доступный план и состояния дочерних агентов.

Живой output сохраняет переданные владельцем command, status и exitCode. Наличие command определяет элемент команды, даже если значение пустое; отсутствие метаданных в старом кадре и завершение хода не подставляют их автоматически.

Ввод продолжает активный ход через steer; конфликт сохраняет текст и не запускает новый ход. Экран передаёт клиенту показанный activeTurnId (null для нового хода); если состояние уже изменилось, отправка отклоняется до HTTP и текст сохраняется. Неизвестный результат не повторяется автоматически. Принятое прерывание отображается отдельно от фактического завершения. Формы вопросов и разрешений требуют явного выбора пользователя; ответ отправляется нативному запросу исходного поколения, а не становится сообщением чата.

## Локальный отсчёт и очередь

START/STOP мгновенно меняют локальный отсчёт независимо от доступности timer. Подтверждённые интервалы приходят через snapshot, SSE или ledger. Время фиксируется при нажатии по serverTime + performance.now; задержка обработки не увеличивает интервал. Reload дополняет elapsed разницей wall-clock, внутри документа отсчёт монотонный.

Каждый аккаунт имеет отдельный sessionStorage ключ `brai.timer.outbox.v2:<encoded userId>`. Ключи `brai.timer.pending.v1` и `brai.timer.outbox.v1` не читаются и не импортируются. При смене аккаунта старый клиент размонтируется, отменяет HTTP и SSE; его очередь сохраняется только под исходным аккаунтом.

FIFO ограничен 512 неизменными намерениями. Публикация требует сохранения в sessionStorage; повреждённое хранилище не перезаписывается. Ошибка или заполнение очереди показываются пользователю. PubAck позволяет отправить следующую команду без ожидания обработки. Unknown повторяет исходный body/ID; accepted не публикуется снова даже после NOT_FOUND. Lookup выполняется раз в две секунды, до восьми последовательных результатов за проход. Только окончательный результат удаляет намерение. Поздний ответ старого действия не заменяет последнее локальное действие.
