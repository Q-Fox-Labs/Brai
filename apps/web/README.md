# Веб-интерфейс Brai

Next.js показывает вход по почте и шестизначному коду, личный таймер и страницу агента `/agent`. Сервер обращается к auth, timer, agent и history через NATS. Общая история доступна только через серверный API. Браузер использует HTTP/SSE; веб-приложение не читает БД или внутренний код сервисов. Схемы принадлежат [auth](../../services/auth/README.md), [timer](../../services/timer/README.md), [agent](../../services/agent/README.md) и [history](../../services/history/README.md).

## Навигация и тема

На desktop разделы «Агент», «Таймер» и «Дела» доступны в боковой панели; нижний desktop dock закомментирован, его реализация сохранена. Активный таймер показывает время и анимацию в иконке боковой панели. На мобильном разделы доступны в нижнем доке. Адреса: `/agent`, `/` и `/do`. Панель профиля показывает почту текущего аккаунта и выход; общая оболочка переключает светлую и тёмную темы. Режим хранится в `brai_theme_mode`; без сохранённого выбора используется системная тема. Экран входа сохраняет тёмное оформление, а декоративный Galaxy отключается при reduced motion или недоступном WebGL.

Посещённые экраны остаются в памяти до выхода или смены аккаунта: чат, черновик, настройки, история, очередь таймера и локальное дерево дел сохраняются. Скрытые клиенты агента и таймера продолжают получать обновления. Таймер и базовое состояние агента подключаются сразу после входа: отсчёт, список проектов и чатов, статусы и лимиты обновляются в фоне. История выбранного чата и подробности загружаются по запросу; дела создаются при первом посещении. Переключение разделов меняет адрес через History API без запроса серверного маршрута, сохраняет оболочку и поддерживает Back/Forward. Новый документ получает проверенную сессию от сервера и сразу отображает рабочую оболочку либо форму входа. Промежуточного экрана проверки входа нет. При каждом новом документе корневой layout показывает заставку Brai-old на всех маршрутах, включая будущие. Она остаётся в серверной разметке и во время гидратации; страница монтируется под ней с сохранённой геометрией, но скрыта и inert. Граница ждёт window.load, шрифты, исходные три секунды показа и два кадра измерения. Первые чтения Timer, Agent и открытой ленты удерживают её через useStartupReady; ошибки освобождают ожидание и показывают доступный экран с ошибкой. После первого открытия переходы и фоновые переподключения заставку не возвращают. Для нового асинхронного компонента useStartupReady(ready) добавляет ожидание его первоначальных данных; собственная заставка ему не нужна. После простоя, восстановления вкладки, возврата фокуса или соединения сессия сверяется в фоне; временный отказ сохраняет подтверждённый экран, а отзыв или смена аккаунта удаляет его. При недоступном auth во время первого открытия показывается повтор подключения, а не ложный выход. Выход прекращает запросы и SSE. Мобильные панели закрываются жестом, нажатием вне панели, Escape или Back и возвращают фокус к кнопке открытия; экранная клавиатура скрывает док.

Страница фокуса переносит отсчёт и анимации Brai-Old, дневную историю с редактором и панель целей. История отображает часть ночной сессии в каждом затронутом московском дне; изменение или подтверждённое удаление относится ко всей исходной сессии. Дневные и общие итоги приходят от владельца таймера независимо от загруженных страниц. Календарь цели — Europe/Moscow, 4 октября 2026 включительно — 1 ноября 2026 исключительно, 28 дней по 8 часов (224 часа). Сохранённая сумма не включает активный интервал, миллисекунды сохраняются до форматирования. Локальный отсчёт, неизменная очередь команд, возврат во вкладку и сообщения об ошибках продолжают работать через существующий клиент HTTP/SSE.

[«Дела»](app/do/README.md) — интерактивный задачник с синтетическими данными: раскрытие дерева, цветные индикаторы, перенос с автопрокруткой, нумерация и панель подробностей. Его изменения живут только в памяти; API и БД задач не подключены.

## Запуск и конфигурация

Из корня: `npm ci`, `npm run build:web`, `npm run typecheck:web`, `npm run test:web`. Из `apps/web`: `npm start` или `npm run dev`. Версии закреплены в package.json и lockfile.

Сервер получает `NATS_URL`, `NATS_USER`, `NATS_PASSWORD`, `NATS_INBOX_PREFIX` (по умолчанию `_INBOX.brai_web`) и `WEB_ORIGIN` — канонический публичный HTTPS origin без пути. Для локального прямого запуска origin берётся из URL запроса. Эти переменные не имеют префикса NEXT_PUBLIC. Приложение не читает секретные .env файлы самостоятельно.

`WEB_TRUST_PROXY` по умолчанию выключен. Включать значением `true` можно только при закрытом ingress за доверенным reverse proxy, который заменяет недоверенный X-Forwarded-For. Тогда сервер передаёт auth только последний адрес XFF, проверенный как IP. Без этого настройки XFF не передаётся; ограничение частоты auth использует общий fallback.

## Вход и выход

POST `/api/auth/send-code` принимает `{email}`. POST `/api/auth/verify-code` принимает `{email,otp}`; otp — строка ровно из шести цифр. JSON ограничен 2048 bytes; дополнительные поля отклоняются схемой владельца. GET `/api/auth/session` возвращает только `{user:{id,email}}`; отсутствие или истечение сессии, а также отказ владельца со статусом 401/403 дают 401. Ответ владельца с временным отказом (429/5xx), неожиданным статусом или некорректной оболочкой ответа по схеме владельца даёт 503 `{code:"AUTH_UNAVAILABLE",outcome:"not-published"}`. POST `/api/auth/sign-out` отзывает текущую сессию и после подтверждения закрывает её SSE. Все мутации требуют совпадающего Origin. Каждый Set-Cookie auth передаётся отдельным заголовком; session token не возвращается в JSON.

Отправка кода и вход выполняют по одному NATS request-reply с timeout 10 секунд без автоматического повтора. Неопределённый исход проверки кода восстанавливается проверкой текущей сессии. Неудачный выход не показывается как успешный. Интерфейс прекращает запросы/SSE перед выходом; при неудаче снова открывает клиент прежнего аккаунта. Проверка текущего аккаунта каждые две секунды обнаруживает выход или вход в другой вкладке.

## Личный HTTP/SSE контракт

Все операции таймера требуют текущей сессии собственного сервиса Auth. Каждый HTTP запрос клиента передаёт `X-Brai-User` с ID аккаунта документа; SSE использует query `expectedUserId`. Сервер сравнивает это ожидание с проверенной сессией; отсутствие или несовпадение даёт 401 до чтения и публикации. Эти поля не предоставляют полномочий. Сервер добавляет доверенный userId в v2 DTO только после проверки сессии; тело браузерной команды с userId запрещено. Это исключает перенос очереди прежнего аккаунта под cookie другого аккаунта при смене входа в соседней вкладке.

| Метод | Запрос | Успешный ответ |
| --- | --- | --- |
| POST `/api/timer/start` | `{commandId,timerId,startedAt}` | 202 `{commandId,status:"queued"}` после PubAck |
| POST `/api/timer/stop` | `{commandId,timerId,stoppedAt}` | такой же 202 |
| POST `/api/timer/edit` | `{commandId,timerId,expectedVersion,startedAt,stoppedAt}` | такой же 202 |
| POST `/api/timer/delete` | `{commandId,timerId,expectedVersion}` | такой же 202 |
| GET `/api/timer` | нет | SnapshotResponse |
| GET `/api/timer/history?cursor=…&limit=50` | limit 1..100, непрозрачный cursor | HistoryResponse |
| GET `/api/timer/commands/{commandId}` | commandId | CommandLookupResponse |
| GET `/api/timer/statistics` | нет | StatisticsResponse |
| GET `/api/timer/events?expectedUserId=…` | ID аккаунта документа | SSE snapshot/change/heartbeat; change включает `started`, `stopped`, `edited`, `deleted` или `rejected` |

POST принимает JSON до 2048 bytes. Схемы, временные метки и идемпотентность принадлежат таймеру. Ответы не кешируются. Ошибка `{code,outcome}` различает отказ до публикации (`not-published`), неизвестный исход PubAck (`unknown`) и чтение (`query`). 404 NOT_FOUND результата не доказывает отсутствие команды в очереди. Принятая команда сохраняет userId владельца при выходе, повторе и обработке; новая сессия её не переназначает.

Браузер не передаёт `userId`; web добавляет его только после проверки сессии. Для edit/delete клиент передаёт owner `expectedVersion`, которую получил из свежего snapshot. Каждая успешная start/stop/edit/delete увеличивает общую owner version; устаревшее значение заканчивается `VERSION_CONFLICT`, и клиент обновляет snapshot перед новой попыткой. Один `commandId` повторяется только с исходным body. Ответ `NOT_FOUND` при lookup не доказывает, что команда не стоит в очереди.

Edit задаёт абсолютные `startedAt` и `stoppedAt` в UTC с миллисекундами; UI пересчитывает длительность из них, а timer считает `durationMs`. Удаление исключает интервал из выдаваемой истории и статистики, сохраняя исходные и edit/delete результаты журнала. Потребитель считает `edited` отдельным событием от `stopped`; edit несёт полную новую версию интервала, а delete — `timerId`.

Страницы history несут `historyRevision`. Успешные edit/delete увеличивают её; start/stop не меняют её и не инвалидируют cursor. Если страница отвечает `HISTORY_CHANGED`, клиент сбрасывает cursor и читает историю с начала. Чужой, активный, удалённый или отсутствующий target получает `NOT_FOUND`. Пересечение интервалов после edit получает `INTERVAL_OVERLAP`.

Statistics читает всю историю владельца независимо от текущих страниц. `totalCompletedMs` и дневные суммы — целые миллисекунды; активные и удалённые интервалы исключены. Все даты вычисляются по `Europe/Moscow`, интервалы делятся на границах локальной полуночи. `daily` содержит все ненулевые дни истории и все 28 дат challenge, даже если сумма равна нулю; дневная цель — 28 800 000 ms, процент не ограничен 100. Challenge длится с 2026-10-04 включительно до 2026-11-01 исключительно, по 8 часов в день (806 400 000 ms всего). Его `daily` ровно 28 элементов для графика; `closedDays` считает достигнутые дневные цели. `remainingDays` равно 28 до начала, включает сегодняшнюю дату во время challenge и равно 0 после завершения. `requiredDailyMs` может быть дробным и равен 0 после достижения цели или при нуле оставшихся дней.

Один процесс владеет pull durable `web_events` в `BRAI_TIMER_EVENTS_V2`. Общая durable между несколькими web процессами не поддерживается. Hub отправляет события только соответствующему userId. Подписка присоединяется до snapshot; bootstrap и transport очереди ограничены 64 событиями, клиентов не более 128. Переполнение или gap версии закрывают поток; свежий snapshot восстанавливает состояние. ACK означает bounded fan-out, а не получение браузером.

Перед каждым frame сервер заново проверяет сессию и совпадение её ID/владельца. Каждые две секунды heartbeat выполняет ту же проверку, даже если таймер не меняется. Потеря сессии или ошибка auth закрывают поток; успешный выход немедленно закрывает все потоки этой сессии в процессе. Уже переданные transport bytes нельзя отозвать. SSE не воспроизводит события v1.

## Общая история: HTTP

GET `/api/history` возвращает `{items,next_cursor}` из [контракта history](../../services/history/schemas/messages.schema.json). Разрешены query-фильтры `source`, `category_id`, `type_id`, `actor_id`, `object_type`, `object_id`, `occurred_from`, `occurred_to`, а также `limit` (1..100; по умолчанию 50) и непрозрачный `cursor` до 2048 символов. Время — RFC 3339 с явным часовым поясом. GET `/api/history/{source}/{id}` возвращает `{event}`; source — код источника, id — UUID. Дополнительные и повторные query-поля запрещены.

Оба маршрута проверяют текущую сессию собственного сервиса Auth и передают её строковый ID как доверенный `user_id` в `brai.history.v1.query.list` или `.get`. Браузер не задаёт пользователя или scope. Сервис истории читает только `user/<текущий ID>` через собственную веб-роль RLS. Чужая, системная или отсутствующая строка даёт 404 `NOT_FOUND`. Веб-сервер не получает SQL-credentials и не вызывает MCP или subjects записи. Пользовательская страница истории пока не создаётся.

## Уведомления

`/alerts` работает в постоянной оболочке аккаунта. Колокольчик в desktop rail и мобильных настройках показывает общее число непрочитанных; цвет приходит из выбранной владельцем категории. Ноль скрывает badge, больше 99 отображается как `99+`. До первой успешной сверки число неизвестно. Потеря связи сохраняет последний подтверждённый счётчик и ленту.

GET `/api/alerts` принимает только `limit` и `cursor` и возвращает страницу по [схеме alerts](../../services/alerts/schemas/messages.schema.json). GET `/api/alerts/summary` возвращает счётчик и категорию, GET `/api/alerts/{service}/{id}` — доступную запись без изменения отметки. POST `/api/alerts/{service}/{id}/read` и `/api/alerts/read-all` принимают пустой JSON `{}` и явно меняют отметки текущего пользователя. Мутации требуют канонический Origin. Просмотр ленты не отмечает записи. JSON раскрывается отдельно и отображается безопасным текстом.

Каждый HTTP-запрос проверяет Better Auth, передаёт владельцу её `user.id` и проверяет wire-данные по схеме сервиса. `x-brai-user` должен совпадать с текущим аккаунтом браузера; это ограничение старого клиента, а не источник полномочий. SSE GET `/api/alerts/events?expectedUserId=...` требует такую же привязку.

Один клиент аккаунта получает Core NATS signals через один серверный subscriber на `brai.alerts.v1.changed`. SSE передаёт `ready`, `changed` и `heartbeat` без содержимого уведомлений. Подписчик подключается перед bootstrap-сверкой, личный сигнал получает только владелец, общий — все аккаунты. Сервер ограничивает число соединений 128 и очередь 64 сигналами; переполнение, потеря NATS, отзыв сессии или ошибка Auth закрывают поток. Перед выдачей и на heartbeat раз в две секунды сессия проверяется заново. Подтверждённый выход немедленно закрывает потоки сессии в текущем процессе.

Браузер перечитывает данные после сигнала, переподключения, возвращения фокуса и каждые 15 секунд. Лента загружает страницы по 50 записей, сохраняет посещённое состояние и обновляет уже загруженные страницы. При выходе или смене аккаунта подключения и запросы отменяются; запоздавшие ответы игнорируются.

Каждое чтение делает одну попытку NATS request-reply, timeout 10 секунд. Вход проверяется по схемам владельца, wire request ограничен 64 KiB, ответ — 512 KiB. Все ответы имеют `Cache-Control: no-store`. Ошибки возвращают `{code,outcome:"query"}`; отсутствие сессии — 401, неверные поля/курсор — 400, превышение допустимого размера — 413, перегрузка/недоступность — 503, deadline — 504. Некорректный или слишком большой wire-ответ — 502 `BAD_REPLY`; внутренний отказ владельца — 500 `INTERNAL`. Текст внутренней ошибки браузеру не передаётся. Ошибки проверки auth сохраняют текущий контракт входа.

## Агент: HTTP/SSE

Защищённая `/agent` использует существующий Account. Web проверяет текущую сессию, Origin для мутаций и ожидаемый user id. Доступ к Codex socket/profile у web отсутствует.

`BRAI_AGENT_ALLOWED_EMAILS` задаёт разрешённые адреса через запятую, например `owner@example.test,operator@example.test`. Задавайте адреса в нижнем регистре; сервер удаляет пробелы по краям элементов и сравнивает адрес с подтверждённой почтой текущей сессии без учёта регистра. Пустое значение запрещает все операции agent: HTTP 403 `AGENT_ACCESS_DENIED`. Вход по почте и личный таймер работают независимо от этого списка.

Для общего Agent-профиля `BRAI_AGENT_OWNER_EMAIL` и `BRAI_AGENT_OWNER_ID` задают доверенную серверную пару. Оба значения обязательны вместе; неполная пара даёт 503 `AGENT_OWNER_NOT_CONFIGURED`. Настроенная пара требует совпадения email текущей сессии без учёта регистра и `emailVerified=true`; другой email даёт 403 `AGENT_ACCESS_DENIED`, неподтверждённый — 403 `AGENT_OWNER_EMAIL_UNVERIFIED`. Без пары сохраняется прежний ownerId из сессии. Внутренние Agent/artifacts вызовы получают этот ownerId; браузерные `x-brai-user` и `expectedUserId` всегда содержат локальный ID аккаунта и сверяются с локальной сессией. Браузер не может задать ownerId. HTTP и SSE заменяют канонический `expectedUserId` в URL вложений на локальный ID, сохраняя текст и данные владельца.

Только вызовы Agent artifacts могут использовать отдельные `AGENT_ARTIFACTS_NATS_URL`, `AGENT_ARTIFACTS_NATS_USER`, `AGENT_ARTIFACTS_NATS_PASSWORD`, `AGENT_ARTIFACTS_NATS_INBOX_PREFIX` (по умолчанию `_INBOX.brai_web_agent_artifacts`). Без отдельного URL они используют общее соединение `NATS_*`. Auth, timer, history и сам Agent RPC остаются на прежнем соединении. Web artifacts требует subjects `brai.artifacts.v1.prepare`, `get`, `relation.add`, `reference.list` и ответы своего inbox.

POST `/api/agent/attachments/prepare` проверяет исходный URL `prepare` по доверенному `AGENT_ARTIFACTS_UPLOAD_BASE_URL` (fallback `ARTIFACTS_UPLOAD_BASE_URL`): тот же origin и точный `/upload/{token}`, без credentials/query/fragment. Browser получает URL своего origin `/api/agent/uploads/{token}`. Caddy разрешает только PUT, удаляет Cookie/Authorization и переписывает путь в `/upload/{token}` для `BRAI_AGENT_ARTIFACTS_UPLOAD_UPSTREAM`. Защищённые GET/HEAD вложений проходят локальную session-проверку и получают файлы от `BRAI_AGENT_ARTIFACTS_FILE_SERVER`. Прежний `/upload` использует свой `BRAI_ARTIFACTS_UPLOAD_UPSTREAM`.

Каталог проектов и чатов обновляется каждые 10 секунд только в видимой вкладке раздела «Агент», а также при возвращении видимости. Один опрос и одно чтение каждого проекта могут выполняться одновременно; новое чтение того же проекта ждёт следующего опроса. Обновление перечитывает уже загруженный диапазон до 1000 чатов, сохраняет раскрытие списка, выбор чата и положение прокрутки. Ошибка сохраняет прежние строки и cursor. Native поток открытых чатов продолжает работать независимо.

GET `/api/agent/<action>` читает `projects/status/threads/open/turns/items/activities/item`; поля передаются query. POST `/api/agent/<action>` принимает `create/start/steer/interrupt/answer`, с JSON body без action. Единственный закрытый контракт принадлежит [agent](../../services/agent/README.md). Мутации автоматически не повторяются; unknown сохраняет черновик и требует проверки чата.

GET `goalGet` читает native цель; POST `goalSet/goalClear` управляет ей через тот же закрытый контракт. «Пауза» и «Удалить цель и остановить» приостанавливают или удаляют цель и прерывают текущий ход владельцем; «Продолжить» разрешает native продолжения. Частичный результат этих действий остаётся unknown и блокирует новые мутации до проверки чата.

«+» проекта сразу открывает локальный редактор нового чата без запросов status/create/open и без проверки доступности. Один черновик нового чата сохраняется в памяти аккаунта при переходе к существующему чату, другому разделу или проекту. Создание выполняется только при отправке первого сообщения; затем web открывает созданный чат и отправляет сообщение. Черновик очищается после принятого start или подтверждения точного operationId в истории; последующие правки текста и новые вложения сохраняются. Подтверждённый отказ сохраняет черновик и использует уже созданный чат при ручном повторе. Неизвестный start проверяется чтением истории, без повторной отправки; неизвестное создание блокирует повтор в том же проекте. Выход или смена аккаунта удаляют черновик.

Панель ввода компактно группирует слева прикрепление изображений, иконки режима и подтверждений, ползунки модели и рассуждения. Кнопки режимов переключают значения по кругу; текущий режим показан при наведении. Новые чаты начинают с Sol / Med; при выборе Sol начальный уровень также Med. Сохранённый выбор и настройки существующих чатов сохраняются. Модель выбирается в порядке Luna → Sol → Astra, рассуждение — по доступным уровням выбранной модели. Оба ползунка имеют ширину 120 px и подписанный бегунок; в узком поле кнопки и дорожки уменьшаются, чтобы вся панель оставалась одной строкой. Длина дорожки не зависит от количества уровней; выбор выполняется мышью или касанием без клавиатурного переключения. Справа находится круглая кнопка со стрелкой вверх для отправки и корректировки либо квадратом для остановки. Уголок ввода увеличивает высоту при движении вверх и уменьшает при движении вниз в пределах 65–180 px. Общая надпись «Действие принято» и видимая строка сочетаний клавиш убраны; ошибки и сами сочетания сохранены. Активный ход и незавершённая цель не блокируют выбор режима, подтверждений, модели и рассуждения для следующего сообщения или очереди. Корректировка использует настройки текущего хода. При отправке команды, потере соединения или неизвестном исходе защитные блокировки сохраняются.

Рядом с полем сообщения доступны режимы «Обычный», «План» и «Цель». Режим входит в настройки каждого чата и каждого сообщения очереди. Планирование передаёт native collaboration mode; текст режима «Цель» становится objective Codex без отдельного web-цикла. Изображения новой цели отклоняются до отправки; скрытый бюджет не задаётся. Активная, заблокированная или ограниченная цель владеет промежутками между ходами: очередь и смена настроек ждут явной паузы, удаления или завершения. Пустое поле показывает «Стоп» для остановки всей цели.

План предложения, текущие шаги и цель открываются в закрываемой правой половине рабочего пространства; на телефоне материал занимает отдельную полноэкранную область с Escape и удержанием фокуса. Новая запись открывается один раз. Обновления закрытой записи показывают отметку «обновлено»; карточка в чате открывает её снова. Выбор и закрытие сохраняются в локальном cache чата, документы остаются в истории Codex. Заголовок переключает несколько материалов. «Выполнить план» отправляет точный завершённый документ с поручением реализации в обычном режиме и сохраняет пользовательский черновик. Streaming, сокращённый текст и активный ход блокируют выполнение. «Предложить правки» выбирает планирование и фокусирует сохранённый черновик без отправки.

Шаги выполнения — transient snapshot, а не отдельная сохранённая история: stale сохраняет показанный прогресс при потере соединения, unavailable обозначает отсутствие восстановимых шагов. Цель показывает objective, native статус, использованные время и токены, известный бюджет; stale/unavailable и отключение связи блокируют управление. Сокращение документа или данных обозначается явно.

GET `/api/agent/events?expectedUserId=…` открывает один SSE на аккаунт. Подписка подключается до GET `projects`; событие `ready {generation}` подтверждает поколение и доступные configured проекты. `agent` передаёт оболочку `{projectId,threadId,generation,epoch,seq,event}`: первый кадр чата и новый epoch содержат AG-UI `STATE_SNAPSHOT`, следующие — стандартный `STATE_DELTA` (RFC6902) с дополнительным `baseSeq`. Diff строится от последнего переданного снимка. Кадр до1MiB, снимок до512KiB; сервер хранит до16 последних ожидающих и16 отправленных снимков, по одному на чат. Старые pending снимки заменяются новыми. GET с явными projectId/threadId сохраняет прежний wire с полными снимками.

Клиент восстанавливает snapshot библиотекой `fast-json-patch`, проверяет исходную native оболочку и применяет состояние через официальный `@ag-ui/client defaultApplyEvents` и upstream EventSchema. Несовпадение baseSeq требует нового GETopen, старые seq игнорируются. Одновременно применяются один снимок и последний ожидающий; очереди посимвольного воспроизведения нет. До16 баз SSE сохраняются и до первого выбора чата: HTTPopen может опережать последний переданный кадр. До8 последних чатов сохраняют passive SDK состояние и получают фоновые события через общий SSE. Выбор чата меняет только получателя, без нового соединения или open. При первом посещении, настоящем разрыве, смене generation/epoch или вытеснении нужен свежий open. Мутации и старые формы до подтверждения блокируются. Dispose закрывает HTTP/SSE/SDK. История запрашивается отдельно через native cursor.

Каждые пять секунд heartbeat проверяет сессию, разрешённую почту и поколение сервиса. Единичный временный сбой status допускается; три подряд, отзыв сессии, NATS reconnect или смена поколения закрывают поток и требуют свежего состояния. Переполнение очереди, повреждённый кадр и отмена освобождают подписку.
Проекты и их чаты сгруппированы в левой панели. Каждая группа сначала показывает пять названий; «Показать больше» раскрывает загруженный список и затем читает следующую native страницу. Выбранный чат выделен; длинное название сокращено в строке и доступно полностью через подсказку. Справа история прокручивается отдельно от закреплённого поля сообщения. На узком экране панель открывается кнопкой «Чаты».

## Локальный отсчёт и очередь

START/STOP мгновенно меняют локальный отсчёт независимо от доступности timer. Подтверждённые интервалы приходят через snapshot, SSE или ledger. Время фиксируется при нажатии по serverTime + performance.now; задержка обработки не увеличивает интервал. Reload дополняет elapsed разницей wall-clock, внутри документа отсчёт монотонный.

Каждый аккаунт имеет отдельный sessionStorage ключ `brai.timer.outbox.v2:<encoded userId>`. Ключи `brai.timer.pending.v1` и `brai.timer.outbox.v1` не читаются и не импортируются. При смене аккаунта старый клиент размонтируется, отменяет HTTP и SSE; его очередь сохраняется только под исходным аккаунтом.

Общий SSE agent передаёт `limits {generation,limits}` из периодического status. Кадр содержит только закрытую проекцию владельца, проверенную `validateLimits`; отсутствие или некорректная проекция даёт `unavailable`, временный сбой — `stale`. Медленный клиент удерживает не более одного последнего кадра лимита. Клиент хранит отдельную проекцию аккаунта и принимает свежий снимок после переподключения, даже если revision не изменилась. Нижний блок левой панели показывает primary/secondary окна, остаток и сброс в часовом поясе браузера; неизвестный сброс не подменяется датой или восстановленным процентом.

Рядом с названием окна отображается время до сброса: полные дни и оставшиеся часы, при остатке меньше суток — только часы. Под полосой квоты тёмно-зелёная полоса показывает долю оставшегося времени относительно `windowDurationMins` (для недели — семь суток), ограниченную 0–100%. Отсчёт обновляется каждые 30 секунд. При неизвестном времени сброса отсчёт и полоса времени скрыты; при неизвестной длительности скрыта только полоса времени.

При задержке обновления панель сохраняет последние значения без мигающих служебных надписей. Пояснение о задержке доступно при наведении на панель.

FIFO ограничен 512 неизменными намерениями. Публикация требует сохранения в sessionStorage; повреждённое хранилище не перезаписывается. Ошибка или заполнение очереди показываются пользователю. PubAck позволяет отправить следующую команду без ожидания обработки. Unknown повторяет исходный body/ID; accepted не публикуется снова даже после NOT_FOUND. Lookup выполняется раз в две секунды, до восьми последовательных результатов за проход. Только окончательный результат удаляет намерение. Поздний ответ старого действия не заменяет последнее локальное действие.

На `/agent` переподключение сохраняет показанные сообщения и черновик; отправка и формы ждут свежего состояния. SSE передаёт изменения не чаще одного раза за50мс: промежуточные снимки объединяются, полная история на каждый символ не отправляется. Сигнал связи каждые пять секунд поддерживает поток в паузах. Единичный сбой проверки статуса не закрывает соединение; три последовательных сбоя требуют переподключения, проверка сессии остаётся строгой. При открытии чат прокручивается вниз; поступление сообщений следует за нижним краем, пока пользователь не прокрутил вверх. Загрузка прежних сообщений сохраняет позицию чтения.

Следование ленты включается только у самого нижнего края (допуск1пкс для округления браузером). Позиция проверяется до применения snapshot, даже если scroll event ещё не обработан. Последовательные действия между сообщениями объединяются в закрытый блок «Думаю». Закрытая группа не монтирует список: `activities` читает только заголовки партиями до100ID одного хода. Раскрытие действия читает `item`; команда, вывод и diff показываются точным текстом. Ошибка чтения допускает ручной повтор. Кеши разделены по generation/epoch/project/thread/turn/item/revision: до256 заголовков и16 полных действий, максимум4 параллельных чтения и64 ожидающих. Открытая группа обновляет заголовки и раскрытый detail при изменении revision; поздний ответ после смены чата игнорируется.

Сохранённая страница истории и живое окно объединяются по общим ID с сохранением порядка обоих окон; ранние элементы более длинного живого окна не добавляются после итога. Запрос разрешения показывает причину, непосредственные кнопки разового разрешения и отказа, подробности команды по раскрытию. Решения с изменением политики и разрешение на сеанс доступны отдельно с понятным описанием; ответ сохраняет исходное значение Codex без расширения прав.

Вопросы показываются отдельной карточкой над полем сообщения, по одному вопросу за раз. Варианты имеют номера и описания; суффикс `(Recommended)`, `(Рекомендуемый)` или `(Рекомендуется)` отображается отметкой «Рекомендуемый», но ответ сохраняет исходный label. Первое выделение не отправляет ответ. Выбор, собственный ответ (если разрешён `isOther` или нет вариантов) и явный пропуск переводят дальше; после последнего решения отправляется весь набор. Навигация не пропускает вопросы: если остаются нерешённые, карточка возвращается к первому из них. Пропуск передаётся пустым массивом answers. Крестик только сворачивает карточку, кнопка «Ответить на вопросы» восстанавливает текущий вопрос и черновики. При нескольких запросах показывается первый ожидающий. Карточка остаётся при временной потере связи, но отправка блокируется существующим состоянием соединения; новый generation/epoch начинает новый экземпляр. Секретный ответ использует password без автозаполнения. Стрелки вверх/вниз переключают фокус вариантов, Enter выбирает вариант или подтверждает свой ответ; Shift+Enter добавляет строку, Escape сворачивает карточку. Голосового ввода нет.

Повторный выбор одного из8последних открытых чатов сразу показывает его snapshot, до1000 элементов history, draft и выбор модели/рассуждения из памяти текущего аккаунта. Дисковое хранение и отдельные фоновые подключения не используются; controls ждут свежий SSE. History повторно читается при отсутствии страницы, смене generation/epoch или отсутствии пересечения окон после долгого перерыва. Поздние ответы не меняют другую selection. GET `/api/agent/models` читает owner каталог; перед новым заданием selector показывает только его model/effort. Выбор передаётся POST start и сохраняется отдельно по чату; активный steer не меняет настройки.

Третий selector — «Разрешения»: default «Подтверждать за меня», также доступны «Запрашивать разрешение» и «Полный доступ». Выбор сохраняется в том же cache по чату, передаётся create/start и блокируется на время активного хода. Пользовательский config.toml не является доступным preset: интерфейс показывает только реализованные native режимы.

Справа от работающего чата показан индикатор с доступным именем «Агент работает»; reduced motion выключает вращение. Metadata всех чатов обновляется общим SSE без фоновых open. Порядок задаёт `lastMessageAt` (Unix ms) последнего сообщения пользователя или агента; служебный `updatedAt` не влияет, равные метки сохраняют порядок списка.

Ответы агента и сообщения пользователя используют безопасный Markdown: ссылки, code, списки, заголовки, цитаты и таблицы. HTML остаётся текстом; исполняемые URL запрещены. Три селектора имеют доступные имена без видимых подписей. «Отправить» запускает новый ход с текстом или изображениями. Во время хода текст или вложения дают «Скорректировать» (steer), отсутствие обоих — «Стоп» (interrupt). Enter отправляет сообщение или корректировку; пустой Enter не останавливает ход. Shift+Enter вставляет строку, Ctrl/⌘+Enter ставит сообщение в локальную FIFO очередь выбранного чата. Подтверждение IME и удержание Enter не отправляют сообщение. Блокировки связи, мутации и неизвестного результата сохраняются.

Очередь хранит до 16 сообщений суммарно в памяти аккаунта вместе с изображениями и выбранными настройками. Сообщения видны над полем ввода и удаляются по одному. Очередь выбранного чата запускает следующий ход после завершения текущего, при свежем соединении и отсутствии запросов разрешений. При переключении чата очередь сохраняется и возобновляется после возвращения; переключение верхних вкладок не останавливает выбранный чат. После принятого start следующее сообщение ждёт обновления native turn ID, чтобы старый idle snapshot не запустил второй ход. Ошибка, неизвестный исход или устаревшие настройки останавливают очередь без автоматического повтора; текст остаётся в очереди. Новые изменения черновика не очищаются ответом очереди. Выход, смена аккаунта и перезагрузка страницы очищают очередь.

Кнопка «+» выбирает несколько PNG, JPEG или WebP; Ctrl/⌘+V в поле сообщения добавляет файлы из буфера обмена. Обычная текстовая вставка сохраняется. Предпросмотр показывает имя файла, кнопку удаления и отметку «Уменьшено» для подготовленной копии. Поддержку изображений и допустимое число вложений интерфейс читает из свежего каталога владельца. Во время активного хода используется только фактическая модель чата.

Пределы Brai: до 8 изображений, суммарно 640 КиБ данных до base64. Исходный файл — до 20 МиБ и 32 миллионов пикселей. Помещающийся оригинал отправляется без изменения; большой файл преобразуется в JPEG/WebP с длинной стороной до 2048 пикселей. Подготовка по одному файлу и ограниченная очередь защищают браузер от параллельного декодирования. Копия не уменьшается ниже 512 пикселей по длинной стороне (либо исходного размера); если места недостаточно, файл отклоняется с причиной, предыдущие вложения сохраняются. SVG, неверный MIME и повреждённые файлы отклоняются.

Вложения входят в черновик каждого из восьми сохранённых чатов и живут только в памяти текущего аккаунта. Смена чата, модели или аккаунта отменяет вставку позднего результата подготовки. После accepted удаляются только отправленные изображения из исходного чата; правки текста во время отправки сохраняются. Отказ и unknown сохраняют черновик. Неизвестный исход блокирует повторную отправку и показывает просьбу проверить чат. История показывает `imageCount` пользователя; binary владелец в историю и SSE не передаёт.

Для нового чата название/preview Codex из списка сохраняется, когда более свежие события передают пустую пару title/preview. Свежие статус, активность и время сообщения остаются актуальными. Непустое новое имя или preview заменяет прежнюю пару; metadata разных ID не смешивается.

Служебное сообщение `send_user_message_question_reply` показывает вопрос и выбранный ответ без JSON, тегов и протокольного ID. Распознаётся только полная корректная запись; обычный JSON и повреждённые сообщения сохраняют исходное отображение. История Codex не меняется.


В списке чатов вопрос обозначает ожидающий ответ, вращающийся индикатор — работу, галочка — непрочитанный итог. Вопрос имеет приоритет и остаётся после просмотра до ответа. Галочка исчезает, когда конец итогового сообщения виден в активной вкладке браузера и разделе «Агент». Чтение сохраняется в localStorage этого браузера отдельно для аккаунта (до 1000 чатов); при недоступном хранилище — в памяти. Выбор строки не раскрывает меню: три точки появляются при наведении; клавиатура показывает кнопку при фокусе на ней.


Чтение итога определяется последним показанным сообщением истории, даже если его нет в компактном live окне. Наблюдение конца сообщения сохраняется при обновлениях seq; первый кадр, прокрутка и возвращение видимой вкладки также проверяют чтение. Скрытые три точки стоят вне раскладки: место под них появляется только при наведении, фокусе самой кнопки или открытом меню. В этот момент меню заменяет индикатор статуса.

Фильтр скрывает только распознанную обёртку Codex Desktop со списком вложений; запрос после заголовка My request и изображения остаются видимыми. Ошибка завершённого хода показывается в ленте. Для перегруженной модели интерфейс предлагает выбрать другую модель или повторить запрос позже. Отклонённые server request видны как уведомления без формы ответа и не блокируют очередь.


Четвёртая иконка composer после вложений, режима и разрешений показывает заполнение контекстного окна кольцом. Наведение, фокус или касание открывают подсказку с использованным и оставшимся процентом и числом токенов последнего native запроса. Escape, потеря фокуса или уход указателя закрывают подсказку. Неизвестные счётчики, лимит и потеря связи обозначаются явно; лимиты моделей не назначаются вручную. Процент ограничен 100%, число токенов сохраняет фактическое значение.

Асинхронные вопросы Codex из `agentMessage.questions` используют ту же карточку, что `request_user_input`; обычные сообщения со списками не превращаются в формы. Пока async вопрос ожидает ответ, его исходный текстовый список скрыт в истории и вопрос показан над composer. Завершение хода не скрывает вопрос. Ответ из другого клиента обновляет карточку; если часть вопросов уже решена, черновик оставшегося вопроса сохраняется.
